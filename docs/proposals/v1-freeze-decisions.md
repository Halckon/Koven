# v1 冻结前的兼容性约束（Z1–Z11）

> **性质**：非规范候选约束清单 · **状态**：未启用 · **读取时机**：为下列 v1 路线图条目起草 Spec 或 Guide 增量时；评审 v1 公开表面是否为后续演进留有余地时 · **唯一真源**：本页维护 Z1–Z11 的结论与可直接并入 Spec 的条款；v1 的范围与状态以 [Roadmap](../roadmap/README.md) 为准，现行语义以 [Guide v0.47](../guide/README.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。来源是[演进总纲之十三](evolution-13-implementation-roadmap.md) §3：
v1 发布后，公开的名字、签名与可观察行为只能增加不能修改，所以有十件事要在对应条目动工前定下。
2026-11-11 用户要求把结论写入对应 v1 条目的 Spec 草稿。

**关于落点的说明。** 核对后发现，这些条目（T1、L6b、L6、L1、L21、L16、S3、V6、V2）在 `docs/specs/` 中**都还没有 Spec 草稿**。
Spec 编号全局唯一且有进行中的分支在使用，为尚未起草的功能预占编号、预写整份 Spec 超出了本次范围。因此本页采用如下做法：

- 每项给出可以原样并入 Spec 的三段文字：需求、非目标、验收。
- 在 v1 路线图中登记决策 D16，并把本页加入上述条目的依据链接；起草这些条目的 Spec 时，路线图会把起草者带到这里。
- 需要改动 Guide 文字或新增 ADR 的项单独标出，它们仍须按正常流程启用。

编号用 Z，避免与 v1 路线图的条目 V1–V6 混淆（之十三初稿曾用 V1–V10）。

## 2. 各项条款

### Z1 线程合同的措辞（T1）

现行 [Guide 13](../guide/13-program-runtime-standard-library.md) 写的是“任何线程中的 abort 都终止整个进程”，[Guide 09](../guide/09-nullability-errors.md) 写的是“不转成 `Err`，不展开其他线程的栈”。
**2026-11-14 裁决：Guide 不改。** 此前本项列了三个选项，其中倾向的选项 a 是把“不执行尚未运行的 drop”对工作线程放宽为未指定。
[evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R7 指出这不能带来兼容：v1 承诺的还有“进程一定终止”。
之十一 J48 已改为“失败在显式的监督边界处被接住”，普通线程不是边界，v1 程序的行为日后不变，所以三个选项都不再需要。

无论选哪一项，下面给 T1 的约束都成立：

- **需求**：`join(): T` 的签名按现行 Guide 实现。`Sender.send` 返回 `Boolean`、`Receiver.receive` 返回 `T?` 的形态保持，它们已经能表达“对方不在了”。
- **非目标**：不承诺 abort 发生后其他线程立即停止运行；不承诺 abort 报告与其他线程输出之间的先后；不提供 detach；不提供在线程内捕获 abort 的手段。
- **验收**：测试只断言“进程以 abort 状态结束且 stderr 含 abort 报告”，不断言其他线程在此之前或之后的输出是否出现。

依据：[之十一](evolution-11-failure-interfaces-units.md) J48。

### Z2 `time` / `sleep` / `math` 的包划分与命名（L6b）

- **需求**：
  - 时间分为三个类型：单调时钟的时间点（`Instant`）、时长（`Duration`）、日历时间（`SystemTime`）。计时与超时只用前两个；`SystemTime` 只提供自纪元起的秒与纳秒。
  - `sleep` 接受 `Duration`，不接受裸整数。
  - 包名为 `koven.time` 与 `koven.math`。`koven.math` 的超越函数在合同中写明“不保证跨平台逐位一致”；加减乘除与开方保证。
- **非目标**：时区、历法、日期格式化与解析；区域相关的任何行为；随机数（另立条目）。
- **验收**：单调时钟两次读数不回退；`sleep(d)` 之后单调时钟前进不少于 `d`；公开表面与[之十二](evolution-12-stdlib-platform.md) §3 的清单逐项一致。

### Z3 runtime 中系统调用的组织（L6、T1、L6b）

- **需求**：runtime 中凡直接调用操作系统或 C 库系统接口之处，集中在一个模块之后；该模块的每个入口有一段与平台无关的合同说明（输入、输出、错误种类、明确不保证的行为）。runtime 其余部分不直接包含系统头文件。
- **非目标**：不引入新的平台；不改变任何用户可见行为；不要求用 Koven 源码实现（那是之十二 PL2）。
- **验收**：一个脚本或评审清单确认系统头文件的包含只出现在该模块；两个现行目标的既有测试结果不变。

依据：之十二 PL0。IO 与线程的 runtime 尚未动工，从第一行就这样组织没有额外成本。

### Z4 `Hashable` 的方法形状不向用户暴露（L1）

- **需求**：`Hashable` 在 v1 只有两种用途——结构推导、作泛型上界。不公开任何“取哈希值”的成员（不提供 `hashCode()` 一类方法），用户不能手动实现。`Equatable` 经 `==` 使用，`Display` 的 `toString()` 按现行 Guide 公开。
- **非目标**：自定义哈希；向用户暴露哈希值的类型与位宽；承诺哈希值在进程之间稳定。
- **验收**：存在一个被拒绝的用例——用户类型声明实现 `Hashable` 或调用其成员——并得到诊断。

依据：之十一 J44。将来库类型需要声明哈希时，取“写入哈希器”的形状；v1 若公开了返回整数的方法，就改不回来。

### Z5 显式流的关闭（L6 的后继）

仅当显式流 owner 在 v1 之内定义时适用；路线图目前把它列为“另行定义”。

- **需求**：流是 `MoveOnly` 的资源类型。显式关闭是消费流并返回 `Result<Unit, IoError>` 的方法；未显式关闭时由 `deinit` 尽力关闭并丢弃错误。带缓冲的写入方在文档中明确“未显式关闭即丢弃错误，可能丢数据”。
- **非目标**：`use { }` 一类作用域函数（可后加）；异步关闭。
- **验收**：关闭两次（编译期被拒绝，因为第一次已消费）、关闭失败、未关闭即析构三种情形各有用例。

依据：[之七](evolution-07-concurrency-async-io-ffi.md) J23、IO0。

### Z6 `main` 返回 `Result<Unit, E>`（L21）

- **需求**：保持路线图现有表述：`E` 满足 `Display`。
- **非目标**：不要求 `E` 实现任何其他接口；不在 v1 引入通用错误接口。
- **验收**：按路线图现有验收。

依据：之十一 §2.3。将来的 `Error` 接口继承 `Display`，所以这条约束向后兼容，不需要现在做任何事；列在这里只为防止起草时收紧。

### Z7 集合高层 API 的命名与接收者（L16、S3）

- **需求**：
  - 名字取 Kotlin 的：`forEach`、`map`、`filter`、`fold`、`contains`、`indexOf`、`reversed`、`sorted` 等；返回新集合的用过去分词形式，原地修改的用动词原形，与 Kotlin 一致。
  - 每个签名按下面的问题审查一遍并在 Spec 中记录结论：将来接收者由具体的 `List` 换成 `Iterable<T>` 或视图时，这个名字与参数表是否仍然成立。
  - 可能 abort 的操作同时提供返回 `T?` 的版本，命名用 `OrNull` 后缀（现行规则）。
- **非目标**：惰性序列；用户自定义类型进入 `for`；`Iterable` / `Iterator` 接口本身。
- **验收**：Spec 附一张“名字 × Kotlin 对应 × 接收者泛化后是否仍成立”的表。

依据：之十一 J43；[之六](evolution-06-text-globals-extensions-metadata.md) TX0。

### Z8 project 清单中的语言版本字段（V6）

- **需求**：project 清单含一个语言版本字段。v1 只接受一个取值；缺失时按 v1 处理并给出提示；取值不被识别时报错并列出本编译器支持的取值。
- **非目标**：按版本切换任何语义（v1 只有一个版本）；依赖声明、依赖解析。
- **验收**：缺失、合法、不被识别三种情形各有用例。
- **流程**：清单格式由 ADR-0022 管辖，增加字段须按 ADR 生命周期处理（新增 ADR 或对其后继）；本页只给出需求。

依据：之十一 J47。没有这个字段，以后启用保留字只能对全部代码同时生效。

### Z9 一致性矩阵的形态（V2）

- **需求**：每个用例由源码与期望的可观察结果组成（退出状态、标准输出、诊断编号与位置）。期望中不出现编译器内部产物（中间表示、内部错误类别名）。“已知未实现”作为矩阵外的登记存在，不写进用例的期望。
- **非目标**：不要求现在就能对第二个实现运行。
- **验收**：对现有 `conformance/expectations.json` 做一次核对，列出其中引用了内部产物的条目（若有）及处置。

依据：[之十](evolution-10-coverage-gaps.md) §7.9。本项未检查现有矩阵是否已经满足；核对本身就是验收的第一步。

### Z11 目录枚举遇到不可表示的文件名（L6）

2026-11-14 核对：[Guide 13](../guide/13-program-runtime-standard-library.md) 已启用 `Directory.list(path: String, maxEntries: Int): Result<Array<DirectoryEntry>, IoError>`，条目名是 owned `String`，
并规定“不可表示的文件名使整个调用失败”。本项初稿写的是“v1 不发布返回 `String` 文件名的目录枚举”，与已启用的 Guide 不符，改写如下。

- **需求**：按现行 Guide 实现；遇到无法表示为 UTF-8 的文件名时整个调用失败。
- **非目标**：跳过这类条目；有损转换；在 v1 内引入无损路径类型。
- **验收**：含非 UTF-8 文件名的目录，`Directory.list` 返回错误而不是部分结果。

依据：[之十二](evolution-12-stdlib-platform.md) §4 规则 3（评审 R8）。失败是不丢信息的行为，日后增加无损的路径类型与相应的枚举接口是纯增量。
反过来，v1 若发布了“跳过”或“有损转换”，以后就改不回来。

### Z10 `unsafe` 合同的失败安全条款

不属于任何 v1 条目。条款正文见 [U0 提纲](unsafe-aliasing-contract-outline.md) §4。
时限：在 `unsafe` 向标准库作者开放（U1）之前定稿。

## 3. 未覆盖的风险

- Z2、Z7 给出的是命名与划分的约束，不是完整的 API 表面；完整表面仍须由各自的 Spec 与 Guide 增量给出。
- Z3 只能约束新写的 runtime 代码；已有的 runtime 是否需要回头整理，由对应 Spec 决定。
- 本页没有覆盖文本 API（L5）：它的签名已由 SPEC-0366 启用、SPEC-0368 部分实施，属于已经冻结的表面，不在“动工之前”的范围内。之六 TX0 对它的审查须另行安排。
