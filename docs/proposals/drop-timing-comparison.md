# 析构时机：两个方案的对比

> **性质**：非规范候选设计对比 · **状态**：未启用；方向已裁决（2026-11-14 取方案 B） · **读取时机**：裁决 [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) 的 A3，或启动[演进总纲之四](evolution-04-route-capability-unsafe-suspend.md) 的 C1（`DropPolicy`）时 · **唯一真源**：本页维护两个方案的对比与倾向；现行析构规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。没有做任何性能测量。

## 1. 问题

评审 A3 建议重新评估“确定性最早析构”是否值得成为长期语言承诺，并指出之四保留它的理由部分来自既有承诺与黄金输出，这些不应成为设计理由。
它的倾向是：语言默认规定词法资源生命周期，在确实不可观察的前提下允许优化提前释放。

## 2. 现行规则（已对照 Guide 原文）

- [Guide 10](../guide/10-ownership-borrowing-drop.md) 是双轨：声明了 `deinit` 的类型及其字段递归包含这类类型的复合类型是“资源类型”，在词法作用域结束时按声明逆序析构；
  其余是“纯内存类型”，在 owner 不再 live 的最早边界析构，从未使用的 owner 在绑定建立后立即析构。
- 最早边界有精确定义，覆盖分支、循环回边、临时值与提前返回；所有权检查输出源码有序的 drop facts，后端消费它们。
- [Guide 07](../guide/07-calls-lambdas-closures.md) 把闭包持有的 loan 的结束点定义为“该闭包值的 ASAP drop point”。也就是说，最早析构点目前还承担着“借用何时结束”的定义。
- [Guide 13](../guide/13-program-runtime-standard-library.md)：每个 live 的 `Rc` 句柄在自己的 ASAP drop point 递减强计数；计数不可读。

由此得到一个事实：**在 v1，纯内存类型的析构时机对用户代码不可观察**。它们没有 `deinit`，计数读不到，没有 `Weak`，没有裸指针。
能感知到的只有内存峰值与分配器是否复用。

一个需要核对的疑点：Guide 10 把 `Box<T>`、`Array<T>`、`List<T>` 列为纯内存类型，资源类型的传递只写了“字段递归包含”。
`Box<File>`、`List<File>`、`Rc<File>` 这样以资源类型为实参的容器属于哪一轨，这段文字没有明说。若按纯内存处理，容器在最后一次使用后析构会提前运行 `File` 的 `deinit`，这是可观察的。
**我没有核对其他章节或实现对此的处理**，只把它记为待查。

## 3. 两个方案

**方案 A：最早析构加屏障**（之一 D8、D10 与之四 C1 的现行候选）。析构不可观察的类型**必须**在最早边界析构，该边界由规范精确定义。
以后每出现一种让析构可观察的机制，就在“可观察来源”的封闭列表里加一项，使相关类型退回词法析构：声明 `deinit`、被 `Weak` 观察、派生过裸指针、载荷未知的存在类型。

**方案 B：词法析构，允许提前**（评审 A3 的倾向）。规范只规定一个时机：值在词法作用域结束时析构。
析构不可观察时，实现**可以**在最后一次使用之后的任何位置提前析构；规范不规定具体位置。借用何时结束与 owner 何时析构分开定义。

之四 C1 末尾已经提出过“先写词法、再写提前”的叙述顺序，并指出它与方案 A 对合法程序的可观察行为相同。两个方案真正的差别只有一处：**提前析构是规范的强制要求，还是实现的许可**。

## 4. 对比

| 维度 | 方案 A | 方案 B |
|---|---|---|
| v1 程序的可观察行为 | 现状 | 相同（纯内存类型的析构时机本来不可观察），除内存峰值不再受保证 |
| 规范体量 | 需要最早边界的完整定义（现在是 Guide 10 的一整节），加一张会增长的屏障列表 | 一句默认规则加一句许可 |
| 新机制漏了登记时的后果 | 漏加屏障 = 对象被提前释放，是内存安全问题 | 漏声明“不可观察” = 少一次优化 |
| `unsafe` 作者要记住的 | owner 在最后一次使用后就可能消失；从它派生的裸指针必须靠屏障标记保活 | owner 活到作用域结束，除非编译器能证明提前释放不可观察 |
| 借用的结束点 | 现在借用了最早析构点的定义（Guide 07 的闭包 loan） | 必须另行定义为“持有者最后一次使用”。这正是路线 L 的 L1 要做的；在 L1 之前单独切换到方案 B，要么改写 Guide 07 的这句话，要么闭包的 loan 变长、原本合法的程序被拒绝 |
| 内存峰值 | 有保证：最后一次使用后立即归还 | 尽力而为；需要保证时用内层代码块或显式消费来缩短作用域 |
| 调试 | 变量在最后一次使用后已被释放，调试器里看不到它 | 调试构建可以让变量活到作用域结束 |
| 挂起帧的大小（v3） | 跨挂起点保存的值更少 | 相同，因为许可仍允许提前释放 |
| 测试与一致性矩阵 | drop facts 的位置是规范的一部分，黄金输出据此断言 | drop facts 的位置是实现细节；一致性用例只断言可观察结果 |
| 编译器实现 | 现状 | 可以原样保留现有规划器；活性分析仍然需要（借用要用） |
| 与 Kotlin / Rust / Swift 使用者的直觉 | 需要解释“为什么这个值在这一行就没了” | 与 Rust 的作用域析构、Swift 的词法生命周期一致 |

## 5. 对 v1 冻结的影响

上一轮我说这条“可能受 v1 冻结的时限约束”。核对之后，影响比我说的小：

- v1 按方案 A 发布，以后改为方案 B，是把一项内存峰值保证降为尽力而为。对不含 `deinit` 的类型，这不改变任何程序的输出。它不是破坏性的语义变更，但依赖“立即归还”来控制峰值的程序可能退化。
- 反方向（先 B 后 A）是增加保证，总是兼容的。
- 所以不必赶在 v1 冻结前裁决。v1 期间只需要不新增依赖最早析构点的对外承诺，例如不在文档里把内存峰值写成保证。§2 的疑点若属实，则是 v1 自己要修的问题，与选哪个方案无关。

## 6. 倾向

倾向方案 B，随 C1 的 Guide 改写一并启用，不提前到 v1：

- 决定性的理由是失效方向：方案 A 下每个新机制都要记得加屏障，漏了就是释放后使用；方案 B 下漏了只是慢一点。之一的判据 T3 要求在不可逆处取更严的一侧，这里同理。
- 规范更短，读者只需记住一个默认时机。
- 实现可以不变，所以没有迁移成本；黄金输出继续作为实现测试存在，只是不再属于规范。
- 时机放在 L1 之后，因为那时借用的结束点已经不依赖析构点，Guide 07 的那句话可以一起改。

方案 B 的代价要明说：内存峰值不再有规范层面的保证；“提前到哪里”在不同编译器版本之间可以变化。后者不违反仓库的确定性要求——给定编译器的产物仍然确定——但一致性矩阵不能再断言这些位置。

## 7. 未核对与不确定

- 没有测量两种方案下的内存峰值差异，也没有统计现有程序里有多少依赖“立即归还”。
- §2 的容器疑点未核对。
- 没有核对现有黄金输出中有多少条断言的是纯内存类型的析构位置；方案 B 下它们要从一致性用例移到实现测试。
- Swift 的词法生命周期与 Mojo 的 ASAP 行为取自之一的调研记录，本轮没有重新联网核对。

## 8. 裁决与“一条线”（2026-11-14）

用户裁决取方案 B，随 C1 的 Guide 改写启用，并确认终态应统一成一条线。统一后的形态：

- **规范里只有一条规则**：值在词法作用域结束时按声明逆序析构；析构不可观察时，实现可以在最后一次使用之后提前析构。
  “纯内存类型 / 资源类型”的二分不再出现在规范里；“析构是否可观察”是由能力系统推导的一项性质，不是用户要记的两类类型。
- **实现里只有一个规划器**：析构点 = f(活性, 析构是否可观察)。现行的两轨、以及 Single 与 Unit 各一份共四处实现，收敛为一处（之四 C1、之一 D10）。
- **借用的结束点单独定义**为持有者的最后一次使用（路线 L 的 L1），不再借用析构点。

启用之前的次序不变：v1 按现行双轨发布；L1 完成后，随 C1 一并改写 Guide 10 与 Guide 07 的相应文字。§2 的容器疑点与 §7 的未核对项仍须先处理。
这是候选方向的裁决，不是 Guide 的启用。
