## 1. 合同回答什么与核心术语

`unsafe` 代码能做编译器不检查的事。合同规定两个方向的责任：

- **unsafe 代码必须保证什么**，使安全代码所依赖的不变量继续成立。
- **安全代码与编译器可以假设什么**，据此做借用检查、析构规划与后端优化。

合同之外的行为都有定义；合同之内列出的违反是未定义行为（§6）。合同保持精简，使标准库作者能逐条对照自己的代码。

### 1.1 核心术语

| 术语 | 定义 |
|---|---|
| **place** | 标识一段有稳定所有权归属的存储位置（变量根 + 零或多个字段/索引投影，沿用 [Guide 10](../guide/10-ownership-borrowing-drop.md)） |
| **loan** | 安全代码对某 place 建立的共享（`Shared`）或独占（`Exclusive`）访问授权，带静态确定的起止边界与派生树（[之二](evolution-02-route-loan-kernel.md)） |
| **来源（origin）** | 持有者当前依赖的 loan 集合；`from` 与 `flows` 合同描述跨函数边界的来源传递 |
| **裸指针（`RawPtr<T>`）** | 不拥有、不借用、不触发析构的地址值；附带逻辑**来历（provenance）**，即它获准访问的分配块或 owner place 范围 |
| **有效性不变量** | 一个值作为其类型存在所必需的底层条件：已初始化、位模式合法（如 `Boolean` 仅 0/1、`enum` 判别值合法）、引用非空且对齐、不可变不变量未被破坏 |
| **安全不变量** | 类型对安全代码承诺的高层语义条件：例如 `List` 的“长度不超过容量”、`String` 的“字节为合法 UTF-8”、`Cell` 不交出内部引用 |

两类不变量的生效时机：

| 名称 | 何时必须成立 |
|---|---|
| 有效性不变量 | **任何时刻**，包括 `unsafe` 代码内部；在任何点构造或读取违反有效性不变量的值即为 UB3 |
| 安全不变量 | 值交还给安全代码时，以及任何可能运行安全代码、调用回调或触发析构的时刻（见 §4 FS2） |

## 3. 别名条款、来历与后端属性映射

### 3.1 五条基础别名条款（AL1–AL5）

- **AL1（不与存活 loan 冲突）**：经裸指针读写某 place，必须受其派生来源的访问权限支持，且不得与**其他**重叠存活的 loan 冲突（沿用 Guide 10 冲突矩阵与借用派生树）：
  - 经独占所有权或 `inout` 绑定（含其字段投影）派生的裸指针，继承该独占绑定的写权限，不与其所派生的祖先独占 loan 冲突（因此 `inout` 持有者在函数体内经自身字段派生 `RawPtr` 并写回——如 U1 的 `replace` / `swap`——合法），但仍不得与该 place 上**其他**存活的共享/独占 loan 或尚未结束的派生子 loan 冲突；
  - 经共享借用（`Shared` loan）派生的裸指针只继承读权限；对其执行写操作构成 UB1，除非落入 AL7 的 `RawCell` 内部可变例外。
- **AL2（不晚于 owner 析构或释放）**：裸指针的解引用读写不得晚于其所指存储的 owner 被析构、整体移动导致原存储失效，或堆分配被释放（UB2）。对仍存活的分配槽位，经 `ptr.read()` 移出值后槽位变为**未初始化**而非已释放：允许随后用 `ptr.write(new)` 重新初始化该槽位（支撑 U1 `replace` / `swap`），但重新初始化前将其作为有效值读取或析构构成 UB5。经 `addressOf(place)` 取址时，[之四](evolution-04-route-capability-unsafe-suspend.md) U1 R1.2 在该 owner place 上建立 place 级析构屏障，将其析构点提升为至少词法作用域结束；跨作用域保存指针须由库另行保证 owner 存活（如堆分配或显式存活延长原语）。
- **AL3（交还值满足全部不变量）**：经 `unsafe` 块或受信任函数交还给安全代码的每个值，必须同时满足其类型的有效性不变量、安全不变量、能力判定前提与恰好一份析构义务。
- **AL4（`from` / `flows` 来源覆盖）**：声明了 `from` 或 `flows` 的 `unsafe` / `trusted` 函数，其返回值或写入目标实际依赖的存储，必须完全被签名声明的来源 loan 覆盖（不得返回未声明来源或局部栈地址）。
- **AL5（受信任能力声明全域成立）**：受信任的能力声明（如 `Shareable`、`Transferable`）必须在安全代码可能构造的所有调用序列与并发交错下成立。

### 3.2 裸指针来历与内部可变例外（AL6–AL7）

- **AL6（裸指针来历与配对释放规则）**：
  1. 经 `addressOf(place)` 得到的 `RawPtr<T>`，其来历仅覆盖该 `place` 所占的字节范围；经 `alloc(size, align)` 得到的指针，其来历仅覆盖该次分配的 `[base, base + size)` 字节范围。
  2. `ptr.offset(n)` 与 `ptr.cast<U>()` 继承原指针的来历，不得通过偏移从某变量或分配块越界访问相邻的另一个局部变量或另一块独立分配（即便运行时地址恰好相邻）。
  3. 指针与整数互转时，从整数恢复指针必须指向仍存活的既有分配块并恢复其有效来历；凭空拼凑整数地址解引用为 UB10（设备寄存器一类 MMIO 须走 MM6 易失读写原语，不走普通指针解引用）。
  4. **配对释放**：`dealloc(ptr, size, align)` 的实参 `ptr` 必须与某次仍存活的 `alloc(size, align)` 返回的**起始基址指针**（相同分配块与相同 `(size, align)` 布局）严格配对；向 `dealloc` 传入分配内部偏移指针（即使满足对齐）、栈地址、已释放指针或布局不匹配的 `(size, align)` 构成 UB11。
- **AL7（`RawCell<T>` 内部可变例外）**：
  1. `RawCell<T>`（KB6，[之四](evolution-04-route-capability-unsafe-suspend.md) C2）是“经共享借用（`Shared` loan）仍可取得指向内部的裸指针并写入”的**唯一**合法例外。对不含 `RawCell` 的类型，经共享借用取裸指针并写入构成 UB1。
  2. 落实之四 C2 R2.4 义务：无运行时借用检查的 `Cell<T>` 只能提供整值的 `get` / `set` / `replace`，**严禁经共享借用交出指向内部存储的安全 `borrow` / `inout` 引用**（否则另一共享借用的写入将直接令已交出引用悬垂或破坏别名假设，构成 UB1）。带运行时借用标志的单元（如 `RefCell`）交出的守卫须以运行时排他计数保证无重叠写。

### 3.3 参数模式到后端别名属性的映射（AL8，之八 §3.2 / VE1 前置）

基于 AL1–AL7 与 §5 内存模型，编译器后端在满足本合同的前提下可为函数参数发射以下别名与捕获属性（之八 §3.2 与 VE1 的依据）。**关于 `nocapture` 的前置条件**：缺少 `from` / `flows` 只证明函数不返回或写入安全 loan，**不足以**单独证明地址未逃逸（AL6 允许 `unsafe` 代码把派生指针转为整数并返回或传给 FFI）。因此发射 `nocapture` 必须同时满足：（1）参数未出现在 `from` / `flows` 合同中，**且**（2）后端经独立捕获分析证实其地址未通过 `addressOf`、指针转整数或 FFI 逃逸（纯安全函数体自动满足；含 `unsafe` 或调用未证实 `nocapture` 的函数时不得仅凭无 `from` / `flows` 发射）：

| 参数模式与类型条件 | 允许发射的后端属性（LLVM 语义） | 禁止条件与依据 |
|---|---|---|
| `borrow x: T`（`T` 递归不含 `RawCell`） | `readonly`、`nonnull`、`align`；满足上述捕获证明时可加 `nocapture` | 只要 `T` 递归含 `RawCell`，**严禁**发射 `readonly`（AL7 / 之四 R2.3）；若 `x` 出现在 `from`/`flows` 合同中或地址可能经 `addressOf`/转整数/FFI 逃逸，**严禁**发射 `nocapture` |
| `borrow x: T`（`T` 递归含 `RawCell`） | `nonnull`、`align`；满足上述捕获证明时可加 `nocapture` | 不得标 `readonly` 或 `noalias`（允许经其他共享借用并发/交替写入内部可变单元）；捕获证明不成立时严禁 `nocapture` |
| `inout x: T`（任意类型） | `noalias`（对当前调用可见的非原子访问）、`nonnull`、`align`；满足上述捕获证明时可加 `nocapture` | 若 `x` 出现在 `from`/`flows` 合同中或地址可能经 `addressOf`/转整数/FFI 逃逸，**严禁**发射 `nocapture`；内部可变类型处于独占借用时仍无其他合法访问者，可保 `noalias` |
| `own x: T`（间接 owner 指针表示） | `noalias`（唯一所有权移交）、`nonnull`、`align` | 仅对唯一独占 owner 成立；`Rc<T>` 等共享句柄指针不得对底层共享载荷标 `noalias` |

## 4. 失败安全条款（FS1–FS8）

**背景。** v1 中任何 abort 都终止整个进程，所以 `unsafe` 代码在 abort 之后留下的状态无人能观察。
[之十一](evolution-11-failure-interfaces-units.md) J48（2026-11-14 修订）把目标方向定为**显式监督边界**：在监督边界之内发生普通失败时，展开到该边界并执行栈上各作用域的析构。
一旦如此，`unsafe` 代码在失败发生的那一刻留下的状态，就会被随后运行的析构看到。
这一条款在第一行用户 `unsafe` 出现之前写入，是因为它无法事后追加——追加等于宣布此前写的全部 `unsafe` 代码可能不合格。

- **FS1（可能失败的操作）**：下列操作可能不返回，`unsafe` 代码必须按“可能不返回”对待：
  - 带检查的整数运算、带检查的转换、下标访问、`!!`、`error()`；
  - 内存分配；
  - 对任何函数的调用，除非该函数在本合同中被列为“不失败”（见 FS4）；
  - 类型参数上的任何操作：调用其方法、析构它的值、复制或克隆它；
  - 调用闭包；
  - 任何值的析构，只要它的类型有用户定义的 `deinit` 或含有这样的字段。
- **FS2（义务）**：在每一个可能失败的操作开始执行的时刻，下面两条必须成立：
  1. 当前执行单元上将被析构的每一个值——局部变量、已构造的临时值、被修改的容器本身——处于其析构可以安全运行的状态；
  2. 其他线程经共享类型能看到的状态，满足该类型的安全不变量，或者已被标记为“持有者异常终止”（如锁中毒）。
- **FS3（允许泄漏，不允许重复析构、读未初始化或抹除安全义务）**：在**显式监督边界内发生展开且进程继续运行**的失败路径上，析构**不承担安全义务**的值可以不被析构（泄漏）；析构承担安全义务的值——等待借用型子任务的作用域、结束访问授权的 guard——必须按展开顺序被析构，`unsafe` 代码不得使它们的义务消失（2026-11-14 收窄，评审 R3）；绝不允许被析构两次，析构也绝不允许读到未初始化的存储。因此常用写法是：在进入安全不变量暂时被打破的区间之前，先把容器的可见长度调低，使失败时多出来的元素只是泄漏。
  - **与致命终止的区分**：v1 的整进程 abort，以及 FS6（`deinit` 中失败）与 FS7 / FFI5（失败跨越 C 帧）触发的致命终止，均直接结束整个进程而**不执行**待运行析构；此类终止不会让其余安全代码继续观察到未清理状态，不适用上文“必须执行待运行析构”的运行时承诺。
  - 与 [IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md) 一致：在继续运行的展开路径上，对仍有在途外部访问的缓冲区保留不释放，合乎 FS3 的“允许泄漏”；但泄漏不得抹除等待子任务或释放访问授权的义务。
- **FS4（不失败的操作清单）**：合同列出封闭清单，`unsafe` 代码可以在安全不变量被暂时打破的区间内使用它们：裸指针的读、写、偏移与类型转换；布局查询（`sizeOf` / `alignOf`）；显式环绕/饱和算术；对 `Copyable` 且无 `deinit` 值的按位复制；原子操作。清单之外的操作一律按 FS1 处理。
- **FS5（推荐结构）**：先做完所有可能失败的计算（算出新容量、调用用户比较函数、分配新缓冲），再进入只含 FS4 操作的区间完成状态切换。做不到时，用一个局部的 `ScopeGuard` 守卫值，使其析构负责把状态恢复到满足 FS2。
- **FS6（析构中的失败）**：析构过程中再次失败（以及按现行共识，正常路径 `deinit` 首次失败），进程直接终止，不继续执行剩余待运行析构。因此 `deinit` 中应当只做不失败的操作与资源释放。
- **FS7（外部函数）**：失败不得穿过外部函数的帧。从 Koven 传给 C 的回调若发生失败，进程直接终止，不继续执行剩余待运行析构（同 FFI5）。
- **FS8（在 v1 及之后的编写与检验要求）**：即使 v1 运行时在进程级 abort 时直接终止进程、不执行待运行析构，`unsafe` 代码仍须**按“监督边界内可能展开并执行待运行析构”的假设编写**，避免日后启用显式监督边界时既有 `unsafe` 代码整体失效。检测手段：参考解释器（[之十](evolution-10-coverage-gaps.md) §7.10）在每个 FS1 操作处注入**可展开的失败**并运行待执行析构，检查是否出现重复析构、读未初始化或抹除安全义务。

**示例**（候选伪代码，说明 FS2 与 FS3）：向列表中部插入元素时，必须先完成可能失败的 `clone()`，再进入不失败的指针搬移区间：

```text
错误的次序：
  1. 把后半段向后移动一格        （此刻下标 i 处有一个重复的元素）
  2. 调用 clone() 得到新元素     ← 可能失败；若失败，列表析构时下标 i 的元素被析构两次（UB4）
  3. 写入下标 i

正确的次序：
  1. 调用 clone() 得到新元素     ← 可能失败；此时列表完好
  2. 把后半段向后移动一格        （只含 FS4 不失败操作）
  3. 写入下标 i；长度加一
```

## 5. 内存模型（MM1–MM7）

- **MM1（数据竞争定义）**：两个线程访问同一内存位置，至少一个是写，至少一个不是原子操作，且二者之间没有先后次序（happens-before）约束。安全代码中不可能出现数据竞争（由 `Transferable` / `Shareable` 与借用规则保证）；`unsafe` 代码中出现即未定义行为（UB6）。
- **MM2（先后次序来源）**：至少包括现行 [Guide 13](../guide/13-program-runtime-standard-library.md) 已规定的两条——“`join` 返回时，线程中的全部写入对调用者可见；`send` 之前的写入，对收到该值的 `receive` 之后可见”——以及线程创建（创建前写入对新线程可见）、锁的释放与获取、原子操作各自的同步规则。
- **MM3（原子操作）**：采用 C/C++ 的原子次序模型，由 LLVM 直接实现，不自行设计。标准库原子类型不带次序参数的方法默认使用最强次序（`SeqCst`）；较弱次序须显式传参。首批倾向提供三种（`SeqCst`、`Acquire`/`Release`、`Relaxed`），其余按需增补。
- **MM4（没有“良性竞争”）**：不为“只是读到旧值也无妨”的写法开例外；此类需求一律使用原子操作（如 `Relaxed`）表达。
- **MM5（与优化的关系）**：编译器可以假设不存在数据竞争，据此重排与合并非原子访问。AL8 的后端属性映射以 §3 与本节为共同依据。
- **MM6（易失访问）**：设备寄存器一类 MMIO 访问不属于普通内存模型，由单独的易失读写原语承担（[之十](evolution-10-coverage-gaps.md) §7.4）。易失语义仅禁止编译器省略、合并或**在易失访问之间**重排它们；易失访问**不约束**其与普通非原子内存访问之间的相对重排，也**不提供**跨线程的 `happens-before` 同步（线程间通信或普通内存与 MMIO / DMA 之间的顺序保证仍须使用 MM2–MM3 的原子操作或显式内存栅栏）。
- **MM7（未初始化内存读取）**：读取任何未初始化字节（包括填充字节或已 `ptr.read()` 移出后的存储）一律为未定义行为（UB5）；不提供“读取未初始化内存得到任意固定位模式”的宽松语义，除非经专门的字节拷贝原语在未初始化缓冲区之间搬运且不作为强类型值读取。跨线程无锁内存回收（如 epoch / hazard pointer）属于共享库自身的安全合同，不作为内核内存模型的特殊规则。

## 6. 未定义行为清单（UB1–UB11）

逐条编号；清单之外的行为都有定义。

| 编号 | 未定义行为 | 所属条款 | 最小违反示例 |
|---|---|---|---|
| UB1 | 经裸指针的访问违反派生权限或与其他重叠存活 loan 冲突（含对非 `RawCell` 类型经共享借用写入，或 `Cell` 交出内部引用后再写入） | AL1、AL7 | 持有 `borrow val r = x` 时，经先前取得的 `RawPtr` 写入 `x`；或 `Cell.getRef(&c)` 交出引用后经另一共享借用 `c.set(newVal)` |
| UB2 | 解引用指向已析构或已释放存储的指针（含悬垂栈指针与释放后使用；存活分配上 `ptr.read()` 移出后的未初始化槽位允许 `ptr.write(new)`，但读取或析构归 UB5） | AL2 | `dealloc(p)` 后再执行 `p.read()`；或把局部 `addressOf(x)` 存到外层并在离开作用域后解引用 |
| UB3 | 构造或读取不满足有效性不变量的值 | §1.1 | 经 `ptr.cast<Boolean>()` 写入字节值 `2` 后按 `Boolean` 读取；或对非空引用槽位写入零指针 |
| UB4 | 同一份析构义务被履行两次 | AL3、FS3 | 对同一 `RawPtr<File>` 连续执行两次 `val f1 = p.read(); val f2 = p.read()`（中间未写入新值），把同一份 `File` 析构义务复制给两个存活 owner，离开作用域时各执行一次 `File.deinit` |
| UB5 | 读取或析构未初始化的存储（含 `alloc` 刚分配或 `ptr.read()` 移出后尚未 `ptr.write` 的槽位） | AL2、MM7 | `alloc` 刚分配的裸缓冲未写入即调用 `p.read()` 作为 `Int` 或 `String` 读取；或对 `p.read()` 移出后未回填的槽位按已初始化值执行析构 |
| UB6 | 数据竞争 | MM1、MM4 | 两个线程在无同步且无原子操作的情况下同时对同一 `RawPtr<Int>` 一读一写 |
| UB7 | `from` / `flows` 声明与实际依赖不符 | AL4 | `trusted fun bad(borrow a: Arr, borrow b: Arr): borrow Int from a` 实际返回指向 `b` 的借用 |
| UB8 | 受信任的能力声明不成立而被安全代码依赖 | AL5 | 为含非原子计数 `Rc<T>` 的包装类型手工声明受信任的 `Shareable` / `Transferable`，随后跨线程并发访问 |
| UB9 | 违反外部函数边界的五条合同 | §8 FFI1–FFI5 | C 函数留存 Koven 借用实参指针并在返回后写入；或经 C 回调触发 abort 试图展开穿过 C 帧 |
| UB10 | 访问超出分配/来历范围，或未满足类型对齐要求 | AL6 | 对长度为 `n` 的数组缓冲执行 `p.offset(n).read()`；或把未按 8 字节对齐的地址强制 `cast<Long>()` 后解引用 |
| UB11 | 非法释放或布局不匹配释放 | AL6 | 对 `p = alloc(size, align)` 的内部指针 `p.offset(1)` 调用 `dealloc`；或对栈地址、已释放指针、不匹配 `(size, align)` 调用 `dealloc` |

**关于“仅违反安全不变量但未违反有效性不变量”的定性**：
不列为未定义行为的（有定义，尽管通常是程序错误）包括：内存泄漏、死锁、显式环绕算术溢出。对于失败路径上仅违反**安全不变量**（例如 `String` 内部字节暂非合法 UTF-8，但其长度/指针/容量本身均为有效初始化值），单就该状态本身**不构成 UB**（不会触发编译器据此做任意未定义优化）；但一旦后续安全代码或 `unsafe` 代码依赖该安全不变量并据此越界访问或重复析构，则在该访问点构成对应的 UB（UB4 / UB10）。

## 7. 受信任的声明与审查范围（TR1–TR4）

- **TR1（`unsafe` 函数体与块内检查边界）**：`unsafe { ... }` 块与 `unsafe` / `trusted` 函数体**仅**解锁特权原语（裸指针解引用、偏移、类型转换、`extern "C"` 调用、未初始化读写）及签名合同自证；**不关闭**普通类型检查、未标 `trusted` 处的安全借用检查或语法规则。对调用方而言，安全包装函数的签名（参数模式、`from`/`flows`、返回类型能力）即为完整合同。
- **TR2（受信任能力声明）**：为内部使用 `unsafe` 实现的同步类型（如 `Arc`、`Mutex`、原子类型）手工断言 `Transferable` / `Shareable` 属于受信任声明，仅特权标准库包（以及 U3 开放后的用户 `unsafe`）可用；声明者须证明 AL5 与 MM1–MM2 在全部公开 API 组合下成立。
- **TR3（逻辑接口实现不要求 `unsafe`）**：库类型为容器手工声明 `Equatable` / `Hashable` / `Comparable`（[之十一](evolution-11-failure-interfaces-units.md) §2.4）写错时仅破坏逻辑语义而不破坏内存安全，**不属于**受信任声明，不要求 `unsafe`。
- **TR4（审查范围与 `private` 字段绑定，2026-11-15 裁决，[演算 §11](loan-kernel-calculus.md)）**：受信任不是单个函数的性质。
  1. 含受信任签名的类型，其借用字段与受 `unsafe` 维护的不变量字段必须是 `private`（否则外部代码可直接访问字段破坏已交出独占借用的前提，见演算 K15）。
  2. 人工审查范围是**能访问这些 `private` 字段的全部代码**，不只是标了 `unsafe` / `trusted` 的单个函数。按 [Guide 02](../guide/02-names-files-packages.md) 现行规则，成员的 `private` 在声明它的 classifier 内可见，因此审查范围是**该类型的全部成员**；同文件的顶层函数与扩展函数不在其内。
  3. 以后若有规则扩大 `private` 成员的可见范围，审查范围随之同步扩大。

## 8. 外部函数边界（FF0：之七 J22 五条合同与反例）

落实[之七](evolution-07-concurrency-async-io-ffi.md) §4.2 J22 与 §4.3 FF0，列出 C ABI 边界的五条硬合同及每条的说明性违反反例：

| 编号 | 边界合同（J22） | 违反反例（违反它会怎样） |
|---|---|---|
| FFI1 | **外部调用一律是 `unsafe` 操作** | C 函数签名与实际链接符号参数个数/ABI 不一致（如声明为 `Int` 实为指针），安全代码若直接调用将在栈帧破坏或非法指针解引用处触发 UB3 / UB10 |
| FFI2 | **借用实参以指针传入，仅在本次调用期间有效**；被调方若要留存，必须在 Koven 一侧显式使用 `RawPtr` 并履行 AL2 存活义务 | C 函数把 Koven 传入的 `borrow` 缓冲区指针存进全局静态变量，调用返回后 Koven 释放该缓冲区，C 侧后续异步回调写入触发 UB2（释放后使用） |
| FFI3 | **回调只接受无捕获的、以 C ABI 导出的函数**，上下文经显式用户数据指针传递 | 把捕获了局部借用的 Koven 闭包直接强转为 C 函数指针传入 `qsort` 等 C 接口，因 ABI 不含环境指针且逃逸出词法作用域，触发 UB2 / UB3 |
| FFI4 | **`String` 与 C 字符串（NUL 结尾）之间只有显式转换**，不做隐式零拷贝假定 | 直接把 Koven `String` 的底层 UTF-8 字节指针当作 `const char*` 传给 `strlen`/`printf`，因 Koven `String` 不保证末尾带 NUL 且内部可能含 `\0`，导致越界读（UB10）或截断 |
| FFI5 | **abort 不展开，跨越 C 帧时直接终止进程**（同 FS7） | Koven 传给 C 库的回调函数中触发 `error()` 或越界 abort 时试图做栈展开穿过 C 栈帧，会跳过 C 侧清理并破坏 C ABI 栈展开合同；按 FFI5 须在边界处直接终止进程 |

## 9. 验证与检测矩阵

定稿与迁入标志（严格对齐[之四](evolution-04-route-capability-unsafe-suspend.md) U0 与 2026-11-27 `#koven-design` OD5 共识）：本合同文本继续留在 `docs/proposals/` 评审，**不靠搬目录降低门槛**；在定稿迁入 `docs/compiler-specs/` 并启动 U1 之前，须同时满足两条硬门槛：（1）路线 L 的参考检查器能把 AL1、AL2 表述为对其模型的附加前提；（2）每条运行时可触发的 UB 规则（`UB1–UB6`、`UB9`、`UB10`、`UB11`）至少配备一个可执行的违反示例，并登记实际捕获器与实测捕获结果（其中 UB6 迁入门槛为实际跑通 TSan 数据竞争捕获；Loom / GenMC 级弱内存模型检查单独分行登记为迁入后的 U1 验收欠项，不挡 U0 迁入，也绝不与 TSan 互相替代）；（3）纯编译期/类型合同条款（`UB7`、`UB8`）及下表标注的外部不可见边界归入试金石反例矩阵与 TR4 人工审查范围，不放宽运行时条款的捕获门槛。

| 条款 | 违反编号 | 自动化检测手段 | 迁入前实测登记状态（用例 / 捕获器 / 结果） | 未覆盖边界（人工审查） |
|---|---|---|---|---|
| 借用、来历与配对释放 | UB1、UB2、UB10、UB11 | ASan（堆/栈越界、释放后使用、非法/重复释放与布局不匹配）、参考解释器（[之十](evolution-10-coverage-gaps.md) W13）带借用栈/来历与分配表追踪（类似 Miri/Tree Borrows） | 待补（U0 迁入硬门槛） | 原生发布构建中的静态优化假设违背 |
| 有效性、初始化与析构 | UB3、UB4、UB5 | UBSan、MSan / 参考解释器逐字节初始化位图与析构计数校验；FS8 在每个 FS1 操作处注入失败 | 待补（U0 迁入硬门槛） | 外部 C 库内部构造的非法位模式 |
| 并发内存模型（真实数据竞争） | UB6（数据竞争） | TSan（运行时数据竞争检测） | 待补（U0 迁入硬门槛，须实际跑通 TSan 捕获） | — |
| 并发内存模型（弱内存交错） | UB6（弱内存重排） | 内存模型级并发模型检查（Loom / GenMC 风格，建模普通内存位置、原子操作与 happens-before；注：[失败与清理模型](failure-cleanup-model.md)仅建模任务失败、析构与在途 IO，不表达数据竞争） | 待补 / **U1 验收欠项**（不挡 U0 迁入，亦不得与 TSan 互代） | 弱内存序（`Relaxed`/`Acquire`/`Release`）在特定硬件架构上的罕见重排 |
| 受信任合同与能力 | UB7、UB8 | 试金石程序 + 反例矩阵（之五）、参考检查器附加前提检验、TR4 全类型成员审查 | 静态/原型范围（非运行时 UB 门槛） | `trusted` 签名背后任意算法不变量 |
| 外部函数边界 | UB9（FFI1–FFI5） | C 头文件签名比对（FF3 绑定生成器）、ASan + FFI 边界回调 abort 进程终止测试 | 待补（U0 迁入硬门槛） | 第三方 C 库内部隐式留存指针 |

## 10. 开放问题

- FS1 把“任何未列入清单的函数调用”都算作可能失败，是否过于保守；若日后确有强需求，可单独立案增加编译器检查的 `noabort` 标注，当前按 T3 不提前引入。
- 合同定稿迁入 Compiler Contracts 时，是否同步派生一份面向标准库作者的一页速查清单。
