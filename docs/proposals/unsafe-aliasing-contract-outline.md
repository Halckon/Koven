# unsafe 合同提纲（路线 U 的 U0）

> **性质**：非规范候选设计（提纲） · **状态**：未启用 · **读取时机**：仅在起草 unsafe 代码须遵守的合同、裁决内存模型或失败安全条款时 · **唯一真源**：本页维护 U0 合同的章节结构、失败安全条款草案与内存模型取向；U0 在路线中的位置见[演进总纲之四](evolution-04-route-capability-unsafe-suspend.md)，`unsafe` / `extern` / `RawPtr` 的表面草图见 [unsafe 与 FFI 边界](unsafe-and-ffi-boundary.md)，现行语义以 [Guide v0.47](../guide/README.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。现行 Koven 没有用户可写的 `unsafe`。
这是一份提纲：§4（失败安全）与 §5（内存模型）按 2026-11-11 的要求先写成条款草案，其余各节只列出要回答的问题。
合同定稿后的归属是 Compiler Contracts，不是 Guide。

## 1. 合同回答什么

`unsafe` 代码能做编译器不检查的事。合同规定两个方向的责任：

- **unsafe 代码必须保证什么**，使安全代码所依赖的不变量继续成立。
- **安全代码与编译器可以假设什么**，据此做检查与优化。

合同之外的行为都有定义；合同之内列出的违反是未定义行为（§6）。合同要足够短，使一个标准库作者能逐条对照自己的代码。

两类不变量须区分（术语待定稿）：

| 名称 | 含义 | 何时必须成立 |
|---|---|---|
| 有效性不变量 | 一个值作为其类型存在所必需的条件：已初始化、位模式合法、指针非悬垂 | 任何时刻，包括 unsafe 代码内部 |
| 安全不变量 | 类型对安全代码承诺的条件：例如“长度不超过容量”“内容是合法 UTF-8” | 值交还给安全代码时，以及任何可能运行安全代码或析构的时刻（见 §4） |

## 3. 别名条款（沿用之四的草案）

1. 经裸指针读写某 place，不得与该 place 上存活的 loan 冲突（按 Guide 10 的矩阵）。
2. 裸指针的使用不得晚于其所指存储的 owner 被析构或移动。
3. 交还给安全代码的每个值，必须满足其类型的全部不变量（已初始化、能力判定成立、析构义务恰好一份）。
4. 声明了 `from` 的 unsafe 函数，其结果实际依赖的存储必须被所声明来源的 loan 覆盖。
5. 受信任的能力声明必须在所有调用序列下成立。

待补：裸指针的来历规则（由哪个 place 得来的指针可以访问哪段存储）；内部可变标记类型内部的例外如何表述。

## 4. 失败安全条款（草案）

**背景。** v1 中任何 abort 都终止整个进程，所以 unsafe 代码在 abort 之后是什么状态无人能观察。
[之十一](evolution-11-failure-interfaces-units.md) J48 把“线程是失败边界”列为目标方向：线程出错时终止并执行其栈上的析构。
一旦如此，unsafe 代码在失败发生的那一刻留下的状态，就会被随后运行的析构看到。
这一条款现在写入，是因为它无法事后追加——追加等于宣布此前写的全部 unsafe 代码可能不合格。

**FS1 可能失败的操作。** 下列操作可能不返回，unsafe 代码必须按“可能不返回”对待：

- 带检查的整数运算、带检查的转换、下标访问、`!!`、`error()`；
- 内存分配；
- 对任何函数的调用，除非该函数在本合同中被列为“不失败”（见 FS4）；
- 类型参数上的任何操作：调用其方法、析构它的值、复制或克隆它；
- 调用闭包；
- 任何值的析构，只要它的类型有用户定义的 `deinit` 或含有这样的字段。

**FS2 义务。** 在每一个可能失败的操作开始执行的时刻，下面两条必须成立：

1. 当前线程上将被析构的每一个值——局部变量、已构造的临时值、被修改的容器本身——处于其析构可以安全运行的状态。
2. 其他线程经共享类型能看到的状态，满足该类型的安全不变量，或者已被标记为“持有者异常终止”。

**FS3 允许泄漏，不允许重复析构或读未初始化。** 失败路径上，析构**不承担安全义务**的值可以不被析构（泄漏）；
析构承担安全义务的值——等待借用型子任务的作用域、结束访问授权的 guard——必须被析构，`unsafe` 代码不得使它们的义务消失（2026-11-14 收窄，评审 R3）；
不可以被析构两次，析构也不可以读到未初始化的存储。因此常用写法是：在进入不变量被暂时打破的区间之前，
先把容器的可见长度调低，使失败时多出来的元素只是泄漏。

与 2026-11-14 讨论的关系（[IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md)）：把仍可能被外部访问的存储保留下来不释放，是合乎那组原则的兜底，FS3 的“允许泄漏”与之一致。
反方向不成立：泄漏不能使“等待借用型子任务”“结束访问授权”这类安全义务消失，所以 FS3 已按评审 R3 收窄。
哪些类型的析构承担安全义务，由能力系统给出（之四 C1 的待拆分维度）。验证：失败注入用例须确认释放来源之前已完成必要的等待。

**FS4 不失败的操作。** 合同列出一份封闭清单，unsafe 代码可以在不变量被打破的区间内使用它们：
裸指针的读、写、偏移与类型转换；布局查询；显式的环绕算术；对 `Copyable` 且无 `deinit` 的值的按位复制；原子操作。
清单之外的操作一律按 FS1 处理。

**FS5 推荐结构。** 先做完所有可能失败的计算（算出新容量、调用用户的比较函数、分配新缓冲），再进入只含 FS4 操作的区间完成状态切换。
做不到时，用一个局部的守卫值，使其析构负责把状态恢复到满足 FS2。

**FS6 析构中的失败。** 析构过程中再次失败，进程终止。因此 `deinit` 中应当只做不失败的操作与释放资源。

**FS7 外部函数。** 失败不得穿过外部函数的帧。从 Koven 传给 C 的回调若发生失败，进程终止。

**FS8 在 v1 及之后的效力。** 即使实现仍以进程为失败单位，本条款也必须遵守。检测手段：参考解释器（[之十](evolution-10-coverage-gaps.md) §7.10）
在每个可能失败的操作处注入失败并运行析构，检查是否出现重复析构、读未初始化或不变量被破坏。

**一个例子**（候选伪代码，说明 FS2 与 FS3）：向列表中部插入元素时，先移动后半段，再写入新元素。

```text
错误的次序：
  1. 把后半段向后移动一格        （此刻下标 i 处有一个重复的元素）
  2. 调用 clone() 得到新元素     ← 可能失败；若失败，列表析构时下标 i 的元素被析构两次
  3. 写入下标 i

正确的次序：
  1. 调用 clone() 得到新元素     ← 可能失败；此时列表完好
  2. 把后半段向后移动一格        （只含不失败的操作）
  3. 写入下标 i；长度加一
```

## 5. 内存模型（取向）

**MM1 数据竞争的定义。** 两个线程访问同一内存位置，至少一个是写，至少一个不是原子操作，且二者之间没有先后次序约束。
安全代码中不可能出现数据竞争，这是 `Transferable` / `Shareable` 与借用规则共同保证的。unsafe 代码中出现即未定义行为。

**MM2 先后次序的来源。** 至少包括现行 [Guide 13](../guide/13-program-runtime-standard-library.md) 已规定的两条——
“`join` 返回时，线程中的全部写入对调用者可见；`send` 之前的写入，对收到该值的 `receive` 之后可见”——
再加线程创建（创建之前的写入对新线程可见）、锁的释放与获取、原子操作各自的规则。

**MM3 原子操作。** 采用 C/C++ 的原子次序模型，由 LLVM 直接实现；不自行设计。
标准库的原子类型上，不带次序参数的方法使用最强的次序；较弱的次序须显式传参。是否提供全部五种取值在 U1 决定，
倾向先提供三种（最强、获取/释放、无次序约束），其余等有用例再加。

**MM4 没有“良性竞争”。** 不为“只是读到旧值也无妨”的写法开例外；这类需求用原子类型表达。

**MM5 与优化的关系。** 编译器可以假设不存在数据竞争，据此重排与合并非原子访问。参数模式到后端别名属性的映射（[之八](evolution-08-compiler-ir-escape-simd-selfhost.md) §3.2）以本节与 §3 为依据。

**MM6 易失访问。** 设备寄存器一类的访问不属于本模型，由单独的易失读写原语承担（之十 §7.4），编译器不得省略或合并它们。

待定：未初始化内存的读取规则；指针与整数互相转换后的来历；跨线程的内存释放与正在进行的读取之间的规则（即内存回收问题，属于共享库的设计而非模型本身）。

## 6. 未定义行为清单（骨架）

逐条编号，定稿时每条附一个最小示例。清单之外的行为都有定义。

| 编号 | 行为 | 所属条款 |
|---|---|---|
| UB1 | 经裸指针的访问与存活的 loan 冲突 | §3 第 1 条 |
| UB2 | 使用指向已析构、已移出或已释放存储的指针 | §3 第 2 条 |
| UB3 | 把不满足有效性不变量的值当作该类型使用 | §1 |
| UB4 | 同一份析构义务被履行两次 | §3 第 3 条、FS3 |
| UB5 | 读未初始化的存储 | 待 §5 定稿 |
| UB6 | 数据竞争 | MM1 |
| UB7 | `from` 声明与实际依赖不符 | §3 第 4 条 |
| UB8 | 受信任的能力声明不成立而被依赖 | §3 第 5 条 |
| UB9 | 违反外部函数边界的五条合同 | §2 第 7 节 |
| UB10 | 访问超出分配范围；对齐不满足 | 待补 |

不列为未定义行为的（有定义，尽管多半是错误）：泄漏；死锁；整数环绕（仅当使用显式环绕算术时）；失败路径上违反 FS2 的**安全不变量**部分——
它使后续行为不可预期，但只要有效性不变量仍成立，就不是未定义行为。最后一点是否成立须在定稿时确认。

## 7. 受信任的声明

要回答的问题：

- unsafe 函数的签名（参数模式、`from`、返回类型的能力）对调用方构成完整合同；函数体内哪些检查被关闭、哪些仍然进行。
- 为类型手工声明 `Transferable` / `Shareable` 的语法与位置；声明者要证明什么。
- 库类型声明 `Equatable` / `Hashable`（[之十一](evolution-11-failure-interfaces-units.md) §2.4）是否属于受信任声明：它们写错不破坏内存安全，倾向不要求 `unsafe`。

## 8. 验证

- 每条条款配一个违反示例，以及能捕获它的手段：检测工具、参考解释器，或“目前无法自动检测”的明确标注。
- 定稿标志沿用之四：路线 L 的参考检查器能把 §3 第 1、2 条表述为对其模型的附加前提。
- FS 条款的验证见 FS8。

## 9. 开放问题

- FS1 把“任何函数调用”都算作可能失败，是否过于保守。可选的缓解是允许函数声明“不失败”并由编译器检查其函数体只含 FS4 操作与其他不失败函数；这是新的语言能力，倾向等有需求再议。
- FS2 第 2 条要求共享类型能表达“持有者异常终止”，这是对 C4 的设计要求，须在 C4 的提案里落实。
- §6 最后一段关于“违反安全不变量但不违反有效性不变量”的定性。
- 本合同是否需要一份面向使用者的简版（一页清单），正文留在 Compiler Contracts。

## 10. 来源与核对状态

别名条款取自之四。有效性与安全两类不变量的区分、“失败路径上允许泄漏不允许重复析构”的原则、先调低长度再操作的写法，
来自 Rust 社区关于 unsafe 代码与异常安全的通行表述，**本轮未联网核对出处**。C/C++ 原子次序模型由 LLVM 支持这一点同样来自已有知识。
Guide 13 的两条可见性规则已对照原文。
