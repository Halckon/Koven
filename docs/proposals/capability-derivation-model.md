# 结构能力推导的原型（内核基底 KB4）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；原型已实现并通过自身的用例（2026-11-15），不构成正确性证明 · **读取时机**：设计或评审[演进总纲之四](evolution-04-route-capability-unsafe-suspend.md) 的 C0（能力引擎）、C1（析构策略）、C3（`Shareable`）时；裁决类型参数的默认上界时 · **唯一真源**：本页维护原型的模型、用例与发现；能力的设计文字以之四为准，现行 `Copyable` 以 [Guide 11](../guide/11-copyability-layout-construction.md)、现行 `Transferable` 与资源分类以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

## 1. 目的

[借用内核演算](loan-kernel-calculus.md)检验的是 KB2、KB3。之一列出的内核基底里，KB4“结构能力推导”被其余各项依赖：析构规划要问“析构是否可观察”，借用要问“是否可逃逸”，并发要问“是否可转移、可共享”。
这个原型检验之四 C0 的主张——能力推导可以是一个机制，新增能力只是往表里加一行——并借它检验 C1 的析构性质拆分（评审 R3）与 `Arc` 的条件（评审 R5）。

原型在 `scripts/loan_kernel/capability.py`，用例在 `scripts/loan_kernel/capability_cases/`，测试在 `scripts/tests/test_capability.py`。

## 2. 模型

```text
能力     = 名称 + 叶子公理表（内建类型 -> 条件）+ 哪些声明种类可按字段推导 + 声明 deinit 后是否还能满足
条件     = 不满足 | 一组要求 { (类型参数, 能力), … }；空集即无条件满足
推导     = 对每个声明、每项能力求一个条件：各字段的条件之并；任一字段不满足则不满足
受信任声明 = 以 unsafe 实现的类型直接给出某项能力的条件，覆盖推导
```

- 条件按**声明**求一次，不按实例求。实例是否满足，把条件里的类型参数换成实参再求即可。所以自引用、互引用、实参不断增长的递归（`Grow<T>` 含 `Grow<List<T>>`）都收敛。
- 全部声明、全部能力一起从“无条件满足”出发，反复收紧到不动点。递归类型因此按“假设自己满足”处理：`class PlainCycle(next: PlainCycle?)` 可转移、可提前析构。
- 类型参数带默认上界；声明可以逐项放弃。类型实参不满足上界即类型不良构。

原型里的七项能力：`Copyable`、`Transferable`、`Shareable`、`Escapable`，以及析构的三项性质 `EarlyDrop`（可提前析构）、`Forgettable`（可遗忘）、`ImplicitDrop`（可隐式析构）。
后两项的反面分别是“析构承担安全义务，不得被遗忘”与“必须显式消费”。DSL 的写法（`opaque class`、`trusted … if …`、`unforgettable`、`consume`、`T: ?Cap`）都是原型记法，不是语法提案。

## 3. 用例

| 文件 | 内容 |
|---|---|
| C1 | 与 Guide 10、11 现行的 `Copyable`、`Transferable`、资源分类规则对照：`value class`、`enum`、普通 `class`、`T?`、`Box`、`List`、`Rc` |
| C2 | 自引用、互引用、参数增长的递归、多参数交换的递归、未使用的类型参数 |
| C3 | `RawCell`、库实现的 `Cell`、`Mutex`、原子类型、`Arc`；只读视图与独占视图的可转移性 |
| C4 | 析构的三项性质：守卫、作用域对象、必须消费的值、三者的复合；`Rc` 对载荷的要求；存在类型 |
| C5 | 类型参数默认可逃逸；可能携带来源的类型须声明为视图 |
| C6 | 把 `lang-frontend` 的资源分类测试表（`resource_deinit_type_facts`，20 行）逐行移植，对照现行实现 |

测试另有三条：把一条预期写反必须被报告；新增一项虚构能力只需一行（C0 的验收）；改 `Rc` 的一条叶子公理即可表达“`Weak` 出现后 `Rc` 的析构可被观察”。

## 4. 发现

1. **一个机制够用。** 七项能力都是“叶子表加对字段取合取”，结果与 Guide 的现行规则（抽查）和实现的 20 行分类表一致。实现对未实例化泛型给出的“未知”，在这里是一个条件（“当 `T` 可提前析构时”），信息更多。
2. **各项能力必须一起求解。** `borrow T` 可转移当且仅当 `T` 可共享；`Arc<T>` 可共享要求 `T` 既可共享又可转移。一项能力的条件会引用另一项，所以 C0 模型里“泛型实例的推导方式”须允许跨能力引用，引擎不能逐项独立运行。
3. **拆分之后不再需要“有序的格”。** C1 原先的三值格拆成三项布尔性质后，全部能力都是合取，C0 里“取最保守”这一种组合方式可以删去。
   三项并非完全独立：不可遗忘、必须显式消费都蕴含不可提前析构，“可提前析构”就是“没有任何析构义务”的那一角。可遗忘与可隐式析构之间互相独立，四种组合都有意义（守卫、作用域对象、必须消费的票据、线性值）。
4. **不可遗忘的类型一出现，类型参数就需要默认上界，这是一个待裁决的设计点。** 泛型代码会隐式析构 `T` 的值，也可能把它放进 `Rc`；若 `T` 可以是不可遗忘或必须消费的类型，这些代码就不成立。
   原型采用：不写任何东西的 `T` 默认要求可逃逸、可遗忘、可隐式析构；独占 owner（`Box`、`List`、`Array`、`T?`）放弃后两项，因为它们的析构性质随载荷；`Rc` 不放弃。存在类型打包时同样要求这三项。
   反过来的选择是默认不要求、由每个会遗忘或共享的 API 自己写上界，标注更多。v1 没有不可遗忘或必须消费的类型，日后增加默认上界对既有代码是兼容的，所以这一条不受 v1 冻结约束。
5. **受信任声明须能写条件，而不只是“满足”。** `Arc`、`Mutex` 的能力都依赖类型参数。之四 C3 把受信任声明列为唯一新增的语言面，它的形态至少是“能力 + 对类型参数的一组要求”。
6. **“可能携带来源的类型须声明为 `view class`”可以由推导直接检查**（之一 D12 把这个关键字定为声明式断言）：非视图声明的可逃逸条件若不成立，或依赖一个放弃了可逃逸上界的参数，即报错。
7. **诊断的解释路径在环上要小心。** 第一版解释 `MutualA` 为什么不可转移时，沿着环走回了它自己，而不是指出真正的原因（另一条字段里的 `Rc`）。已修正：环不算原因。实现现有的诊断是否有同类问题，没有核对。

## 5. 没有覆盖的

- 实现的判定结果是四值的（满足、不满足、未知、错误），原型只有前两种加条件；错误恢复没有建模。
- interface 上界（`T : SomeInterface`）、`Equatable` / `Hashable` 这类“可推导也可声明”的能力、闭包环境的能力。
- enum 的各个 case 没有分开；`value class` 的布局约束不在其内。
- 存在类型只用一个叶子代表，没有建模打包时的检查，也没有建模 interface 声明所带的能力上界。
- 只抽查了 Guide 的规则，没有逐条对照；对照实现的只有资源分类这一张表，`Copyable` 与 `Transferable` 的实现测试没有移植。
- 原型的规则是否正确，没有证明。
