# 借用内核演算（内核 MVP 第 1–3 步）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；规则为草案，原型已实现并通过 §5、§9–§27 的用例（2026-11-17），不构成健全性证明 · **读取时机**：实现或评审借用内核的参考检查器原型时；核对 [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R1 的验证用例时 · **唯一真源**：本页维护演算的语法、判定规则与用例清单；模型的来由见[演进总纲之二](evolution-02-route-loan-kernel.md) §2，现行借用规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权修改编译器。它描述的是目标模型（之二的 L1–L4），不是现行 v0.47 的调用期借用。

## 1. 目的与边界

评审的结论是先验证组合、再冻结内核。本页把之二的借用模型写成一个可以执行的最小演算，用来回答一个问题：
**“两种来源合同加一棵 loan 派生树”能否同时接受该接受的程序、拒绝该拒绝的程序。**

- 范围：评审 §5 的前两组验证——切片、自有字段视图、只读 guard；返回重借、`splitAt`、可变迭代器。
- 方法：一个独立的参考检查器，输入演算程序，输出接受或带位置的拒绝。它基于用例，不是健全性证明。
- 不在本步：泛型与迭代接口（第 2 步）、存在类型（第 3 步）、失败出口与清理义务（第 4 步）、闭包、可空类型、两阶段借用、线程、数值推理、`deinit` 函数体的内容。
- 某个用例必须靠“这个内建类型例外”才能通过时，结论是回到设计，不是给原型加特判。

## 2. 语法

条件一律写作 `*`，表示检查器不对取值做任何推理，两个分支都要检查。

```text
程序    P ::= D* F*
声明    D ::= class C(f: τ, …) [deinit]                 owned 类；deinit 只是一个标记
            | view class V(k f: τ, …)                   k ::= borrow | inout | （无，表示 owned 字段）
函数    F ::= fun g(m x: τ, …): ρ [from o, …] [trusted] { s* return e }
模式    m ::= own | borrow | inout
类型    τ ::= Int | C | V
结果    ρ ::= τ | borrow τ | inout τ | Unit
来源    o ::= x          结果依赖持有者 x 本身            （DependsOn）
            | x.f        结果沿用 x 的借用字段 f 的来源    （Forwards）
语句    s ::= val x = e | p = e | use(p) | g(a, …) | { s* }
            | if (*) { s* } else { s* } | while (*) { s* }
表达式  e ::= n | p | move p | &p | &mut p | C(e, …) | V(e, …) | g(a, …)
place   p ::= x | p.f
```

`use(p)` 是一次读取，只用于标出“这里还在用”。结果为借用的函数，`return e` 按“交出一个借用”求值：返回一个借用值即对它重借。`trusted` 的函数不检查函数体，只信任签名，对应 `unsafe` 实现的库函数。

## 3. 状态

检查器在每个程序点维护：

```text
Loan    = { id, place, kind: Shared | Exclusive, parent: Loan?, site }
Init(x) = Available | Moved | MaybeMoved             按字段细分到 place
Origins(h) = 持有者 h 持有的 Loan 集合                 h 是借用局部、视图实例（按借用字段细分）或调用的结果
Live(h) = h 在该点之后还会被使用                        后向分析
```

- 一个 loan 可以被多个持有者共同持有；只要有一个持有者存活，它就存活。
- 函数体内，每个借用参数与每个视图参数的每个借用字段，各带一个符号 loan，代表调用方那边的来源。

## 4. 规则

| # | 规则 |
|---|---|
| K1 冲突 | 对 place `q` 做种类为 `a` 的访问（读、写、移动、析构）时，若存在存活的 loan `l`，`q` 与 `l.place` 重叠，且 `a` 与 `l.kind` 不相容，则拒绝。相容矩阵沿用 Guide 10。经持有 `l` 的持有者所做的访问不算冲突，除非 K4 |
| K2 建立 | `&p` 在 `p` 上建立 Shared loan，`&mut p` 建立 Exclusive loan。`p` 若是经某个持有者到达的，新 loan 的 `parent` 是那个持有者据以访问的 loan（重借） |
| K3 存活 | loan 存活当且仅当它的某个持有者存活。持有者从定义起存活到最后一次使用，不到作用域结束。**实现时补充**：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活（见 §8 第 1 条） |
| K4 暂停 | 持有者 `h` 持有的 loan `l` 有存活的子 loan `c` 时，经 `h` 对与 `c.place` 重叠的 place 的访问，按 `c.kind` 判冲突 |
| K5 调用 | 对每个实参按参数模式建立 loan：`borrow` 建 Shared，`inout` 建 Exclusive，`own` 是移动。结果的 Origins 由被调方的合同决定：`from x` 则在实参这个 place 上建立一个子 loan 交给结果（结果为 `inout` 时是 Exclusive，否则 Shared）；`from x.f` 则结果取得实参视图的字段 `f` 当前持有的 loan。没有流入结果的实参 loan 在调用返回时结束 |
| K6 合同 | 函数体的返回值持有的每个 loan 必须被签名声明覆盖：落在参数 `x` 自身存储上的，或由借用 `x` 派生的，要求声明 `from x`；属于 `x.f` 的符号 loan 的，要求声明 `from x.f` 或 `from x`（后者更保守，也成立）；落在局部变量上的一律拒绝。初稿末句“结果为 `inout` 且来源是独占视图时只允许 `from x`”已撤销，见 §8 第 2 条与 §9 |
| K7 构造 | `V(e, …)` 的实例在每个 `borrow` 字段上持有实参处建立的 Shared loan，在每个 `inout` 字段上持有 Exclusive loan；实参本身是持有者时，取得它的 Origins |
| K8 移动与初始化 | `move p` 之后 `p` 为 Moved；使用 Moved 或 MaybeMoved 的 place 拒绝。含 `inout` 字段的视图与 owned 类不可隐式复制；只读视图可复制，副本持有相同的 loan |
| K9 析构 | 作用域结束时，仍 Available 的 owner 按声明逆序析构；析构是对该 owner 的一次“析构”访问，按 K1 判冲突。带 `deinit` 标记的类不提前析构 |
| K10 合流 | 分支与循环的合流处：Origins 取并集；Init 取交（一条路径上 Moved 即为 MaybeMoved）；循环迭代到不动点 |
| K11 多结果 | 一次调用产生的子 loan 只有一个；结果若是含多个持有者的值（例如返回两个视图），它们共同持有这一个 loan。它们之间是否不相交不由检查器判断，只对 `trusted` 的函数成立 |

规则与之二的对应：K2、K4、K5 是 R4.4 的改写；K5、K6 是 R3.4 的两种来源写法；K6 末句是 R4.5；K11 是之二“不相交证明不由内核承担”。

## 6. 已知这一步答不了的

- **可同时保留多个独占元素的迭代器**。E1 只覆盖出借式。非出借式需要“独占视图把来源分给多个结果”，K6 末句禁止它，只能靠 `trusted` 签名；它如何进入迭代接口属于第 2 步。
- **转发的可见性**。类型之外的函数写 `from s.source` 时字段名是否总是可见（之二 §6 的建议），演算里没有可见性，答不了。
- **两阶段借用**。`list.push(list.size)` 一类写法现行规则靠 Reserved 状态接受，本步不建模；所有 `inout` 实参一律立即 Active，因此原型会比现行规则多拒绝这类程序。（§22.2 已补。）
- 规则是草案。实现过程中发现规则自相矛盾或某个用例两头都说不通，是这一步最有价值的产出，须记录在本页并回到之二修订。

## 8. 原型得到的发现

写原型的过程中，规则在五处与初稿不同或暴露了问题。前四条需要回到之二确认。

1. **K3 少了一条。** “依赖持有者本身”的结果持有的是视图变量存储上的 loan。初稿只说“持有者存活到最后一次使用”，于是视图在最后一次使用后就算死了，它持有的底层来源随之失效，
   而那个结果可能正指向底层数据（用例 A4：声明 `from this`、实际返回底层元素，这是 K6 允许的保守声明）。补充的规则是：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活。没有它，A4 的第二个函数会被错误地接受。
2. **“独占视图不提供转发”不需要单列为规则。** 越过 `inout` 字段时累加所凭借的 loan，函数体返回的借用就必然带着视图本身这个来源，K6 自然要求 `from this`（用例 G1 的 `leak`）。
   第 2 步进一步发现这条特例必须撤销：受信任的签名需要它所禁止的写法（§9.3 第 5 条）。
3. **父 loan 不随子 loan 延续，比 Rust 宽。** 父持有者死后，子借用只保护它自己所指的那部分存储；同一对象上不相交的字段可以被再次访问（用例 G2 的最后一个函数）。
   Rust 在同样的程序上会拒绝，因为重借使整个父借用保持存活。原型的做法在“字段不相交”成立的前提下是健全的，但这是一个与 Rust 不同的选择，应当明确裁决，而不是由实现默认带入。
4. **按值接收的视图参数上，`from s` 没有意义。** 参数在返回时就死了，“依赖持有者本身”无从谈起；原型把它判为签名错误，只允许 `from s.f`。这正是之二 §6 记下的“转发全部来源”的拼写问题，原型没有解决它。
5. **被覆盖之前不再使用的旧借用不算存活**（F5 接受、F4 拒绝）。这是 K3 的直接后果，初稿的用例清单没有覆盖，我最初写的预期是错的。

原型的近似之处，它们使原型偏保守，不影响上述结论：

- 一条语句之内不区分先后：语句用到的变量在整条语句期间都算存活。
- loan 以建立它的语法位置为身份，循环里同一位置的 loan 合并为一个。
- 不建模两阶段借用；`inout` 实参一律立即生效。（§22.2 已补接收者位置。）
- 一处冲突之后的连带报告没有抑制；用例都写成只触发一处。

仍然没有回答的：这些规则是否健全。原型只说明规则在 29 个用例上给出了预期的结果。

## 9. 第 2 步：泛型、抽象签名与流向

对应评审 §5 的第三组验证（迭代、高阶借用函数、局部的视图容器）与 R6 要求的四种迭代。原型已实现，用例 H1–H6 通过。

### 9.1 增加的语法与规则

```text
函数    F ::= fun [<T, …>] g(m x: τ, …): ρ [from o, …] [flows o into x, …] [trusted] { … }
签名    S ::= sig [<T, …>] N(m x: τ, …): ρ [from o, …] [flows o into x, …]
类型    τ ::= … | T（类型参数）| fn N（合同为签名 N 的函数类型）
来源    o ::= x | x.f | x.origins    x.origins 表示转发 x 携带的全部来源（§12 起改为这个占位，并允许多级路径）
```

| # | 规则 |
|---|---|
| K12 细化 | 把函数 `g` 当作 `fn N` 类型的值使用时，`g` 声明的每个来源与流向都须被 `N` 的声明覆盖。覆盖关系：`x` 覆盖 `x.origins`，`x.origins` 覆盖 `x.f` |
| K13 不透明值 | 类型参数的值携带一组未知的来源，不可隐式复制。按值参数上 `from x` 等同于 `from x.origins`，因为按值参数在返回时已不存在，没有“本身”可依赖 |
| K14 流向 | `flows o into x`：调用之后，`o` 所指的来源由实参 `x` 背后的持有者持有。函数体让某个来源流进了 `inout` 参数而签名没有声明相应的流向，按 K6 拒绝 |

接口方法与函数类型在原型里是同一个机制：一个抽象签名，加上 K12。原型没有接口声明，迭代器的 `next` 以函数类型的参数传入（字典传递）。

| H6 | 高阶借用函数：函数类型的合同 `from r`；实参函数的来源是另一个参数；函数体经函数参数返回未声明的来源 | 接受；拒绝（K12）；拒绝（K6） |

### 9.3 发现

1. **四种迭代对应四种合同，不能归到一个接口。** 按值迭代没有来源；借用外部存储的是 `from it.字段`；多个独占元素并存的是受信任签名上的 `from it.字段`；出借式是 `from it`。
   泛型算法能依据的合同只有两种形状：
   - 出借式合同 `from it`：四种迭代器都满足它，但算法一次只能持有一个元素。逐个处理的算法（遍历、折叠、计数、存在性判断）按它写一次，对全部迭代器可用；`for` 应绑定这一种。
   - 转发式合同 `from it.origins`：算法可以同时持有、返回、收集元素（排序、收集、带前瞻的配对、返回元素的最值）。出借式迭代器不满足它（H4 的最后一个函数）。

   所以标准库需要两个迭代接口，或一个接口加一个区分二者的标记；这回答了评审 R6 “哪些算法可以统一、哪些不能”。之十一 §2.3 已据此拆为 `Iterator` 与 `LendingIterator`（暂名）。
2. **“转发全部来源”的写法是必需的。** 泛型与接口的语境里没有字段名可写，之二 §6 建议的“借用字段名在 `from` 中总是可见”不够用。原型用 `x.origins` 占位，正式拼写待定。按值参数上直接写 `from x` 即可（K13），这同时解决了 §8 第 4 条。
3. **来源合同需要第三种子句：流向。** 没有 `flows`，把视图放进一个已有的容器、收集借用元素都无法检查（H5）。之二把“origin 流入已有持有者”列在 L5 的待定项里；它是迭代与容器的必经能力，不是可选项。结构化并发的 `scope.launch(f)` 需要的是同一个子句。
4. **函数类型必须带来源合同**，并且合同之间有细化关系（H6）。这与接口方法是同一个机制，不需要两套规则。
5. **撤销“独占视图不提供转发”。** 多个独占元素并存的迭代器恰恰需要这种签名，只能由受信任的函数声明；非受信任的函数体写不出来（越过独占字段时累加来源，K6 拒绝）。所以它不是一条规则，而是“只有受信任代码才写得出”的后果。
6. **受信任签名的健全性依赖字段私有。** 探测程序：取出一个独占元素后，直接经迭代器的字段写同一块存储，原型接受。演算没有可见性；真实语言里必须靠“视图的独占字段对类型之外不可访问”来排除它。这是对之四 U0 合同的一条要求。

### 9.4 这一步没有回答的

- **可空元素的歧义**（评审 R6 的前半）：`next()` 返回值的类型怎样区分“元素是 null”与“迭代结束”，是类型表示的问题，不涉及来源，演算检验不了。之十一已改为返回不折叠的和类型。
- **类型参数是否可逃逸**。原型把每个类型参数都当作可能携带来源；“默认带可逃逸上界、显式放弃”这一层没有建模，所以答不了“现有泛型代码是否不受影响”。（§13 已补。）
- 没有检查类型实参与形参是否匹配；没有闭包捕获；没有真正的接口声明与见证。
- 规则是否健全，仍然没有证明。

第 1、2 步的发现已于 2026-11-14 并回[之二](evolution-02-route-loan-kernel.md) §2 与之十一 §2.3。

## 10. 第 3 步：存在类型的载荷访问与槽位访问

对应评审 R2 与[之三](evolution-03-route-existential.md) §2.4。原型已实现，用例 I1–I5 通过。这一步的发现已于 2026-11-14 并回之三 §2.4 与 §5。

记法说明：`any I`、`pack I(e)`、`*x = e` 与调用处的 `&mut` 都是演算自己的记法，不是 Koven 语法，也不是拼写提案。
Koven 里声明侧的 `inout x: T` 与泛型 `fun <T>` 是现行语法（Guide 03、08），调用处的独占标注写作 `&x`；存在类型是 v2 候选，之三的候选写法是直接以 interface 名作类型（`inout s: Shape`），隐式打包。
演算把它写成 `any I` 只为在规则里区分“具体类型”与“存在类型”。

### 10.1 增加的语法与规则

```text
声明    D ::= … | interface I | class C(…) is I, …
类型    τ ::= … | any I（接口 I 的存在类型）
表达式  e ::= … | pack I(e)（把实现 I 的具体类型的值打包为 any I）
语句    s ::= … | *x = e（经独占借用 x 整体替换它所指的值）
```

每个借用值多带一个标记：它是**槽位访问**（所指的存储恰好按它的类型存放）还是**载荷访问**（只知道所指实现了接口 `I`）。

| # | 规则 |
|---|---|
| X0 标记的来由 | 以下三处得到载荷访问：按 `borrow` / `inout` 接收 `any I` 的参数；返回类型为 `borrow` / `inout any I` 的调用结果；视图里类型为 `any I` 的借用字段，以及经它重借出来的借用。对拥有 `any I` 的变量或拥有字段取借用，得到槽位访问。移动、重借与分支合流保留标记 |
| X1 整体替换 | `*x = e` 要求 `x` 是槽位访问，且 `e` 的类型恰为所指类型。给拥有 `any I` 的变量或字段赋值，要求右侧是 `any I`（先 `pack`） |
| X2 槽位不变 | 形参写作 `inout any I` 时，实参所指可以是实现 `I` 的具体类型或 `any I`，被调用方得到载荷访问。形参是具体类型或类型参数 `T` 时，实参须是槽位访问，且 `T` 在一次调用里的各处实例一致 |

X2 的后半是对 `inout` 位置的不变性：`inout T` 既读出 `T` 也写入 `T`，所以所指类型必须恰为 `T`，不能是它的子类型或实现者。

### 10.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| I1 | 按 `inout any Shape` 接收后调用方法；以具体类型的位置或拥有存在类型的变量作实参；在函数体里 `*s = v`；把没有实现接口的类型交进去或打包 | 前两者接受；拒绝（X1）；拒绝（TYPE） |
| I2 | 评审 R2 的反例：`overwrite<T>(inout dst: T, own value: T)`，以 `Circle` 的位置和一个 `any Shape` 的值调用；在接收 `inout any Shape` 的函数里把它转交给 `overwrite`；先移动改名再转交；经 `inout Circle` 写入 `Square` | 全部拒绝（X2、X2、X2、X1） |
| I3 | 拥有存在类型的变量与字段：直接替换；取借用后 `*r = …`；交给 `overwrite`，此时 `T = any Shape`。具体类型的槽位交给 `overwrite`。把未打包的具体值赋给存在类型的变量；经返回 `inout any Shape` 的方法取得访问后整体替换 | 前四者接受；拒绝（X1）；拒绝（X1） |
| I4 | 载荷访问上的借用规则：访问存活时写来源；返回未声明的来源；同一个变量两次按独占交出 | 拒绝（K1）；拒绝（K6）；拒绝（K1） |
| I5 | 视图里存放 `inout any Shape`：经字段调用方法；经字段交给 `overwrite`。把载荷访问交给不做替换的泛型函数 `same<T>(inout x: T): inout T`；经它的结果整体替换；把两个载荷访问交给 `swap<T>`；把两个存在类型槽位交给 `swap<T>` | 接受；拒绝（X2）；接受（§11 的 X4 之后）；拒绝（X1）；拒绝（X2）；接受 |

测试里增加了一条变异检验：去掉 X2 之后 I2 不再被拒绝。

### 10.3 发现

1. **评审 R2 的反例被两条规则排除，且两条都需要。** 直接调用靠“`T` 的实例须一致”（`Circle` 与 `any Shape` 不是同一类型）；经 `inout any Shape` 参数转交靠载荷标记。只做前一条时，转交这条路仍然通，因为在被调用方看来两边都是 `any Shape`。
2. **载荷与槽位是借用值上的一个标记，不是两种类型，也不需要两种拼写。** 之三 §2.4 的结论成立：`inout any I` 的参数总是载荷访问。标记由 X0 的三个来由决定，调用方不需要写任何东西。
3. **标记必须覆盖存进视图的借用。** 第一版原型只在参数上打标记，探测程序把 `&mut circle` 存进字段类型为 `inout any Shape` 的视图，再对该字段取借用交给 `overwrite`，原型接受了——这是一个真实的漏洞，已用 X0 的第三个来由补上（I5）。
   它说明“载荷访问”要跟着借用值走到每一处存放位置，包括之后的容器与闭包捕获；演算里只有视图字段这一种。
4. **“返回 `inout any I` 的总是载荷访问”有代价。** 类型自己的方法返回它内部一个真实存在类型槽位的独占借用时（I3 的 `slot`），调用方也不能经它整体替换，只能调用专门的替换方法或直接写字段。
   放开它需要在返回类型上区分两种访问，也就是一种新的拼写。建议先不加，等出现具体需求。
5. **载荷访问不能交给任何泛型 `inout T`，这是保守的。** `same<T>(inout x: T)` 不做替换，仍被拒绝（I5）。更要紧的是按 `inout T` 写的泛型算法（例如交换、就地排序的比较与移动）都不能直接用于一个 `inout any Shape`。
   精确的做法是“打开”存在类型：在调用处把 `T` 绑定为那个未知的具体类型。这样 `same` 可用；`overwrite` 仍被拒绝，因为拿不出一个类型恰为该未知类型的值。原型没有建模打开，这是之三需要回答的一个设计点。（§11 的 X4 已在原型里补上打开。）
6. **借用规则与这个标记正交。** I4 的三个拒绝与不涉及存在类型时完全相同，没有为存在类型改动 K1–K14 的任何一条。

### 10.4 这一步没有回答的

- 存在类型的打开（发现 5），以及泛型约束 `T : I`。原型的类型参数没有上界。
- 嵌套位置：`Box<any I>`、`List<any I>` 里的槽位，演算没有泛型类。按 X0 推断它们是槽位，但没有用例检验。
- 构造视图时没有核对借用字段的类型是否匹配；方法调用没有经过见证表，`any I` 上的方法在原型里是受信任的普通函数。
- 存在类型携带借用（`any I` 的载荷是一个视图）时来源怎样记录，没有建模。
- 大小、布局与析构：整体替换时旧载荷何时析构，属于之四，不在这一步。
- 规则是否健全，仍然没有证明。

## 11. 对前面发现的修补（2026-11-14）

第 2、3 步各留下一个“原型接受了不该接受的”或“拒绝了不该拒绝的”问题，这里在原型里补上。两处都是演算里的做法，是否进入语言设计仍待裁决。

```text
字段    … | private [borrow | inout] f: τ
函数    F ::= fun … [from …] [flows …] [in C] [trusted] { … }      in C：该函数是类型 C 的成员
```

| # | 规则 |
|---|---|
| K15 私有字段 | 经 `private` 字段的访问只允许出现在 `C` 的成员函数里 |
| X4 打开 | 载荷访问交给泛型的 `inout T` 时，`T` 绑定为这一处独有的未知具体类型。调用结果的类型若是 `T`，结果仍是载荷访问 |

X4 取代了 §10 里“载荷访问不能交给任何泛型 `inout T`”的保守做法。X2 的“`T` 的各处实例须一致”不变，它现在同时负责拒绝：`overwrite`（另一个实参的类型不是那个未知类型），以及把两个载荷访问交给 `swap<T>`（两处各自打开，得到两个不同的未知类型）。

| # | 程序要点 | 预期 |
|---|---|---|
| J1 | 迭代器的独占字段声明为 `private`：取出一个独占元素后在类型之外经字段写同一块存储；访问公开字段；只经成员函数取两个元素 | 拒绝（K15）；接受；接受 |
| I5（更新） | 见 §10.2 | |

发现：

1. **K15 关上了 §9.3 第 6 条的探测程序，但信任边界因此是整个类型的成员。** 成员函数可以访问私有字段；一个没有标受信任的成员函数经字段写存储，原型照样接受，而此前交出的独占元素可能正指着那里。
   所以“受信任”不是单个函数的性质：一个类型只要有受信任的成员，它的全部成员都在需要人工审查的范围内。这与 Rust 里 `unsafe` 的健全性以模块为界是同一个结论，U0 须按类型（或模块）而不是按函数划定审查范围。
2. **打开存在类型不需要新规则，只需要让类型参数能绑定到一个未知类型。** 拒绝 `overwrite` 与 `swap` 的仍是 X2。原型里打开是隐式的；它与之三“泛型实例以存在类型为实参单态化”并存时各走哪一条，没有建模。
3. 仍未修补的：返回 `inout` 存在类型的调用结果一律是载荷访问（§10.3 第 4 条），以及父 loan 不随子 loan 延续（§8，已决定暂时保持）。

## 12. 多级来源与嵌套视图（2026-11-15）

起因是一个问题：`x` 有借用字段 `a`、`b` 时，“转发全部来源”是否就是 `x.a` 加 `x.b`，多级嵌套时能否写多级，从而不需要单独的“全部”写法。

```text
来源    o ::= x | x.f₁.….fₙ | x.origins
```

| # | 规则 |
|---|---|
| K16 路径 | 视图按值含有另一个视图时，内层的借用字段记在 `外层字段.内层字段` 之下。来源写到任意一级：写到借用字段即只覆盖它；写到中间一级覆盖它之下的全部借用字段 |
| K16 覆盖 | 来源 `x.f.g` 被 `x`、`x.origins`、`x.f`、`x.f.g` 中任意一个声明覆盖 |

| # | 程序要点 | 预期 |
|---|---|---|
| K1 | 两级视图：`from x.inner.a` 返回该字段，之后写另外两个来源、写它自己的来源；`from x.inner` 返回 `inner.b`；按值的 `from x`；声明 `x.inner.a` 却返回 `inner.b`；声明 `x.c` 却返回 `inner.a`；按值含有独占视图的视图被隐式复制 | 前两处写接受，第三处拒绝（K1）；前缀与整体各拒绝相应的写（K1）；两处拒绝（K6）；拒绝（K8） |

发现：

1. **对具体类型，“全部来源”确实只是各级借用字段的并集，不需要单独的写法。** 写字段路径更精确（K1 里写无关的来源被接受），写前缀或参数名则是简写。
2. **仍然需要一个“全部”的写法，但只剩一处**：参数的类型是类型参数或接口，并且参数按 `borrow` / `inout` 传递。那里没有字段名，而 `from x` 已经表示“依赖 `x` 本身”。迭代接口的 `next` 就是这种签名，它由标准库作者写一次，普通用户的代码里基本不出现。
   按值参数不需要它（K13：`from x` 即全部）。占位拼写由 `x.*` 改为 `x.origins`。
3. **第一版原型对嵌套视图是不健全的。** 构造外层视图时丢掉了内层视图携带的来源：经外层返回内层的借用之后写它的来源，原型接受；声明一个分支却返回另一个分支，原型也接受。两处都已修正并由 K1 覆盖。
   这说明之前“41 个用例通过”没有覆盖嵌套；现在覆盖的仍然只有两级、只有按值嵌套。
4. 没有覆盖的：视图经借用字段指向另一个视图（借用的借用）时来源怎样分层；嵌套三级以上；嵌套视图上的流向子句。（§13 已补。）

## 13. 补上的覆盖（2026-11-15）

类型参数  <T>       默认可逃逸：只能实例化为不携带来源的类型

发现：

1. **“默认可逃逸、显式放弃”可以建模，并且现有泛型代码的写法不受影响。** 不带标记的 `<T>` 不需要任何 `from`，与今天一样；只有打算接受视图的泛型代码才写标记并声明来源。代价是泛型库要逐个决定是否放开：`List<T>` 不放开就装不了视图。
   第 2 步的迭代用例（H3–H5）的类型参数因此都改成了 `view`，这正是之二 L5 说的“迭代器所需的泛型能力”。
2. **借用的借用不需要新规则**，路径记法直接延伸。经共享外层只能得到内层的共享访问，与 Rust 的 `&&mut T` 一致。
3. **又发现并修掉两个漏洞。** 一是把借用值本身当作类型参数的值传入时，结果丢掉了来源（借用被当成了它所指的类型）；二是把一个新的内层视图写进局部视图的字段时，新来源没有被记录。两处都已修正并有用例。
   连同 §10、§12 的两次，原型至今发现的四个漏洞都出在“来源随值存进某个位置”时漏记。参考检查器的实现应当把“值携带的来源”做成值表示的一部分，而不是在各个存放点分别处理。
4. 仍未覆盖的：经借用把来源写进视图字段（要求把流向子句推广到具体类型的字段，K14 当时只拒绝；§18 已补）；递归的视图类型（原型遇到环就停止展开，没有用例）；闭包捕获；两阶段借用；健全性证明。

## 14. 借用与析构的配合（2026-11-15）

[析构义务的原型](drop-obligation-model.md)不含借用。这里在借用原型一侧补上二者的接口，检验已裁决的统一析构规则与“借用的结束点单独定义”（[析构时机对比](drop-timing-comparison.md) §8）能否并存。

| # | 规则 |
|---|---|
| K18 提前析构 | 打开该选项时，局部 owner 在某条语句之后满足三条即在那里析构：它不再被用到；没有存活的 loan 指向它；它的析构不可观察（没有 `deinit`，也不按值含有这样的字段） |

K18 的第二条就是“存活的 loan 使 owner 保持存活”：owner 的析构点由“它与从它借出的一切都不再使用”决定，而不是由它自己的最后一次使用决定。

检验的性质有两条，都在测试里：

1. **打开提前析构之后，全部用例（当时 47 个）被接受或拒绝的结果逐行不变。** 这些用例里一共发生了 107 次提前析构。也就是说，程序是否合法不依赖析构发生在哪里——这正是把“提前”定为许可而不是规定所需要的。
2. 用例 L1：被借用的 owner 留到借用的最后一次使用之后才析构；无关的 owner 更早析构；可观察的值不提前；分支两边各析构一次。

发现：

1. **两条裁决可以并存，而且接口只有一句话**：析构点 = 活性（含从它借出的 loan）加“是否可观察”。借用规则不需要知道析构策略，析构规划只需要向借用一侧问“还有没有存活的 loan 指向它”。
2. 这条性质依赖 K9 的写法：作用域结束处的析构与存活的 loan 冲突即拒绝。提前析构从不制造新的冲突，因为它只在没有存活 loan 时发生。
3. 没有做的：两个原型没有合并成一个，各有一份活性分析；“可观察”在这里按 `deinit` 标记判断，没有接上[能力推导原型](capability-derivation-model.md)（§19 已接上）；参数与视图不参与提前析构。

## 15. 内部可变（内核基底 KB6，2026-11-15）

对应[之四](evolution-04-route-capability-unsafe-suspend.md) C2。要检验的是：“共享借用即不可变”的例外怎样进入借用规则。用例 M1。

```text
声明    cell class C(…)      内部可变类型（演算记法；之四里是含 RawCell 的类型）
```

| # | 规则 |
|---|---|
| K19 内容 | 内部可变类型的字段不能在非受信任的函数里访问；读写都经受信任函数，以共享借用传入整个值 |
| K19 流向 | `flows o into x` 的目标可以是 `borrow` 参数，当且仅当它的类型是内部可变类型。经局部的共享借用值调用时，来源流入它所指的每个变量；所指在调用方时，记在相应的参数上并须由本函数的 `flows` 声明 |

| # | 程序要点 | 预期 |
|---|---|---|
| M1 | 两个共享借用交替调用受信任的改写函数；非受信任代码直接读字段；把视图经共享借用放进内部可变的槽，之后写它的来源（直接传 `&s`、经局部借用值传）；槽比来源活得久；转交函数声明或不声明流向、经局部副本转交；对普通类型声明经共享借用的流向 | 接受；拒绝（K19）；拒绝（K1）两次；拒绝（K9）；接受、拒绝（K6）两次；拒绝（SIG） |

发现：

1. **改写本身不需要动借用规则。** 经共享借用改写内容，是受信任函数签名背后的事；K1–K18 没有一条依赖“共享借用下内容不变”。这印证之四 R2.3：这个假设只存在于将来的代码生成优化里，所以标记必须在内核，但借用检查不为它改。
2. **需要改的只有一处：流向子句的目标。** 没有内部可变时，来源只能经独占借用流进已有的持有者；有了它，经共享借用也能流进去（把一个视图 `set` 进 `Cell`）。规则须把“目标是 `borrow` 参数”限定在内部可变类型上，否则任何共享借用都能改变别人持有的来源。
   来源一律记在**拥有该存储的变量**上，而不是记在借用值上，所以多个共享借用同时存在时仍然只有一份账。
3. **不可检查的义务归 U0。** 受信任函数若经共享借用交出指向内容的借用（`get` 返回内部引用），之后另一个共享借用的改写会使它失效，而借用规则看不到。之四 R2.4 要求 `Cell` 只提供整值的取放、不借出内部引用，这是库作者的义务，须写进 U0，原型检验不了。
4. 没有覆盖：带运行时借用标志的单元（`RefCell` 类）交出的守卫；内部可变与 `Shareable` 的配合在[能力推导原型](capability-derivation-model.md)里（`RawCell` 恒不可共享），两个原型没有接起来（§19 已接上）。

## 16. 闭包捕获（2026-11-15）

之一把闭包定为“匿名的、含借用字段的积类型加单方法见证”。若成立，闭包在内核里不需要任何专门的规则；若不成立，就多出一条基底。用例 N1 把闭包**手工展开**成它声称等价的形式来检验：环境是一个视图类（只读捕获是 `borrow` 字段，可写捕获是 `inout` 字段，按值捕获是普通类的字段），函数体是以环境为第一个参数的函数，高阶函数以 `view F` 的类型参数加一个函数类型的参数接收它。原型没有闭包语法。

| 情形 | 结果 | 由哪条规则得到 |
|---|---|---|
| 不逃逸的只读闭包，调用两次；之后写被捕获的变量 | 接受 | K3：闭包不再使用后 loan 结束 |
| 闭包仍存活时写被捕获的变量；只读 | 拒绝；接受 | K1 |
| 可写闭包：调用两次；存活期间读被捕获的变量 | 接受；拒绝 | K1（独占 loan） |
| 可写闭包不可复制；只读闭包可复制 | 拒绝；接受 | K8 |
| 一个只读捕获加一个可写捕获 | 各按自己的种类 | K11 |
| 返回捕获了局部变量的闭包；返回捕获了参数的闭包并声明 `from` | 拒绝；接受 | K6 |
| 闭包返回指向被捕获变量的借用 | 结果保护来源 | `from env.a`（K5、K16） |
| 按值捕获的闭包交给要求可逃逸的 `<F>`（例如启动线程）；借用捕获的闭包交给它 | 接受；拒绝 | K17 |

发现：

1. **这 13 种情形都不需要新规则，之一的说法在原型里成立。** “借用捕获的闭包不能逃逸”不是一条规则，而是 K6、K9、K17 的结果；“可写闭包不可复制、调用时独占”是 K8 与独占字段的结果。
2. **它依赖两项已有但尚未进入语言的能力**：类型参数可以放开可逃逸上界（K17 的 `view F`），以及函数类型带来源合同（§9 的 K12）。高阶函数要接收借用捕获的闭包，签名就得用到前者。
3. 留给糖的：每个被捕获变量用哪种方式捕获的推断；环境类型与见证的生成（KB5）。
4. 没有检验的：现行 [Guide 07](../guide/07-calls-lambdas-closures.md) 对 borrowed closure 与 mutating closure 的专门限制是否与这里推出的结果逐条一致（可能更严或更松）；递归闭包；捕获另一个闭包；闭包作为存在类型的载荷。

## 17. 帧挂起（内核基底 KB8，2026-11-15）

[之四](evolution-04-route-capability-unsafe-suspend.md) §4 给挂起定了三条前置约束（S0.1 帧地址稳定、S0.2 结构化是借用的前提、S0.3 挂起点状态守恒），[之七](evolution-07-concurrency-async-io-ffi.md) J18 规定默认不换线程。这一步检验它们放进借用内核之后是否自洽、各自需要多少新规则。以下写法都是演算记法，不是 Koven 语法。

### 17.1 增加的记法与规则

- `suspend fun`：可以包含挂起点的函数。`parallel suspend fun`：恢复时可能换线程的函数（J18 的显式并行入口）。
- 语句 `suspend`：一个挂起点。调用 `suspend` 函数也是调用方的一个挂起点，此时实参的 loan 仍由被调帧持有。
- `val t = start f(args)`：创建任务。实参已求值并存进任务的帧，函数体尚未执行；任务值持有全部实参带来的 loan，不可复制。
- `poll t`：让任务开始执行但不等它结束。`await t`：等它结束并消费它，是一个挂起点。
- `local class`：值绑定在创建它的线程上，不可转移（代表非原子共享计数一类）。

| 规则 | 内容 |
|---|---|
| S0 | 挂起点、对 `suspend` 函数的调用、`await` 只能出现在 `suspend` 函数里 |
| S1 | 仅用于对照：假设已开始执行的帧仍可移动时，帧内有指向本帧局部变量的存活 loan 即拒绝 |
| S2 | 状态守恒：挂起点不是一次访问，owner 可用性与 loan 集合原样跨过它。**它不产生任何检查** |
| S3 | 已开始执行的任务不可移动 |
| S4 | 已开始执行的任务在离开作用域前须被 `await`；任一分支上开始过即算开始过。未开始的任务可以直接丢弃 |
| S5 | 在 `parallel` 函数里，跨挂起点存活的每个值须可转移；共享借用可转移当且仅当所指的类型可共享（不含内部可变、不含 `local`）；没有上界的类型参数按不可转移处理 |

### 17.2 用例

| 用例 | 内容 |
|---|---|
| P1 | 借用跨挂起点后继续使用；跨挂起点期间写被借出的变量（K1）；借用在挂起前结束；把局部按 `inout` 交给会挂起的函数；借用参数跨挂起点；移动后挂起再使用（K8）；非 `suspend` 函数里挂起（S0） |
| P2 | 任务持有实参的 loan 直到被 `await`；两个只读任务并存；只读任务与可写任务冲突（K1）；未开始的任务可丢弃、可移动；已开始的不可移动（S3）、须等待（S4，含只在一个分支上开始、内层作用域）；重复 `await`（K8） |
| P3 | 默认函数里 `local` 值、指向内部可变值的共享借用都可以跨挂起点；`parallel` 函数里它们被拒绝（S5），拥有的普通值、指向普通值的共享借用被接受；只在挂起前使用的 `local` 值不受影响 |

另有两条测试：对 P1 打开“帧可移动”的假设，恰好多出三处拒绝；把 P3 的 `parallel` 去掉，全部拒绝消失。

### 17.3 发现

1. **S0.3 成立，而且不需要规则。** 挂起点对借用检查是空操作：已有的 K1、K3、K8 在挂起点前后照常工作，P1 的接受与拒绝全部由它们得到。之四说它是“要增加的唯一一条不变量”，在借用一侧它是不需要增加任何东西；析构义务一侧没有检验（见 17.4）。
2. **S0.1 的适用面比“帧内自引用”宽。** 打开帧可移动的假设后被拒绝的三处里，有一处没有任何借用变量：只是把局部变量按 `inout` 传给一个会挂起的函数（P1 `calleeFrameHoldsLoan`）。被调帧嵌在调用方的帧里并持有指向它的借用，这已经是自引用。所以放弃帧地址稳定的代价不是“不能写自引用”，而是“不能把局部按借用交给任何会挂起的函数”，S0.1 没有可行的替代。
3. **“已创建未启动”与“已启动”不能写成两个由函数连接的类型。** 已启动的任务不可移动，于是不能作为“启动”函数的返回值交出来。原型用的是变量上的流敏感状态（开始过即钉住）。另一种不加规则的表达是让“启动”按独占借用取得任务并返回一个持有该 loan 的句柄，由已有规则禁止移动；这种表达没有在原型里检验。
4. **S4 是一条“必须显式消费”的义务。** 已开始的任务既不能丢弃也不能移走，只能等待。这正是之四里暂时预留的那种类型。两个出路：把它作为内核里第一个必须消费的类型；或者不让任务值出现在用户代码里，只在受信任的结构化作用域库内部创建和等待，S3、S4 变成那段受信任代码的义务而不是语言规则。之七的结构化并发已经是后一种形态，这样 KB8 不迫使“必须显式消费”提前定案。**裁决（2026-11-15）：采用后者。** 任务值（进行中的调用及其帧）不出现在用户代码里；用户拿到的是可以等待的句柄，帧由结构化作用域库持有。
5. **S5 只在并行入口出现，默认情形没有任何限制**，与 J18 的预期一致。它检查的是“跨挂起点存活的值”，这组值由已有的活性分析直接给出，诊断可以指出是哪个挂起点（之七 §2.3 关心的问题）。
6. **泛型的并行函数需要能力上界。** 没有上界的类型参数只能按不可转移处理，所以并行入口的签名要写出 `Transferable` 上界；这依赖能力推导原型，两者尚未接起来，原型里的可转移判定只是 `local` 与内部可变两个标记的近似。（§19 已接上，并补了上界。）

### 17.4 这一步没有回答的

- 析构义务的守恒：挂起点两侧待执行的析构是否相同、取消时由谁执行，析构义务原型没有挂起点。（§21 已补。）
- 取消：J19 把取消当作值，`await` 的失败出口与[失败与清理的状态模型](failure-cleanup-model.md)的模型 A 没有接到这里。
- 动态数量的任务：把任务交给作用域持有（来源流入持有者，§15 的流向子句）与 S4 的配合。
- 帧大小无法静态确定的情形（递归、经存在类型的 `suspend` 调用）、`suspend` 闭包、生成器。
- 发现 3 的借用句柄表达；发现 6 的能力上界。

## 18. 经借用把来源写进视图（2026-11-15）

此前把携带来源的值写进视图，只支持两种情形：直接写局部视图的按值字段（K16 写入），以及流入类型参数的持有者（K14）。经借用写一个具体的视图一律拒绝。这一步放开它。用例 Q1。

### 18.1 增加的记法与规则

```text
流向    flows o into x | flows o into x.f₁.….fₙ      目标可以写到字段路径，覆盖关系与来源的路径相同
```

| # | 规则 |
|---|---|
| K20 一份账 | 值携带的来源只记在**拥有该存储的变量**上。经借用到达一个视图时，它各借用字段当前持有的来源从所指的变量上现查，不以建立借用时的副本为准。所指在调用方时，记在相应的参数名下 |
| K20 写入 | 经独占借用整体替换（`*x = e`）或改写按值字段（`x.f = e`）时，新值携带的来源记到所指的存储上。所指唯一时旧来源解除，否则并入 |
| K20 核对 | 函数返回时，借用参数名下每个字段路径多出来的来源，都须被一条目标覆盖该路径的 `flows` 声明覆盖；落在局部变量上的拒绝（K6）。合同细化（K12）对目标路径同样适用：`into x` 覆盖 `into x.f` |
| K20 调用 | 调用方按声明把来源**并入**目标路径之下的每个借用字段，不解除旧来源。目标可以是对变量的借用、对它按值字段的借用，或一个借用值 |

另外改正一处：因流向而在调用之后继续存在的实参 loan，种类跟随参数自己的模式。此前只要签名带 `flows` 就一律按独占计，于是把一个只读来源放进容器之后，连读它都被拒绝。

### 18.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| Q1 定义处 | 改写 `inout` 参数的内层视图：目标写到该路径、写到整个参数、写到另一个分支、不声明、只在一个分支上改写、写入局部变量的借用；整体替换同理；类型参数的槽位被整体替换；转交给另一个带流向的函数 | 前两者接受；其余拒绝（K6）；转交须自己声明 |
| Q1 调用处 | 持有者保护新来源，且新来源仍可读；持有者比来源活得久；旧来源在调用方不解除；经局部借用值写入后再经它读出；借用值可能指向两个视图之一；以按值字段的借用作目标；泛型的 `flows x into out` 以视图实例化 | 拒绝写（K1）、接受读；拒绝（K9）；拒绝写（K1）；其余各拒绝对新来源的写（K1） |
| Q1 其他 | 局部经借用整体替换后旧来源解除；函数类型的合同目标为 `v.mid`，实参函数的目标为 `v.mid.deep` 或 `v`；经视图的借用字段走到另一个视图再写入 | 接受；接受、拒绝（K12）；拒绝（K14，未支持） |

另有两条测试：让别名路径只读建立借用时的副本，Q1 恰好少报；去掉写入的记账，K6 与 K9 的拒绝全部消失。

### 18.3 发现

1. **流向子句推广到字段路径不需要新机制。** 目标的路径与来源的路径是同一种写法、同一个覆盖关系，K6、K12 原样适用。Rust 在这里需要 `&mut V<'a>` 对 `'a` 不变；这里没有对应物：来源并入持有者之后，“持有者比来源活得久”由已有的 K9 拒绝。
2. **又发现三个漏洞，仍然都是来源漏记。**
   - 经独占借用整体替换（`*x = e`）完全不记来源：把指向局部变量的视图写进调用方的槽位，原型接受。它从第 3 步引入 `*x = e` 起就存在，此前没有用例把整体替换与视图放在一起。
   - 泛型的 `flows x into out` 以视图实例化时，来源记在一个读字段时看不到的键上：之后从容器里读出的借用不保护新来源。
   - 借用值带着建立时的字段来源副本；经别的路径写入之后，经它读到的是旧账。
   三处都已修正并由 Q1 与变异测试覆盖。连同此前四个，七个漏洞同属一类。K20 把 §13 的建议落成了规则：来源只有一份账，在拥有存储的变量上，其他路径一律现查。参考检查器应当从这条规则出发设计数据结构，而不是事后逐个补存放点。
3. **函数体内可以解除旧来源，调用方不能。** 函数体内写入的目标唯一，旧值确定被换掉；调用方只看到“可能流入”，只能并入。所以经函数改写视图之后，旧来源在调用方继续受保护，直到持有者不再使用（Q1 `callerKeepsOldSource`）。要更精确需要在签名里区分“替换”与“并入”，这是一个新的子句。**裁决（2026-11-15）：不加。** `flows` 只有“可能流入”一种含义，调用方一律并入；诊断须指出持有者自哪里起可能仍借着旧来源。
4. **来源种类的改正说明此前的用例偏弱。** “带流向就按独占计”在已有用例里没有造成任何错判，只因为“只读来源流入之后仍可读”从未被检验。现在 Q1 有这一条。
5. 没有覆盖的：经视图的借用字段走到另一个视图再写入（目标路径越过借用字段，账要记到那个视图的拥有者上；调用方一侧须把目标参数的字段映射回它背后的变量），当时拒绝，§22 已放开；按值接收的视图经它的独占字段改写调用方的视图，同属这一项；对借用值再取借用（借用的借用作为值）时字段来源的现查。

## 19. 原型合并第一步：能力判定取自能力推导（2026-11-15）

借用原型此前自己近似四项判定：可否隐式复制、是否可逃逸、可否转移到另一个线程、析构是否可观察。这一步把它们全部改为向[能力推导原型](capability-derivation-model.md)询问，借用原型里不再有自己的版本。用例 R1。

做法：演算的类型声明逐个翻译成能力推导的声明。`cell class` 翻译为“含有一个 `RawCell` 字段”，`local class` 翻译为“含有一个非原子共享计数的字段”，两个标记因此不再有独立的含义。

| 判定 | 此前 | 现在 |
|---|---|---|
| 可隐式复制（K8） | 不含独占字段的视图 | `Copyable` |
| 可逃逸（K17） | 不是视图 | `Escapable` |
| 可转移（S5） | 按 `local` 与内部可变两个标记递归 | `Transferable`；共享借用看所指的 `Shareable` |
| 析构可观察（K18） | 按 `deinit` 标记递归 | 不满足 `EarlyDrop` |

增加的记法与规则：

```text
类型参数  <T: Cap + Cap>     能力上界
```

| # | 规则 |
|---|---|
| CAP 声明 | 能力推导对声明的检查原样适用：可能携带来源的类型须声明为视图 |
| CAP 上界 | 类型参数只凭它声明的上界回答能力询问；调用处实参的类型须满足被调方的上界，调用方自己的类型参数须带着相同的上界 |

发现：

1. **已有的 53 个用例的结果一个都没变**，其中的提前析构次序也没变。四项近似在已有用例的范围内与推导一致。
2. **不一致的地方有三处，都在已有用例之外，其中一处是漏洞。**
   - 视图按值拥有一个普通类的值时，旧判定仍允许隐式复制这个视图，等于复制了一份所有权。推导正确地判它不可复制。
   - 普通类声明了借用字段，旧原型不报错；推导要求它声明为视图。
   - 没有任何借用字段的视图，旧判定一律当作不可逃逸；推导判它可逃逸。这是旧判定过严。
3. **并行入口的上界可以表达，并且沿调用链传递**：`parallel` 函数的类型参数写了 `Transferable` 上界之后，跨挂起点持有它的值被接受；调用它的泛型函数须带着同样的上界，否则在调用处被拒绝。这补上了 §17.3 第 6 条。
4. 没有做的：类型本身带类型参数（演算的类没有泛型，条件式的推导结果用不上）；`Forgettable` 与 `ImplicitDrop` 两项在借用原型里没有使用者；析构义务原型仍然用自己的类型标记，活性分析仍是两份，这是合并的下一步（§20）。

## 20. 原型合并第二步：析构交给析构义务的检验器（2026-11-15）

借用原型此前只判断“析构与存活的 loan 是否冲突”，它定下的析构本身对不对没有人检验；[析构义务原型](drop-obligation-model.md)有一个独立的检验器，但它的输入来自自己的规划器，不含借用。这一步把两者接起来：借用检查器在检查每个函数的同时，把它写成一段只含所有权操作、析构显式的程序，交给析构义务的检验器。用例 S1，以及全部已有用例里被接受的函数。

写出的内容：

| 借用原型里的事 | 写成 |
|---|---|
| 声明一个拥有的值（含按值参数） | `let`，附失败时的清理清单 |
| `move`、整体赋值 | `move`；先析构旧值再 `set` |
| 任何读、写、借用，**包括经借用值或视图到达 owner 的访问** | 对 owner 的 `use` |
| 调用 | 一个可能失败的操作，附清理清单 |
| 提前析构（K18）、作用域结束、函数结束 | `drop`；可能已移走的带析构标志 |
| 分支、循环、代码块 | 原样；循环取到达不动点的那一遍 |

类型是否可观察取自能力推导。检验器不知道借用，它只执行这段程序并穷举路径与失败，检查析构义务原型的 V1–V5。

| # | 规则 |
|---|---|
| K18 补偿 | 打开提前析构时，不可观察的值只在一条分支上被移走或析构、此后不再使用、名下没有存活的 loan，就在另一条分支的末尾析构 |

发现：

1. **全部被接受的函数都通过检验器**，提前析构打开与关闭两种情况共 292 次检验，没有一处违反。经借用的访问记为对 owner 的使用，所以“存活的 loan 使 owner 保持存活”（K3 的补充、K18 的第二条）第一次得到了借用原型之外的检验：去掉它，检验器报“使用了已析构的值”。
2. **活性分析只剩一份。** 析构义务一侧不再需要自己算活性：析构点由借用原型定，检验器只负责验。析构义务原型自己的规划器保留，用于借用原型表达不了的部分（部分移出、拆开、必须消费、`deinit` 函数体）。
3. **借用原型原先会让不可观察的值也带上析构标志。** 提前析构只在语句之后触发，值在一条分支上被移走或提前析构后，另一条分支没有对应的析构，合流后成了“可能已移走”，只能在函数结束处带标志析构。析构义务原型的规划器在这里是在分支末尾补一次析构。已按后者补上（K18 补偿），现在全部用例里带标志的只有一处，正是可观察的值，与“析构标志只用于可观察的值”的裁决一致。
4. **失败时的清理清单在借用一侧同样是“此刻的状态”。** 每个声明与调用处的清单就是当时仍拥有的变量的逆序，没有另外的分析；检验器穷举失败路径没有发现泄漏。借用原型本身仍然没有失败出口，失败路径上不做借用检查。
5. 没有做的：视图与类型参数的值不提前析构；按值参数不提前析构；函数结束处此前没有析构与 loan 的冲突检查（返回值的来源由 K6 负责），这一步只是把析构写了出来；部分移出、`deinit` 函数体、挂起点两侧的析构没有经过这条路；析构义务原型的类型标记仍是自己的。

## 21. 挂起点两侧的析构义务（2026-11-15）

§17 只检验了挂起的借用一侧。这一步借 §20 接好的路检验析构一侧：挂起点两侧待执行的析构是否相同，帧被销毁而不再恢复时由谁析构、析构什么。用例 P4。

### 21.1 规则

| # | 规则 |
|---|---|
| S2 延伸 | 挂起点不析构任何东西，也不改变任何值的归属。留在帧里的是三类值：之后还会用到的；被存活的借用指向的；此刻仍拥有、等着在作用域结束时析构的 |
| S5 修正 | 并行函数里须可转移的是留在帧里的全部三类值，不只是“之后还会用到的” |
| S6 挂起前析构 | 不再使用、名下没有存活 loan、析构不可观察的值，在挂起点之前必须已经析构。这里“提前析构”是义务，不是许可 |
| S7 按状态析构 | 帧在挂起点被销毁而不再恢复时，析构它此刻仍拥有的值，自内向外、声明逆序，可能已移走的看析构标志。每个挂起点一份清单，与可失败操作的清理清单是同一种东西 |

写进析构义务程序的是一条 `suspend` 语句，附 S7 的清单；检验器把“帧在这里被销毁”当作一条要穷举的路径。

### 21.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| P4 并行 | 只在挂起前使用的 `local` 普通值；只在挂起前使用的 `local` 且带 `deinit` 的守卫；把守卫放进内层代码块；挂起前把守卫移走；守卫跨过对 `suspend` 函数的调用；可转移的带 `deinit` 的值跨过挂起点 | 接受；拒绝（S5）；接受；接受；拒绝（S5）；接受 |
| P4 默认 | 不换线程的函数里守卫与文件跨过挂起点 | 接受；帧里记着两个都不再使用但尚未析构的值 |
| P4 销毁 | 一个值只在一条分支上被移走之后挂起，再声明一个值并调用 `suspend` 函数 | 各挂起点的清单随状态变化，检验器穷举“在此销毁”没有泄漏 |

测试：去掉 S6，`local` 普通值所在的挂起点多出一处 S5；去掉挂起点上的清单，检验器报泄漏；关闭提前析构时，S6 的析构仍然出现在挂起之前。

### 21.3 发现

1. **§17 的并行检查有一个漏洞。** 它只看“挂起之后还会用到的值”。一个带 `deinit` 的值即使之后不再使用，也要留到作用域结束才析构，所以它一直在帧里；并行函数里它会在另一个线程上被析构。绑定在线程上的守卫（非原子计数、线程局部的锁）跨过挂起点，§17 的原型接受了。这正是 Rust 里“锁守卫跨过 `await`”那类错误。已按 S5 修正，P4 覆盖。
2. **“提前析构只是许可”在挂起点处不成立，需要裁决。** P3 里“只在挂起前使用的 `local` 值不受影响”这一条，实际依赖它在挂起前已经析构。若提前只是许可，编译器可以把它留到作用域结束，它就跨过了挂起点；程序是否合法于是取决于一项优化。两种出路：
   - **S6：挂起点之前必须析构。** 普通值用完即走，不会因为“还没到作用域结束”而被判为跨过挂起点；帧的大小也因此可以预期。代价是统一析构规则多一处例外：在挂起点，许可变成义务。
   - **一律按词法作用域计。** 规则没有例外，但用户得像在 Rust 里那样，为了让一个用完的普通值不跨过挂起点而手工加代码块或显式移走。
   原型按 S6 实现。它不改变任何可观察的行为：涉及的值析构不可观察，差别只在它们的析构发生在哪个线程，而那正是 S5 要管的事。
   **裁决（2026-11-15）：采用 S6，并限定它只适用于没有逃逸的值。** 即本函数仍独占拥有、没有被移走、名下没有存活的借用、地址没有被取成裸指针的值。地址被取过的 owner 按[之四](evolution-04-route-capability-unsafe-suspend.md) R1.2 留到词法作用域结束，它跨过挂起点并受 S5 检查。前三条原型已实现；演算没有裸指针，第四条没有检验。
3. **S0.3 在析构一侧同样不需要规则。** 挂起点不析构、不移动，两侧的义务自然相同；检验器沿正常路径走过挂起点没有任何特殊处理。新增的 S6 不是为守恒，而是为第 2 条。
4. **“取消时由谁析构”在正常路径上不是问题。** 取消是值（之七 J19）：挂起原语返回一个表示取消的结果，函数照常运行到返回，析构走的就是普通的作用域结束与失败出口。帧在挂起点被直接销毁只发生在所在执行器异常终止时，由销毁帧的一方按 S7 的清单执行。清单的数量是挂起点的数量，内容就是那一刻的状态，没有另外的分析。
5. **带 `deinit` 的值跨过挂起点在默认函数里没有任何限制**，与 J18 一致；限制只在并行入口出现。
6. 没有覆盖的：帧被销毁时指向它的借用（借用型子任务，之十一 J48 第 7 条要求先等齐）；`deinit` 永不挂起这一条没有检查；视图与类型参数的值不参与 S6；任务值按裁决不出现在用户代码里，§17 的 `start` / `poll` / `await` 记法没有随之改写成作用域库的形态；在途 IO 的缓冲区（之七 §2.7）。

## 22. 借用一侧的三项记账（2026-11-15）

清“集中做”一栏里借用一侧的三项：越过借用字段的流向、两阶段借用、递归的视图类型。用例 Q2、T1、U1。

### 22.1 流向越过借用字段

视图 `Holder(inout target: L1)` 经它的独占字段改写另一个视图 `L1`。此前函数体里这样写被拒绝（K14），调用处不支持。

| # | 规则 |
|---|---|
| K20 越过 | 写入的位置越过借用字段时，账记在那个字段所指的视图的拥有者上；所指在调用方时记在参数名下的完整路径上（`h.target.mid.deep.a`） |
| K20 按值目标 | `flows` 的目标可以是按值的视图参数，条件是目标路径经它的独占字段走到另一个视图。参数自己的存储随它消失，不算流出 |
| K20 调用（延伸） | 调用方沿目标路径逐级走：按值字段留在同一处存储，借用字段换到它所指的存储；最后把来源并入走到的那个拥有者。目标写得粗（`into h`）时，它之下每条越过借用字段的路径都这样走一遍 |

Q2：按值、按 `move`、按 `inout` 交出 `Holder`，以及直接以 `h.target` 作实参，四种调用之后从**被改写的视图自己**读出的借用都保护新来源；声明粗的目标同样；经共享字段的流向在签名处被拒绝（SIG）；拥有者比来源活得久被拒绝（K9）；转交须自己声明。

### 22.2 两阶段借用

| # | 规则 |
|---|---|
| K21 预留 | 接收者位置的独占借用，在其余实参求值期间只算共享：可以读它、对它建立共享借用，不能写、移动或再建立独占借用 |
| K21 生效 | 其余实参求值完毕时转为独占。此刻仍存活并与它重叠的 loan 都是冲突，包括作为实参交给被调方的共享借用 |

演算没有方法，接收者记作“名为 `this` 的第一个参数，按 `inout` 传入，实参是直接的 `&mut`”。范围与 [Guide 10](../guide/10-ownership-borrowing-drop.md) 的 Two-Phase Borrows 相同：只有接收者，普通实参位置不推迟。

T1：`push(&mut v, size(&v))` 与 `push(&mut v, v.len)` 接受；同样的写法在普通参数位置拒绝；`update(&mut v, &v)`、实参里再次独占借用、实参里移走接收者、更早的借用仍存活、上一次的出借结果仍存活，都拒绝；放在循环里接受。

### 22.3 递归的视图类型

`view class Node(borrow next: Node, borrow data: Arr)`：经借用字段指向同类型的视图。

| # | 规则 |
|---|---|
| K16 折叠 | 参数名下的来源只展开到第一次回到同一类型为止。再往里的借用字段没有自己的记录，它们的来源归到回到同一类型的那个字段名下：`n.next.data`、`n.next.next.data` 都由 `from n.next` 覆盖 |

U1：`from n.next` 返回第二个、第三个节点的数据，以及沿链走任意多步的循环，接受；声明 `from n.data` 或不声明，拒绝（K6）；调用方一侧，结果保护链上更深处的来源，只读自己数据的结果不保护它们。

### 22.4 发现

1. **“来源只记一份账”在多一层间接时仍然成立，不需要新机制。** 越过借用字段只是把“拥有者”换成了另一个变量；调用方沿路径走的每一步都是已有的两种情形之一。
2. **又发现三个来源漏记的漏洞，都与“所指在调用方”有关。**
   - 调用返回的、指向调用方视图的借用，经它读字段时查不到来源：函数可以不声明 `from` 就返回视图字段里的借用。
   - 把视图的一个借用字段（它指向另一个视图）直接作实参时，没有带上那个视图各字段的来源。
   - 递归视图的参数，第二层以后的字段没有任何来源记录（22.3）。
   第一处的原因是 §18 的“现查”只查了局部变量，没有查参数名下的账。至此同类漏洞共十个。它们集中在三件事上：值被存进某处、借用被再传一手、所指不在本函数里。参考检查器的测试应当按这三条轴系统地生成，而不是靠想到一个补一个。
3. **两阶段借用不改变内核的形状。** 它只是把一个 loan 的种类推迟确定，冲突判定用的仍是 K1。现行规则的三条边界（只读可以、写与移动不行、交给被调方的共享借用在生效时冲突）在原型里逐条得到。原型此前比现行规则多拒绝的那一类程序，现在一致了。
4. **递归视图的精度有上限，这是折叠的代价。** 链上更深处的来源只能整体声明、整体保护：结果只指向第三个节点的数据，调用方也会保护第二个节点的数据。要更精确需要按深度区分，而深度不是静态可知的。
5. 没有覆盖的：越过借用字段的流向在失败路径上；接收者经借用值或视图字段传入时的两阶段借用（现行规则同样只管直接的接收者）；互相递归的两个视图类型；递归视图上的流向；按值递归（需要间接 owner，演算没有）。

## 23. 来源记账的用例生成器（2026-11-16）

### 23.1 枚举的轴

### 23.2 找出的漏洞与修正

第一次运行有 62 段程序与预期不符，归为三个漏洞；顺着“值被存进某处”再手工探了一步，找到第四个。四个仍然都是来源漏记，至此同类漏洞共十四个。

| # | 漏洞 | 修正 |
|---|---|---|
| 1 | **流进调用方持有者的来源不算存活。** `fun f(inout h: V, inout s: Arr) flows s into h` 的函数体在放入之后可以经 `s` 写来源：`h` 在本函数里不再使用，名下的 loan 就被当作结束了 | K20 存活 |
| 2 | **指向另一个视图的视图带着旧副本。** `H(inout target: V)` 构造时把 `V` 各字段的来源抄了一份；经 `h.target` 改写所指的视图之后，直接读字段是对的，把 `&h` 整个交给函数时带出去的却是旧副本 | K20 现查（延伸） |
| 3 | **经独占字段整体改写所指的视图时，字段自己的那份借用被一并作废。** `h.target = V(s)` 之后 `h.target` 不再指向任何存储，经它读出的借用不保护任何来源 | 只作废该字段之下的副本 |
| 4 | **可逃逸的类收下来源之后可以带着它逃逸。** `Bag` 与 `Slot` 经 `flows x into bag` 收下视图，类型仍是可逃逸的类：交给 `<T>`、交给按值的 `Bag` 参数、存进另一个类的字段，都被接受且不再保护来源；声明 `from` 后按值返回，调用方那边的值也不再记着来源 | K14 目标（23.4 的裁决；起初补的是“按账判断”，已撤掉） |

| # | 规则 |
|---|---|
| K20 存活 | 记在参数名下、落在调用方存储里的来源，在本函数返回之前一直存活。调用方的持有者在返回之后还在，与它在本函数里是否还被使用无关 |
| K20 现查（延伸） | 视图名下只有它自己的借用字段的账。借用字段之外的路径（它所指的另一个视图的字段）一律沿路径走到那个视图的拥有者上取，包括把这个视图整个借出、复制或移走的时候 |
| K14 目标 | `flows o into x` 的目标与声明了 `from` 的按值结果，类型上须能携带来源：视图、`view T`，或以它们实例化的泛型类型。否则在签名处拒绝（SIG） |

### 23.3 发现

1. **三条轴之外还要加一条：持有者自己在哪里。** §22.4 的三条轴都是从“读出的借用”出发的。漏洞 1 不涉及读出的借用：来源流进调用方的持有者之后，没有任何本函数里的变量替它保持存活。把“持有者也在调用方”作为所指位置的一个取值之后才生成出这一类程序。
2. **“所指在调用方”仍是漏洞最多的地方。** 四个里有两个（1、4 的返回一支）出在函数边界上。此前“存活”完全由本函数里的变量决定，这在所指与持有者都在局部时成立；边界上要补的是同一句话的另一半：调用方的东西在返回之后都还在。
3. **漏洞 2、3 说明副本应当更少，而不是更勤地同步。** 两处都是视图名下存着所指视图的字段来源。修正之后副本只在一处还有意义：所指在调用方、没有拥有者变量可查时，参数名下的那份就是账本身。参考检查器重写时，视图的账应当只到自己的借用字段为止。
4. **漏洞 4 来自演算没有泛型类型，但暴露的问题是真的。** `Bag` 在演算里代表“以视图实例化的 `Bag<T>`”，声明却是一个普通的类。流向子句的目标若可以是一个从类型上看不出能携带来源的值，逃逸性就不能只问类型，检查器处处要同时查账。裁决与随之的改动见 23.4。
5. **变异测试确认了修正各自被生成用例检验到。** 去掉 K20 存活，恰好是“放入后写来源”与不透明持有者的“写来源”变为接受；去掉现查的延伸，恰好是独占字段所指视图上“经调用返回”的 12 段少报；让能力推导把两个容器判为可逃逸，“交给可逃逸的类型参数”与“存进普通类的字段”不再在标记处被拒绝。漏洞 3 的修正在一行赋值逻辑里，没有单独的变异测试，由 20 余段生成用例直接覆盖。
6. 没有覆盖的：借用的借用作为值（44 个组合因此不适用）；泛型函数体内以 `view T` 为持有者的读出（`T` 上没有可读的字段，只能整体转交）；循环与分支里的放入；失败路径；三处以上的间接。生成器只生成直线型的函数体。

### 23.4 裁决：流向的目标须是类型上能携带来源的值（2026-11-16）

**裁决。** `flows o into x` 的目标必须是类型上能携带来源的值；逃逸性只由类型决定。`flows … into` 这个拼写先作占位，与 `p.origins`、`view T` 一样待定。

演算随之增加一种声明，并撤掉“按账判断可逃逸”：

```text
声明    D ::= … | [cell] view class C<view T>(f: τ, …)     泛型容器；类型里只写 C
```

- 它代表“以携带来源的类型实例化的 `C<T>`”。演算仍然没有类型实参：写 `C` 的地方一律是这样的实例，所以它类型上不可逃逸、不可复制。不携带来源的容器用普通的 `class`。
- 这与[能力推导原型](capability-derivation-model.md)已有的结论一致（用例 C5）：能装视图的容器须声明为 `view class C<view T>`，写成 `class C<view T>` 是声明错误。借用原型把这个声明翻译给推导器，实参取一个携带来源的代表，逃逸性由推导得出。
- 容器的内容只经受信任函数访问，它携带的来源整体记在值名下，随移动、按值转交与按值返回走；作为视图的按值字段时记在该字段名下。
- 原有用例 H5、K4 的 `Bag` 与 M1 的 `Slot` 改为这种声明，预期不变。

| 情形 | 结果 | 规则 |
|---|---|---|
| 容器交给可逃逸的类型参数（空容器同样） | 拒绝 | K17，类型上的判断 |
| 容器按值转交给声明了 `from x` 的函数、存进视图的按值字段、声明 `from` 后返回，之后读出借用再写来源 | 拒绝 | K1 |
| 转交或返回容器的函数不声明来源 | 拒绝 | K6 |
| 容器存进普通类的字段 | 拒绝 | CAP：可能携带来源的类型须声明为 `view class` |
| 流向的目标是普通类、不带 `view` 的类型参数；普通类的结果声明 `from` | 拒绝 | SIG（K14 目标） |

没有覆盖的：容器自己再带借用字段；容器的类型实参（一个 `Bag` 里装的是哪种视图、两个 `Bag` 是否同一实例化）。两者都要等演算有了真正的类型实参。

## 24. 失败出口上的借用检查（2026-11-16）

此前借用原型没有失败出口：可失败的操作只带一份清理清单交给析构义务的检验器，失败路径上不做借用检查。这一步补上。用例 V1。

### 24.1 要检查的是什么

操作失败时函数从那里离开，仍拥有的值自内向外、声明逆序析构，本函数没有别的代码再运行；调用方的持有者不会指向本函数的局部存储（K6 已保证）。所以失败路径上唯一还能读到局部存储的代码，是清理途中运行的 `deinit`。问题归结为一句话：**来源会不会先于一个析构可观察的持有者被析构。**

这同时暴露出正常路径上缺的一条。[之二](evolution-02-route-loan-kernel.md) R1.2 规定带 `deinit` 的持有者死亡点是词法作用域结束，原型没有实现：持有者按最后一次使用算死亡，它的 `deinit` 经借用字段读出去这件事没有被当作使用。

| # | 规则 |
|---|---|
| K3 可观察 | 析构可观察的值（能力推导判为不可提前析构）活到它被析构或移走的那一刻，它持有的 loan 随之存活。没有上界的类型参数的值按可观察计 |
| K9 函数结束 | 函数正常结束时与代码块结束时一样检查：逆序析构，被析构的存储上不得有存活的 loan |
| K22 失败出口 | 每个可失败的操作（声明、调用、挂起点）处，按此刻的状态逆序析构仍拥有的值，被析构的存储上不得有存活的 loan。此刻存活的只有尚未析构的可观察持有者所持有的 |
| K22 流向 | 调用失败时，它声明的流向须假定已经发生：被调方可能在写入之后才失败 |

挂起点上帧被销毁而不再恢复（S7）用的是同一条 K22，与析构一侧“每个挂起点一份清单”对应。

### 24.2 用例

| 程序要点 | 预期 |
|---|---|
| 带 `deinit` 的视图不再使用之后写它的来源；不带 `deinit` 的同样写法；先把它交出去再写 | 拒绝（K1）；接受；接受 |
| 来源先声明、持有者后声明，之后有可失败的调用 | 接受 |
| 持有者先声明，后声明的局部经流向放进它：带 `deinit`；不带 | 拒绝（函数结束处 K9，放入的那次调用 K22）；接受 |
| 同上，来源在内层代码块里 | 拒绝（代码块结束处 K9，调用处 K22） |
| 放入之后、把持有者交出去之前有可失败的调用 | 正常路径接受；放入的调用与其后的调用各拒绝（K22） |
| 可失败的调用在放入之前 | 接受 |
| 只在一条分支上把持有者交出去 | 拒绝（K9、K22） |
| 放入之后有挂起点、调用挂起函数、声明新的局部 | 各拒绝（K22） |

两条变异测试：去掉离开函数时的检查，V1 里 10 处 K22 与函数结束处的 2 处 K9 恰好消失，代码块结束处的不变；把一切判为可提前析构，V1 全部被接受。

### 24.3 发现

1. **失败路径不需要新的借用机制。** 它是“在每个可失败的操作处再做一次作用域结束的检查”，用的是同一个冲突判定。清单与析构一侧的清理清单是同一份，都只是那一刻的状态。
2. **正常路径上漏了一条，而且是之二已经写明的 R1.2。** 59 个手写用例与 1029 段生成程序里没有一个持有者带 `deinit`，所以一直没有碰到。它不是来源漏记，是存活的定义少了一半：值的最后一次使用可能是它的析构。
3. **“先放进去、稍后再交出去”在失败路径上站不住。** 持有者先声明、来源后声明时，正常路径可以靠在来源析构之前把持有者交出去而成立；但放入的那次调用自己就可能在写入之后失败，这时来源先被析构。所以这种写法总是被拒绝，与中间有没有别的操作无关。可行的写法只有一种：来源声明在持有者之前。诊断应当直接这样建议。
4. **没有上界的类型参数的值按可观察计，泛型代码因此更保守。** H3 的 `twoAtOnce` 多出一处拒绝：第二个元素的类型未知，它的析构可能读它借着的东西，所以它活到作用域结束。要放宽需要让类型参数声明“可提前析构”的上界；能力推导里已有这项能力（`EarlyDrop`）。**裁决（2026-11-16）：先不开放给用户写，保留日后放开的可能。** 受影响的只有携带来源的类型参数的值；需要早结束时把值交出去或收进更小的代码块。
5. **原型里顺带补了一处类型绑定。** 高阶函数的结果类型是类型参数、而它由函数实参的合同决定时，调用方此前拿到的是一个未知类型的值；K3 可观察之后这会造成误拒绝（H4）。现在函数实参的具体结果类型确定同名的类型参数。这是原型的精度问题，不是规则。
6. 没有覆盖的：已开始的任务在失败出口上（S4 要求离开前等待，失败时由谁等属于作用域库与取消，见覆盖页的下一步）；`deinit` 在清理途中再次失败（析构义务原型定为终止进程，借用一侧没有再检查）；容器里装着带 `deinit` 的视图时容器是否可观察（演算的容器没有类型实参，按不可观察计）；生成器没有生成带 `deinit` 的持有者与失败点。

## 25. 作用域库的形态（2026-11-16）

§17.3 第 4 项的裁决是任务值不出现在用户代码里，帧由结构化作用域库持有。§17 的 `start`、`poll`、`await` 因此是库内部的记法。这一步把用户看到的那一层写出来，检验它需要多少新规则。用例 W1。结论是不需要：它由流向子句、容器声明（§23.4）与可观察的持有者（§24）组合得到。

### 25.1 写法

```text
cell view class Scope<view T>(…) deinit                         作用域：内部可变的容器，析构时等齐全部子任务
view class Job(borrow scope: Scope)                             句柄：不能比作用域活得久
fun <view F> launch(borrow sc: Scope, own f: F): Job from sc flows f into sc trusted
fun <view F: Transferable> launchParallel(…同上…) trusted        并行入口：子任务的环境须可转移
sig <view E> Body(borrow sc: Scope, inout env: E): Unit flows env into sc
fun <view E> scoped(inout env: E, own body: fn Body): Unit {    不是受信任函数，由检查器检查
  val sc = Scope(0)
  body(&sc, env)
}
```

子任务与作用域体都按 §16 的做法手工展开成“环境加函数”。受信任的只有 `launch`、`join` 与 `Scope` 的析构；S3、S4 是这三处的义务。`scoped` 是普通函数：作用域是它的局部变量，作用域体把环境的来源流进去，函数结束时作用域先于一切被析构。

| 情形 | 结果 | 由哪条规则得到 |
|---|---|---|
| 两个只读子任务；循环里启动任意多个；作用域体内等待句柄 | 接受 | K14、K19（经共享借用流入内部可变的容器） |
| 可写子任务之后再启动只读子任务，或父自己写同一个变量；只读子任务之后父读 | 拒绝；拒绝；接受 | K20 存活：流进调用方作用域的来源活到返回 |
| 可写子任务只声明 `flows env.b into sc`；不声明流向 | 拒绝 | K6。经环境的独占字段取得的借用依赖环境本身（之二 R4.5），须声明 `flows env into sc` |
| 子任务借用作用域体的局部变量 | 拒绝 | K6：局部存储不能流进调用方的持有者 |
| 句柄从作用域体返回 | 拒绝 | K6 |
| 并行入口：环境里是普通值的共享借用；是内部可变值的共享借用；后者交给不并行的入口 | 接受；拒绝；接受 | 能力上界（CAP） |
| 调用方：`scoped` 返回之后写被借出的变量 | 接受 | 流向只进了 `scoped` 的局部，调用方什么都不保留 |
| 用户自己持有作用域：启动之后写来源；来源声明在作用域之后；把作用域交给可逃逸的类型参数 | 拒绝（K1）；拒绝（K9、K22）；拒绝（K17） | K3 可观察、K22、容器类型上不可逃逸 |

一条变异测试：去掉 `Scope` 的 `deinit`，“作用域还在时写来源”与“来源声明在作用域之后”的三处拒绝恰好消失。

### 25.2 发现

1. **结构化并发在内核里不是一条规则。** “子任务可以借用父的局部变量”拆开是三件已有的事：来源流进一个持有者（K14）；这个持有者类型上不可逃逸（§23.4）；它的析构可观察，所以活到析构点，来源必须比它先声明（§24）。作用域库只需要保证析构时等齐子任务。
2. **“子任务不能借作用域体的局部变量”是 K6 的结果，不需要第二个生命周期。** Rust 的 `thread::scope` 用 `'scope` 与 `'env` 两个参数表达这一点；这里作用域是调用方的持有者，作用域体的局部存储流不进去。
3. **失败出口上由谁等待：作用域的析构。** 作用域体失败时，`scoped` 的帧按 K22 清理，作用域先被析构并等齐子任务，之后才轮到更早声明的值。这要求“等齐”写在析构里而不是写在 `scoped` 的正常路径上。子任务失败之后让父失败（失败模型 A 的“传播”）是 `scoped` 在正常路径上的一次普通失败，不是 `deinit` 失败，所以与“`deinit` 失败即终止进程”不冲突。
4. **取消不进入借用检查。** 取消是值（之七 J19）：`join` 返回一个表示取消的结果，子任务照常运行到返回。失败模型 A 还要求失败待传播时阻塞的子任务能被唤醒，那是对阻塞原语的要求，同样不在借用规则里。
5. **用户自己持有作用域也是安全的，但没有必要开放。** 上表最后一行说明规则已经足够；把构造函数留给库只是为了让“等齐”的义务集中在一处。
6. **可写捕获须声明整个环境流入。** 这是 R4.5 的直接后果，作用域体的合同因此写作 `flows env into sc` 而不是 `flows env.origins into sc`。前者使环境在作用域存活期间整体被独占；对作用域体来说没有损失，因为环境本来就是为它建的。
7. 没有覆盖的：`suspend` 的作用域体与挂起的 `join`（演算的合同细化不检查 `suspend`）；句柄携带结果类型；子任务再开作用域；作用域值跨线程（它是内部可变的，按 §19 不可共享，并行入口内部如何持有它属于库的受信任实现）；§17 的 `start`、`poll`、`await` 与这里的 `launch`、`join` 之间的对应没有机械地检验，只是约定前者在受信任函数内部。

## 26. 原型合并的余项：部分移出与析构能力（2026-11-16）

§20 留下三件事没有经过“借用原型定析构、析构义务的检验器来验”这条路：部分移出、`deinit` 函数体、析构义务原型自己的类型标记。这一步做了第一件与第三件。用例 X1，以及析构义务原型 D3 新增的两个函数。

### 26.1 部分移出

```text
表达式  e ::= … | move x.f        从拥有的变量里移出一个按值字段（只支持一层）
```

| # | 规则 |
|---|---|
| K23 移出 | `move x.f` 要求 `x` 是本函数拥有的变量、`f` 是它的按值字段、`x` 的类型没有声明 `deinit`。它是对 `x.f` 的一次移动，与指向 `x.f` 的存活 loan 冲突（K1），不影响其余字段上的 loan |
| K8 部分 | 字段移出之后，这个字段不可再用，`x` 不可再整体使用、借用或移动；其余字段照常。对 `x` 整体赋值之后恢复 |
| K23 来源 | 字段携带的来源随它走；`x` 名下只留其余字段的账 |

写给检验器的程序里，类与视图现在带着字段，于是一个变量的析构义务按字段分开：移出是 `take`，经字段的访问记为对那个字段的 `use`，字段全部移出的变量不再析构。

X1：移出一个字段后用另一个；用已移出的字段、整体移动、整体借用、重复移出、循环里移出，都拒绝（K8）；整体赋值之后恢复；从声明了 `deinit` 的类型移出，拒绝（K23）；移出带 `deinit` 的字段再交出去；字段被借用时移出，拒绝（K1），另一个字段被借用时接受；经借用移出，拒绝（K8）；从按值参数移出并返回；嵌套视图移出后，来源跟着走，余下的字段保留自己的来源。

### 26.2 析构能力取自能力推导

析构义务原型此前自己判断三件事：析构是否可观察、可否遗忘、可否隐式析构。前两件按字段递归，第三件只看类型自己的标记。现在三件都翻译成能力推导的声明，由推导器按字段得出（`EarlyDrop`、`Forgettable`、`ImplicitDrop`）。至此三个原型的能力判定只有一份。

### 26.3 发现

1. **部分移出不需要新的借用规则。** 它是 place 上已有的两件事的组合：移动是一次与存活 loan 不相容的访问（K8），冲突按 place 的前缀关系判定（K1）。新增的只有“变量的初始化状态细分到字段”，演算 §3 的状态定义本来就是这样写的，原型此前没有实现。
2. **析构义务原型有一个漏洞，换成能力推导之后暴露出来。** “必须显式消费”的值装进另一个类型之后可以被隐式析构：原型只看类型自己的标记，不看字段。能力推导按字段推导，装着它的类型同样不可隐式析构（D3 `boxedTicketDropped`）。这是三个原型各自近似同一件事的代价，§19 合并能力判定时在借用一侧也找到过同类问题。
3. **检验器独立发现“移走的字段被再析构一次”。** 让借用原型忘掉字段已被移出，它定下的析构交给检验器后报重复析构。
4. **`deinit` 的类型不能被部分移出，这条在两个原型里一致**（析构义务 D2，这里 K23）。要拆开这样的值须用“消费并解除析构”（析构义务原型的 `open`），借用原型还没有这个操作。
5. 没有做的：`deinit` 函数体进入这条路（需要 `this` 作为拥有各字段的变量、函数体里的部分移出与 `open`，以及“从 `this` 借出的引用”与借用规则的配合）；`open`；多层字段的移出；移出后对单个字段重新赋值；只在一条分支上移出字段时的补偿析构（现在带析构标志留到作用域结束）；`take` 之外的 `replace`（留下空值）。

## 27. 原型合并的最后一项：`deinit` 函数体（2026-11-17）

[析构义务原型 §6](drop-obligation-model.md) 已经检验过 `deinit` 函数体，但那里没有借用。这一步让它走“借用原型定析构、检验器来验”的同一条路。用例 Y1。

```text
声明  d ::= … | deinit C { s* }      类型 C 的析构函数体；C 须声明了 deinit
```

| # | 规则 |
|---|---|
| K24 `this` | 函数体里 `this` 是一个拥有各字段的变量（析构义务原型 §6.2 的“拥有”）。可以从它移出字段（K23 对它不设“类型没有 `deinit`”的限制），不能整体移走。函数体结束时仍拥有的字段按声明逆序析构 |
| K24 签名 | 函数体没有签名：没有 `from`，没有 `flows`。于是任何来源都不能经 `this` 的字段流出去（K6） |

其余都是已有规则：移出字段之后不能再把 `this` 当整体使用（K8 部分）；字段被借用时不能移出（K1）；失败出口上逆序析构仍拥有的值并检查借用（K22）；`this` 是视图时，它的借用字段带着调用方的来源，与按值的视图参数相同。

写给检验器时，`this` 的类型是“同样的字段、不再有 `deinit` 这份义务”。检验函数体时把它放进“声明一个该类型的值然后析构它”的程序里；检验其他函数时，凡是析构到写出了函数体的类型，检验器都真的执行那段函数体。

Y1：调用 `this` 上的方法；移出字段交给按值的关闭函数；移出一个、用另一个；移出后整体使用，拒绝（K8）；整体移走，拒绝（K24）；只在一条分支上移出；从 `this` 借出引用并跨过可能失败的调用；借着字段移出它，拒绝（K1）；借着一个字段移出另一个；视图类型的 `deinit`；把来源写进 `this` 的独占字段所指之处，拒绝（K6）；函数体之外仍不能从这些类型移出字段（K23）。

发现：

1. **`deinit` 函数体不需要新的借用规则。** `this` 就是一个按值参数，加上 §26 的部分移出。新增的两条都是限制：不能整体移走，没有签名。
2. **“从 `this` 借出的引用”没有特殊之处**（析构义务页 §6.4 留下的问题）。它是对一个局部变量的字段的借用，活不过函数体；字段被借着时移不走，失败出口上也照常检查。
3. **`deinit` 不能让来源流出去，这是没有签名的直接后果，不必另立规则。** 视图类型的 `deinit` 经独占字段往调用方写入一个携带来源的值，就需要一条 `flows`，而 `deinit` 写不出来。隐式析构点没有地方记这条流向，所以这个限制应当保留。
4. **检验器独立发现两类错误**：借用原型忘了字段已被移出，报重复析构；把 `this` 当作不拥有字段，报泄漏。
5. **只在一条分支上移出带 `deinit` 的字段时，`this` 余下的部分带析构标志。** 与“析构标志只用于可观察的值”一致；全部用例里带标志的现在是三处。
6. 至此三个原型的合并做完：能力判定一份（§19、§26），活性与析构点一份（§20、§21），部分移出与 `deinit` 函数体都经过检验器（§26、本节）。析构义务原型自己的规划器仍保留，用于借用原型还没有的操作与政策对照：`open`、`replace`、必须消费、`this` 的另两种访问方式、`deinit` 失败的两种政策。
7. 没有做的：“消费并解除析构”（`open`）与留下空值的取出（`replace`）在借用原型里；内部可变、绑定线程与容器类型的 `deinit` 函数体（`this` 写给检验器时不带字段）；泛型类型的 `deinit`；`deinit` 不得挂起；检验器只在默认政策（`deinit` 失败即终止）下运行。

## 28. 借的是持有者，还是它所指的存储？（2026-11-18，待裁决）

设 `h` 是一个 `borrow A` 参数。它涉及两处存储：本函数的参数 `h`，以及调用方的 `A`。把 `h` 交给借用参数，是在第二处重借；按 §2 的 `&p` 对无字段的变量取址，则借的是第一处。借到参数自身，不能因此取得改写调用方 `A` 的权限。

用 `scripts/loan_kernel/checker.py` 分别检查下面两种函数体（每次只留一个调用）：

```text
class A(n: Int)
fun write(inout a: A): Unit { a.n = 1 }
fun probe(borrow h: A): Unit {
  write(h)       // 原型拒绝：K1，共享借用不能独占重借
  write(&mut h)  // 原型接受：与上式不同，但也不应满足 write 的参数类型
}
```

将 `probe` 的参数改为 `inout h: A`，两式都被原型接受；只有前式是已定义的独占重借。原因在 `Checker.borrow`：`resolve` 给出的地址是变量 `h`，但构造结果类型时只保留 `res.ty.name`（`A`），丢了内层的 `borrow` / `inout`。因此原型把指向持有者的借用当作指向 `A` 的借用。这是候选检查器的类型区分缺口，不是现行编译器的结论。

**生成器需要什么。** §23 跳过的 44 个组合都出现在持有者由调用方交入、经局部借用值写入的路径。这里要更新调用方的视图或容器，不是替换本地参数里的借用值。可以先用返回重借的函数取得局部持有者，而不引入二层借用类型。最小对照：在 §23 的公共声明后加 `fun pass(inout v: V): inout V from v { return v }`；令 `f(inout h: V, borrow s: Arr)` 依次执行 `val w = pass(h)`、`setV(w, s)`。声明 `flows s into h` 时原型接受，删掉子句时在 `f` 的签名报 K6。这只验证了 `V` 整体的重借，不代表 44 个组合都可直接启用。

**待裁决。** 建议先对裸借用变量的显式取址报错，保留已有的实参重借与字段访问；生成器按实际写入目标构造重借。若要把指向借用值的借用作为一等值，则必须保留内层类型，并区分持有者自身的局部寿命与所指来源，不能直接沿用现在的扁平类型。本节没有改变原型规则。

### 28.1 生成器：先验证调用方的 `V` 整体

生成器对这一种持有者用 `val w = pass(h)`、`setV(w, s)` 写入，再从 `h` 读出。原来跳过的 8 个组合中，3 种读法（直接读、经调用返回、字段作实参）各配 `borrow`、`inout` 两种来源，共启用 6 个。另 2 个的读法是“经借用值”：`h` 本身已是借用参数，与“经调用返回”重复，仍跳过。

这 6 个组合共生成 24 段程序。声明正确时接受；漏报流向或返回来源时按 K6 拒绝；对 `inout` 来源，在读出借用最后一次使用之前或之后改写都按 K4 拒绝。后一种拒绝保护的是调用方仍活着的 `h`，不是局部的 `w`。其余 36 个原先因写入路径跳过的组合未动；下一类可检验按值嵌套的 `W.inner`，不应把 `W` 整体当作 `V`。

### 28.2 生成器：调用方 `W` 的按值字段 `inner`

`val w = pass(&mut h.inner)` 取得内层 `V` 的独占重借；`setV(w, s)` 之后不再用 `w`，而从外层 `h` 读。四种读法是 `&h.inner.a.len`、`readW(h)`、`lenOf(h.inner.a)` 和 `readV(&h.inner)`。每种读法配两种来源：`borrow` 有 1 段接受、2 段 K6 拒绝；`inout` 另有 2 段 K4 拒绝，分别在读出的借用最后一次使用前、后写来源。

新增 8 个组合、32 段程序，原型均在预期行给出预期结果。借助已有 K6 和 K4 就能检验这条写回路径，不需要二层借用类型。与 §28.1 一样，重复的“经借用值”读法仍跳过。这里的 `inner` 是按值字段，不代表已经验证了沿独占借用字段 `H.target` 写入。

### 28.3 生成器：沿 `H.target` 写入，再从哪里读？

`H.target` 是独占借用字段，不是按值存放的 `V`。`pass(h.target)` 重借它所指的 `V`；经返回的 `w` 调用 `setV(w, s)` 后，分两处核对：

- `h` 是调用方传入的参数：本函数没有所指视图的变量名。经 `&h.target.a.len`、`readH(h)`、`lenOf(h.target.a)`、`readV(h.target)` 读出，漏报流向或返回来源按 K6 拒绝；`inout` 来源仍受 K4 保护。12 个原先跳过的组合中启用 8 个，生成 32 段程序；2 个读法重复，2 个无法在本函数里命名拥有者。
- `h = H(&mut v)` 在本地构造：经同样的 `pass(h.target)` 写入后不再使用 `h` 或 `w`，直接 `readV(&v)`。在使用结果 `e` 前写新来源 `s`，按 K1 拒绝；把同一写操作移到最后一次 `use(e)` 之后则接受。这两段手写对照不计入生成器。它们检验的是从拥有者读回的行为，不依赖还能通过 `h` 访问 `v`。

两个观察位置均不需要修改借用规则。

### 28.4 生成器：通过函数合同读回调用方的 `Env`

`val w = passEnv(h)` 重借环境，`setEnv(w, s)` 把新来源写入。之后不再使用 `w`。关键读法是 `val e = call(h, envBody)`：`call` 在泛型函数体内调用 `body(f)`，结果的来源由 `Body` 的 `from f.origins` 合同给出。另用 `&h.a.len` 和 `lenOf(h.a)` 作对照；这两种读法不能代替合同读回。

3 种读法配 `borrow`、`inout` 两种来源，启用 6 个组合，共 24 段程序，其中 8 段经函数合同读回。流向或返回来源漏掉 `s` 都按 K6 拒绝；`inout` 来源在 `e` 使用前后改写都按 K4 拒绝，后者是因为调用方的环境仍持有来源。重复的“经借用值”读法仍跳过。本节验证的是用视图表示的闭包环境和现有函数合同，不涉及捕获语法或运行时闭包实现。

### 28.5 生成器：不透明的 `Bag` 只按合同读回

`val w = passBag(h)` 重借调用方的容器；`put(w, V(s))` 依 `flows x into bag` 放入来源，随后只用 `peekBag(h)` 读回。`peekBag` 的结果声明 `from bag`，因此调用者可以写 `from h`，不能像 `V.a` 那样用某个可见字段区分新旧来源。此处不生成“返回来源只声明旧字段”的反例。原先跳过的 6 个组合中，只启用合同读回 × 两种来源：共 6 段程序，2 段接受，2 段因流向错报为 `o` 而按 K6 拒绝，另 2 段因改写 `inout` 来源而按 K4 拒绝。其余读法不是无法读字段，就是与合同读回重复。

调用方的 `h` 即使不再使用也保护 `s`，所以上述 K4 不能单独证明 `peekBag` 结果的活性。另用局部 `h = Bag(0)` 对照：经 `passBag(&mut h)` 写入 `V(&s)`，用 `peekBag(&h)` 取得 `e`。在最后一次 `use(e)` 之前写 `s` 按 K1 拒绝，之后写则接受。这两段不计入生成器；验证的是调用端对 `put`、`peekBag` 合同的检查，而非受信任函数体或真正的容器类型实参。

至此 §23 中因“借用的借用”而跳过的 44 个组合已逐类核对：用所指的重借启用 30 个，其余 14 个因读法重复、内容不透明或无法命名拥有者仍跳过。没有启用对裸借用变量显式取址的语义。

## 29. 分支合流：只在一条路径替换局部视图

`h` 初始是 `V(&o)`；`if (*) { h = V(&s) }` 后执行 `val e = readV(&h)`。这里直接替换局部 `h`，不用 `setV`：直接替换在写入分支解除旧来源，而 `flows` 在调用处只并入来源，不能用来区分旧来源究竟来自哪条路径。

在最后一次 `use(e)` 前写 `o` 或写 `s`，分别按 K1 拒绝；此时写无关的 `x` 则接受。把对 `o` 和 `s` 的写都放到 `use(e)` 后，也接受。K10 合流保留两个可能的来源，但不延长读出借用的寿命。变异对照：只保留写入分支，恰好漏报写 `o`；只保留未写分支，恰好漏报写 `s`。这四段检验的是局部视图的一次分支合流，不覆盖循环回边或调用方持有者。

## 30. 循环回边：第二轮才到达读出位置的来源

局部视图 `h` 初始借 `o`，`mid` 初始借 `m`。循环体 `while (*) { h = mid; mid = V(&s) }` 先把 `mid` 的当前值复制给 `h`，再改写 `mid`。因此零轮退出时 `h` 借 `o`，一轮退出时借 `m`，两轮及以上退出时才借 `s`。循环后只从 `h` 读：`val e = readV(&h)`。

在 `use(e)` 前，分别写 `o`、`m`、`s` 都按 K1 拒绝，写无关的 `x` 接受；把三个来源的写都放在 `use(e)` 后也接受。将同一程序的 `while (*)` 换为 `if (*)`，保留零轮和一轮出口，只有写 `s` 从拒绝变为接受。另在测试进程内将检查器的来源传播限制为一次合流，保留原程序的循环活性分析，也恰好只漏报写 `s`。这五段程序区分一次扫描与跨回边传播，不证明任意循环都能正确收敛。

## 31. 分支流入调用方：不读回持有者

`h` 是调用方交入的 `inout V`。只在 `if (*)` 的一条路径执行 `setV(h, s)`，此后不再访问 `h`，也不产生读回的借用。合流后写 `s` 仍按 K4 拒绝：即使本函数不再使用 `h`，调用方的 `h` 也可能已持有 `s`。同一合流状态还用于核对函数签名：若不声明 `flows s into h`，即使合流后什么也不做，也在签名处按 K6 拒绝。

两项接受对照区分限制的范围：合流后写无关的 `x` 可以；在从未执行放入的 `else` 分支内写 `s` 也可以。去掉 `setV(h, s)` 后四段全都接受。这里验证的是 K10 的可能来源、K20 的调用方存活和 K6 的流向核对在同一个出口上的组合，不是新的借用规则。

## 32. 分支流入带 `deinit` 的局部持有者：在哪个调用处失败？

`g` 先借 `o`，其 `deinit Guard` 读取 `this.a.len`。只有 `then` 调用 `setGuard(&mut g, &s)`。每条正常路径都执行 `release(move g)`，因此正常离开函数时不再拥有 `g`。生成器交叉改变 `s` 与 `g` 的声明顺序，以及另一可失败调用 `mayFail()` 的位置，共 8 段程序。

| 声明顺序 | 放入调用 `setGuard` | `mayFail` 在写入分支、放入之后 | 在未写分支 | 在合流后、移走前 | 在移走后 |
|---|---|---|---|---|---|
| `s` 先于 `g` | 接受 | 接受 | 接受 | 接受 | 接受 |
| `s` 晚于 `g` | K22 | K22 | 接受 | K22 | 接受 |

表中结论针对**调用点**：最后一行的四段程序都在 `setGuard` 处报 K22，因为调用可能先写入、再失败。合流后的 `mayFail` 仍要考虑已写入的路径；未写分支里的 `mayFail` 不继承另一个分支的流向。移走 `g` 后，本函数不再对它负责。来源先声明时，逆序清理先析构 `g`，再析构 `s`，不发生冲突。

独立进程中仅关闭失败出口检查，8 段均接受；保持此设置再删去 `release(move g)`，只有来源晚声明的 4 段在正常出口报 K9。这区分了正常出口与 K22，不验证析构过程中再次失败的政策。

## 33. 三个借用字段：从外层读回底层替换后的来源

`q.link` 独占借用 `h`，`h.target` 独占借用 `v`，`v.a` 最初共享借用 `o`。先建完整链，再执行 `q.link.target = V(&s)`：整体替换的是唯一的 `v`，不是通过 `flows` 保守并入。分别直接取 `&q.link.target.a.len` 和经 `readOuter(&q)` 返回（合同为 `from q.link.target.a`）。两种读法各有三个对照：读出的 `e` 最后使用前写 `s` 报 K1，写原来源 `o` 接受；最后使用后写 `s` 也接受。

**发现的是误拒绝，不是漏报。** 旧原型在两种读法上都保护了 `s`，但对写 `o` 也报 K1。中间视图构造时携带的来源副本仍指向 `o`；查到 `v` 的当前字段后再与该副本取并集，已经被替换的来源就回来了。修正在局部变量直接构造时避免保存这类副本：独占字段显式借用同类型的完整本地视图（`&mut v`）时，保留字段自己的借用，只省去外层类型能按 K20 重新展开的具名路径。`val k = move h` 把整份视图移入新局部变量时转移原账，不把为读出而展开的字段重新存回去。同一组六段在移动中间视图后仍得出相同结论。没有从读取到的来源集合反推一个精确地址。变异对照：只读外层持有者的记录、不沿路径现查时，经调用返回会漏报写 `s`。本节不证明递归类型或任意深度路径的精度。

**为什么不能在读回时一律取代副本。** `expose(borrow x: W): P from x` 可以返回 `P(&x.inner)`。在调用处，`from x` 给的是来源 `w`，不是 `p.target` 的精确地址 `w.inner`。若把 `w` 当作 `V` 的账本，会把找不到的 `a` 当成空来源，漏报写 `s`。另加两段合同对照：经 `readP(&p)` 读出后，在 `use(e)` 前写 `s` 须报 K1，之后写则接受。K11 调用结果的记录保持不变。

**递归折叠边界也不是可重建的字段。** 对 `N(inout next: N, borrow data: Arr)`，外层只展开 `next`、`data`。`second(&h)` 按 `from n.next` 读出 `h.next.data` 后再整体替换 `h.next`，之前读出的结果仍须保护替换前的来源。两段手写对照分别在 `use(e)` 前后写旧来源：前者报 K1，后者接受。不能因为所指是本地视图就裁剪折叠边界之外的 `next.data`。

## 34. 合流后的三个借用字段：底层视图有两个可能的拥有者

`left = V(&l)`、`right = V(&r)` 是两个不同的本地视图变量。`h.target` 起初指向 `left`，只在 `if (*)` 的写入分支将 `h` 替换为 `H(&mut right)`。合流后才构造 `q = Outer(&mut h)`。与 §29 不同，这里需要沿 `q.link.target.a` 到两个可能的拥有者上取来源，不是对同一个 `V.a` 合并两份值。

直接取 `&q.link.target.a.len` 和经 `readOuter(&q)` 返回各有四段：在最后一次 `use(e)` 前写 `l` 或 `r` 分别按 K1 拒绝；此时写无关的 `x` 接受，最后使用后写 `l`、`r` 也接受。删去条件写入时，只有写 `l` 被拒绝；将条件写入改为无条件写入时，只有写 `r` 被拒绝。这排除了“不管哪条路径可达，一律保护两个来源”的解释。

不沿路径现查、只取外层记录的变异会漏报两段经调用返回后写来源的程序。当前原型不需修改。本节只验证多目标的**读回**，没有经这个多目标路径写入新来源。

## 35. 经多目标路径写入后，分别从两个拥有者读回

沿用 §34 的分支：`h.target` 可能指向 `left` 或 `right`，各自原先借用 `l` 或 `r`。合流后执行一次 `q.link.target = V(&s)`，再直接从 `readV(&left)` 或 `readV(&right)` 读出 `e`。赋值只替换实际所指的一个视图；对任一拥有者来说，必须同时考虑它被替换和未被替换的路径。

| 读回位置 | `use(e)` 前不可写（K1） | `use(e)` 前可写 |
|---|---|---|
| `left` | `s`、`l` | `r` |
| `right` | `s`、`r` | `l` |

最后一次使用后，两侧各自的新旧来源都可写。固定分支后，选中侧只保护 `s`，未选中侧只保护自己的旧来源。两侧各四段程序，不需要新规则；这里验证的是本地整体赋值，不是调用合同 `flows`。

## 36. 经同一路径调用 `setV`：唯一目标也不解除旧来源

把 §35 的整体赋值换成 `setV(q.link.target, &s)`，其余程序不变。左右两侧仍有可能被选中时，两种写法给出相同诊断：从某一侧读出的借用保护 `s` 和本侧旧来源，不保护另一侧旧来源。最后一次使用后，两处写入都可放行。单看这 8 段不能区分替换与并入。

固定路径才看得出差别。若始终选 `left`，经 `readV(&left)` 读出后，本地赋值允许写 `l`，`setV` 则按 K1 拒绝写 `l`；两种写法都拒绝写 `s`。若从未选中的 `right` 读回，两种写法都只保护 `r`。固定选 `right` 时左右对称。虽然 `setV` 的函数体执行整体替换，调用者只能依赖 `flows s into v`：它说明新来源可能流入，并未承诺旧来源已解除。

## 37. 先调用再合流：未执行调用的拥有者不接收新来源

`h` 起初选择 `left`。左分支构造 `q = Outer(&mut h)` 并执行 `setV(q.link.target, &s)`；右分支只把 `h` 改为指向 `right`。这与 §36 的区别是调用位置：§36 在选择目标之后才调用，两侧都有可能接收 `s`；本节执行调用时只可能写 `left`。

合流后从 `left` 读回，最后使用前写 `s` 或 `l` 按 K1 拒绝，写 `r` 接受；从 `right` 读回则只有写 `r` 被拒绝，写 `s` 和 `l` 都接受。两侧借用在最后一次使用之后都不再限制写入。固定为只走右分支时，两个拥有者都只保护自己的旧来源；固定为只走左分支时，只有 `left` 多保护 `s`。这验证了 K10 合并各拥有者在可达路径上的记录，不会把流向追记到未执行调用的目标上。

## 38. 两条分支都调用 `setV`：来源按拥有者合并

左分支经 `a.link.target` 向 `left` 放入 `s`；右分支把 `h` 改指 `right`，再经 `b.link.target` 向 `right` 放入 `t`。合流后从具体拥有者读回，不再使用 `h`。在 `use(e)` 前逐一写四个来源，结果如下：

| 读回位置 | 拒绝写入（K1） | 允许写入 |
|---|---|---|
| `readV(&left)` | `l`、`s` | `r`、`t` |
| `readV(&right)` | `r`、`t` | `l`、`s` |

每侧另有一段在最后使用后写本侧新旧来源，均接受。固定为只走左分支时，右侧只保护 `r`；固定为只走右分支时，左侧只保护 `l`。这 10 段及其单路径对照区分了按拥有者合并与不分目标地合并两条流向；未检验合流后经 `h` 再次写入。

## 39. 在类型自己的方法中拆开 `own this`

`Z1.lk` 用 `in Conn` 表示类型作者的成员边界（不是模块系统）。K25 在此切片仅接受普通带 `deinit` 的类：首参为 `own this: Conn`，每个字段为按值、不携带来源的类值，并按声明顺序各绑定一个新名字。`open this as sock, buf` 消费完整的 `this`，不执行 `Conn.deinit`。之后使用 `this` 报 K8；若 `this.sock` 的借用在拆开后仍有使用，拆开处报 K1。调用点也核对具体类的按值形参：`close(&x)` 或移交错误的类均报 TYPE；`close(move x)` 后再用 `x` 报 K8。重复形参不能覆盖接收者，同名类型参数也不能冒充具体类。整体赋值不能把借用放进具体类的拥有槽位；构造器也拒绝把借用装进具体按值类字段，而移动拥有值来构造后仍可拆开。`Z1.lk` 也覆盖了三个类型不符的入口：给按值类字段写入借用（TYPE）、经 `inout` 把借用写入槽位（X1），以及返回与声明不符的具体类（TYPE）。具体类的 `inout` 槽位比较完整类型，不只比较名字：`inout Conn` 拒绝同名的 `fn Conn`（X1），接受移入拥有的 `Conn`。对 `fn Conn` 取 `&mut` 时保留 `fn` 标记：该槽位接受同签名的函数值，拒绝同名的类值。其他槽位的判断不变。把具名函数当作 `fn` 实参时，具体 `own` 形参必须与合同的名义类型一致（K12）。非成员、共享接收者报 K25；`deinit` 自身不能拆开 `this`（K24）。

析构程序只有一次 `open`。紧随其后的调用失败时按 `buf, sock` 清理；把 `sock` 移交给第二个调用后，其失败出口和正常出口都只清理 `buf`。仅在首个失败出口删去 `sock` 的清理，独立检验器报 V1。未验证携带来源的字段或泛型实例、标量字段、不同失败政策及 `replace`。

## 40. 只在一条分支拆开 `this`

`Z2.lk` 在一臂执行 `open this as sock, buf`，另一臂仍可借用完整的 `this`。两臂内的调用失败时，拆解臂清理 `buf, sock, outer`，未拆解臂清理 `outer, this`。拆解臂正常结束时在块内清理 `buf, sock`；合流后的调用失败或函数正常退出时，先清理 `outer`，再仅在仍拥有 `this` 的路径上析构它。合流后读 `this` 的对照在使用处报 K8。

现有合流和析构标志足以生成上述计划，不改检查器。变异对照分别去掉正常出口的 `this` 标志（拆解臂报 V2），以及合流后失败清单中的 `this`（未拆解臂报 V1）。这里只验证一次双臂合流及默认配置下的调用失败清理，未验证析构函数体自身失败或携带来源的字段；循环对照见 §41。

## 41. 循环拆解与重建 `this`

`Z3.lk` 在循环体开头拆解 `this`。若未在回边前恢复所有权，第二次分析循环体时 `this` 已是可能移走，拆解处报 K8。若每轮用移出的 `sock` 和 `buf` 重建 `this`，回边和零轮路径都拥有完整值，循环后可以读取它，最终无需析构标志。

循环体内、重建前的调用失败时，按 `buf, sock` 清理，不析构原 `this`；循环后的调用失败或正常返回时清理完整的 `this`。独立检验器枚举零、一、两轮及调用成败。删掉最终析构，零轮正常退出报 V1；删掉重建前失败清单中的 `sock`，第一轮重建成功、第二轮调用失败的见证报 V1。不改检查器；未验证携带来源的字段或析构函数体自身失败；条件重建见 §42。

## 42. 循环回边要求两臂都重建 `this`

`Z4.lk` 的两段对照分别只在左臂、只在右臂重建。两者都在 `open` 处报 K8：任一臂不重建，下一轮的入口就不能保证仍拥有 `this`。两臂都重建时，循环后可读 `this`，失败清理也无需析构标志。

左臂在重建前调用，失败时按 `buf, sock` 清理；右臂在重建后调用，失败时只清理完整的 `this`。检验器枚举零至两轮及分支和调用成败。分别删掉左臂的 `sock` 或右臂的 `this` 清理，均在首轮成功重建、第二轮进入被改动的臂并调用失败时得到 V1 见证。不改检查器；此处只检验普通按值类字段和调用失败，不检验析构函数体自身失败。

## 43. 按值拆出携带共享来源的视图

`Z5.lk` 的 `Holder` 是带 `deinit` 的视图，按值持有 `Slice` 和 `File`。此切片只新增一种可拆字段：没有 `deinit` 的普通视图，内部仅有一个指向不携带来源的普通类值的共享借用。`open` 消费 `this` 时，把 `slice.source` 的 loan 集合改用新绑定下的键 `source` 保存，不创建新 loan，也不把来源留在已消费的 `this` 名下。

用本地 `a` 构造接收者后，拆出的 `slice` 还会读取 `a` 时，经 `&mut a` 写入在调用处报 K1；最后一次读之后可写。原接收者自带的 `this.slice.source` 可以按原合同返回；省略 `from` 或换成本地来源后返回，均在返回处报 K6。拆出的 `file` 和 `slice` 在正常退出及调用失败时都按逆声明序清理；只删掉失败清单中的 `slice`，检验器报 V1。独占子视图仍报 K25；未覆盖递归、容器、带析构的子视图或循环里的来源转移；单臂拆解见 §44。

## 44. 单臂拆出共享视图时的来源与清理

`Z6.lk` 只在左臂用本地 `a` 重建 `Holder`，随后拆出 `slice` 和 `file`。左臂读 `slice` 之前经 `&mut a` 写入报 K1，读后可写。右臂保留原接收者，继续读其参数来源，不限制对无关本地 `a` 的写入。合流后也可写 `a`：左臂的视图已退出，右臂的接收者从未借用 `a`。

臂内首次调用失败时，左臂按 `file, slice, a` 清理，右臂按 `f, a, this` 清理。合流后调用失败时清理 `f?, a, this?`（问号表示仅在仍拥有的路径上清理），不再清理块内绑定。变异分别漏掉左臂失败清单中的 `slice` 和合流后失败清单中的 `this`，各自得到 V1，见证分别落在左臂首次调用失败与右臂成功后合流调用失败。不改检查器；没有验证两臂共享同一个来源；视图移到分支外的对照见 §45。

## 45. 把拆出的共享视图移到分支外

`Z7.lk` 的外层 `out` 初始借用 `b`。拆解臂把携带来源 `a` 的 `slice` 移入 `out`，另一臂保留初值。合流后，在最后一次读取 `out` 前写 `a` 或 `b` 均报 K1，读取后两者均可写。只走拆解臂时只保护 `a`；只走空臂时只保护 `b`。两项单路径对照用同一写入点区分赋值替换和分支合流。

臂内移交后调用失败时清理 `file, out, b, a`，不再清理 `slice`。合流后清理 `out, f?, b, a, this?`。只漏掉臂内失败清单的 `out` 会报 V1，见证落在移交完成后、臂内调用失败时。不改检查器；此处只检验外层绑定的本地整体赋值，经调用转交的对照见 §46。

## 46. 经 `flows` 移交拆出的视图

`Z8.lk` 的 `deliver` 拆出 `slice` 后，将它按值交给 `put`，由 `put` 经 `inout dst` 写入调用方的槽位。`deliver` 声明 `flows this.slice.source into dst` 时接受；省略声明则在方法签名处报 K6。调用者仍按合同把来源 `a` 并入 `dst`，不因 `put` 的实现确实替换了旧值就解除旧来源 `b`。最后一次读取 `dst` 前，写 `a` 或 `b` 均报 K1；读后均可写。

若 `put` 调用失败，`slice` 已移交，`deliver` 只清理 `file`；删掉该清理，检验器在参数绑定成功、`put` 调用失败时报告 V1。外层调用者若在 `deliver` 调用处失败，按 `dst, b, a` 清理，不再清理已经移交的 `f`。两个函数的析构计划分别验证，不是跨函数展开执行。无需修改检查器；独占子视图未验证；单臂调用见 §47。

## 47. 只在一臂移交拆出的视图

`Z9.lk` 仅在左臂调用 `deliver`。在最后一次读取 `dst` 前，合流后写 `a` 或 `b` 均报 K1。固定走调用臂也拒绝两处写入：即使没有合流，`flows` 也不解除旧来源 `b`。固定走空臂则只拒绝写 `b`；合流后最后一次读取结束，两处写入都接受。

臂内 `deliver` 调用失败时按 `dst, b, a` 清理，`f` 已移交。合流后调用失败时按 `dst, f?, b, a` 清理，只有空臂仍拥有 `f`。分别漏掉臂内失败清单的 `dst` 和合流后失败清单的 `f`，检验器在对应调用失败的两条路径上报告 V1。不改检查器；只验证调用者这一层的析构计划，不跨函数展开。

## 48. 两臂向同一个槽位移交不同来源

`Z10.lk` 的 `dst` 初始借用 `old`。左臂经 `deliver` 并入 `a` 并移交 `f`；右臂并入 `b` 并移交 `g`。最后一次读 `dst` 前，合流版对 `a, b, old` 的写入均报 K1；固定左臂只保护 `a, old`，固定右臂只保护 `b, old`。合流后读完再写，三个写入都接受。

移交调用失败时，左臂按 `dst, g, old, b, a` 清理，右臂按 `dst, f, old, b, a` 清理；合流后的失败清单是 `dst, g?, f?, old, b, a`。分别漏掉两个臂内清单中仍归调用方的 `File`，检验器在对应臂的移交失败路径报 V1。无需修改检查器；本节只验证同一个目标槽位和调用者的析构计划。

## 49. 两臂移交到不同槽位时按拥有者合流

`Z11.lk` 的 `left`、`right` 起初分别借用 `l`、`r`。左臂经 `deliver` 把 `a` 并入 `left`，右臂把 `b` 并入 `right`。合流后若只读 `left`，在读前写 `a` 或 `l` 报 K1，写 `b` 或 `r` 则接受；只读 `right` 时对称。把写入移到最后一次读之后，四处都接受。两个新来源不因合流而混入同一个槽位的来源集合。

左臂调用失败时保留 `g` 的析构义务，右臂则保留 `f`。合流后的调用失败时，依次清理 `right, left, g?, f?, r, l, b, a`。分别删掉合流清单中的 `g?` 或 `f?`，检验器在相应臂调用成功、合流调用失败的路径报 V1。无需修改检查器；只覆盖两个直接的本地槽位，不涵盖跨函数展开的清理；经别名选择目标见 §50。

## 50. 经别名移交时仍按实际槽位记来源

`Z12.lk` 用同一个 `target` 独占借用传参：左臂沿用指向 `left` 的借用，右臂先改指 `right` 再调用。合流后读 `left` 只保护 `{a, l}`，读 `right` 只保护 `{b, r}`。固定左臂时，未选中的 `right` 只保护旧来源 `r`；固定右臂时，未选中的 `left` 只保护旧来源 `l`。三种路径中，每一侧读完再写四个来源均接受。

臂内及合流后的失败清单与 §49 相同。`target` 不是拥有绑定；在任一臂的移交失败清单里漏掉该臂选中的槽位，检验器在对应臂报告 V1。无需修改检查器；本节只验证在臂内选定别名并调用，先合流再经别名移交见 §51。

## 51. 先合流再经别名移交

`Z13.lk` 先经分支让独占借用 `target` 在合流后可能指向 `left` 或 `right`，再在合流后把拆出的共享视图 `Slice(&a)` 经 `deliver(..., target)` 移交。合流后读 `left` 保护 `{a, l}` 而不保护 `r`，读 `right` 保护 `{a, r}` 而不保护 `l`；固定不改指（只指 `left`）时 `right` 只保护 `r`，固定改指（只指 `right`）时 `left` 只保护 `l`。三种路径在最后一次读完后写入三个来源均接受。

合流后无条件调用 `deliver`，消费 `f` 不需要析构标志；`deliver` 与随后的 `mayFail` 在失败时均按 `right, left, r, l, a` 清理。在 `deliver` 的失败清单中分别漏掉 `left` 或 `right`，检验器在经过分支后该调用失败的路径报 V1。无需修改检查器；至此单共享借用视图的 `open` 移交已覆盖直线、分支与合流后别名，独占子视图见 §52。

## 52. 按值拆出携带独占借用的单字段视图

`Z14.lk` 的 `MutHolder` 是带 `deinit` 的视图，按值持有 `MutSlice(inout source: Arr)` 和 `File`。放开 `open` 接受单 `inout` 借用字段的非递归普通子视图（多字段视图仍在 `Z5.lk` 报 K25）：`open this as slice, file` 把 `this` 名下的独占来源转移到新绑定 `slice.source` 下，不新建 loan 也不留在已消费的 `this` 名下。

用本地 `a` 构造接收者并拆解后，在最后一次使用 `slice` 前读 `a` 或写 `a` 均报 K1，经 `slice.source` 写 `a` 接受；最后一次使用后读、写 `a` 均接受。对拆出的独占视图做隐式复制报 K8。原接收者的独占来源既可按 `from this.slice.source` 转发 `inout Int`，也可按值返回 `move slice` 并由调用方继续保护原存储；省略 `from` 或换成本地来源后返回均报 K6。正常退出与调用失败均按 `file, slice` 清理；只漏掉失败清单中的 `slice`，检验器在调用失败时报 V1。单臂拆解与移出分支见 §53。

## 53. 独占子视图的单臂拆解与移出分支

`Z15.lk` 检验两类本地分支场景。其一，只在左臂用本地 `a` 重建 `MutHolder` 并拆出 `slice` 与 `file`：臂内最后一次使用 `slice` 前，读 `a` 与写 `a` 均报 K1，之后可读写；右臂保留原接收者，不限制对无关本地 `a` 的读写；合流后同样可读写 `a`。臂内与合流后的失败清理分别为 `file, slice, a`、`f, a, this` 与 `f?, a, this?`；漏掉左臂的 `slice` 或合流后的 `this`，检验器在对应路径报 V1。

其二，外层 `out` 初始独占借用 `b`，左臂拆出携带 `a` 的 `slice` 并经 `out = move slice` 移到分支外。合流后在最后一次使用 `out` 前，读、写 `a` 与读、写 `b` 均报 K1；固定走左臂时整体赋值解除旧来源 `b`，仅读、写 `a` 报 K1；固定走右臂时仅读、写 `b` 报 K1；使用完 `out` 后四处均接受。臂内移交后的失败清单为 `file, out, b, a`（不再清理已移走的 `slice`），合流后为 `out, f?, b, a, this?`；漏掉臂内清单的 `out` 报 V1。无需修改检查器；独占子视图经 `flows` 移交调用方槽位见 §54。

## 54. 独占子视图经 `flows` 移交到调用方槽位与合流别名

`Z16.lk` 的 `deliverMut` 拆出 `MutSlice` 后按值交给 `putMut`，声明 `flows this.slice.source into dst` 时接受，省略声明在签名处报 K6。直线移交后，`flows` 合同只并入来源、不解除旧独占来源 `b`：在最后一次使用 `dst` 前，对 `a` 与 `b` 的读、写均报 K1；使用完后四处均接受。

在合流后经独占别名 `target` 移交的场景中，`target` 在分支后可能指向 `left` 或 `right`。合流后使用 `left` 前读、写 `a` 与 `l` 均报 K1，读、写 `r` 接受；使用 `right` 前读、写 `a` 与 `r` 均报 K1，读、写 `l` 接受。固定只指 `left` 时 `right` 仅保护 `r`，固定只指 `right` 时 `left` 仅保护 `l`；最后一次使用后均接受。`deliverMut` 失败时仅清理 `file`（漏掉报 V1）；调用者中 `deliverMut` 与随后的 `mayFail` 失败时均按 `right, left, r, l, a` 清理（漏掉 `left` 或 `right` 报 V1）。无需修改检查器；至此单借用字段（共享与独占）子视图的 `open` 主线已覆盖，多字段与按值嵌套子视图见 §55。

## 55. 按值拆出多借用字段与按值嵌套的非递归子视图

`Z17.lk` 的 `DeepHolder` 按值持有 `Nested(inner: MixPair, borrow tail: Arr)` 和 `File`，其中 `MixPair(borrow ro: Arr, inout rw: Arr)` 同时携带共享与独占借用字段。放开 `open` 接受非递归、无 `deinit` 的多借用字段及按值嵌套子视图（递归子视图在 `Z5.lk` 报 K25，带 `deinit` 的子视图在 `Z17.lk` 报 K25）：`open this as nested, file` 剥离顶层字段前缀 `nested.` 后，把 `inner.ro`、`inner.rw`、`tail` 三条路径各自的来源账独立移交给 `nested`。

本地构造并拆解后，在最后一次使用 `nested` 前：`a` 与 `c` 可读不可写（K1），`b` 不可读也不可写（K1），使用完后三者均放行；因按值含独占子视图，对 `nested` 隐式复制报 K8。合同转发精确到字段路径：`from this.nested.inner.ro` 与 `from this.nested.inner.rw` 分别接受，跨字段错声明或返回本地来源均报 K6。经 `flows this.nested.inner.ro into dst` 仅移交共享子字段时，调用方只保护 `a` 与旧来源 `old`，不误保护无关字段 `b` 与 `c`。调用失败与正常退出按 `file, nested` 清理；漏掉失败清单中的 `nested`，检验器报 V1。越过借用字段嵌套的子视图在 `Z17.lk` 报 K25；带 `deinit` 的子视图见 §56。

## 56. 按值拆出带 `deinit` 的非递归子视图

`Z18.lk` 的 `GuardHolder` 按值持有带 `deinit` 的子视图 `GuardSlice(borrow source: Arr) deinit`（且写出 `deinit GuardSlice` 函数体）与 `File`。放开 `open` 接受带 `deinit` 的非递归按值子视图后，`open this as guard, file` 只解除外层 `GuardHolder.deinit`，拆出的 `guard` 仍保留自身的 `GuardSlice.deinit` 义务。

因 `GuardSlice` 析构可观察，拆出后即使不再使用 `guard`，写其本地来源 `a` 仍报 K1；先经 `releaseGuard(move guard)` 移走后则可写 `a`。本地 `a` 先于 `open` 声明时，`guard` 在逆序清理中先于 `a` 析构，正常退出与 `mayFail` 均接受；若把借用较晚局部 `late` 的 `guard` 移入更早声明的 `out`，则在 `mayFail` 报 K22、函数出口报 K9。只在一条分支移走 `guard` 时，合流后保留析构标志 `guard?`，正常退出与 `mayFail` 的清理清单均为 `file, guard?`。检验器真实执行 `deinit GuardSlice`：在合流失败清单中漏掉 `guard?` 报 V1，在正常退出去掉条件标志报 V2。越过借用字段嵌套的子视图见 §57。

## 57. 按值拆出越过借用字段嵌套的非递归子视图

`Z19.lk` 放开 `open` 接受借用字段指向另一非递归非容器视图的子视图（递归子视图仍在 `Z5.lk` 报 K25，容器子视图在 `Z17.lk` 报 K25）。`RoLink(borrow inner: Slice)` 拆出后同时保护外层借用的 `s` 与内层借用的 `a`（写任一者均报 K1，读 `a` 接受，使用后均放行）；经 `RoOverMut(borrow inner: MutSlice)` 写内层独占字段报 K1；合同转发 `from this.link.inner.source` 接受，省略报 K6。

`RwLink(inout inner: Slice)` 拆出后，经 `link.inner = Slice(&b)` 整体替换唯一本地底层视图 `v` 时，按 K20 清掉 `link` 上的过期副本并从 `v` 现查：随后经 `readRwLink(&link)` 读回只保护新来源 `b`（K1），旧来源 `a` 已解除。若 `own this` 的参数来源经 `open` 后执行 `link.inner = Slice(s)`，流向记在 `this.link.inner.source` 下：声明 `flows s into this.link.inner` 时接受且调用方直接从原 `v` 读回保护 `a` 与 `b`（K1），省略流向在签名处报 K6。调用失败与正常退出按 `file, link` 清理，漏掉 `link` 报 V1。容器子视图与递归子视图见 §58。

## 58. 按值拆出容器子视图与递归子视图

`Z20.lk` 放开 `open` 接受非内部可变、非线程绑定的按值容器子视图（`view class Bag<view T>`）与递归子视图（`view class Node(borrow next: Node, borrow data: Arr)`）；顶层直接借用字段（`Z5.lk`）与内部可变子视图（`Z17.lk`）仍报 K25。

**发现并修掉两处容器记账边界。** 其一，容器作为外层视图的按值字段时来源记在字段名下（`held["bag"]`），拆成独立变量后必须放回 `"*"`，否则拆出的容器丢账；其二，`Checker.borrow` 此前只对 `kind in ("view", "opaque")` 复制携带来源，因容器的 `type_of` 为 `cls`，经 `&bag` 调用声明 `from bag.origins` 的函数时会丢掉 `"*"` 来源，已一并补上 `self.carrier(res.ty.name)`。

容器侧：拆出 `bag` 后，经 `peekBag(&bag)`（`from bag.origins`）读出的借用在最后一次使用前写原来源 `a` 报 K1，使用后可写；按 `from this.bag` 转发 `peekBag(&bag)` 接受，省略 `from`、返回本地来源，或返回依赖局部容器自身的 `peekBagSelf(&bag)`（`from bag`）均报 K6。递归侧：拆出三层链 `node` 后，`third(&node)`（`from n.next`）保护深层来源 `a`（K1）而不误保护顶层 `c`，使用后可写；按折叠边界 `from this.node.next` 转发 `&node.next.data.len` 接受，错声明 `from this.node.data` 报 K6。两类子视图的调用失败与正常退出均按 `file, bag` / `file, node` 清理，漏掉子视图均报 V1。顶层直接借用字段见 §59。

## 59. 按值拆出顶层直接借用字段

`Z21.lk` 放开 `open` 接受视图的顶层直接 `borrow` / `inout` 字段（顶层借用容器及 `local`/`cell` 子视图分别仍在规则、`Z5.lk` 与 `Z17.lk` 报 K25）：`open this as source, file` 将直接借用字段绑定为 `borrow T` / `inout T` 局部，并把字段自身的 loan 放到 `""` 下、把指向另一视图时的子字段账剥离前缀后一并带入。在析构义务检验器一侧（`drop_plan.py`），`open` 拆出的无析构义务占位字段（`"&"`）记为 `borrowed`，不产生虚假的 V1 泄漏，其余拥有字段仍须履行析构义务。

`RoDirect(borrow source: Arr, file: File)` 拆出后，最后一次使用 `source` 前写 `a` 报 K1、读 `a` 接受，使用后可写；按 `from this.source` 转发接受，省略报 K6。`RwDirect(inout source: Arr, file: File)` 拆出后，使用前读、写 `a` 均报 K1，经 `source` 写及使用后读写均接受；转发 `inout Arr` 须声明 `from this.source`，返回本地来源报 K6。`ViewDirect(inout inner: Slice, file: File)` 拆出后，经 `*inner = Slice(&b)` 替换唯一本地视图 `v` 时解除旧来源 `a`、保护新来源 `b`（K1）；改写调用方视图时须声明 `flows s into this.inner`（省略报 K6），调用方从原 `v` 读回保护新旧来源（K1）。调用失败与正常退出仅清理拥有字段 `file`，漏掉 `file` 报 V1。留下空值的 `replace` 见 §60。

## 60. 留下空值的 `replace`（K26）

`Z22.lk` 在借用原型中接通 `empty` 类型标记与 `replace p`（规则 K26），与析构义务检验器（`drop_plan.py`）的 `replace` / D8 对齐。`replace p` 要求 `p` 为一层按值字段且字段类型声明了 `empty`（无来源普通类）；对未声明 `empty` 的字段或借用字段均报 K26。`replace p` 对 `p` 按写访问判借用冲突：经共享借用调用报 K1，字段被借用期间报 K1，同对象上不相交的另一字段被借用时接受，经 `inout` 参数调用接受。

与部分移出（K23）不同，`replace` 在原处留下空值，原对象保持完整且不记入 `gone`：既可用于带 `deinit` 的类型（包括普通函数与 `deinit` 函数体），也可在循环中反复执行而不触发回边 K8。对本函数拥有的对象，检查器发射 `DP.Stmt("replace")` 与移交，使新绑定 `n` 与原对象 `u` 各自保有独立析构义务；`mayFail` 失败清单为 `n, u`，检验器真实执行 `deinit Unlinker`：漏掉较晚的 `n` 同时报 V4（逆序违规）与 V1（泄漏），漏掉较早的 `u` 报 V1。携带来源的 `empty` 视图字段见 §61。

## 61. 携带来源的 `empty` 视图字段 `replace`

`Z23.lk` 将 `replace p`（K26）扩展到非 `cell`、非 `local`、非 `carrier` 的 `empty` 视图字段（如 `OptSlice`、`OptMutSlice`、`OptGuardSlice deinit`）。`replace` 将该字段的来源账随取出值移交；当被替换的存储目标唯一（`len(targets) == 1`）时，按 K20 清空原槽位在该字段路径下的来源账（经借用到达时同时清除借用上的过期副本），否则（如合流后的多目标别名）保守保留各可能拥有者的旧来源。

在带 `deinit` 的 `DualHolder` 上，`val taken = replace h.first` 后：`taken` 存活期间保护 `a`（K1），用完后即使 `h` 仍活到作用域结束，`a` 也已解除、可写，而 `h.second` 仍保护 `b`（K1）。对独占视图 `OptMutSlice`，`taken` 存活期间对 `a` 的读与写均报 K1，用完后均放行。对带 `deinit` 的 `OptGuardSlice`，`taken` 活到析构点，用完后写 `a` 仍报 K1，经 `releaseOptGuard(move taken)` 移走后可写；失败清单为 `taken, h, a`，漏掉 `taken` 报 V1 与 V4，漏掉 `h` 报 V1。经 `inout` 参数 `replace h.first` 转发来源时，声明 `from h.first` 接受，错声明 `from h.second` 报 K6。合流别名 `target` 可能指向 `left` 或 `right` 时，`taken` 用完后两侧旧来源仍受保护；固定单目标时只解除被替换侧。`cell`/`local` 子视图的 `open` 仍未验证。
