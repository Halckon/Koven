# 借用内核演算（内核 MVP 第 1–3 步）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；规则为草案，原型已实现并通过 §5、§9–§22 的用例（2026-11-15），不构成健全性证明 · **读取时机**：实现或评审借用内核的参考检查器原型时；核对 [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R1 的验证用例时 · **唯一真源**：本页维护演算的语法、判定规则与用例清单；模型的来由见[演进总纲之二](evolution-02-route-loan-kernel.md) §2，现行借用规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权修改编译器。它描述的是目标模型（之二的 L1–L4），不是现行 v0.47 的调用期借用。

## 1. 目的与边界

评审的结论是先验证组合、再冻结内核。本页把之二的借用模型写成一个可以执行的最小演算，用来回答一个问题：
**“两种来源合同加一棵 loan 派生树”能否同时接受该接受的程序、拒绝该拒绝的程序。**

- 范围：评审 §5 的前两组验证——切片、自有字段视图、只读 guard；返回重借、`splitAt`、可变迭代器。
- 方法：一个独立的参考检查器，输入演算程序，输出接受或带位置的拒绝。它基于用例，不是健全性证明。
- 不在本步：泛型与迭代接口（第 2 步）、存在类型（第 3 步）、失败出口与清理义务（第 4 步）、闭包、可空类型、两阶段借用、线程、数值推理、`deinit` 函数体的内容。
- 某个用例必须靠“这个内建类型例外”才能通过时，结论是回到设计，不是给原型加特判。

## 2. 语法

条件一律写作 `*`，表示检查器不对取值做任何推理，两个分支都要检查。

```text
程序    P ::= D* F*
声明    D ::= class C(f: τ, …) [deinit]                 owned 类；deinit 只是一个标记
            | view class V(k f: τ, …)                   k ::= borrow | inout | （无，表示 owned 字段）
函数    F ::= fun g(m x: τ, …): ρ [from o, …] [trusted] { s* return e }
模式    m ::= own | borrow | inout
类型    τ ::= Int | C | V
结果    ρ ::= τ | borrow τ | inout τ | Unit
来源    o ::= x          结果依赖持有者 x 本身            （DependsOn）
            | x.f        结果沿用 x 的借用字段 f 的来源    （Forwards）
语句    s ::= val x = e | p = e | use(p) | g(a, …) | { s* }
            | if (*) { s* } else { s* } | while (*) { s* }
表达式  e ::= n | p | move p | &p | &mut p | C(e, …) | V(e, …) | g(a, …)
place   p ::= x | p.f
```

`use(p)` 是一次读取，只用于标出“这里还在用”。结果为借用的函数，`return e` 按“交出一个借用”求值：返回一个借用值即对它重借。`trusted` 的函数不检查函数体，只信任签名，对应 `unsafe` 实现的库函数。

## 3. 状态

检查器在每个程序点维护：

```text
Loan    = { id, place, kind: Shared | Exclusive, parent: Loan?, site }
Init(x) = Available | Moved | MaybeMoved             按字段细分到 place
Origins(h) = 持有者 h 持有的 Loan 集合                 h 是借用局部、视图实例（按借用字段细分）或调用的结果
Live(h) = h 在该点之后还会被使用                        后向分析
```

- 一个 loan 可以被多个持有者共同持有；只要有一个持有者存活，它就存活。
- 函数体内，每个借用参数与每个视图参数的每个借用字段，各带一个符号 loan，代表调用方那边的来源。

## 4. 规则

| # | 规则 |
|---|---|
| K1 冲突 | 对 place `q` 做种类为 `a` 的访问（读、写、移动、析构）时，若存在存活的 loan `l`，`q` 与 `l.place` 重叠，且 `a` 与 `l.kind` 不相容，则拒绝。相容矩阵沿用 Guide 10。经持有 `l` 的持有者所做的访问不算冲突，除非 K4 |
| K2 建立 | `&p` 在 `p` 上建立 Shared loan，`&mut p` 建立 Exclusive loan。`p` 若是经某个持有者到达的，新 loan 的 `parent` 是那个持有者据以访问的 loan（重借） |
| K3 存活 | loan 存活当且仅当它的某个持有者存活。持有者从定义起存活到最后一次使用，不到作用域结束。**实现时补充**：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活（见 §8 第 1 条） |
| K4 暂停 | 持有者 `h` 持有的 loan `l` 有存活的子 loan `c` 时，经 `h` 对与 `c.place` 重叠的 place 的访问，按 `c.kind` 判冲突 |
| K5 调用 | 对每个实参按参数模式建立 loan：`borrow` 建 Shared，`inout` 建 Exclusive，`own` 是移动。结果的 Origins 由被调方的合同决定：`from x` 则在实参这个 place 上建立一个子 loan 交给结果（结果为 `inout` 时是 Exclusive，否则 Shared）；`from x.f` 则结果取得实参视图的字段 `f` 当前持有的 loan。没有流入结果的实参 loan 在调用返回时结束 |
| K6 合同 | 函数体的返回值持有的每个 loan 必须被签名声明覆盖：落在参数 `x` 自身存储上的，或由借用 `x` 派生的，要求声明 `from x`；属于 `x.f` 的符号 loan 的，要求声明 `from x.f` 或 `from x`（后者更保守，也成立）；落在局部变量上的一律拒绝。初稿末句“结果为 `inout` 且来源是独占视图时只允许 `from x`”已撤销，见 §8 第 2 条与 §9 |
| K7 构造 | `V(e, …)` 的实例在每个 `borrow` 字段上持有实参处建立的 Shared loan，在每个 `inout` 字段上持有 Exclusive loan；实参本身是持有者时，取得它的 Origins |
| K8 移动与初始化 | `move p` 之后 `p` 为 Moved；使用 Moved 或 MaybeMoved 的 place 拒绝。含 `inout` 字段的视图与 owned 类不可隐式复制；只读视图可复制，副本持有相同的 loan |
| K9 析构 | 作用域结束时，仍 Available 的 owner 按声明逆序析构；析构是对该 owner 的一次“析构”访问，按 K1 判冲突。带 `deinit` 标记的类不提前析构 |
| K10 合流 | 分支与循环的合流处：Origins 取并集；Init 取交（一条路径上 Moved 即为 MaybeMoved）；循环迭代到不动点 |
| K11 多结果 | 一次调用产生的子 loan 只有一个；结果若是含多个持有者的值（例如返回两个视图），它们共同持有这一个 loan。它们之间是否不相交不由检查器判断，只对 `trusted` 的函数成立 |

规则与之二的对应：K2、K4、K5 是 R4.4 的改写；K5、K6 是 R3.4 的两种来源写法；K6 末句是 R4.5；K11 是之二“不相交证明不由内核承担”。

## 6. 已知这一步答不了的

- **可同时保留多个独占元素的迭代器**。E1 只覆盖出借式。非出借式需要“独占视图把来源分给多个结果”，K6 末句禁止它，只能靠 `trusted` 签名；它如何进入迭代接口属于第 2 步。
- **转发的可见性**。类型之外的函数写 `from s.source` 时字段名是否总是可见（之二 §6 的建议），演算里没有可见性，答不了。
- **两阶段借用**。`list.push(list.size)` 一类写法现行规则靠 Reserved 状态接受，本步不建模；所有 `inout` 实参一律立即 Active，因此原型会比现行规则多拒绝这类程序。（§22.2 已补。）
- 规则是草案。实现过程中发现规则自相矛盾或某个用例两头都说不通，是这一步最有价值的产出，须记录在本页并回到之二修订。

## 8. 原型得到的发现

写原型的过程中，规则在五处与初稿不同或暴露了问题。前四条需要回到之二确认。

1. **K3 少了一条。** “依赖持有者本身”的结果持有的是视图变量存储上的 loan。初稿只说“持有者存活到最后一次使用”，于是视图在最后一次使用后就算死了，它持有的底层来源随之失效，
   而那个结果可能正指向底层数据（用例 A4：声明 `from this`、实际返回底层元素，这是 K6 允许的保守声明）。补充的规则是：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活。没有它，A4 的第二个函数会被错误地接受。
2. **“独占视图不提供转发”不需要单列为规则。** 越过 `inout` 字段时累加所凭借的 loan，函数体返回的借用就必然带着视图本身这个来源，K6 自然要求 `from this`（用例 G1 的 `leak`）。
   第 2 步进一步发现这条特例必须撤销：受信任的签名需要它所禁止的写法（§9.3 第 5 条）。
3. **父 loan 不随子 loan 延续，比 Rust 宽。** 父持有者死后，子借用只保护它自己所指的那部分存储；同一对象上不相交的字段可以被再次访问（用例 G2 的最后一个函数）。
   Rust 在同样的程序上会拒绝，因为重借使整个父借用保持存活。原型的做法在“字段不相交”成立的前提下是健全的，但这是一个与 Rust 不同的选择，应当明确裁决，而不是由实现默认带入。
4. **按值接收的视图参数上，`from s` 没有意义。** 参数在返回时就死了，“依赖持有者本身”无从谈起；原型把它判为签名错误，只允许 `from s.f`。这正是之二 §6 记下的“转发全部来源”的拼写问题，原型没有解决它。
5. **被覆盖之前不再使用的旧借用不算存活**（F5 接受、F4 拒绝）。这是 K3 的直接后果，初稿的用例清单没有覆盖，我最初写的预期是错的。

原型的近似之处，它们使原型偏保守，不影响上述结论：

- 一条语句之内不区分先后：语句用到的变量在整条语句期间都算存活。
- loan 以建立它的语法位置为身份，循环里同一位置的 loan 合并为一个。
- 不建模两阶段借用；`inout` 实参一律立即生效。（§22.2 已补接收者位置。）
- 一处冲突之后的连带报告没有抑制；用例都写成只触发一处。

仍然没有回答的：这些规则是否健全。原型只说明规则在 29 个用例上给出了预期的结果。

## 9. 第 2 步：泛型、抽象签名与流向

对应评审 §5 的第三组验证（迭代、高阶借用函数、局部的视图容器）与 R6 要求的四种迭代。原型已实现，用例 H1–H6 通过。

### 9.1 增加的语法与规则

```text
函数    F ::= fun [<T, …>] g(m x: τ, …): ρ [from o, …] [flows o into x, …] [trusted] { … }
签名    S ::= sig [<T, …>] N(m x: τ, …): ρ [from o, …] [flows o into x, …]
类型    τ ::= … | T（类型参数）| fn N（合同为签名 N 的函数类型）
来源    o ::= x | x.f | x.origins    x.origins 表示转发 x 携带的全部来源（§12 起改为这个占位，并允许多级路径）
```

| # | 规则 |
|---|---|
| K12 细化 | 把函数 `g` 当作 `fn N` 类型的值使用时，`g` 声明的每个来源与流向都须被 `N` 的声明覆盖。覆盖关系：`x` 覆盖 `x.origins`，`x.origins` 覆盖 `x.f` |
| K13 不透明值 | 类型参数的值携带一组未知的来源，不可隐式复制。按值参数上 `from x` 等同于 `from x.origins`，因为按值参数在返回时已不存在，没有“本身”可依赖 |
| K14 流向 | `flows o into x`：调用之后，`o` 所指的来源由实参 `x` 背后的持有者持有。函数体让某个来源流进了 `inout` 参数而签名没有声明相应的流向，按 K6 拒绝 |

接口方法与函数类型在原型里是同一个机制：一个抽象签名，加上 K12。原型没有接口声明，迭代器的 `next` 以函数类型的参数传入（字典传递）。

| H6 | 高阶借用函数：函数类型的合同 `from r`；实参函数的来源是另一个参数；函数体经函数参数返回未声明的来源 | 接受；拒绝（K12）；拒绝（K6） |

### 9.3 发现

1. **四种迭代对应四种合同，不能归到一个接口。** 按值迭代没有来源；借用外部存储的是 `from it.字段`；多个独占元素并存的是受信任签名上的 `from it.字段`；出借式是 `from it`。
   泛型算法能依据的合同只有两种形状：
   - 出借式合同 `from it`：四种迭代器都满足它，但算法一次只能持有一个元素。逐个处理的算法（遍历、折叠、计数、存在性判断）按它写一次，对全部迭代器可用；`for` 应绑定这一种。
   - 转发式合同 `from it.origins`：算法可以同时持有、返回、收集元素（排序、收集、带前瞻的配对、返回元素的最值）。出借式迭代器不满足它（H4 的最后一个函数）。

   所以标准库需要两个迭代接口，或一个接口加一个区分二者的标记；这回答了评审 R6 “哪些算法可以统一、哪些不能”。之十一 §2.3 已据此拆为 `Iterator` 与 `LendingIterator`（暂名）。
2. **“转发全部来源”的写法是必需的。** 泛型与接口的语境里没有字段名可写，之二 §6 建议的“借用字段名在 `from` 中总是可见”不够用。原型用 `x.origins` 占位，正式拼写待定。按值参数上直接写 `from x` 即可（K13），这同时解决了 §8 第 4 条。
3. **来源合同需要第三种子句：流向。** 没有 `flows`，把视图放进一个已有的容器、收集借用元素都无法检查（H5）。之二把“origin 流入已有持有者”列在 L5 的待定项里；它是迭代与容器的必经能力，不是可选项。结构化并发的 `scope.launch(f)` 需要的是同一个子句。
4. **函数类型必须带来源合同**，并且合同之间有细化关系（H6）。这与接口方法是同一个机制，不需要两套规则。
5. **撤销“独占视图不提供转发”。** 多个独占元素并存的迭代器恰恰需要这种签名，只能由受信任的函数声明；非受信任的函数体写不出来（越过独占字段时累加来源，K6 拒绝）。所以它不是一条规则，而是“只有受信任代码才写得出”的后果。
6. **受信任签名的健全性依赖字段私有。** 探测程序：取出一个独占元素后，直接经迭代器的字段写同一块存储，原型接受。演算没有可见性；真实语言里必须靠“视图的独占字段对类型之外不可访问”来排除它。这是对之四 U0 合同的一条要求。

### 9.4 这一步没有回答的

- **可空元素的歧义**（评审 R6 的前半）：`next()` 返回值的类型怎样区分“元素是 null”与“迭代结束”，是类型表示的问题，不涉及来源，演算检验不了。之十一已改为返回不折叠的和类型。
- **类型参数是否可逃逸**。原型把每个类型参数都当作可能携带来源；“默认带可逃逸上界、显式放弃”这一层没有建模，所以答不了“现有泛型代码是否不受影响”。（§13 已补。）
- 没有检查类型实参与形参是否匹配；没有闭包捕获；没有真正的接口声明与见证。
- 规则是否健全，仍然没有证明。

第 1、2 步的发现已于 2026-11-14 并回[之二](evolution-02-route-loan-kernel.md) §2 与之十一 §2.3。

## 10. 第 3 步：存在类型的载荷访问与槽位访问

对应评审 R2 与[之三](evolution-03-route-existential.md) §2.4。原型已实现，用例 I1–I5 通过。这一步的发现已于 2026-11-14 并回之三 §2.4 与 §5。

记法说明：`any I`、`pack I(e)`、`*x = e` 与调用处的 `&mut` 都是演算自己的记法，不是 Koven 语法，也不是拼写提案。
Koven 里声明侧的 `inout x: T` 与泛型 `fun <T>` 是现行语法（Guide 03、08），调用处的独占标注写作 `&x`；存在类型是 v2 候选，之三的候选写法是直接以 interface 名作类型（`inout s: Shape`），隐式打包。
演算把它写成 `any I` 只为在规则里区分“具体类型”与“存在类型”。

### 10.1 增加的语法与规则

```text
声明    D ::= … | interface I | class C(…) is I, …
类型    τ ::= … | any I（接口 I 的存在类型）
表达式  e ::= … | pack I(e)（把实现 I 的具体类型的值打包为 any I）
语句    s ::= … | *x = e（经独占借用 x 整体替换它所指的值）
```

每个借用值多带一个标记：它是**槽位访问**（所指的存储恰好按它的类型存放）还是**载荷访问**（只知道所指实现了接口 `I`）。

| # | 规则 |
|---|---|
| X0 标记的来由 | 以下三处得到载荷访问：按 `borrow` / `inout` 接收 `any I` 的参数；返回类型为 `borrow` / `inout any I` 的调用结果；视图里类型为 `any I` 的借用字段，以及经它重借出来的借用。对拥有 `any I` 的变量或拥有字段取借用，得到槽位访问。移动、重借与分支合流保留标记 |
| X1 整体替换 | `*x = e` 要求 `x` 是槽位访问，且 `e` 的类型恰为所指类型。给拥有 `any I` 的变量或字段赋值，要求右侧是 `any I`（先 `pack`） |
| X2 槽位不变 | 形参写作 `inout any I` 时，实参所指可以是实现 `I` 的具体类型或 `any I`，被调用方得到载荷访问。形参是具体类型或类型参数 `T` 时，实参须是槽位访问，且 `T` 在一次调用里的各处实例一致 |

X2 的后半是对 `inout` 位置的不变性：`inout T` 既读出 `T` 也写入 `T`，所以所指类型必须恰为 `T`，不能是它的子类型或实现者。

### 10.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| I1 | 按 `inout any Shape` 接收后调用方法；以具体类型的位置或拥有存在类型的变量作实参；在函数体里 `*s = v`；把没有实现接口的类型交进去或打包 | 前两者接受；拒绝（X1）；拒绝（TYPE） |
| I2 | 评审 R2 的反例：`overwrite<T>(inout dst: T, own value: T)`，以 `Circle` 的位置和一个 `any Shape` 的值调用；在接收 `inout any Shape` 的函数里把它转交给 `overwrite`；先移动改名再转交；经 `inout Circle` 写入 `Square` | 全部拒绝（X2、X2、X2、X1） |
| I3 | 拥有存在类型的变量与字段：直接替换；取借用后 `*r = …`；交给 `overwrite`，此时 `T = any Shape`。具体类型的槽位交给 `overwrite`。把未打包的具体值赋给存在类型的变量；经返回 `inout any Shape` 的方法取得访问后整体替换 | 前四者接受；拒绝（X1）；拒绝（X1） |
| I4 | 载荷访问上的借用规则：访问存活时写来源；返回未声明的来源；同一个变量两次按独占交出 | 拒绝（K1）；拒绝（K6）；拒绝（K1） |
| I5 | 视图里存放 `inout any Shape`：经字段调用方法；经字段交给 `overwrite`。把载荷访问交给不做替换的泛型函数 `same<T>(inout x: T): inout T`；经它的结果整体替换；把两个载荷访问交给 `swap<T>`；把两个存在类型槽位交给 `swap<T>` | 接受；拒绝（X2）；接受（§11 的 X4 之后）；拒绝（X1）；拒绝（X2）；接受 |

测试里增加了一条变异检验：去掉 X2 之后 I2 不再被拒绝。

### 10.3 发现

1. **评审 R2 的反例被两条规则排除，且两条都需要。** 直接调用靠“`T` 的实例须一致”（`Circle` 与 `any Shape` 不是同一类型）；经 `inout any Shape` 参数转交靠载荷标记。只做前一条时，转交这条路仍然通，因为在被调用方看来两边都是 `any Shape`。
2. **载荷与槽位是借用值上的一个标记，不是两种类型，也不需要两种拼写。** 之三 §2.4 的结论成立：`inout any I` 的参数总是载荷访问。标记由 X0 的三个来由决定，调用方不需要写任何东西。
3. **标记必须覆盖存进视图的借用。** 第一版原型只在参数上打标记，探测程序把 `&mut circle` 存进字段类型为 `inout any Shape` 的视图，再对该字段取借用交给 `overwrite`，原型接受了——这是一个真实的漏洞，已用 X0 的第三个来由补上（I5）。
   它说明“载荷访问”要跟着借用值走到每一处存放位置，包括之后的容器与闭包捕获；演算里只有视图字段这一种。
4. **“返回 `inout any I` 的总是载荷访问”有代价。** 类型自己的方法返回它内部一个真实存在类型槽位的独占借用时（I3 的 `slot`），调用方也不能经它整体替换，只能调用专门的替换方法或直接写字段。
   放开它需要在返回类型上区分两种访问，也就是一种新的拼写。建议先不加，等出现具体需求。
5. **载荷访问不能交给任何泛型 `inout T`，这是保守的。** `same<T>(inout x: T)` 不做替换，仍被拒绝（I5）。更要紧的是按 `inout T` 写的泛型算法（例如交换、就地排序的比较与移动）都不能直接用于一个 `inout any Shape`。
   精确的做法是“打开”存在类型：在调用处把 `T` 绑定为那个未知的具体类型。这样 `same` 可用；`overwrite` 仍被拒绝，因为拿不出一个类型恰为该未知类型的值。原型没有建模打开，这是之三需要回答的一个设计点。（§11 的 X4 已在原型里补上打开。）
6. **借用规则与这个标记正交。** I4 的三个拒绝与不涉及存在类型时完全相同，没有为存在类型改动 K1–K14 的任何一条。

### 10.4 这一步没有回答的

- 存在类型的打开（发现 5），以及泛型约束 `T : I`。原型的类型参数没有上界。
- 嵌套位置：`Box<any I>`、`List<any I>` 里的槽位，演算没有泛型类。按 X0 推断它们是槽位，但没有用例检验。
- 构造视图时没有核对借用字段的类型是否匹配；方法调用没有经过见证表，`any I` 上的方法在原型里是受信任的普通函数。
- 存在类型携带借用（`any I` 的载荷是一个视图）时来源怎样记录，没有建模。
- 大小、布局与析构：整体替换时旧载荷何时析构，属于之四，不在这一步。
- 规则是否健全，仍然没有证明。

## 11. 对前面发现的修补（2026-11-14）

第 2、3 步各留下一个“原型接受了不该接受的”或“拒绝了不该拒绝的”问题，这里在原型里补上。两处都是演算里的做法，是否进入语言设计仍待裁决。

```text
字段    … | private [borrow | inout] f: τ
函数    F ::= fun … [from …] [flows …] [in C] [trusted] { … }      in C：该函数是类型 C 的成员
```

| # | 规则 |
|---|---|
| K15 私有字段 | 经 `private` 字段的访问只允许出现在 `C` 的成员函数里 |
| X4 打开 | 载荷访问交给泛型的 `inout T` 时，`T` 绑定为这一处独有的未知具体类型。调用结果的类型若是 `T`，结果仍是载荷访问 |

X4 取代了 §10 里“载荷访问不能交给任何泛型 `inout T`”的保守做法。X2 的“`T` 的各处实例须一致”不变，它现在同时负责拒绝：`overwrite`（另一个实参的类型不是那个未知类型），以及把两个载荷访问交给 `swap<T>`（两处各自打开，得到两个不同的未知类型）。

| # | 程序要点 | 预期 |
|---|---|---|
| J1 | 迭代器的独占字段声明为 `private`：取出一个独占元素后在类型之外经字段写同一块存储；访问公开字段；只经成员函数取两个元素 | 拒绝（K15）；接受；接受 |
| I5（更新） | 见 §10.2 | |

发现：

1. **K15 关上了 §9.3 第 6 条的探测程序，但信任边界因此是整个类型的成员。** 成员函数可以访问私有字段；一个没有标受信任的成员函数经字段写存储，原型照样接受，而此前交出的独占元素可能正指着那里。
   所以“受信任”不是单个函数的性质：一个类型只要有受信任的成员，它的全部成员都在需要人工审查的范围内。这与 Rust 里 `unsafe` 的健全性以模块为界是同一个结论，U0 须按类型（或模块）而不是按函数划定审查范围。
2. **打开存在类型不需要新规则，只需要让类型参数能绑定到一个未知类型。** 拒绝 `overwrite` 与 `swap` 的仍是 X2。原型里打开是隐式的；它与之三“泛型实例以存在类型为实参单态化”并存时各走哪一条，没有建模。
3. 仍未修补的：返回 `inout` 存在类型的调用结果一律是载荷访问（§10.3 第 4 条），以及父 loan 不随子 loan 延续（§8，已决定暂时保持）。

## 12. 多级来源与嵌套视图（2026-11-15）

起因是一个问题：`x` 有借用字段 `a`、`b` 时，“转发全部来源”是否就是 `x.a` 加 `x.b`，多级嵌套时能否写多级，从而不需要单独的“全部”写法。

```text
来源    o ::= x | x.f₁.….fₙ | x.origins
```

| # | 规则 |
|---|---|
| K16 路径 | 视图按值含有另一个视图时，内层的借用字段记在 `外层字段.内层字段` 之下。来源写到任意一级：写到借用字段即只覆盖它；写到中间一级覆盖它之下的全部借用字段 |
| K16 覆盖 | 来源 `x.f.g` 被 `x`、`x.origins`、`x.f`、`x.f.g` 中任意一个声明覆盖 |

| # | 程序要点 | 预期 |
|---|---|---|
| K1 | 两级视图：`from x.inner.a` 返回该字段，之后写另外两个来源、写它自己的来源；`from x.inner` 返回 `inner.b`；按值的 `from x`；声明 `x.inner.a` 却返回 `inner.b`；声明 `x.c` 却返回 `inner.a`；按值含有独占视图的视图被隐式复制 | 前两处写接受，第三处拒绝（K1）；前缀与整体各拒绝相应的写（K1）；两处拒绝（K6）；拒绝（K8） |

发现：

1. **对具体类型，“全部来源”确实只是各级借用字段的并集，不需要单独的写法。** 写字段路径更精确（K1 里写无关的来源被接受），写前缀或参数名则是简写。
2. **仍然需要一个“全部”的写法，但只剩一处**：参数的类型是类型参数或接口，并且参数按 `borrow` / `inout` 传递。那里没有字段名，而 `from x` 已经表示“依赖 `x` 本身”。迭代接口的 `next` 就是这种签名，它由标准库作者写一次，普通用户的代码里基本不出现。
   按值参数不需要它（K13：`from x` 即全部）。占位拼写由 `x.*` 改为 `x.origins`。
3. **第一版原型对嵌套视图是不健全的。** 构造外层视图时丢掉了内层视图携带的来源：经外层返回内层的借用之后写它的来源，原型接受；声明一个分支却返回另一个分支，原型也接受。两处都已修正并由 K1 覆盖。
   这说明之前“41 个用例通过”没有覆盖嵌套；现在覆盖的仍然只有两级、只有按值嵌套。
4. 没有覆盖的：视图经借用字段指向另一个视图（借用的借用）时来源怎样分层；嵌套三级以上；嵌套视图上的流向子句。（§13 已补。）

## 13. 补上的覆盖（2026-11-15）

类型参数  <T>       默认可逃逸：只能实例化为不携带来源的类型

发现：

1. **“默认可逃逸、显式放弃”可以建模，并且现有泛型代码的写法不受影响。** 不带标记的 `<T>` 不需要任何 `from`，与今天一样；只有打算接受视图的泛型代码才写标记并声明来源。代价是泛型库要逐个决定是否放开：`List<T>` 不放开就装不了视图。
   第 2 步的迭代用例（H3–H5）的类型参数因此都改成了 `view`，这正是之二 L5 说的“迭代器所需的泛型能力”。
2. **借用的借用不需要新规则**，路径记法直接延伸。经共享外层只能得到内层的共享访问，与 Rust 的 `&&mut T` 一致。
3. **又发现并修掉两个漏洞。** 一是把借用值本身当作类型参数的值传入时，结果丢掉了来源（借用被当成了它所指的类型）；二是把一个新的内层视图写进局部视图的字段时，新来源没有被记录。两处都已修正并有用例。
   连同 §10、§12 的两次，原型至今发现的四个漏洞都出在“来源随值存进某个位置”时漏记。参考检查器的实现应当把“值携带的来源”做成值表示的一部分，而不是在各个存放点分别处理。
4. 仍未覆盖的：经借用把来源写进视图字段（要求把流向子句推广到具体类型的字段，K14 当时只拒绝；§18 已补）；递归的视图类型（原型遇到环就停止展开，没有用例）；闭包捕获；两阶段借用；健全性证明。

## 14. 借用与析构的配合（2026-11-15）

[析构义务的原型](drop-obligation-model.md)不含借用。这里在借用原型一侧补上二者的接口，检验已裁决的统一析构规则与“借用的结束点单独定义”（[析构时机对比](drop-timing-comparison.md) §8）能否并存。

| # | 规则 |
|---|---|
| K18 提前析构 | 打开该选项时，局部 owner 在某条语句之后满足三条即在那里析构：它不再被用到；没有存活的 loan 指向它；它的析构不可观察（没有 `deinit`，也不按值含有这样的字段） |

K18 的第二条就是“存活的 loan 使 owner 保持存活”：owner 的析构点由“它与从它借出的一切都不再使用”决定，而不是由它自己的最后一次使用决定。

检验的性质有两条，都在测试里：

1. **打开提前析构之后，全部用例（当时 47 个）被接受或拒绝的结果逐行不变。** 这些用例里一共发生了 107 次提前析构。也就是说，程序是否合法不依赖析构发生在哪里——这正是把“提前”定为许可而不是规定所需要的。
2. 用例 L1：被借用的 owner 留到借用的最后一次使用之后才析构；无关的 owner 更早析构；可观察的值不提前；分支两边各析构一次。

发现：

1. **两条裁决可以并存，而且接口只有一句话**：析构点 = 活性（含从它借出的 loan）加“是否可观察”。借用规则不需要知道析构策略，析构规划只需要向借用一侧问“还有没有存活的 loan 指向它”。
2. 这条性质依赖 K9 的写法：作用域结束处的析构与存活的 loan 冲突即拒绝。提前析构从不制造新的冲突，因为它只在没有存活 loan 时发生。
3. 没有做的：两个原型没有合并成一个，各有一份活性分析；“可观察”在这里按 `deinit` 标记判断，没有接上[能力推导原型](capability-derivation-model.md)（§19 已接上）；参数与视图不参与提前析构。

## 15. 内部可变（内核基底 KB6，2026-11-15）

对应[之四](evolution-04-route-capability-unsafe-suspend.md) C2。要检验的是：“共享借用即不可变”的例外怎样进入借用规则。用例 M1。

```text
声明    cell class C(…)      内部可变类型（演算记法；之四里是含 RawCell 的类型）
```

| # | 规则 |
|---|---|
| K19 内容 | 内部可变类型的字段不能在非受信任的函数里访问；读写都经受信任函数，以共享借用传入整个值 |
| K19 流向 | `flows o into x` 的目标可以是 `borrow` 参数，当且仅当它的类型是内部可变类型。经局部的共享借用值调用时，来源流入它所指的每个变量；所指在调用方时，记在相应的参数上并须由本函数的 `flows` 声明 |

| # | 程序要点 | 预期 |
|---|---|---|
| M1 | 两个共享借用交替调用受信任的改写函数；非受信任代码直接读字段；把视图经共享借用放进内部可变的槽，之后写它的来源（直接传 `&s`、经局部借用值传）；槽比来源活得久；转交函数声明或不声明流向、经局部副本转交；对普通类型声明经共享借用的流向 | 接受；拒绝（K19）；拒绝（K1）两次；拒绝（K9）；接受、拒绝（K6）两次；拒绝（SIG） |

发现：

1. **改写本身不需要动借用规则。** 经共享借用改写内容，是受信任函数签名背后的事；K1–K18 没有一条依赖“共享借用下内容不变”。这印证之四 R2.3：这个假设只存在于将来的代码生成优化里，所以标记必须在内核，但借用检查不为它改。
2. **需要改的只有一处：流向子句的目标。** 没有内部可变时，来源只能经独占借用流进已有的持有者；有了它，经共享借用也能流进去（把一个视图 `set` 进 `Cell`）。规则须把“目标是 `borrow` 参数”限定在内部可变类型上，否则任何共享借用都能改变别人持有的来源。
   来源一律记在**拥有该存储的变量**上，而不是记在借用值上，所以多个共享借用同时存在时仍然只有一份账。
3. **不可检查的义务归 U0。** 受信任函数若经共享借用交出指向内容的借用（`get` 返回内部引用），之后另一个共享借用的改写会使它失效，而借用规则看不到。之四 R2.4 要求 `Cell` 只提供整值的取放、不借出内部引用，这是库作者的义务，须写进 U0，原型检验不了。
4. 没有覆盖：带运行时借用标志的单元（`RefCell` 类）交出的守卫；内部可变与 `Shareable` 的配合在[能力推导原型](capability-derivation-model.md)里（`RawCell` 恒不可共享），两个原型没有接起来（§19 已接上）。

## 16. 闭包捕获（2026-11-15）

之一把闭包定为“匿名的、含借用字段的积类型加单方法见证”。若成立，闭包在内核里不需要任何专门的规则；若不成立，就多出一条基底。用例 N1 把闭包**手工展开**成它声称等价的形式来检验：环境是一个视图类（只读捕获是 `borrow` 字段，可写捕获是 `inout` 字段，按值捕获是普通类的字段），函数体是以环境为第一个参数的函数，高阶函数以 `view F` 的类型参数加一个函数类型的参数接收它。原型没有闭包语法。

| 情形 | 结果 | 由哪条规则得到 |
|---|---|---|
| 不逃逸的只读闭包，调用两次；之后写被捕获的变量 | 接受 | K3：闭包不再使用后 loan 结束 |
| 闭包仍存活时写被捕获的变量；只读 | 拒绝；接受 | K1 |
| 可写闭包：调用两次；存活期间读被捕获的变量 | 接受；拒绝 | K1（独占 loan） |
| 可写闭包不可复制；只读闭包可复制 | 拒绝；接受 | K8 |
| 一个只读捕获加一个可写捕获 | 各按自己的种类 | K11 |
| 返回捕获了局部变量的闭包；返回捕获了参数的闭包并声明 `from` | 拒绝；接受 | K6 |
| 闭包返回指向被捕获变量的借用 | 结果保护来源 | `from env.a`（K5、K16） |
| 按值捕获的闭包交给要求可逃逸的 `<F>`（例如启动线程）；借用捕获的闭包交给它 | 接受；拒绝 | K17 |

发现：

1. **这 13 种情形都不需要新规则，之一的说法在原型里成立。** “借用捕获的闭包不能逃逸”不是一条规则，而是 K6、K9、K17 的结果；“可写闭包不可复制、调用时独占”是 K8 与独占字段的结果。
2. **它依赖两项已有但尚未进入语言的能力**：类型参数可以放开可逃逸上界（K17 的 `view F`），以及函数类型带来源合同（§9 的 K12）。高阶函数要接收借用捕获的闭包，签名就得用到前者。
3. 留给糖的：每个被捕获变量用哪种方式捕获的推断；环境类型与见证的生成（KB5）。
4. 没有检验的：现行 [Guide 07](../guide/07-calls-lambdas-closures.md) 对 borrowed closure 与 mutating closure 的专门限制是否与这里推出的结果逐条一致（可能更严或更松）；递归闭包；捕获另一个闭包；闭包作为存在类型的载荷。

## 17. 帧挂起（内核基底 KB8，2026-11-15）

[之四](evolution-04-route-capability-unsafe-suspend.md) §4 给挂起定了三条前置约束（S0.1 帧地址稳定、S0.2 结构化是借用的前提、S0.3 挂起点状态守恒），[之七](evolution-07-concurrency-async-io-ffi.md) J18 规定默认不换线程。这一步检验它们放进借用内核之后是否自洽、各自需要多少新规则。以下写法都是演算记法，不是 Koven 语法。

### 17.1 增加的记法与规则

- `suspend fun`：可以包含挂起点的函数。`parallel suspend fun`：恢复时可能换线程的函数（J18 的显式并行入口）。
- 语句 `suspend`：一个挂起点。调用 `suspend` 函数也是调用方的一个挂起点，此时实参的 loan 仍由被调帧持有。
- `val t = start f(args)`：创建任务。实参已求值并存进任务的帧，函数体尚未执行；任务值持有全部实参带来的 loan，不可复制。
- `poll t`：让任务开始执行但不等它结束。`await t`：等它结束并消费它，是一个挂起点。
- `local class`：值绑定在创建它的线程上，不可转移（代表非原子共享计数一类）。

| 规则 | 内容 |
|---|---|
| S0 | 挂起点、对 `suspend` 函数的调用、`await` 只能出现在 `suspend` 函数里 |
| S1 | 仅用于对照：假设已开始执行的帧仍可移动时，帧内有指向本帧局部变量的存活 loan 即拒绝 |
| S2 | 状态守恒：挂起点不是一次访问，owner 可用性与 loan 集合原样跨过它。**它不产生任何检查** |
| S3 | 已开始执行的任务不可移动 |
| S4 | 已开始执行的任务在离开作用域前须被 `await`；任一分支上开始过即算开始过。未开始的任务可以直接丢弃 |
| S5 | 在 `parallel` 函数里，跨挂起点存活的每个值须可转移；共享借用可转移当且仅当所指的类型可共享（不含内部可变、不含 `local`）；没有上界的类型参数按不可转移处理 |

### 17.2 用例

| 用例 | 内容 |
|---|---|
| P1 | 借用跨挂起点后继续使用；跨挂起点期间写被借出的变量（K1）；借用在挂起前结束；把局部按 `inout` 交给会挂起的函数；借用参数跨挂起点；移动后挂起再使用（K8）；非 `suspend` 函数里挂起（S0） |
| P2 | 任务持有实参的 loan 直到被 `await`；两个只读任务并存；只读任务与可写任务冲突（K1）；未开始的任务可丢弃、可移动；已开始的不可移动（S3）、须等待（S4，含只在一个分支上开始、内层作用域）；重复 `await`（K8） |
| P3 | 默认函数里 `local` 值、指向内部可变值的共享借用都可以跨挂起点；`parallel` 函数里它们被拒绝（S5），拥有的普通值、指向普通值的共享借用被接受；只在挂起前使用的 `local` 值不受影响 |

另有两条测试：对 P1 打开“帧可移动”的假设，恰好多出三处拒绝；把 P3 的 `parallel` 去掉，全部拒绝消失。

### 17.3 发现

1. **S0.3 成立，而且不需要规则。** 挂起点对借用检查是空操作：已有的 K1、K3、K8 在挂起点前后照常工作，P1 的接受与拒绝全部由它们得到。之四说它是“要增加的唯一一条不变量”，在借用一侧它是不需要增加任何东西；析构义务一侧没有检验（见 17.4）。
2. **S0.1 的适用面比“帧内自引用”宽。** 打开帧可移动的假设后被拒绝的三处里，有一处没有任何借用变量：只是把局部变量按 `inout` 传给一个会挂起的函数（P1 `calleeFrameHoldsLoan`）。被调帧嵌在调用方的帧里并持有指向它的借用，这已经是自引用。所以放弃帧地址稳定的代价不是“不能写自引用”，而是“不能把局部按借用交给任何会挂起的函数”，S0.1 没有可行的替代。
3. **“已创建未启动”与“已启动”不能写成两个由函数连接的类型。** 已启动的任务不可移动，于是不能作为“启动”函数的返回值交出来。原型用的是变量上的流敏感状态（开始过即钉住）。另一种不加规则的表达是让“启动”按独占借用取得任务并返回一个持有该 loan 的句柄，由已有规则禁止移动；这种表达没有在原型里检验。
4. **S4 是一条“必须显式消费”的义务。** 已开始的任务既不能丢弃也不能移走，只能等待。这正是之四里暂时预留的那种类型。两个出路：把它作为内核里第一个必须消费的类型；或者不让任务值出现在用户代码里，只在受信任的结构化作用域库内部创建和等待，S3、S4 变成那段受信任代码的义务而不是语言规则。之七的结构化并发已经是后一种形态，这样 KB8 不迫使“必须显式消费”提前定案。**裁决（2026-11-15）：采用后者。** 任务值（进行中的调用及其帧）不出现在用户代码里；用户拿到的是可以等待的句柄，帧由结构化作用域库持有。
5. **S5 只在并行入口出现，默认情形没有任何限制**，与 J18 的预期一致。它检查的是“跨挂起点存活的值”，这组值由已有的活性分析直接给出，诊断可以指出是哪个挂起点（之七 §2.3 关心的问题）。
6. **泛型的并行函数需要能力上界。** 没有上界的类型参数只能按不可转移处理，所以并行入口的签名要写出 `Transferable` 上界；这依赖能力推导原型，两者尚未接起来，原型里的可转移判定只是 `local` 与内部可变两个标记的近似。（§19 已接上，并补了上界。）

### 17.4 这一步没有回答的

- 析构义务的守恒：挂起点两侧待执行的析构是否相同、取消时由谁执行，析构义务原型没有挂起点。（§21 已补。）
- 取消：J19 把取消当作值，`await` 的失败出口与[失败与清理的状态模型](failure-cleanup-model.md)的模型 A 没有接到这里。
- 动态数量的任务：把任务交给作用域持有（来源流入持有者，§15 的流向子句）与 S4 的配合。
- 帧大小无法静态确定的情形（递归、经存在类型的 `suspend` 调用）、`suspend` 闭包、生成器。
- 发现 3 的借用句柄表达；发现 6 的能力上界。

## 18. 经借用把来源写进视图（2026-11-15）

此前把携带来源的值写进视图，只支持两种情形：直接写局部视图的按值字段（K16 写入），以及流入类型参数的持有者（K14）。经借用写一个具体的视图一律拒绝。这一步放开它。用例 Q1。

### 18.1 增加的记法与规则

```text
流向    flows o into x | flows o into x.f₁.….fₙ      目标可以写到字段路径，覆盖关系与来源的路径相同
```

| # | 规则 |
|---|---|
| K20 一份账 | 值携带的来源只记在**拥有该存储的变量**上。经借用到达一个视图时，它各借用字段当前持有的来源从所指的变量上现查，不以建立借用时的副本为准。所指在调用方时，记在相应的参数名下 |
| K20 写入 | 经独占借用整体替换（`*x = e`）或改写按值字段（`x.f = e`）时，新值携带的来源记到所指的存储上。所指唯一时旧来源解除，否则并入 |
| K20 核对 | 函数返回时，借用参数名下每个字段路径多出来的来源，都须被一条目标覆盖该路径的 `flows` 声明覆盖；落在局部变量上的拒绝（K6）。合同细化（K12）对目标路径同样适用：`into x` 覆盖 `into x.f` |
| K20 调用 | 调用方按声明把来源**并入**目标路径之下的每个借用字段，不解除旧来源。目标可以是对变量的借用、对它按值字段的借用，或一个借用值 |

另外改正一处：因流向而在调用之后继续存在的实参 loan，种类跟随参数自己的模式。此前只要签名带 `flows` 就一律按独占计，于是把一个只读来源放进容器之后，连读它都被拒绝。

### 18.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| Q1 定义处 | 改写 `inout` 参数的内层视图：目标写到该路径、写到整个参数、写到另一个分支、不声明、只在一个分支上改写、写入局部变量的借用；整体替换同理；类型参数的槽位被整体替换；转交给另一个带流向的函数 | 前两者接受；其余拒绝（K6）；转交须自己声明 |
| Q1 调用处 | 持有者保护新来源，且新来源仍可读；持有者比来源活得久；旧来源在调用方不解除；经局部借用值写入后再经它读出；借用值可能指向两个视图之一；以按值字段的借用作目标；泛型的 `flows x into out` 以视图实例化 | 拒绝写（K1）、接受读；拒绝（K9）；拒绝写（K1）；其余各拒绝对新来源的写（K1） |
| Q1 其他 | 局部经借用整体替换后旧来源解除；函数类型的合同目标为 `v.mid`，实参函数的目标为 `v.mid.deep` 或 `v`；经视图的借用字段走到另一个视图再写入 | 接受；接受、拒绝（K12）；拒绝（K14，未支持） |

另有两条测试：让别名路径只读建立借用时的副本，Q1 恰好少报；去掉写入的记账，K6 与 K9 的拒绝全部消失。

### 18.3 发现

1. **流向子句推广到字段路径不需要新机制。** 目标的路径与来源的路径是同一种写法、同一个覆盖关系，K6、K12 原样适用。Rust 在这里需要 `&mut V<'a>` 对 `'a` 不变；这里没有对应物：来源并入持有者之后，“持有者比来源活得久”由已有的 K9 拒绝。
2. **又发现三个漏洞，仍然都是来源漏记。**
   - 经独占借用整体替换（`*x = e`）完全不记来源：把指向局部变量的视图写进调用方的槽位，原型接受。它从第 3 步引入 `*x = e` 起就存在，此前没有用例把整体替换与视图放在一起。
   - 泛型的 `flows x into out` 以视图实例化时，来源记在一个读字段时看不到的键上：之后从容器里读出的借用不保护新来源。
   - 借用值带着建立时的字段来源副本；经别的路径写入之后，经它读到的是旧账。
   三处都已修正并由 Q1 与变异测试覆盖。连同此前四个，七个漏洞同属一类。K20 把 §13 的建议落成了规则：来源只有一份账，在拥有存储的变量上，其他路径一律现查。参考检查器应当从这条规则出发设计数据结构，而不是事后逐个补存放点。
3. **函数体内可以解除旧来源，调用方不能。** 函数体内写入的目标唯一，旧值确定被换掉；调用方只看到“可能流入”，只能并入。所以经函数改写视图之后，旧来源在调用方继续受保护，直到持有者不再使用（Q1 `callerKeepsOldSource`）。要更精确需要在签名里区分“替换”与“并入”，这是一个新的子句。**裁决（2026-11-15）：不加。** `flows` 只有“可能流入”一种含义，调用方一律并入；诊断须指出持有者自哪里起可能仍借着旧来源。
4. **来源种类的改正说明此前的用例偏弱。** “带流向就按独占计”在已有用例里没有造成任何错判，只因为“只读来源流入之后仍可读”从未被检验。现在 Q1 有这一条。
5. 没有覆盖的：经视图的借用字段走到另一个视图再写入（目标路径越过借用字段，账要记到那个视图的拥有者上；调用方一侧须把目标参数的字段映射回它背后的变量），当时拒绝，§22 已放开；按值接收的视图经它的独占字段改写调用方的视图，同属这一项；对借用值再取借用（借用的借用作为值）时字段来源的现查。

## 19. 原型合并第一步：能力判定取自能力推导（2026-11-15）

借用原型此前自己近似四项判定：可否隐式复制、是否可逃逸、可否转移到另一个线程、析构是否可观察。这一步把它们全部改为向[能力推导原型](capability-derivation-model.md)询问，借用原型里不再有自己的版本。用例 R1。

做法：演算的类型声明逐个翻译成能力推导的声明。`cell class` 翻译为“含有一个 `RawCell` 字段”，`local class` 翻译为“含有一个非原子共享计数的字段”，两个标记因此不再有独立的含义。

| 判定 | 此前 | 现在 |
|---|---|---|
| 可隐式复制（K8） | 不含独占字段的视图 | `Copyable` |
| 可逃逸（K17） | 不是视图 | `Escapable` |
| 可转移（S5） | 按 `local` 与内部可变两个标记递归 | `Transferable`；共享借用看所指的 `Shareable` |
| 析构可观察（K18） | 按 `deinit` 标记递归 | 不满足 `EarlyDrop` |

增加的记法与规则：

```text
类型参数  <T: Cap + Cap>     能力上界
```

| # | 规则 |
|---|---|
| CAP 声明 | 能力推导对声明的检查原样适用：可能携带来源的类型须声明为视图 |
| CAP 上界 | 类型参数只凭它声明的上界回答能力询问；调用处实参的类型须满足被调方的上界，调用方自己的类型参数须带着相同的上界 |

发现：

1. **已有的 53 个用例的结果一个都没变**，其中的提前析构次序也没变。四项近似在已有用例的范围内与推导一致。
2. **不一致的地方有三处，都在已有用例之外，其中一处是漏洞。**
   - 视图按值拥有一个普通类的值时，旧判定仍允许隐式复制这个视图，等于复制了一份所有权。推导正确地判它不可复制。
   - 普通类声明了借用字段，旧原型不报错；推导要求它声明为视图。
   - 没有任何借用字段的视图，旧判定一律当作不可逃逸；推导判它可逃逸。这是旧判定过严。
3. **并行入口的上界可以表达，并且沿调用链传递**：`parallel` 函数的类型参数写了 `Transferable` 上界之后，跨挂起点持有它的值被接受；调用它的泛型函数须带着同样的上界，否则在调用处被拒绝。这补上了 §17.3 第 6 条。
4. 没有做的：类型本身带类型参数（演算的类没有泛型，条件式的推导结果用不上）；`Forgettable` 与 `ImplicitDrop` 两项在借用原型里没有使用者；析构义务原型仍然用自己的类型标记，活性分析仍是两份，这是合并的下一步（§20）。

## 20. 原型合并第二步：析构交给析构义务的检验器（2026-11-15）

借用原型此前只判断“析构与存活的 loan 是否冲突”，它定下的析构本身对不对没有人检验；[析构义务原型](drop-obligation-model.md)有一个独立的检验器，但它的输入来自自己的规划器，不含借用。这一步把两者接起来：借用检查器在检查每个函数的同时，把它写成一段只含所有权操作、析构显式的程序，交给析构义务的检验器。用例 S1，以及全部已有用例里被接受的函数。

写出的内容：

| 借用原型里的事 | 写成 |
|---|---|
| 声明一个拥有的值（含按值参数） | `let`，附失败时的清理清单 |
| `move`、整体赋值 | `move`；先析构旧值再 `set` |
| 任何读、写、借用，**包括经借用值或视图到达 owner 的访问** | 对 owner 的 `use` |
| 调用 | 一个可能失败的操作，附清理清单 |
| 提前析构（K18）、作用域结束、函数结束 | `drop`；可能已移走的带析构标志 |
| 分支、循环、代码块 | 原样；循环取到达不动点的那一遍 |

类型是否可观察取自能力推导。检验器不知道借用，它只执行这段程序并穷举路径与失败，检查析构义务原型的 V1–V5。

| # | 规则 |
|---|---|
| K18 补偿 | 打开提前析构时，不可观察的值只在一条分支上被移走或析构、此后不再使用、名下没有存活的 loan，就在另一条分支的末尾析构 |

发现：

1. **全部被接受的函数都通过检验器**，提前析构打开与关闭两种情况共 292 次检验，没有一处违反。经借用的访问记为对 owner 的使用，所以“存活的 loan 使 owner 保持存活”（K3 的补充、K18 的第二条）第一次得到了借用原型之外的检验：去掉它，检验器报“使用了已析构的值”。
2. **活性分析只剩一份。** 析构义务一侧不再需要自己算活性：析构点由借用原型定，检验器只负责验。析构义务原型自己的规划器保留，用于借用原型表达不了的部分（部分移出、拆开、必须消费、`deinit` 函数体）。
3. **借用原型原先会让不可观察的值也带上析构标志。** 提前析构只在语句之后触发，值在一条分支上被移走或提前析构后，另一条分支没有对应的析构，合流后成了“可能已移走”，只能在函数结束处带标志析构。析构义务原型的规划器在这里是在分支末尾补一次析构。已按后者补上（K18 补偿），现在全部用例里带标志的只有一处，正是可观察的值，与“析构标志只用于可观察的值”的裁决一致。
4. **失败时的清理清单在借用一侧同样是“此刻的状态”。** 每个声明与调用处的清单就是当时仍拥有的变量的逆序，没有另外的分析；检验器穷举失败路径没有发现泄漏。借用原型本身仍然没有失败出口，失败路径上不做借用检查。
5. 没有做的：视图与类型参数的值不提前析构；按值参数不提前析构；函数结束处此前没有析构与 loan 的冲突检查（返回值的来源由 K6 负责），这一步只是把析构写了出来；部分移出、`deinit` 函数体、挂起点两侧的析构没有经过这条路；析构义务原型的类型标记仍是自己的。

## 21. 挂起点两侧的析构义务（2026-11-15）

§17 只检验了挂起的借用一侧。这一步借 §20 接好的路检验析构一侧：挂起点两侧待执行的析构是否相同，帧被销毁而不再恢复时由谁析构、析构什么。用例 P4。

### 21.1 规则

| # | 规则 |
|---|---|
| S2 延伸 | 挂起点不析构任何东西，也不改变任何值的归属。留在帧里的是三类值：之后还会用到的；被存活的借用指向的；此刻仍拥有、等着在作用域结束时析构的 |
| S5 修正 | 并行函数里须可转移的是留在帧里的全部三类值，不只是“之后还会用到的” |
| S6 挂起前析构 | 不再使用、名下没有存活 loan、析构不可观察的值，在挂起点之前必须已经析构。这里“提前析构”是义务，不是许可 |
| S7 按状态析构 | 帧在挂起点被销毁而不再恢复时，析构它此刻仍拥有的值，自内向外、声明逆序，可能已移走的看析构标志。每个挂起点一份清单，与可失败操作的清理清单是同一种东西 |

写进析构义务程序的是一条 `suspend` 语句，附 S7 的清单；检验器把“帧在这里被销毁”当作一条要穷举的路径。

### 21.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| P4 并行 | 只在挂起前使用的 `local` 普通值；只在挂起前使用的 `local` 且带 `deinit` 的守卫；把守卫放进内层代码块；挂起前把守卫移走；守卫跨过对 `suspend` 函数的调用；可转移的带 `deinit` 的值跨过挂起点 | 接受；拒绝（S5）；接受；接受；拒绝（S5）；接受 |
| P4 默认 | 不换线程的函数里守卫与文件跨过挂起点 | 接受；帧里记着两个都不再使用但尚未析构的值 |
| P4 销毁 | 一个值只在一条分支上被移走之后挂起，再声明一个值并调用 `suspend` 函数 | 各挂起点的清单随状态变化，检验器穷举“在此销毁”没有泄漏 |

测试：去掉 S6，`local` 普通值所在的挂起点多出一处 S5；去掉挂起点上的清单，检验器报泄漏；关闭提前析构时，S6 的析构仍然出现在挂起之前。

### 21.3 发现

1. **§17 的并行检查有一个漏洞。** 它只看“挂起之后还会用到的值”。一个带 `deinit` 的值即使之后不再使用，也要留到作用域结束才析构，所以它一直在帧里；并行函数里它会在另一个线程上被析构。绑定在线程上的守卫（非原子计数、线程局部的锁）跨过挂起点，§17 的原型接受了。这正是 Rust 里“锁守卫跨过 `await`”那类错误。已按 S5 修正，P4 覆盖。
2. **“提前析构只是许可”在挂起点处不成立，需要裁决。** P3 里“只在挂起前使用的 `local` 值不受影响”这一条，实际依赖它在挂起前已经析构。若提前只是许可，编译器可以把它留到作用域结束，它就跨过了挂起点；程序是否合法于是取决于一项优化。两种出路：
   - **S6：挂起点之前必须析构。** 普通值用完即走，不会因为“还没到作用域结束”而被判为跨过挂起点；帧的大小也因此可以预期。代价是统一析构规则多一处例外：在挂起点，许可变成义务。
   - **一律按词法作用域计。** 规则没有例外，但用户得像在 Rust 里那样，为了让一个用完的普通值不跨过挂起点而手工加代码块或显式移走。
   原型按 S6 实现。它不改变任何可观察的行为：涉及的值析构不可观察，差别只在它们的析构发生在哪个线程，而那正是 S5 要管的事。
   **裁决（2026-11-15）：采用 S6，并限定它只适用于没有逃逸的值。** 即本函数仍独占拥有、没有被移走、名下没有存活的借用、地址没有被取成裸指针的值。地址被取过的 owner 按[之四](evolution-04-route-capability-unsafe-suspend.md) R1.2 留到词法作用域结束，它跨过挂起点并受 S5 检查。前三条原型已实现；演算没有裸指针，第四条没有检验。
3. **S0.3 在析构一侧同样不需要规则。** 挂起点不析构、不移动，两侧的义务自然相同；检验器沿正常路径走过挂起点没有任何特殊处理。新增的 S6 不是为守恒，而是为第 2 条。
4. **“取消时由谁析构”在正常路径上不是问题。** 取消是值（之七 J19）：挂起原语返回一个表示取消的结果，函数照常运行到返回，析构走的就是普通的作用域结束与失败出口。帧在挂起点被直接销毁只发生在所在执行器异常终止时，由销毁帧的一方按 S7 的清单执行。清单的数量是挂起点的数量，内容就是那一刻的状态，没有另外的分析。
5. **带 `deinit` 的值跨过挂起点在默认函数里没有任何限制**，与 J18 一致；限制只在并行入口出现。
6. 没有覆盖的：帧被销毁时指向它的借用（借用型子任务，之十一 J48 第 7 条要求先等齐）；`deinit` 永不挂起这一条没有检查；视图与类型参数的值不参与 S6；任务值按裁决不出现在用户代码里，§17 的 `start` / `poll` / `await` 记法没有随之改写成作用域库的形态；在途 IO 的缓冲区（之七 §2.7）。

## 22. 借用一侧的三项记账（2026-11-15）

清“集中做”一栏里借用一侧的三项：越过借用字段的流向、两阶段借用、递归的视图类型。用例 Q2、T1、U1。

### 22.1 流向越过借用字段

视图 `Holder(inout target: L1)` 经它的独占字段改写另一个视图 `L1`。此前函数体里这样写被拒绝（K14），调用处不支持。

| # | 规则 |
|---|---|
| K20 越过 | 写入的位置越过借用字段时，账记在那个字段所指的视图的拥有者上；所指在调用方时记在参数名下的完整路径上（`h.target.mid.deep.a`） |
| K20 按值目标 | `flows` 的目标可以是按值的视图参数，条件是目标路径经它的独占字段走到另一个视图。参数自己的存储随它消失，不算流出 |
| K20 调用（延伸） | 调用方沿目标路径逐级走：按值字段留在同一处存储，借用字段换到它所指的存储；最后把来源并入走到的那个拥有者。目标写得粗（`into h`）时，它之下每条越过借用字段的路径都这样走一遍 |

Q2：按值、按 `move`、按 `inout` 交出 `Holder`，以及直接以 `h.target` 作实参，四种调用之后从**被改写的视图自己**读出的借用都保护新来源；声明粗的目标同样；经共享字段的流向在签名处被拒绝（SIG）；拥有者比来源活得久被拒绝（K9）；转交须自己声明。

### 22.2 两阶段借用

| # | 规则 |
|---|---|
| K21 预留 | 接收者位置的独占借用，在其余实参求值期间只算共享：可以读它、对它建立共享借用，不能写、移动或再建立独占借用 |
| K21 生效 | 其余实参求值完毕时转为独占。此刻仍存活并与它重叠的 loan 都是冲突，包括作为实参交给被调方的共享借用 |

演算没有方法，接收者记作“名为 `this` 的第一个参数，按 `inout` 传入，实参是直接的 `&mut`”。范围与 [Guide 10](../guide/10-ownership-borrowing-drop.md) 的 Two-Phase Borrows 相同：只有接收者，普通实参位置不推迟。

T1：`push(&mut v, size(&v))` 与 `push(&mut v, v.len)` 接受；同样的写法在普通参数位置拒绝；`update(&mut v, &v)`、实参里再次独占借用、实参里移走接收者、更早的借用仍存活、上一次的出借结果仍存活，都拒绝；放在循环里接受。

### 22.3 递归的视图类型

`view class Node(borrow next: Node, borrow data: Arr)`：经借用字段指向同类型的视图。

| # | 规则 |
|---|---|
| K16 折叠 | 参数名下的来源只展开到第一次回到同一类型为止。再往里的借用字段没有自己的记录，它们的来源归到回到同一类型的那个字段名下：`n.next.data`、`n.next.next.data` 都由 `from n.next` 覆盖 |

U1：`from n.next` 返回第二个、第三个节点的数据，以及沿链走任意多步的循环，接受；声明 `from n.data` 或不声明，拒绝（K6）；调用方一侧，结果保护链上更深处的来源，只读自己数据的结果不保护它们。

### 22.4 发现

1. **“来源只记一份账”在多一层间接时仍然成立，不需要新机制。** 越过借用字段只是把“拥有者”换成了另一个变量；调用方沿路径走的每一步都是已有的两种情形之一。
2. **又发现三个来源漏记的漏洞，都与“所指在调用方”有关。**
   - 调用返回的、指向调用方视图的借用，经它读字段时查不到来源：函数可以不声明 `from` 就返回视图字段里的借用。
   - 把视图的一个借用字段（它指向另一个视图）直接作实参时，没有带上那个视图各字段的来源。
   - 递归视图的参数，第二层以后的字段没有任何来源记录（22.3）。
   第一处的原因是 §18 的“现查”只查了局部变量，没有查参数名下的账。至此同类漏洞共十个。它们集中在三件事上：值被存进某处、借用被再传一手、所指不在本函数里。参考检查器的测试应当按这三条轴系统地生成，而不是靠想到一个补一个。
3. **两阶段借用不改变内核的形状。** 它只是把一个 loan 的种类推迟确定，冲突判定用的仍是 K1。现行规则的三条边界（只读可以、写与移动不行、交给被调方的共享借用在生效时冲突）在原型里逐条得到。原型此前比现行规则多拒绝的那一类程序，现在一致了。
4. **递归视图的精度有上限，这是折叠的代价。** 链上更深处的来源只能整体声明、整体保护：结果只指向第三个节点的数据，调用方也会保护第二个节点的数据。要更精确需要按深度区分，而深度不是静态可知的。
5. 没有覆盖的：越过借用字段的流向在失败路径上；接收者经借用值或视图字段传入时的两阶段借用（现行规则同样只管直接的接收者）；互相递归的两个视图类型；递归视图上的流向；按值递归（需要间接 owner，演算没有）。
