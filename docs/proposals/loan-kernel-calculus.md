# 借用内核演算（内核 MVP 第 1–3 步）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；规则为草案，原型已实现并通过 §5、§9 与 §10 的用例（2026-11-14），不构成健全性证明 · **读取时机**：实现或评审借用内核的参考检查器原型时；核对 [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R1 的验证用例时 · **唯一真源**：本页维护演算的语法、判定规则与用例清单；模型的来由见[演进总纲之二](evolution-02-route-loan-kernel.md) §2，现行借用规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权修改编译器。它描述的是目标模型（之二的 L1–L4），不是现行 v0.47 的调用期借用。

## 1. 目的与边界

评审的结论是先验证组合、再冻结内核。本页把之二的借用模型写成一个可以执行的最小演算，用来回答一个问题：
**“两种来源合同加一棵 loan 派生树”能否同时接受该接受的程序、拒绝该拒绝的程序。**

- 范围：评审 §5 的前两组验证——切片、自有字段视图、只读 guard；返回重借、`splitAt`、可变迭代器。
- 方法：一个独立的参考检查器，输入演算程序，输出接受或带位置的拒绝。它基于用例，不是健全性证明。
- 不在本步：泛型与迭代接口（第 2 步）、存在类型（第 3 步）、失败出口与清理义务（第 4 步）、闭包、可空类型、两阶段借用、线程、数值推理、`deinit` 函数体的内容。
- 某个用例必须靠“这个内建类型例外”才能通过时，结论是回到设计，不是给原型加特判。

## 2. 语法

条件一律写作 `*`，表示检查器不对取值做任何推理，两个分支都要检查。

```text
程序    P ::= D* F*
声明    D ::= class C(f: τ, …) [deinit]                 owned 类；deinit 只是一个标记
            | view class V(k f: τ, …)                   k ::= borrow | inout | （无，表示 owned 字段）
函数    F ::= fun g(m x: τ, …): ρ [from o, …] [trusted] { s* return e }
模式    m ::= own | borrow | inout
类型    τ ::= Int | C | V
结果    ρ ::= τ | borrow τ | inout τ | Unit
来源    o ::= x          结果依赖持有者 x 本身            （DependsOn）
            | x.f        结果沿用 x 的借用字段 f 的来源    （Forwards）
语句    s ::= val x = e | p = e | use(p) | g(a, …) | { s* }
            | if (*) { s* } else { s* } | while (*) { s* }
表达式  e ::= n | p | move p | &p | &mut p | C(e, …) | V(e, …) | g(a, …)
place   p ::= x | p.f
```

`use(p)` 是一次读取，只用于标出“这里还在用”。结果为借用的函数，`return e` 按“交出一个借用”求值：返回一个借用值即对它重借。`trusted` 的函数不检查函数体，只信任签名，对应 `unsafe` 实现的库函数。

## 3. 状态

检查器在每个程序点维护：

```text
Loan    = { id, place, kind: Shared | Exclusive, parent: Loan?, site }
Init(x) = Available | Moved | MaybeMoved             按字段细分到 place
Origins(h) = 持有者 h 持有的 Loan 集合                 h 是借用局部、视图实例（按借用字段细分）或调用的结果
Live(h) = h 在该点之后还会被使用                        后向分析
```

- 一个 loan 可以被多个持有者共同持有；只要有一个持有者存活，它就存活。
- 函数体内，每个借用参数与每个视图参数的每个借用字段，各带一个符号 loan，代表调用方那边的来源。

## 4. 规则

| # | 规则 |
|---|---|
| K1 冲突 | 对 place `q` 做种类为 `a` 的访问（读、写、移动、析构）时，若存在存活的 loan `l`，`q` 与 `l.place` 重叠，且 `a` 与 `l.kind` 不相容，则拒绝。相容矩阵沿用 Guide 10。经持有 `l` 的持有者所做的访问不算冲突，除非 K4 |
| K2 建立 | `&p` 在 `p` 上建立 Shared loan，`&mut p` 建立 Exclusive loan。`p` 若是经某个持有者到达的，新 loan 的 `parent` 是那个持有者据以访问的 loan（重借） |
| K3 存活 | loan 存活当且仅当它的某个持有者存活。持有者从定义起存活到最后一次使用，不到作用域结束。**实现时补充**：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活（见 §8 第 1 条） |
| K4 暂停 | 持有者 `h` 持有的 loan `l` 有存活的子 loan `c` 时，经 `h` 对与 `c.place` 重叠的 place 的访问，按 `c.kind` 判冲突 |
| K5 调用 | 对每个实参按参数模式建立 loan：`borrow` 建 Shared，`inout` 建 Exclusive，`own` 是移动。结果的 Origins 由被调方的合同决定：`from x` 则在实参这个 place 上建立一个子 loan 交给结果（结果为 `inout` 时是 Exclusive，否则 Shared）；`from x.f` 则结果取得实参视图的字段 `f` 当前持有的 loan。没有流入结果的实参 loan 在调用返回时结束 |
| K6 合同 | 函数体的返回值持有的每个 loan 必须被签名声明覆盖：落在参数 `x` 自身存储上的，或由借用 `x` 派生的，要求声明 `from x`；属于 `x.f` 的符号 loan 的，要求声明 `from x.f` 或 `from x`（后者更保守，也成立）；落在局部变量上的一律拒绝。初稿末句“结果为 `inout` 且来源是独占视图时只允许 `from x`”已撤销，见 §8 第 2 条与 §9 |
| K7 构造 | `V(e, …)` 的实例在每个 `borrow` 字段上持有实参处建立的 Shared loan，在每个 `inout` 字段上持有 Exclusive loan；实参本身是持有者时，取得它的 Origins |
| K8 移动与初始化 | `move p` 之后 `p` 为 Moved；使用 Moved 或 MaybeMoved 的 place 拒绝。含 `inout` 字段的视图与 owned 类不可隐式复制；只读视图可复制，副本持有相同的 loan |
| K9 析构 | 作用域结束时，仍 Available 的 owner 按声明逆序析构；析构是对该 owner 的一次“析构”访问，按 K1 判冲突。带 `deinit` 标记的类不提前析构 |
| K10 合流 | 分支与循环的合流处：Origins 取并集；Init 取交（一条路径上 Moved 即为 MaybeMoved）；循环迭代到不动点 |
| K11 多结果 | 一次调用产生的子 loan 只有一个；结果若是含多个持有者的值（例如返回两个视图），它们共同持有这一个 loan。它们之间是否不相交不由检查器判断，只对 `trusted` 的函数成立 |

规则与之二的对应：K2、K4、K5 是 R4.4 的改写；K5、K6 是 R3.4 的两种来源写法；K6 末句是 R4.5；K11 是之二“不相交证明不由内核承担”。

## 6. 已知这一步答不了的

- **可同时保留多个独占元素的迭代器**。E1 只覆盖出借式。非出借式需要“独占视图把来源分给多个结果”，K6 末句禁止它，只能靠 `trusted` 签名；它如何进入迭代接口属于第 2 步。
- **转发的可见性**。类型之外的函数写 `from s.source` 时字段名是否总是可见（之二 §6 的建议），演算里没有可见性，答不了。
- **两阶段借用**。`list.push(list.size)` 一类写法现行规则靠 Reserved 状态接受，本步不建模；所有 `inout` 实参一律立即 Active，因此原型会比现行规则多拒绝这类程序。
- 规则是草案。实现过程中发现规则自相矛盾或某个用例两头都说不通，是这一步最有价值的产出，须记录在本页并回到之二修订。

## 8. 原型得到的发现

写原型的过程中，规则在五处与初稿不同或暴露了问题。前四条需要回到之二确认。

1. **K3 少了一条。** “依赖持有者本身”的结果持有的是视图变量存储上的 loan。初稿只说“持有者存活到最后一次使用”，于是视图在最后一次使用后就算死了，它持有的底层来源随之失效，
   而那个结果可能正指向底层数据（用例 A4：声明 `from this`、实际返回底层元素，这是 K6 允许的保守声明）。补充的规则是：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活。没有它，A4 的第二个函数会被错误地接受。
2. **“独占视图不提供转发”不需要单列为规则。** 越过 `inout` 字段时累加所凭借的 loan，函数体返回的借用就必然带着视图本身这个来源，K6 自然要求 `from this`（用例 G1 的 `leak`）。
   第 2 步进一步发现这条特例必须撤销：受信任的签名需要它所禁止的写法（§9.3 第 5 条）。
3. **父 loan 不随子 loan 延续，比 Rust 宽。** 父持有者死后，子借用只保护它自己所指的那部分存储；同一对象上不相交的字段可以被再次访问（用例 G2 的最后一个函数）。
   Rust 在同样的程序上会拒绝，因为重借使整个父借用保持存活。原型的做法在“字段不相交”成立的前提下是健全的，但这是一个与 Rust 不同的选择，应当明确裁决，而不是由实现默认带入。
4. **按值接收的视图参数上，`from s` 没有意义。** 参数在返回时就死了，“依赖持有者本身”无从谈起；原型把它判为签名错误，只允许 `from s.f`。这正是之二 §6 记下的“转发全部来源”的拼写问题，原型没有解决它。
5. **被覆盖之前不再使用的旧借用不算存活**（F5 接受、F4 拒绝）。这是 K3 的直接后果，初稿的用例清单没有覆盖，我最初写的预期是错的。

原型的近似之处，它们使原型偏保守，不影响上述结论：

- 一条语句之内不区分先后：语句用到的变量在整条语句期间都算存活。
- loan 以建立它的语法位置为身份，循环里同一位置的 loan 合并为一个。
- 不建模两阶段借用；`inout` 实参一律立即生效。
- 一处冲突之后的连带报告没有抑制；用例都写成只触发一处。

仍然没有回答的：这些规则是否健全。原型只说明规则在 29 个用例上给出了预期的结果。

## 9. 第 2 步：泛型、抽象签名与流向

对应评审 §5 的第三组验证（迭代、高阶借用函数、局部的视图容器）与 R6 要求的四种迭代。原型已实现，用例 H1–H6 通过。

### 9.1 增加的语法与规则

```text
函数    F ::= fun [<T, …>] g(m x: τ, …): ρ [from o, …] [flows o into x, …] [trusted] { … }
签名    S ::= sig [<T, …>] N(m x: τ, …): ρ [from o, …] [flows o into x, …]
类型    τ ::= … | T（类型参数）| fn N（合同为签名 N 的函数类型）
来源    o ::= x | x.f | x.*          x.* 表示转发 x 携带的全部来源
```

| # | 规则 |
|---|---|
| K12 细化 | 把函数 `g` 当作 `fn N` 类型的值使用时，`g` 声明的每个来源与流向都须被 `N` 的声明覆盖。覆盖关系：`x` 覆盖 `x.*`，`x.*` 覆盖 `x.f` |
| K13 不透明值 | 类型参数的值携带一组未知的来源，不可隐式复制。按值参数上 `from x` 等同于 `from x.*`，因为按值参数在返回时已不存在，没有“本身”可依赖 |
| K14 流向 | `flows o into x`：调用之后，`o` 所指的来源由实参 `x` 背后的持有者持有。函数体让某个来源流进了 `inout` 参数而签名没有声明相应的流向，按 K6 拒绝 |

接口方法与函数类型在原型里是同一个机制：一个抽象签名，加上 K12。原型没有接口声明，迭代器的 `next` 以函数类型的参数传入（字典传递）。

| H2 | 可同时保留多个独占元素的迭代器：受信任的 `next` 声明 `from it.data` 且结果为 `inout`，两个元素同时可写；非受信任的函数体做同样的事 | 前者接受；后者拒绝（K6） |
| H3 | 按出借式合同 `from it` 写的泛型算法：循环里一次取一个；同时持有两个；把转发式迭代器交给它 | 接受；拒绝（K4）；接受 |
| H4 | 按转发式合同 `from it.*` 写的泛型算法：同时持有并返回元素；返回的元素保护来源；独占的转发式迭代器交给它；出借式迭代器交给它 | 接受；写来源被拒绝（K1）；接受；拒绝（K12） |

### 9.3 发现

1. **四种迭代对应四种合同，不能归到一个接口。** 按值迭代没有来源；借用外部存储的是 `from it.字段`；多个独占元素并存的是受信任签名上的 `from it.字段`；出借式是 `from it`。
   泛型算法能依据的合同只有两种形状：
   - 出借式合同 `from it`：四种迭代器都满足它，但算法一次只能持有一个元素。逐个处理的算法（遍历、折叠、计数、存在性判断）按它写一次，对全部迭代器可用；`for` 应绑定这一种。
   - 转发式合同 `from it.*`：算法可以同时持有、返回、收集元素（排序、收集、带前瞻的配对、返回元素的最值）。出借式迭代器不满足它（H4 的最后一个函数）。

   所以标准库需要两个迭代接口，或一个接口加一个区分二者的标记；这回答了评审 R6 “哪些算法可以统一、哪些不能”。之十一 §2.3 已据此拆为 `Iterator` 与 `LendingIterator`（暂名）。
2. **“转发全部来源”的写法是必需的。** 泛型与接口的语境里没有字段名可写，之二 §6 建议的“借用字段名在 `from` 中总是可见”不够用。原型用 `x.*` 占位，正式拼写待定。按值参数上直接写 `from x` 即可（K13），这同时解决了 §8 第 4 条。
3. **来源合同需要第三种子句：流向。** 没有 `flows`，把视图放进一个已有的容器、收集借用元素都无法检查（H5）。之二把“origin 流入已有持有者”列在 L5 的待定项里；它是迭代与容器的必经能力，不是可选项。结构化并发的 `scope.launch(f)` 需要的是同一个子句。
4. **函数类型必须带来源合同**，并且合同之间有细化关系（H6）。这与接口方法是同一个机制，不需要两套规则。
5. **撤销“独占视图不提供转发”。** 多个独占元素并存的迭代器恰恰需要这种签名，只能由受信任的函数声明；非受信任的函数体写不出来（越过独占字段时累加来源，K6 拒绝）。所以它不是一条规则，而是“只有受信任代码才写得出”的后果。
6. **受信任签名的健全性依赖字段私有。** 探测程序：取出一个独占元素后，直接经迭代器的字段写同一块存储，原型接受。演算没有可见性；真实语言里必须靠“视图的独占字段对类型之外不可访问”来排除它。这是对之四 U0 合同的一条要求。

### 9.4 这一步没有回答的

- **可空元素的歧义**（评审 R6 的前半）：`next()` 返回值的类型怎样区分“元素是 null”与“迭代结束”，是类型表示的问题，不涉及来源，演算检验不了。之十一已改为返回不折叠的和类型。
- **类型参数是否可逃逸**。原型把每个类型参数都当作可能携带来源；“默认带可逃逸上界、显式放弃”这一层没有建模，所以答不了“现有泛型代码是否不受影响”。
- 没有检查类型实参与形参是否匹配；没有闭包捕获；没有真正的接口声明与见证。
- 规则是否健全，仍然没有证明。

第 1、2 步的发现已于 2026-11-14 并回[之二](evolution-02-route-loan-kernel.md) §2 与之十一 §2.3。

## 10. 第 3 步：存在类型的载荷访问与槽位访问

对应评审 R2 与[之三](evolution-03-route-existential.md) §2.4。原型已实现，用例 I1–I5 通过。这一步的发现已于 2026-11-14 并回之三 §2.4 与 §5。

记法说明：`any I`、`pack I(e)`、`*x = e` 与调用处的 `&mut` 都是演算自己的记法，不是 Koven 语法，也不是拼写提案。
Koven 里声明侧的 `inout x: T` 与泛型 `fun <T>` 是现行语法（Guide 03、08），调用处的独占标注写作 `&x`；存在类型是 v2 候选，之三的候选写法是直接以 interface 名作类型（`inout s: Shape`），隐式打包。
演算把它写成 `any I` 只为在规则里区分“具体类型”与“存在类型”。

### 10.1 增加的语法与规则

```text
声明    D ::= … | interface I | class C(…) is I, …
类型    τ ::= … | any I（接口 I 的存在类型）
表达式  e ::= … | pack I(e)（把实现 I 的具体类型的值打包为 any I）
语句    s ::= … | *x = e（经独占借用 x 整体替换它所指的值）
```

每个借用值多带一个标记：它是**槽位访问**（所指的存储恰好按它的类型存放）还是**载荷访问**（只知道所指实现了接口 `I`）。

| # | 规则 |
|---|---|
| X0 标记的来由 | 以下三处得到载荷访问：按 `borrow` / `inout` 接收 `any I` 的参数；返回类型为 `borrow` / `inout any I` 的调用结果；视图里类型为 `any I` 的借用字段，以及经它重借出来的借用。对拥有 `any I` 的变量或拥有字段取借用，得到槽位访问。移动、重借与分支合流保留标记 |
| X1 整体替换 | `*x = e` 要求 `x` 是槽位访问，且 `e` 的类型恰为所指类型。给拥有 `any I` 的变量或字段赋值，要求右侧是 `any I`（先 `pack`） |
| X2 槽位不变 | 形参写作 `inout any I` 时，实参所指可以是实现 `I` 的具体类型或 `any I`，被调用方得到载荷访问。形参是具体类型或类型参数 `T` 时，实参须是槽位访问，且 `T` 在一次调用里的各处实例一致 |

X2 的后半是对 `inout` 位置的不变性：`inout T` 既读出 `T` 也写入 `T`，所以所指类型必须恰为 `T`，不能是它的子类型或实现者。

### 10.2 用例

| # | 程序要点 | 预期 |
|---|---|---|
| I1 | 按 `inout any Shape` 接收后调用方法；以具体类型的位置或拥有存在类型的变量作实参；在函数体里 `*s = v`；把没有实现接口的类型交进去或打包 | 前两者接受；拒绝（X1）；拒绝（TYPE） |
| I2 | 评审 R2 的反例：`overwrite<T>(inout dst: T, own value: T)`，以 `Circle` 的位置和一个 `any Shape` 的值调用；在接收 `inout any Shape` 的函数里把它转交给 `overwrite`；先移动改名再转交；经 `inout Circle` 写入 `Square` | 全部拒绝（X2、X2、X2、X1） |
| I3 | 拥有存在类型的变量与字段：直接替换；取借用后 `*r = …`；交给 `overwrite`，此时 `T = any Shape`。具体类型的槽位交给 `overwrite`。把未打包的具体值赋给存在类型的变量；经返回 `inout any Shape` 的方法取得访问后整体替换 | 前四者接受；拒绝（X1）；拒绝（X1） |
| I4 | 载荷访问上的借用规则：访问存活时写来源；返回未声明的来源；同一个变量两次按独占交出 | 拒绝（K1）；拒绝（K6）；拒绝（K1） |
| I5 | 视图里存放 `inout any Shape`：经字段调用方法；经字段交给 `overwrite`。把载荷访问交给不做替换的泛型函数 `same<T>(inout x: T): inout T` | 接受；拒绝（X2）；拒绝（X2，保守） |

测试里增加了一条变异检验：去掉 X2 之后 I2 不再被拒绝。

### 10.3 发现

1. **评审 R2 的反例被两条规则排除，且两条都需要。** 直接调用靠“`T` 的实例须一致”（`Circle` 与 `any Shape` 不是同一类型）；经 `inout any Shape` 参数转交靠载荷标记。只做前一条时，转交这条路仍然通，因为在被调用方看来两边都是 `any Shape`。
2. **载荷与槽位是借用值上的一个标记，不是两种类型，也不需要两种拼写。** 之三 §2.4 的结论成立：`inout any I` 的参数总是载荷访问。标记由 X0 的三个来由决定，调用方不需要写任何东西。
3. **标记必须覆盖存进视图的借用。** 第一版原型只在参数上打标记，探测程序把 `&mut circle` 存进字段类型为 `inout any Shape` 的视图，再对该字段取借用交给 `overwrite`，原型接受了——这是一个真实的漏洞，已用 X0 的第三个来由补上（I5）。
   它说明“载荷访问”要跟着借用值走到每一处存放位置，包括之后的容器与闭包捕获；演算里只有视图字段这一种。
4. **“返回 `inout any I` 的总是载荷访问”有代价。** 类型自己的方法返回它内部一个真实存在类型槽位的独占借用时（I3 的 `slot`），调用方也不能经它整体替换，只能调用专门的替换方法或直接写字段。
   放开它需要在返回类型上区分两种访问，也就是一种新的拼写。建议先不加，等出现具体需求。
5. **载荷访问不能交给任何泛型 `inout T`，这是保守的。** `same<T>(inout x: T)` 不做替换，仍被拒绝（I5）。更要紧的是按 `inout T` 写的泛型算法（例如交换、就地排序的比较与移动）都不能直接用于一个 `inout any Shape`。
   精确的做法是“打开”存在类型：在调用处把 `T` 绑定为那个未知的具体类型。这样 `same` 可用；`overwrite` 仍被拒绝，因为拿不出一个类型恰为该未知类型的值。原型没有建模打开，这是之三需要回答的一个设计点。
6. **借用规则与这个标记正交。** I4 的三个拒绝与不涉及存在类型时完全相同，没有为存在类型改动 K1–K14 的任何一条。

### 10.4 这一步没有回答的

- 存在类型的打开（发现 5），以及泛型约束 `T : I`。原型的类型参数没有上界。
- 嵌套位置：`Box<any I>`、`List<any I>` 里的槽位，演算没有泛型类。按 X0 推断它们是槽位，但没有用例检验。
- 构造视图时没有核对借用字段的类型是否匹配；方法调用没有经过见证表，`any I` 上的方法在原型里是受信任的普通函数。
- 存在类型携带借用（`any I` 的载荷是一个视图）时来源怎样记录，没有建模。
- 大小、布局与析构：整体替换时旧载荷何时析构，属于之四，不在这一步。
- 规则是否健全，仍然没有证明。
