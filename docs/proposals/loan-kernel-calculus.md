# 借用内核演算（内核 MVP 第 1 步）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；规则为草案，原型已实现并通过 §5 的用例（2026-11-14），不构成健全性证明 · **读取时机**：实现或评审借用内核的参考检查器原型时；核对 [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R1 的验证用例时 · **唯一真源**：本页维护演算的语法、判定规则与用例清单；模型的来由见[演进总纲之二](evolution-02-route-loan-kernel.md) §2，现行借用规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权修改编译器。它描述的是目标模型（之二的 L1–L4），不是现行 v0.47 的调用期借用。

## 1. 目的与边界

评审的结论是先验证组合、再冻结内核。本页把之二的借用模型写成一个可以执行的最小演算，用来回答一个问题：
**“两种来源合同加一棵 loan 派生树”能否同时接受该接受的程序、拒绝该拒绝的程序。**

- 范围：评审 §5 的前两组验证——切片、自有字段视图、只读 guard；返回重借、`splitAt`、可变迭代器。
- 方法：一个独立的参考检查器，输入演算程序，输出接受或带位置的拒绝。它基于用例，不是健全性证明。
- 不在本步：泛型与迭代接口（第 2 步）、存在类型（第 3 步）、失败出口与清理义务（第 4 步）、闭包、可空类型、两阶段借用、线程、数值推理、`deinit` 函数体的内容。
- 某个用例必须靠“这个内建类型例外”才能通过时，结论是回到设计，不是给原型加特判。

## 2. 语法

条件一律写作 `*`，表示检查器不对取值做任何推理，两个分支都要检查。

```text
程序    P ::= D* F*
声明    D ::= class C(f: τ, …) [deinit]                 owned 类；deinit 只是一个标记
            | view class V(k f: τ, …)                   k ::= borrow | inout | （无，表示 owned 字段）
函数    F ::= fun g(m x: τ, …): ρ [from o, …] [trusted] { s* return e }
模式    m ::= own | borrow | inout
类型    τ ::= Int | C | V
结果    ρ ::= τ | borrow τ | inout τ | Unit
来源    o ::= x          结果依赖持有者 x 本身            （DependsOn）
            | x.f        结果沿用 x 的借用字段 f 的来源    （Forwards）
语句    s ::= val x = e | p = e | use(p) | g(a, …) | { s* }
            | if (*) { s* } else { s* } | while (*) { s* }
表达式  e ::= n | p | move p | &p | &mut p | C(e, …) | V(e, …) | g(a, …)
place   p ::= x | p.f
```

`use(p)` 是一次读取，只用于标出“这里还在用”。结果为借用的函数，`return e` 按“交出一个借用”求值：返回一个借用值即对它重借。`trusted` 的函数不检查函数体，只信任签名，对应 `unsafe` 实现的库函数。

## 3. 状态

检查器在每个程序点维护：

```text
Loan    = { id, place, kind: Shared | Exclusive, parent: Loan?, site }
Init(x) = Available | Moved | MaybeMoved             按字段细分到 place
Origins(h) = 持有者 h 持有的 Loan 集合                 h 是借用局部、视图实例（按借用字段细分）或调用的结果
Live(h) = h 在该点之后还会被使用                        后向分析
```

- 一个 loan 可以被多个持有者共同持有；只要有一个持有者存活，它就存活。
- 函数体内，每个借用参数与每个视图参数的每个借用字段，各带一个符号 loan，代表调用方那边的来源。

## 4. 规则

| # | 规则 |
|---|---|
| K1 冲突 | 对 place `q` 做种类为 `a` 的访问（读、写、移动、析构）时，若存在存活的 loan `l`，`q` 与 `l.place` 重叠，且 `a` 与 `l.kind` 不相容，则拒绝。相容矩阵沿用 Guide 10。经持有 `l` 的持有者所做的访问不算冲突，除非 K4 |
| K2 建立 | `&p` 在 `p` 上建立 Shared loan，`&mut p` 建立 Exclusive loan。`p` 若是经某个持有者到达的，新 loan 的 `parent` 是那个持有者据以访问的 loan（重借） |
| K3 存活 | loan 存活当且仅当它的某个持有者存活。持有者从定义起存活到最后一次使用，不到作用域结束。**实现时补充**：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活（见 §8 第 1 条） |
| K4 暂停 | 持有者 `h` 持有的 loan `l` 有存活的子 loan `c` 时，经 `h` 对与 `c.place` 重叠的 place 的访问，按 `c.kind` 判冲突 |
| K5 调用 | 对每个实参按参数模式建立 loan：`borrow` 建 Shared，`inout` 建 Exclusive，`own` 是移动。结果的 Origins 由被调方的合同决定：`from x` 则在实参这个 place 上建立一个子 loan 交给结果（结果为 `inout` 时是 Exclusive，否则 Shared）；`from x.f` 则结果取得实参视图的字段 `f` 当前持有的 loan。没有流入结果的实参 loan 在调用返回时结束 |
| K6 合同 | 函数体的返回值持有的每个 loan 必须被签名声明覆盖：落在参数 `x` 自身存储上的，或由借用 `x` 派生的，要求声明 `from x`；属于 `x.f` 的符号 loan 的，要求声明 `from x.f` 或 `from x`（后者更保守，也成立）；落在局部变量上的一律拒绝。结果为 `inout` 且来源 `x` 是独占视图时，只允许 `from x` |
| K7 构造 | `V(e, …)` 的实例在每个 `borrow` 字段上持有实参处建立的 Shared loan，在每个 `inout` 字段上持有 Exclusive loan；实参本身是持有者时，取得它的 Origins |
| K8 移动与初始化 | `move p` 之后 `p` 为 Moved；使用 Moved 或 MaybeMoved 的 place 拒绝。含 `inout` 字段的视图与 owned 类不可隐式复制；只读视图可复制，副本持有相同的 loan |
| K9 析构 | 作用域结束时，仍 Available 的 owner 按声明逆序析构；析构是对该 owner 的一次“析构”访问，按 K1 判冲突。带 `deinit` 标记的类不提前析构 |
| K10 合流 | 分支与循环的合流处：Origins 取并集；Init 取交（一条路径上 Moved 即为 MaybeMoved）；循环迭代到不动点 |
| K11 多结果 | 一次调用产生的子 loan 只有一个；结果若是含多个持有者的值（例如返回两个视图），它们共同持有这一个 loan。它们之间是否不相交不由检查器判断，只对 `trusted` 的函数成立 |

规则与之二的对应：K2、K4、K5 是 R4.4 的改写；K5、K6 是 R3.4 的两种来源写法；K6 末句是 R4.5；K11 是之二“不相交证明不由内核承担”。

## 6. 已知这一步答不了的

- **可同时保留多个独占元素的迭代器**。E1 只覆盖出借式。非出借式需要“独占视图把来源分给多个结果”，K6 末句禁止它，只能靠 `trusted` 签名；它如何进入迭代接口属于第 2 步。
- **转发的可见性**。类型之外的函数写 `from s.source` 时字段名是否总是可见（之二 §6 的建议），演算里没有可见性，答不了。
- **两阶段借用**。`list.push(list.size)` 一类写法现行规则靠 Reserved 状态接受，本步不建模；所有 `inout` 实参一律立即 Active，因此原型会比现行规则多拒绝这类程序。
- 规则是草案。实现过程中发现规则自相矛盾或某个用例两头都说不通，是这一步最有价值的产出，须记录在本页并回到之二修订。

## 7. 原型的形态与验收

**现状（2026-11-14）**：原型在 `scripts/loan_kernel/checker.py`，用例在 `scripts/loan_kernel/cases/`（29 个文件，每个文件里以 `// ERR 规则` 标出预期被拒绝的行），

没有接入 CI，没有接入编译器。下面是写原型之前定的形态与验收，保留作对照。


- 用 Python 写，放在 `scripts/` 下的独立目录，不进 Cargo workspace，不被编译器引用。包含：演算的解析、检查器、§5 的用例及其预期。
- 验收：§5 的每个用例得到预期结果，且拒绝的位置与规则相符；`scripts/tests/` 下有对应的测试可以一条命令运行。

## 8. 原型得到的发现

写原型的过程中，规则在五处与初稿不同或暴露了问题。前四条需要回到之二确认。

1. **K3 少了一条。** “依赖持有者本身”的结果持有的是视图变量存储上的 loan。初稿只说“持有者存活到最后一次使用”，于是视图在最后一次使用后就算死了，它持有的底层来源随之失效，
   而那个结果可能正指向底层数据（用例 A4：声明 `from this`、实际返回底层元素，这是 K6 允许的保守声明）。补充的规则是：存活的 loan 所指的存储若是某个持有者变量，该变量随之存活。没有它，A4 的第二个函数会被错误地接受。
2. **“独占视图不提供转发”不需要单列为规则。** 越过 `inout` 字段时累加所凭借的 loan，函数体返回的借用就必然带着视图本身这个来源，K6 自然要求 `from this`（用例 G1 的 `leak`）。
   K6 的末句只在 `trusted` 函数的签名上还有用，因为那里没有函数体可查。
3. **父 loan 不随子 loan 延续，比 Rust 宽。** 父持有者死后，子借用只保护它自己所指的那部分存储；同一对象上不相交的字段可以被再次访问（用例 G2 的最后一个函数）。
   Rust 在同样的程序上会拒绝，因为重借使整个父借用保持存活。原型的做法在“字段不相交”成立的前提下是健全的，但这是一个与 Rust 不同的选择，应当明确裁决，而不是由实现默认带入。
4. **按值接收的视图参数上，`from s` 没有意义。** 参数在返回时就死了，“依赖持有者本身”无从谈起；原型把它判为签名错误，只允许 `from s.f`。这正是之二 §6 记下的“转发全部来源”的拼写问题，原型没有解决它。
5. **被覆盖之前不再使用的旧借用不算存活**（F5 接受、F4 拒绝）。这是 K3 的直接后果，初稿的用例清单没有覆盖，我最初写的预期是错的。

原型的近似之处，它们使原型偏保守，不影响上述结论：

- 一条语句之内不区分先后：语句用到的变量在整条语句期间都算存活。
- loan 以建立它的语法位置为身份，循环里同一位置的 loan 合并为一个。
- 不建模两阶段借用；`inout` 实参一律立即生效。
- 一处冲突之后的连带报告没有抑制；用例都写成只触发一处。

仍然没有回答的：这些规则是否健全。原型只说明规则在 29 个用例上给出了预期的结果。
