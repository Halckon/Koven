# 演进总纲之十三：实施路线——从当前到 v1，从 v1 到之后

> **性质**：非规范候选计划 · **状态**：未启用 · **读取时机**：仅在安排 v1 之后各路线的先后，或检查 v1 收尾期间有哪些不可逆事项须先裁决时 · **唯一真源**：本页维护阶段划分、各阶段的入口与出口、v1 冻结前的裁决清单；v1 的范围、优先级与状态以 [Roadmap](../roadmap/README.md) 为唯一真源，各步骤的内容以[之一](evolution-01-kernel-and-decisions.md)至[之十二](evolution-12-stdlib-platform.md)为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。v1 路线图只登记了决策 D16（起草相关条目时审阅约束清单的义务），未改动任何条目的范围与状态。
它把前十二页的步骤排成可以执行的先后，并回答一个此前没有回答的问题：**v1 还在开发时，哪些事现在就要定**。

## 1. 当前位置

依据 v1 路线图 2026-11-06 的数据（基线为 Guide v0.47）。v1 的定义是“能写真实命令行工具的语言：单进程、同步 IO；
被接受的程序内存安全、资源确定性释放；AArch64 macOS 与 x86_64 Linux”。

| v1 阶段 | 内容 | 状态摘要 |
|---|---|---|
| S0 | 已交付基线 | 23 项完成 |
| P0 止血 | 调试产物、终止性、CI 工具链、测试诊断 | 6 项完成，4 项进行中 |
| P1 结构 | 编译器分层复审（SPEC-0392）、单文件并入编译单元管线（SPEC-0341）、通用所有权细化层 | 3 项全部进行中 |
| P2 补齐 | 现行 Guide 已定义而实现不全的能力 | 1 项完成，6 项部分完成，3 项未开始 |
| P3 语言增量 | 值语义协议、字符串插值、消费式匹配、不 abort 的 API 变体等 | 8 项完成，1 项部分完成，18 项未开始 |
| P4 文本与 IO | 文本 API、同步 IO、`main` 返回 `Result`、受限线程、`time` / `sleep` / `math` | 5 项全部未开始 |

P3、P4 大部分尚未开始，所以其中的公开表面现在还能调整，这是 §3 的前提。

## 2. 排序原则

1. **v1 期间不实现任何候选能力**。本系列在 v1 期间只产生三类动作：裁决（§3）、纯文档、以及 v1 本来就要做的工程里顺带满足的约束。
2. **同一时间只有一次迁移**。细化层迁移未完成，不启动所有权图（之八 J30）；所有权图未切换权威，不在其上叠加失败出口或帧变换。
3. **每条路线从一个不改变语言的步骤开始**：L0、C0、X0、U0、IR0、PL0、FD0 都是归一或文档。它们先做，因为做错了可以悄悄改。
4. **先内核后表面，先严后宽**。同一阶段里，被依赖最多的先做（能力引擎 C0 排在最前，见[之九](evolution-09-architecture.md) §3）。
5. **每个阶段以试金石程序收口**，不以“功能列表做完”收口。试金石写不顺，回到设计。
6. **版本号只是标签**。阶段之间的先后由依赖决定；某一步若提前具备条件，可以提前，不必等版本号。

## 3. v1 冻结前须裁决的事项

v1 发布后，公开的名字、签名与可观察行为只能增加不能修改（T3）。下列各项在 v1 的对应条目动工之前定下，成本接近于零；之后再定，都是破坏性变更。
每项只需要一个裁决，不需要实现任何新能力。

| # | 事项 | v1 路线图条目 | 建议 | 依据 |
|---|---|---|---|---|
| Z1 | 线程合同的措辞 | 受限线程（P4） | 写“任一线程 abort 导致进程终止”，不承诺其他线程在此之前停止运行；`join(): T` 保持；锁与 channel 的返回值为“对方异常终止”留出表达空间 | [之十一](evolution-11-failure-interfaces-units.md) J48 的预留 2、4 |
| Z2 | `time` / `sleep` / `math` 的包划分与命名 | 同名条目（P4） | 单调时钟与日历时间是两个类型；时区不进标准库；包名按之十二 §3 | [之十二](evolution-12-stdlib-platform.md) PL1 |
| Z3 | runtime 中系统调用的组织 | 同步 IO、线程（P4） | 动工时就收拢在一个模块后面，逐个写下与平台无关的合同 | 之十二 PL0 |
| Z4 | `Hashable` 的方法形状不向用户暴露 | 值语义协议（P3） | v1 只做结构推导与泛型上界，不公开“哈希值怎么算”的成员 | 之十一 J44：将来要用“写入哈希器”的形状 |
| Z5 | 显式流的关闭 | 同步 IO 的后继（“另行定义”） | 若 v1 内定义：关闭是消费资源并返回 `Result` 的方法；析构尽力关闭 | [之七](evolution-07-concurrency-async-io-ffi.md) J23 |
| Z6 | `main` 返回 `Result<Unit, E>` 对 `E` 的要求 | 同名条目（P4） | 保持“`E` 满足 `Display`”；将来的 `Error` 接口继承 `Display`，因此兼容 | 之十一 §2.3 |
| Z7 | 集合高层 API 的命名与接收者 | `forEach` 与高层 API、owned 集合算法（P3） | 命名取 Kotlin；签名按“将来接收者换成 `Iterable` 或视图也不必改名”审查 | 之十一 J43；[之六](evolution-06-text-globals-extensions-metadata.md) TX0 |
| Z8 | project 清单中的语言版本字段 | 发行（P5） | v1 的清单就带上该字段，即使只有一个合法取值 | 之十一 J47：没有它，以后启用保留字只能全局切换 |
| Z9 | 一致性矩阵的形态 | 一致性矩阵（P5） | 用例只含源码与期望的可观察结果，不引用编译器内部产物 | [之十](evolution-10-coverage-gaps.md) §7.9 |
| Z10 | `unsafe` 别名合同的“失败安全”条款 | 无（文档） | 在任何用户 `unsafe` 出现之前写入：`unsafe` 代码不得假设被调函数一定返回 | 之十一 J48 的预留 1 |

Z1–Z9 各自挂在一个已有的 v1 条目上。2026-11-11 用户要求把结论写入对应条目的 Spec；核对后这些条目尚无 Spec 草稿，因此可直接并入 Spec 的条款整理在 [v1 冻结前的兼容性约束](v1-freeze-decisions.md)，并在 v1 路线图登记为决策 D16。Z10 不属于 v1，条款见 [U0 提纲](unsafe-aliasing-contract-outline.md) §4。编号用 Z 是为了避开 v1 路线图已有的条目 V1–V6。

## 4. 阶段

阶段零是 v1 本身，其内部先后以 v1 路线图为准，这里不重复。阶段一至六是 v1 之后。步骤代号的含义见“详见”一列。

### 4.1 总览

| 阶段 | 版本标签 | 主题 | 是否有新的语言能力 | 对应总纲阶段 |
|---|---|---|---|---|
| 零 | → v1.0 | 完成 v1 | 仅 v1 路线图内的 | K0 的一部分 |
| 一 | v1.1 | 归一与测量 | 少量：借用的流敏感放宽、静态不可变存储，**合并为一个 Guide 小版本启用**（`Weak` 改列阶段三，见下） | K0 余下部分、K1 |
| 二 | v2.0 | 借用即类型、只读视图、动态分发 | 是 | K2、K3 |
| 三 | v2.1 | 独占视图、裸内存、容器库化 | 是 | K4、K6 |
| 四 | v2.2 | 共享、作用域线程、失败边界、平台层 | 是 | K5 |

| 六 | v4 及以后 | 系统级、向量、自举 | 是 | K8 |

2026-11-11 用户决定：原“阶段三”拆为两个版本（现阶段三、四）；阶段一的三项语言能力合并为一个 Guide 小版本；

v1 之后每个阶段各用一份路线图文件。版本标签的具体数字是占位，以届时的发布编号为准。

## 5. 关键路径

把各阶段里“别的步骤都在等它”的那一条串起来：

```text
v1.0 ─▶ 细化层收口 ─▶ IR0/ADR ─▶ IR1 = L0 ─▶ IR2 ─▶ IR3 ─▶ L2 ─▶ L3 ─▶ L4 ─▶ U2
                                    │          │                │
                                    C0 ────────┴─▶ C1           └─▶ X0 ─▶ X1 ─▶ X2 ─▶ X3
                                                                 U0 ─▶ U1 ─▶ C2、C4、FF1 ─▶ PL2
                                                   IR4 ─▶ IR5 ─▶ S3 ─┐
                                                   C3 ─▶ S2a ─▶ S2b ─┴─▶ S4（需 PL2）
```

三处最容易成为瓶颈：

- **所有权图的引入（IR0–IR3）**。阶段二及以后的几乎一切都假定检查在图上进行。它须在阶段一完成，且不能与细化层迁移重叠。
- **L3**。文本视图、借用迭代、借用闭包、分叉–合并、区域分配都等它。它是整个系列里验证设计是否成立的第一个大关口，应当最早拿试金石去试。
- **U1 → U2**。标准库“去特殊化”是系统级编程定位的验收，也是自举的前提；它同时依赖 L4、条件实现与标准库三分三件事，容易被其中任何一件拖住。

## 6. 每一步的固定流程

沿用[总纲](ownership-references-dyn-evolution.md) §11.1，不新增流程：独立 proposal → 试金石程序先行 → 用户启用新 Guide 版本 →
需要长期决定的表示写 ADR → 按 Phase 拆 Spec（分支开发，先失败测试）→ 出口时核对退役清单并同步 Architecture。
v1 之后每个阶段各用一份路线图文件（2026-11-11 用户决定），在该阶段入口条件满足时建立；本页不承担状态跟踪。

建立这些文件时有两件事要处理：

- 现行生成脚本只读取 `v1.json`，需扩展为按文件生成视图；这是工具改动，届时立 Spec。
- **条目编号会与本系列的步骤代号相撞**。v1 路线图已经使用 `L1`–`L21`、`S1`–`S7`、`X02`–`X12`、`V1`–`V6` 作为条目编号，
  而本系列用 `L0`–`L5`、`S1`–`S5`、`X0`–`X4` 表示路线步骤。登记到新的路线图文件时，步骤代号一律带路线前缀（例如 `RL-L3`、`RS-S2a`），不直接用作条目编号。

## 7. 近期可以做的事

按“不需要等任何东西”排序。第 1 项作用于 v1 条目的 Spec 起草，其余不触及 v1 的范围：

2. 把 [U0 提纲](unsafe-aliasing-contract-outline.md)补成完整合同：失败安全条款与内存模型取向已有草案，其余各节待写。

## 8. 开放问题

- FD（线程失败边界）留在阶段四还是推迟到阶段五之后；它与 S4 的执行器设计相互影响。
- 阶段一的 Guide 小版本只含 L1 的两项放宽（有限的流敏感、多来源 `from`）与静态不可变存储；可空借用结果属于 L2，在阶段二。`Weak` 是否接受移到阶段三，待用户确认。
- 阶段一的工作量与“小版本”的标签不相称：它包含所有权图的建立与权威切换，是整条路线里工程量最大的一段。标签只描述语言表面的变化量。
- [evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md)（2026-11-13）的结论是：主方向保留，但当前候选不能冻结为可实施的健全性合同，应先用小型语义原型验证五组组合再安排版本。八项发现中只有 R4 的资源保活部分经讨论形成了原则并已吸纳（[IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md)）；其余七项、R4 的失败域建议与三项架构建议都待裁决。在此之前，§4 的阶段划分只是排序假设。
- 独立复审（2026-11-11）指出、本轮**尚未处理**的不一致，进入各阶段路线图之前须逐项收口：
  - 依赖：C1 与 IR2 互相引用的先后；X0 的借用闭包部分需要 X1；FD2 对 IR4 的依赖未画进之一的依赖图；环绕算术在 VE0 与 VE1 的归属不一致；L1 应排在 IR3 之后还是之前；AT0、AT1、BS0、全局可变状态（之六 S3）与形式化小演算没有落在任何阶段；TX3 的位置；路线 F 的 F3–F5 须早于阶段一的新语法。
  - 代号重复：D10、A1–A9、E1–E5 等在不同页面指不同对象。
  - 内核：`DropPolicy` 是按 place 的事实还是按类型的性质，各页表述不一；之九的五类判定未覆盖来源合同、不可移动帧的状态、两阶段借用与失败出口。
  - 一致性规则（J37）：泛型 interface 的实参是否参与“同一实现”的判定、重叠检查的算法、对全部类型的一揽子实现，都未回答；`Comparable<T>` 一行与此相关。
  - 之十二中熵源的阶段标注。
- 各阶段路线图文件的命名与生成脚本的扩展方式。
