# Parser 文法与验证实施建议：评审与路径分解

> **性质**：非规范候选设计（评审意见与实施路径建议） · **状态**：未启用 · **读取时机**：仅在规划 parser 文法形式化、恢复机制收敛或新表面语法的文法门禁时 · **唯一真源**：本页维护对 `docs/Koven_Parser_Grammar_Implementation_Plan_2026-11-08.md` 的评审结论与分解后的路线 F；语言语义仍以 [Guide v0.47](../guide/README.md) 为准，parser 内部合同仍以 [Compiler Contracts](../compiler-specs/README.md) 为准

本文不修改 Guide 或 Compiler Contracts，不批准 Spec。评审于 2026-11-10 在 `a775568f` 上以只读方式进行：
读了被评审文档、相关 Guide 条文、parser 目录结构与提交历史；**没有运行任何 parser 测试，也没有逐行审阅 parser 实现**。
涉及实现结构的判断均标为假设，须由 F0 验证。

## 1. 结论

1. 被评审文档在方法上是严谨的：证据分级、接受的定义、soundness 的论域、恢复与合法语法分轨、不让实现反向定义规范，这些都应保留。
   它指出的三处 Guide 内部冲突（D1–D3）经核对全部属实。
2. 但它回答的主要是“**合法语法**是否无歧义、实现是否与文法一致”，而返工的实际来源不在这里。
   parser 目录下共有 33 个 `fix(parser)` 提交，按标题判断其中 31 个是错误恢复中的边界与归属问题；
   29 个集中在 2026-11-07 至 11-10 这四天内。
   文法证明——无论做到哪一级——对这类问题没有作用，因为非法输入本来就没有文法推导。
3. 所以“先做形式化证明能否从根本上解决返工”的答案是：**不能**。它能解决的是另一类风险（新语法引入歧义、AST 与规范不符），
   这类风险在后续演进中会变得重要，值得做，但应排在恢复机制的结构性收敛之后，并控制在“机器文法 + 冲突检查 + 一致性 oracle”这一档，
   不追求对生产实现的机器证明。
4. 恢复问题更可能需要**构造上保证**而不是更多合同与测试：仓库里已经有 39 个变异矩阵测试文件，修复仍在以每天数个的速度出现，
   说明“写下合同再用测试守住”的边际收益已经很低。§4 给出一个待验证的结构性方向。
5. 文档需要分解。按依赖拆成路线 F 的六步（§5），其中 F0（重定基线与返工归因）和 F1（裁决 D1–D3）可以立即开始，互不依赖。

## 3. 评审意见

### 3.1 应保留的部分

- 接受的四分类（Accept / SyntaxError / ResourceLimit / InternalFailure）与“`Result::Ok` 不等于 Accept”。
- soundness 的论域不预先限制为合法输入；完备性以“预算充分”为前提且预算不成为隐含语法。
- 输入模型保留源码拼写、Span 邻接、trivia 中的换行、入口与上下文，不压缩为 token 种类序列。
- 规范化 AST 之前先提取依赖 Span 的身份（名称、字面量拼写、marker 的有无），并单独检查 Span。
- 未裁决的规则不得由现有 parser 输出充当金标准；pending 不计入通过。
- 证据状态分级，以及对 Kani、TLA+、Lean 各自结论范围的限定。

### 3.3 关于“形式化证明”与“AST 正确性”

把目标拆开看，各自的合适手段不同：

| 想保证的性质 | 合适的手段 | 证明是否必要 |
|---|---|---|
| 规范自身不矛盾 | 裁决 D1–D3 这类冲突；机器文法使矛盾无处藏身 | 否，靠评审 |
| 合法语法无歧义 | 机器文法 + LR 类冲突分析；对需要谓词消歧的地方逐条登记 | 冲突分析本身就是机械证据，够用 |
| 实现接受的恰是文法规定的 | 文法驱动的句子生成（正例）+ 变异（反例）+ 差分 oracle | 否，测试级证据即可；机器证明成本与 parser 变化速度不匹配 |
| AST 结构正确 | 规范化 AST 的金标准 + 打印-重解析往返 + 格式化器往返 | 否 |
| 恢复不越界、不死循环 | 构造上保证（§4）；剩余部分用现有变异矩阵 | 结构优先于证明 |
| 小而稳定的算法正确（lambda header DFA、类型实参预索引） | 可选的有界模型检查或机器证明 | 可选 |

## 4. 恢复机制的结构性方向（假设，待 F0 验证）

31 个修复的标题高度同构：“在 Y 损坏后保留 X”“把 X 留在其 owner 内”“不取走调用方的边界”。这是同一条不变量
（被评审文档的 R1：局部结构只消费自己的分隔符，调用方的 stop 与 closer 必须保留）在不同调用点上反复被违反。
当一条不变量需要在几百个传参位置上分别维持时，逐个修复不会收敛。

可评估的方向是把这条不变量从“约定”变为“构造”：

1. 在词法之后、语法之前，先建立一棵**分隔符 owner 树**：圆括号、方括号、花括号、字符串插值各自成组，每组记录起止 lexeme。
   `LexicalRecoveryIndex` 已经索引了其中相当一部分信息，这一步是把它提升为解析的输入结构，而不是恢复时的查询。
2. 解析某一组的内容时，子解析器拿到的是该组的 **lexeme 区间**。它在物理上读不到区间之外的 token，
   因而不可能消费调用方的 closer 或越过父结构——R1 由构造成立，不需要每个调用点传递并正确组合 hard stop。
3. 停止集只保留**软停止**（同一组内的同步点：声明起始词、分隔符、换行），数量与组合方式大幅减少。
4. 不可避免的启发式集中到一处：未闭合分隔符应在哪里“补上”闭合。这是唯一需要按语言习惯决策的地方
   （例如声明起始词出现在行首时闭合内层花括号），集中之后可以单独规定、单独测试。

需要注意的边界：尖括号不是词法分隔符（`<` 可能是比较），不能进入 owner 树，类型实参仍由现有试探处理；
这一方案也不改变合法输入的解析结果，现有全部正例与变异矩阵可以原样作为回归。

这是基于提交标题与模块结构的推断。F0 的归因若显示多数修复并非“越界消费”一类，则本节不成立，应另寻原因。

每一步都给出止损上限。F0 与 F1 互不依赖，可立即开始；其后两条支线（F2 恢复、F3–F5 文法）可并行。

|---|---|---|---|
| F0 重定基线与返工归因 | 在当前 HEAD 重新固定 SHA；把 33 个修复逐个归类：违反的是 R1–R5 中哪一条、根因在哪个调用关系、当时哪个矩阵本应发现、“子解析器只能看到自己的区间”是否足以避免 | 一张归因表；§4 假设成立与否的结论；SPEC-0392 中仍开放的 R1 条目清单 | 只做分类，不修任何缺陷 |

| F2 恢复的结构性收敛 | 前提：F0 支持 §4。设计 owner 树与区间化的子解析入口；按结构家族逐个迁移（类头与父类型 → 调用实参与分组 → 索引 → block 与 lambda → 字符串插值） | 每个家族一片；Compiler Contracts 中 R1–R5 的合同页 | 门槛是现有正例与矩阵全部不变（已登记为缺陷的除外）；某一家族迁移后若修复流未减少，停下复盘而不是继续迁移 |

### 5.1 F5 需要把关的近期语法

来自[演进总纲](ownership-references-dyn-evolution.md)各路线，按出现先后：

| 语法 | 来源步骤 | 主要文法风险 |
|---|---|---|
| `from a, b`（多来源） | L1 | 逗号在参数表、返回类型之后与函数体或 `=` 之前的归属 |
| `borrow T?`、`inout T` 作为类型 | L2、L4 | 类型位置的前缀修饰与 nullable 后缀的结合方向；与参数 mode 的同形 |
| 可重绑定的借用局部 | L2 | 与现行 `borrow val` 的声明形态一致性 |
| `view class`、`borrow val` 字段 | L3 | `view` 作为上下文关键字；与以 `view` 为名的标识符共存 |
| 下标读写糖 | L4 之后 | 已有封闭的索引语法，需确认脱糖不改变求值顺序条款 |
| 匿名对象 `object : I { … }` | X4 | 表达式位置的 `object` 与声明位置的具名 object |
| `sealed` | X4 | 已是保留字，风险低 |
| `unsafe { … }`、`extern "C"` | U1、U3 | `unsafe` 块与尾 lambda、普通 block 的区分；字符串字面量出现在声明头 |
| `from` 指名静态声明 | [之六](evolution-06-text-globals-extensions-metadata.md) J5 | `from` 之后由参数名扩展为限定名；与多来源的逗号列表叠加 |
| 扩展函数声明 `fun <T> a.b.C<T>.name(…)` | 之六 J9 | 最后一个 `.Identifier` 才是函数名；接收者类型的泛型实参与限定名、函数自身的类型参数表相邻 |
| 通用注解 `@Name(实参)` | 之六 AT0 | 注解可出现的位置集合；与现行“拒绝任何 `@`”条款的衔接；实参表与其后声明头的分界 |
| `yield`、`suspend` 修饰与 `suspend` 函数类型 | [之七](evolution-07-concurrency-async-io-ffi.md) S3、S4 | 已是保留字；`suspend` 在函数类型前缀位置与 `move` 前缀的次序；`yield` 作为表达式还是语句 |

这些语法都还没有定稿。F5 的意义在于：在它们进入 Guide 之前，用机器文法检查一遍，而不是等 parser 实现后再以修复的形式发现问题。

## 6. 对“是否先做形式化”的回答

- **先做的**：F0（一两天量级的归因）与 F1（三个决策）。两者都不需要任何新工具。
- **紧接着做的**：F2。它针对的是已经发生、且仍在发生的返工。
- **在引入下一批新语法之前做完的**：F3 到 F5。它针对的是将要发生的返工。
- **不建议作为前置条件的**：对生产 parser 的整体机器证明。parser 仍在快速变化，证明会随每次修复失效；
  而上面的组合已经覆盖了证明想要防住的绝大部分问题。

## 7. 开放问题

- F1 中 D1 的裁决是否构成语法变化（Guide 03、04 的产生式需改写以包含尾 lambda 后缀）；按文档治理，这可能需要提升 Guide 版本，由用户判断。
- F2 的 owner 树是否作为 `LexedFile` 的一部分发布（影响 LSP 与格式化器的复用），还是 parser 内部结构；前者需要 ADR。
- tree-sitter 文法目前声明了 8 组冲突；用作 oracle 前需确认它在首批切片上的覆盖是否足够，否则 F4 的第二种 oracle 降级为观察项。
- 机器文法的具体记法与工具选型，留给 F3 的 Spec 并在其中完成依赖审计。

## 8. 工作量估计与 Spec 切分（2026-11-11 增补）

### 8.1 工作量

规模参照：parser 目录现有约 1.33 万行非测试 Rust 代码、29 个源文件，另有变异矩阵测试；2026-10 以来提交标题涉及 parser 的提交有 47 个。
以下估计以“Spec 个数与触及面”表示，不给日历时间；它们基于本页的只读评审，F0 完成后应修正。

| 步骤 | Spec 数 | 触及面 | 规模 | 风险 |
|---|---|---|---|---|
| F0 | 1 | 只产出文档 | 小 | 低 |
| F1 | 1（三项裁决合一），外加可能的 Guide 修订 | Guide 三处文字、少量正反例 | 小 | 低；D1 若算语法变化需提升 Guide 版本 |
| F2 | 1 个设计 + 5 个家族迁移 = 6 | parser 的恢复路径，逐家族改写子解析入口 | **大**，是整条路线的主体 | 高：改动面广；但有全部现有正例与矩阵作回归 |
| F3 | 4（词法、表达式、泛型调用与 lambda、声明）+ 1（一致性校验脚本） = 5 | 新增文法文件与脚本，不改 parser | 中 | 中：记法与工具选型需过依赖治理 |
| F4 | 3（句子生成、tree-sitter 差分、往返） | 测试设施，不改 parser | 中 | 中：规范化 AST 的定义会暴露分歧 |
| F5 | 1 | proposal 模板与评审清单 | 小 | 低 |
| F6 | 0–2，可选 | — | — | 没有明确动机就不做 |

合计 17 个左右。结论：**总量不小，但集中在 F2**；F0、F1、F5 加起来是三个小 Spec，F3、F4 不触碰生产 parser，可以与其他工作并行。
F2 是否值得做、做多大，取决于 F0 的归因结果，所以现在能确定下来的只有前两个。

### 8.3 与 v1 的关系

- 序 1、2 是纯文档与小改动，可以在 v1 期间做。序 1 的结果还直接服务于 SPEC-0392 的 parser 部分。
- F2（序 3–8）改动生产 parser。v1 期间是否启动，取决于两件事：序 1 是否支持 §4，以及 parser 修复是否仍在以近期的速度出现。
  2026-11-11 核对：标题为 `fix(parser)` 的提交仍是 33 个，最后一批在 11-10；但本地 HEAD 的日期是 11-11，只隔一天，据此无法判断修复流是否已经停止。
  若修复已经明显减少，F2 可以推迟到 v1 之后；若没有，推迟只会让 v1 的 P3（其中多项需要新语法）继续承受返工。
- F3–F5（序 9–17）的时限是[演进总纲之十三](evolution-13-implementation-roadmap.md)的阶段二：第一批新表面语法进入 Guide 之前。
