# 演进总纲之五：数据结构适配性检验

> **性质**：非规范候选设计（检验记录） · **状态**：未启用 · **读取时机**：仅在评估所有权/引用设计能否支撑常见数据结构与并发原语的库实现，或排查基底能力缺口时 · **唯一真源**：本页维护逐项适配结论与检验发现的缺口；基底能力定义见[之一](evolution-01-kernel-and-decisions.md)，路线步骤见[之二](evolution-02-route-loan-kernel.md)、[之四](evolution-04-route-capability-unsafe-suspend.md)

本文不启用任何规则。“今天”一栏依据 Guide v0.47 的条文判断，**没有实际编译或运行验证**；每一项落地前应先写成试金石程序实测。
代号：L/X/C/U 指路线步骤；KB 指基底能力。

## 1. 结论

1. 用**索引或句柄**表达链接关系的结构（图、双向链表、LRU、并查集、跳表）不依赖任何新能力，按现行规则就应当能写，
   代价是边界检查与一次间接寻址。这印证了“长期关系走句柄”是可用的默认路径，而不是权宜之计。
2. 用**唯一 owner 链**表达的结构（单链表、栈、二叉树、表达式树）现行规则已支持声明与递归操作；
   缺的是迭代式遍历所需的“可重绑定借用局部”和迭代式析构，两者都是检验中新发现的缺口（§4 的 G4、G3）。
3. 需要**共享与回指**的结构（指针式双向链表、带父指针的树、观察者）在路线 C 的共享库之后可在安全代码中写出；
   想要零检查开销的版本属于库作者的 `unsafe` 工作，应用层不受影响。
4. **并发原语**全部可以是库，但依赖最多：内部可变标记、原子 intrinsic、`Shareable`、外部函数。
   其中条件变量的通用形态还依赖独占视图（L4）。
5. Java 的 **AQS 不应照搬**：它的无锁等待队列依赖 GC 回收节点、依赖类继承做模板方法。
   Koven 的等价物是“原子状态 + 线程挂起原语”之上的一组小类型，结构更接近 Rust 标准库与 parking_lot 的做法。
6. 检验共发现 6 处需要处理的缺口（§4），其中 2 处已反映到之四（内部可变标记下沉、原子 intrinsic），
   3 处是新的待决项（析构中的字段移出、可重绑定借用、元素对换），1 处是路线依赖（条件变量依赖 L4）。

## 2. 顺序与链接结构

| 结构 | 今天（v0.47 条文） | 终态的推荐写法 | 依赖 | 应用层需要 `unsafe` |
|---|---|---|---|---|
| 栈 | `MutableList` 的尾部增删 | 同左 | 无 | 否 |
| 队列、双端队列、循环队列 | 以 `Array<T?>` 或 `MutableList<T?>` 加头尾下标实现环形缓冲；空位用 null 表示 | 库内以裸缓冲实现、不要求元素可空的 `Deque<T>` | 终态需 U1、U2 | 否 |
| 单链表（唯一 owner） | `class Node(var value: T, var next: Node?)`；头插、头删用 `replace`；递归遍历与递归插入可写 | 加迭代器视图与游标 | 迭代遍历需 G4；迭代器需 L3；中间插入的可写游标需 L4 | 否 |
| 二叉树、表达式树（唯一 owner） | 子节点为 `Node?` 或 `Box`；递归操作可写 | 同左，加遍历视图 | 同单链表 | 否 |
| 带父回指的树、DOM | 父子关系用下标存放在同一个 `MutableList<Node>` 中 | 句柄版同左；指针版用 `Rc` + `Weak` | 指针版需 C1、C4 | 否 |
| 双向链表、双向循环链表 | 下标版：节点存 `prev`/`next` 下标 | 下标/句柄版为默认；标准库提供的 `LinkedList<T>` 内部用裸指针 | 标准库版需 U1；`Rc`+`Weak` 版需 C2、C4 | 否 |
| 图 | 邻接表存下标；节点句柄可用 `value class NodeId(val index: Int)` | `Arena<T>` + 代际 `Handle<T>` | 代际检查是纯库逻辑；零开销版需 U1 | 否 |
| 二叉堆、优先队列 | 元素 `Copyable` 时用下标读写可写；元素 `MoveOnly` 时缺少对换两个元素的手段（G5） | `MutableList` 之上的库 | G5 | 否 |
| 哈希表 | 内建 `Map` | `.ko` 实现 | U2；查找返回可空借用需 L2 | 否 |
| B 树、字典树、并查集、跳表 | 节点内用定长或可增长容器 + 下标 | 同左 | 无 | 否 |
| LRU 缓存 | `Map` + 下标式双向链表 | 同左 | 无（终态用句柄） | 否 |
| 持久化（结构共享）结构 | `Rc<T>` 共享不可变子结构，无环 | 同左 | 无 | 否 |
| 侵入式容器、自引用结构 | 不可表达 | 仅库作者以裸指针实现 | U1 | 仅库内部 |

读法：除最后一行外，没有任何结构要求应用层写 `unsafe`；“依赖”一栏为空或只含 G 项的，说明现行内核已经足够，欠的是小的规则放宽或库 API。

## 3. 并发结构

| 结构 | 可否库实现 | 需要的基底与步骤 | 说明 |
|---|---|---|---|
| `AtomicLong`、`AtomicBoolean`、`AtomicRef` | 可以，很小 | KB6 内部可变标记（C2）、原子 intrinsic（U1）、受信任的 `Shareable` 声明（C3） | 方法都是对 `this` 的共享借用上的整值操作，不借出内部引用 |
| `Mutex<T>`、读写锁、信号量、闭锁 | 可以 | 原子状态 + 线程挂起原语（经 `extern "C"` 取得）+ C3 | 首选 `withLock { inout state -> … }`；返回 guard 的形态需 L4 |
| 条件变量 | 可以，但分两档 | 作用域档：同 `Mutex`；通用档：另需 L4 | 见下文 |
| 阻塞队列 | 可以 | `Mutex` + 条件变量 + `Deque` | 生产者-消费者场景现行 `Sender`/`Receiver` 已覆盖；有界阻塞队列需要这里的通用实现 |
| 线程池、作用域线程 | 可以 | C3、非逃逸闭包、KB7 | 见之四 C4 |
| 分段加锁的并发哈希表 | 可以 | `Arc`、`Mutex`、C3 | 普通库工作 |
| 无锁队列、无锁栈、无锁哈希表 | 可以，但属于高阶库 | 原子 intrinsic + 一套安全内存回收方案（epoch 或 hazard pointer），全部在 `unsafe` 内 | 没有 GC 的语言都要面对回收问题；内核不需为此增加任何东西 |
| AQS | 不照搬 | — | 见下文 |

### 条件变量为什么依赖独占视图

等待必须“原子地释放锁并挂起，醒来后重新持锁”。在 `withLock { inout state -> … }` 的作用域形态里，`state` 的独占借用在整个 lambda 期间存活；
如果在其中调用一个会释放锁的 `wait`，别的线程就会在这个独占借用仍然存活时修改同一状态，违反 KB2。因此：

- 作用域形态只能提供把等待与条件判断打包的组合子，例如 `mutex.withLockWhen({ s -> 条件 }) { inout s -> … }`：
  等待期间不向用户交出任何借用；
- 通用的 `wait` 需要 guard 是一个可以被**移入等待调用、再移出返回**的独占视图（即 Rust `Condvar::wait(guard) -> guard` 的形态），依赖 L4。

多数阻塞队列、闭锁、屏障只需要前一种，所以共享库（C4）不必等 L4；需要在一次持锁期间多次、在不同条件上等待的代码才需要后一种。

### AQS 为什么不照搬，以及等价物

`AbstractQueuedSynchronizer` 由四样东西组成，逐项对应如下：

| AQS 的组成 | 依赖的 Java 特性 | Koven 的对应 |
|---|---|---|
| 一个 `int` 同步状态，CAS 更新 | `Unsafe` / VarHandle | 原子类型（上表第一行） |
| CLH 变体的无锁等待队列 | **GC 回收出队节点** | 不复刻。等待者管理交给“线程挂起原语”（操作系统的 futex 类设施内部自带等待队列），或用一把内部小锁保护的普通队列 |
| `park` / `unpark` | JVM 内建 | 经 `extern "C"` 封装的库类型 |
| `tryAcquire` 等可覆盖方法 | **类继承**（模板方法） | interface + 泛型组合：`Synchronizer<P : SyncPolicy>`，策略以静态分发注入 |

结论：Koven 不需要、也不适合一个统一的 AQS 基类。需要的是“原子状态 + 挂起原语”这两个小构件，
`Mutex`、读写锁、信号量、闭锁各自在其上用几十行实现。公平性、可中断、超时等特性按需在各类型中提供。

## 4. 检验发现的缺口

| # | 缺口 | 触发它的结构 | 性质 | 处理 |
|---|---|---|---|---|
| G1 | 内核的内部可变入口不能是安全的 `Cell`：原子类型要求“内部可变且 `Shareable`” | 原子类型、`Mutex` | 内核设计修正 | 已修订之四 C2：内核只提供裸标记，`Cell` 下放为库 |
| G2 | 原子读写不能用普通裸指针读写表达 | 全部并发原语 | 内核 intrinsic 缺项 | 已加入之四 U1 的 intrinsic 集 |
| G3 | `deinit` 中 `this` 为只读借用，无法在析构时拆解自身；字段由编译器递归析构 | 长单链表、深树、任何长 owner 链 | 内核规则缺口 | **已决（2026-11-10）**：方案 a，见下 |
| G4 | 借用局部不可重绑定（现行禁止 `borrow var`），无法写迭代式游标 | 链表与树的迭代遍历 | 内核规则放宽 | **已决（2026-11-10）**：随 L2 启用，见下 |
| G5 | 无法对换同一容器中两个 `MoveOnly` 元素 | 二叉堆、原地排序、洗牌 | 库 API 缺项（近期），内核依赖（长期） | **已决（2026-11-10）**：补 `swap(i, j)`，见下 |
| G6 | 条件变量的通用形态需要可移入移出的 guard | 复杂的阻塞结构 | 路线依赖 | 已记入之四 C4：通用档依赖 L4 |

### G3 析构中的字段移出

现象：`class Node(var value: T, var next: Node?)` 组成的百万节点链表，析构时由编译器生成的字段析构逐层递归，栈深与链长成正比。
其他无 GC 语言有同样的问题，通行解法是在析构函数里用循环把后继逐个摘下。现行 Guide 08 规定 `deinit` 的 `this` 是只读借用，
摘不下来。

候选：

| 方案 | 做法 | 评价 |
|---|---|---|
| a | `deinit` 的 `this` 改为独占借用（`inout`） | 用户可在 body 中 `replace(&this.next, null)` 逐个摘链；body 结束时全部字段仍已初始化，编译器后续的字段析构不变。改动最小，且只用到现有原语 |
| b | 编译器对自递归类型生成迭代式析构 | 无语言变化，但只覆盖能被识别的形状（单后继），属于特判 |
| c | 提供“析构时解构自身”的专门语法 | 表达力最强，但引入部分移动，现行明确不支持 |

倾向 **a**。按之一的判据：它是一条规则的放宽（T3 可逆方向正确：先只读后独占是放宽），并使库作者能用公开机制解决问题（T1）。
b 可作为不改语言的近期缓解，但不应成为长期答案。

**用户决定（2026-11-10）：采用方案 a。** 现行规定只读是“先实现受限功能”，不是出于必须只读的语义理由，因此放宽方向成立。
放宽后仍须保持的约束：`this` 不得交给会存储它的位置（独占借用本来就不允许）；body 结束时全部字段仍已初始化；
`deinit` 内不得再次触发自身的析构。该决定只确定方向，Guide 08 的条文修改与实施仍需按流程单独启用。

### G4 可重绑定的借用局部

现象：迭代遍历链表需要 `cur = cur.next` 这样的游标推进。现行 `borrow val` 不可重绑定，只能写成递归。

在路线 L 的统一模型里，这不需要新机制：重绑定就是“旧 Holder 死亡、新 Holder 产生”，新值的 Origins 取代旧值的。
因为 Origins 是逐程序点跟踪的集合，循环回边上的合流照常取并集。建议作为 L2 的一条规则加入（已同步到之二）。

可写游标（遍历中插入或删除）是另一回事：它要求独占 Holder 重绑定为“自己所指对象的一部分”，这是 Rust 借用检查中著名的困难用例，
归入 L4，并应列入其形式化小演算必须覆盖的情形。在此之前，遍历中修改用递归（`fun insert(inout node: Node?, …)`）或下标式结构表达。

**用户决定（2026-11-10）：同意共享借用局部的重绑定随 L2 启用**（之二 R2.6）。表面写法仍待 L2 的提案确定。

### G5 对换同一容器中的两个元素

现象：`MoveOnly` 元素的堆调整需要交换 `a[i]` 与 `a[j]`。内建 `swap(&a, &b)` 要求两个 place 可证明不重叠，
而带运行时下标的 element place 无法静态证明。

处理分两步：近期给 `Array` 与 `MutableList` 补一个 `swap(i, j)` 成员（下标相等时为空操作），可并入[集合后续 API](collection-api-followups.md)评审；
长期在容器迁移到库（U2）后，它就是用裸指针实现的普通库方法，不占用内核。内核不引入下标不相交推理（之二 L4 已有同一结论）。

**用户决定（2026-11-10）：同意为 `Array` 与 `MutableList` 补 `swap(i, j)`。** 已登记到[集合后续 API](collection-api-followups.md)，签名与越界行为由其 Spec 确定。

## 5. 对路线的影响

- 之四 C2：内核原语由安全的 `Cell` 改为裸的内部可变标记；C2 因此依赖 U1。
- 之四 U1：intrinsic 集增加原子操作；线程挂起经外部函数取得，不设 intrinsic。
- 之四 C4：共享库增加条件变量，并区分作用域档与通用档。
- 之二 L2：增加借用局部重绑定规则；L4 的必测情形增加“可写游标”。
- G3、G4、G5 三项已由用户于 2026-11-10 决定（见 §4 各小节）；均为方向决定，不等于 Guide 已启用。
- 试金石程序集增补：百万节点链表的构造与析构（验证 G3）、迭代式链表遍历（G4）、`MoveOnly` 元素的堆排序（G5）、
  有界阻塞队列（条件变量作用域档）、`AtomicLong` 多线程计数（C2/C3/U1 合验）。

## 6. 不适用或不需要的

- 统一的 AQS 基类（§3）。
- 依赖 GC 的无锁算法原样移植；需要时以带回收方案的库实现。
- 依赖对象身份哈希、`synchronized` 对象头锁、`wait`/`notify` 对象监视器的结构：Koven 的对象没有隐含的锁与监视器，使用显式的 `Mutex` 与条件变量。
- 依赖类继承层次的集合框架（抽象基类 + 覆盖）：以 interface 与泛型表达。
