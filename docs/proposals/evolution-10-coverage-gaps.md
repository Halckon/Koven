# 演进总纲之十：尚未覆盖的领域

> **性质**：非规范候选清单 · **状态**：未启用 · **读取时机**：仅在检查中后期规划是否有遗漏领域，或为下一轮设计选题时 · **唯一真源**：本页维护缺口清单 W1–W20、归类与各项的方向稿；W1、W9、W10 展开于[之十一](evolution-11-failure-interfaces-units.md)，已覆盖领域以[之一](evolution-01-kernel-and-decisions.md)至[之九](evolution-09-architecture.md)为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。§2–§4 是清单：每项给出“缺什么、是否触及内核、倾向、接到哪条路线”。§7 是按倾向整理的方向稿，供立项时作为起点；它们仍是候选，细则须另立 proposal。
各项涉及的现行事实已于 2026-11-11 对照 Guide 核对，结果记在 §7 各小节的“现状”一行；未能核对的单独标出。

## 1. 怎样判断“没考虑到”

用[之九](evolution-09-architecture.md)的分层图逐层检查：每一层的接口是否都有人定义、每个扩展点是否都有设计。
再用三个问题筛出优先级：

- 它是否触及内核，或者做出一条日后无法收回的承诺（T3、T4）？是 → 现在就要定方向。
- 它是否是某条已排定路线的隐含前提？是 → 须排在那条路线之前。
- 都不是 → 它是库或工具，可以等到有需求时再做。

## 2. 触及内核或不可逆承诺的（应尽早定方向）

|---|---|---|---|---|

| W2 | **内存模型** | 什么算数据竞争、原子操作的顺序语义、`unsafe` 代码中哪些行为未定义。之四的 U0 定了别名合同，没有定并发下的内存模型 | 采用 C/C++ 的原子顺序模型（LLVM 直接支持），不自行发明。未定义行为清单与别名合同写在同一份文档里 | U0 扩充；须在 C3 与 U3 之前 |

| W6 | **标准库的切分** | freestanding 需要标准库分成“无分配 / 需分配 / 需操作系统”几部分；这同时决定了之九的 L4、L5 如何对应到包 | 三分，且自下而上单向依赖。切分线应在 U2 迁移容器时一并确定，否则迁移完再切要再搬一次 | U2 之前 |
| W7 | **数值语义** | 环绕、饱和、带溢出标志的算术；整数宽度转换；浮点的确定性与 NaN 的相等/排序 | 全部是库函数加少量内建运算，不引入新运算符；默认行为（溢出 abort）不变。浮点的相等与排序规则影响“通用接口”（W9），须先定 | 之八 J32 已提到命名；VE0 之前 |

## 5. 优先级

若只能先做四件，建议是：

1. **W1 失败模型**。它决定线程合同、`unsafe` 合同与所有权图的语句集里要预留什么；预留得晚了就不可补。
2. **W9 通用接口清单**。它决定路线 L 的验收目标与标准库的形状。
3. **W10 编译单元依赖与版本**。保留字的启用方式、一致性规则都依赖它。
4. **W11 调试信息**。它不依赖任何其他路线，现在就能开始，而且每条后续路线都会用到。

前三项已在之十一展开。W2、W4–W6 属于“系统级编程”一侧，可以随路线 U 一起展开，不必提前；它们的方向稿见 §7。

## 6. 开放问题

- W1：把 abort 定为唯一的不可恢复失败后，测试框架怎样断言“这段代码应当 abort”。现行 Guide 只为 `@Test` 预留了 `@` 记号，尚未定义其语法与运行方式；倾向是这类测试在子进程中运行。
- W3：常量泛型若只开放整数，定长数组的长度运算（拼接后长度相加）是否需要类型层面的算术；倾向不需要，先不支持这类签名。
- W4：返回 `Result` 的分配变体是否要覆盖全部容器操作，还是只覆盖预留容量一类。
- W10：语言版本按编译单元声明后，跨版本的泛型实例化以哪一方的规则检查（之十一 J47 给出了非泛型情形的规则）。

## 7. 方向稿

以下各节按 §2、§3 的倾向写成可以直接评审的方向。格式统一为：现状、规则、不做、落点。

### 7.1 W2 内存模型

- **现状**：Guide 未定义并发下的内存模型；v1 的线程只经所有权转移与 channel 通信，安全代码写不出数据竞争，所以至今不需要。
- **规则**：
  1. 数据竞争的定义沿用通行表述：两个线程访问同一内存位置，至少一个是写，且没有先后次序约束。安全代码中不可能出现；`unsafe` 代码中出现即未定义行为。
  2. 原子操作的次序语义采用 C/C++ 的模型，五个次序取值照搬，由 LLVM 直接实现。标准库的原子类型默认用最强的次序，较弱的次序须显式写出。
  3. 未定义行为清单与别名合同（U0）写在同一份文档里，逐条编号；清单之外的行为都有定义。
- **不做**：自行设计内存模型；提供“良性竞争”的例外。
- **落点**：并入 U0；须在 C3（`Shareable`）与 U3（向用户开放 `unsafe`）之前。

### 7.2 W3 泛型的其余部分

- **现状**：类型参数至多一个显式上界；泛型不变；没有默认类型实参、星投影、型变；不接受递归上界。
- **规则**：多约束与 `where`、条件实现、签名中的 `Self` 见[之三](evolution-03-route-existential.md) J38。常量泛型只开放一种：**整数常量作类型实参**，实参必须是编译期常量（KB9），类型层面不做算术。它服务两个用例：定长数组与向量宽度。
- **不做**：关联类型、型变、高阶类型、特化；类型层面的整数运算（例如“拼接后长度相加”的签名）。
- **落点**：J38 的四项在 U2 之前；常量泛型在 VE2（向量类型）之前，另立提案。

### 7.3 W4 分配与内存不足

- **现状**：分配由 native runtime 完成，失败的行为与可替换性未在 Guide 中作为用户可依赖的合同给出（本条未逐句核对 runtime 合同）。
- **规则**：
  1. 分配失败默认 abort。这与“不变量破坏即 abort”一致：绝大多数程序无法从内存不足中有意义地恢复。
  2. 容器另提供返回 `Result` 的预留容量操作（`tryReserve` 一类）。需要处理内存不足的代码先预留、再做不会分配的操作。不为每个操作都配一个可失败版本。
  3. 全局分配器在链接期可替换（之九扩展点）。不给容器加“分配器”类型参数：它会进入每个容器类型的签名，对绝大多数用户是纯负担。
  4. 区域分配做成库类型：从区域借出的值是不可逃逸视图，由路线 L 保证不超过区域存活；区域析构时整体释放。
- **不做**：每容器的分配器参数；垃圾回收的可选模式。
- **落点**：规则 1–3 随 U1；规则 4 需要 L3，是 L3 的试金石之一。

### 7.4 W5 布局控制与硬件接口

- **现状**：`extern`、`RawPtr`、`unsafe` 已从 Guide 移出为候选（[unsafe 与 FFI](unsafe-and-ffi-boundary.md)）；布局不向用户承诺。
- **规则**：
  1. 默认布局不承诺，编译器可以重排字段。需要确定布局时用注解声明（之六 J11 的“指示”类）：与 C 兼容、指定对齐、紧凑排列。
  2. 联合体只以 `unsafe` 读取的形态提供，用于 FFI；Koven 自己的和类型仍是 `enum class`。
  3. 易失读写是两个特权原语，不是类型修饰符；设备寄存器由库在其上封装。
  4. 内联汇编、链接段指定、中断入口放在最后，且只在 `unsafe` 中；它们是 freestanding（U4）的内容，不是通用功能。
- **不做**：位域语法（用库的掩码函数）；默认布局的稳定承诺。
- **落点**：1、2 随 FF0–FF1；3 进 U1 的原语清单；4 随 U4。

### 7.5 W6 标准库的切分

- **现状**：标准库是一个 crate 下的 `koven/**/*.ko`；允许加载的标准 package 是封闭清单。
- **规则**：分三个编译单元，自下而上单向依赖（受之十一 J45 约束）：
  1. **核心**：不分配、不依赖操作系统。基本类型的操作、`Result` 与可空类型的组合函数、通用接口（之十一 §2 的前六个）、原子类型、内部可变标记的安全封装。
  2. **分配**：需要全局分配器。`Box`、`Rc`、`List`、`Map`、`String` 的可增长部分。
  3. **系统**：需要操作系统。文件、网络、线程、时钟、进程。
- **要点**：切分线须在 U2（容器迁移）开始前确定，否则迁移完成后还要再搬一次。对应之九分层图：L4、L5 各自跨这三个单元，分层与切分是两个正交的维度。
- **落点**：U2 之前出切分方案；U4 验收“只链接核心单元的程序可以构建”。

### 7.6 W7 数值语义

- **现状**：整数溢出 abort，不做静默环绕；v1 不提供环绕或饱和变体，Guide 已写明将来作为标准库方法按需引入。浮点遵守 IEEE 754，不因 `NaN` 或无穷而 abort；浮点满足 `Equatable`、`Comparable`，不满足 `Hashable`。
- **规则**：
  1. 环绕、饱和、带溢出标志三组算术以方法提供，命名成组（之八 J32 已提到须定名）；不引入新运算符，不提供“本块内不检查溢出”的形态。
  2. 整数宽度转换沿用现行“检查版 abort、`OrNull` 版返回可空”的成对规则，补一组显式截断方法。
  3. 浮点另给一个全序比较函数供排序与作键使用；`<` 等运算符保持 IEEE 语义。浮点仍不满足 `Hashable`。
- **不做**：隐式数值转换；可配置的全局溢出行为。
- **落点**：1 在 VE0 之前（向量化基线需要环绕算术作对照）；3 随之十一的 `Comparable`。

### 7.7 W8 模式匹配与解构

- **现状**：`enum class` 可带载荷并有穷尽检查；有消费式结构解构；占位、跳过或丢弃分量的语法尚未定义；不允许经字段访问从聚合中移出。
- **规则**：
  1. 解构的每个分量有明确的模式：移出、共享借用或独占借用；默认随被解构值的持有方式而定（拥有则移出，借用则借用）。
  2. 部分移出之后，原值整体不可再用，剩余分量仍可单独使用，直到作用域结束时逐个析构。这是流敏感检查（L1）的直接应用。
  3. 占位符 `_` 表示“不绑定”：对拥有的分量是就地析构，对借用的分量是不取。
- **不排期**：`sealed`（按之一 D5 它是可独立交付的糖，与本节无依赖；有明确需求时再议）；模式中的任意表达式守卫以外的新形态先不加。
- **落点**：L1；语法先过路线 F 的 F5 门。

### 7.8 W11 调试信息

- **现状**：v1 路线图 P0 有进行中的“CLI 最终调试产物与双宿主源码断点”（SPEC-0369），Guide 13 规定 macOS 交付 `.dSYM`、Linux 保留源码行表；即下面第 1 步已在 v1 范围内。第 2、3 步未见规划。
- **规则**：分三步，每步独立可交付：
  1. 行号表：abort 报告与调试器能定位到源码行。
  2. 变量与类型：局部变量、参数、字段可查看；`enum class` 的当前变体、可空类型、`String` 有可读的呈现。
  3. 挂起帧（之七 J34）：帧内变量与恢复点。
- **要点**：调试信息来自 `Span`，而 `Span` 在各阶段已保留，所以主要工作在 codegen，不触及语义。发布构建可剥离。
- **落点**：1、2 不依赖任何路线，可立即立项；3 是 S3 的验收条件。

### 7.9 W12 一致性测试集

- **现状**：v1 路线图的 P5 已有“Conformance 矩阵：按 Guide 每章正反例”一项，状态为部分完成（见 [Roadmap](../roadmap/README.md)）；[Guide 15](../guide/15-conformance-and-staging.md) 有一致性与分期的规定。尚未确认的是该矩阵是否满足下面第 2 条（不依赖编译器内部产物）。本页初稿写“没有这样的测试集”不准确。
- **规则**：
  1. 以 Guide 章节为索引，每条规则至少一个接受用例与一个拒绝用例；用例只含源码与期望的可观察结果（退出状态、标准输出、诊断编号）。
  2. 不依赖编译器内部产物，因此可以对任何实现运行——包括将来用 Koven 写的编译器（之八 BS）。
  3. 候选能力的用例放在单独目录，随 Guide 启用而并入。
- **落点**：BS0 之前；它也是之九所说“语言对实现的窄接口”。

### 7.10 W13 参考解释器

- **规则**：编译期求值器（KB9）扩展到能执行完整的所有权图之后，同一个求值器就是不依赖后端的参考实现。用途有三：与原生执行做差分测试；执行一致性测试集；作为 `unsafe` 代码的未定义行为检测器的基础。
- **不做**：把解释执行作为面向用户的运行方式。
- **落点**：之八 IR5 之后；不单设路线。

### 7.11 W14 编译速度与增量编译

- **现状**：没有编译时间预算；单态化、所有权图、帧变换都会增加编译时间。
- **规则**：
  1. 每条路线的验收增加一项：在固定的基准程序上，编译时间的变化有记录并有解释。
  2. 增量编译的单位是函数：所有权图按函数构造与检查，函数签名不变则调用者不必重查。这要求所有权图的设计从一开始就不含跨函数的隐式状态（之八 IR1）。
  3. 编译单元之间经接口产物依赖（之十一 J46），接口不变则下游不重编。
- **落点**：1 并入[测量候选](measurement-distribution.md)；2 是 IR1 的设计约束；3 随 J46。

### 7.12 W15–W20 库与工具

这几项不触及内核，方向只需各一句：

- **W15 时间、随机数、环境、进程、信号**：经平台层实现。时钟区分“单调时钟”与“日历时间”两个类型；随机数区分“可复现的生成器”与“系统熵源”。信号只以“转成 channel 消息”的形态提供，不允许在信号处理函数里运行任意 Koven 代码。
- **W16 序列化**：只走生成（之六 J13）。标准库定格式无关的读写接口，各格式是独立的库。
- **W17 日志、追踪、度量**：库。上下文经作用域值传递（之六 J7），不经线程局部存储。
- **W18 文本其余部分**：字符属性、规范化、区域相关比较、正则表达式都在库；`String` 本身只承诺 UTF-8 与字节序比较（现行规则）。
- **W19 测试设施**：先定 `@Test` 的语法与“每个测试在何种隔离下运行”（影响 abort 的断言方式）；基准与模糊测试后置，后者需要编译器插桩接口。
- **W20 分发与目标**：交叉编译是 driver 的参数，不是语言特性；运行时加载的插件只经 C ABI；WebAssembly 作为一个目标后置，它没有线程与信号，正好检验 W6 的切分。
