# 演进总纲之十二：标准库清单与平台适配

> **性质**：非规范候选设计 · **状态**：未启用 · **读取时机**：仅在规划标准库各模块的范围、命名与先后，或设计跨平台适配方式时 · **唯一真源**：本页维护模块清单、平台层接口范围、决断 J51–J55 与步骤 PL0–PL4；现行标准库表面以 [Guide 13](../guide/13-program-runtime-standard-library.md) 为准，允许加载的标准 package 以 [Guide 02](../guide/02-names-files-packages.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。它把[之七](evolution-07-concurrency-async-io-ffi.md) §4 的 IO 分层扩展到全部与系统相关的库，
并回答“这些库如何在多个平台上保持同一套接口”。分层见[之九](evolution-09-architecture.md)，标准库三分见[之十](evolution-10-coverage-gaps.md) §7.5。

## 1. 现行事实（已对照 Guide 02、13 与 v1 路线图）

- 允许加载的标准 package 是封闭的四个：`koven.core`（`Result`）、`koven.algorithms`、`koven.text`、`koven.io`。
- `koven.io` 提供 `File`、`Directory`、`Path`、标准流、`IoError`、`DirectoryEntry`，全部是同步阻塞的便利函数；显式的流 owner 与关闭是后继合同。
- 线程与 channel 在 Guide 13 有合同，实现属 v1 的 P4，尚未开始；`time` / `sleep` / `math` 基础 API 同属 P4，尚未定义表面。
- 支持的目标是两个：AArch64 macOS 与 x86_64 Linux（glibc）。两者都是 POSIX 系，所以至今没有遇到真正的平台差异。
- 系统调用目前由 native runtime 发出，不经 Koven 源码；`extern` 与 `unsafe` 尚未启用。

## 2. 决断

| # | 决断 | 理由 |
|---|---|---|
| J51 | **标准库与系统相关的部分只经一个“平台层”接触操作系统**。平台层是一份封闭的函数清单（§4），每个平台各有一份实现；其上的全部标准库代码与平台无关 | 即[之九](evolution-09-architecture.md)的“窄接口”。移植到新平台的工作量因此是可数的：实现清单里的函数 |
| J52 | **可移植接口只承诺各平台都能给出相同含义的行为；平台特有的能力放在以平台命名的包里，显式导入** | 取“最小公分母”作可移植接口，用户不会写出只在某个平台上成立的代码而不自知。平台特有包（权限位、文件描述符、注册表）使差异在 `import` 处可见 |
| J53 | **某平台不具备的能力，对应的包在该平台上不存在，使用它是编译错误，不是运行时失败** | 无操作系统的目标没有文件，WebAssembly 的常见环境没有线程。运行时才发现“此平台不支持”是最差的一种失败。实现手段是源集（之七 J24） |
| J54 | **一律经平台的 C 库或系统库进入系统，不直接发出系统调用指令**（无操作系统的目标除外） | macOS 与 Windows 只把系统库的接口作为稳定边界，系统调用号不保证稳定；Linux 两者皆可，但统一走 C 库使三者同构。代价是依赖 C 库，这在 v1 的两个目标上已经如此 |
| J55 | **语义差异写进合同，不假装统一**。凡各平台行为不同而又无法抹平之处，可移植接口的文档逐条写明“保证什么、不保证什么” | Guide 13 已经这样做（例如写文件“不承诺原子替换与持久化”）。继续沿用，不引入“在某些平台上可能……”一类含糊表述 |

## 3. 模块清单

“层”指标准库三分中的核心（不分配、无系统）、分配、系统。“先后”一栏：v1 表示 v1 路线图已列入；其余为步骤代号，见各页。

### 3.1 不依赖操作系统的

| 包 | 内容 | 层 | 平台相关性 | 先后 |
|---|---|---|---|---|
| `koven.core` | `Result`、可空类型的组合函数、通用接口（[之十一](evolution-11-failure-interfaces-units.md) §2） | 核心 | 无 | v1 已有 `Result`；接口随之十一 |
| `koven.math` | 取整、绝对值、最值、幂与开方、三角与指数对数、常量；整数的环绕与饱和算术（之十 §7.6） | 核心 | 超越函数在不同平台的 C 数学库上末位可能不同；合同应只承诺 IEEE 规定必须精确的那几个（加减乘除、开方） | v1（基础部分） |
| `koven.text` | 文本解析、切分、构建 | 分配 | 无。只做与区域无关的操作 | v1；视图化见[之六](evolution-06-text-globals-extensions-metadata.md) TX |
| `koven.collections` | `List`、`Map`、`Set`、双端队列、堆等 | 分配 | 无 | 内建；迁为库见 U2 |
| `koven.random`（生成器部分） | 给定种子、结果可复现的伪随机数生成器 | 核心 | 无。同一种子在所有平台上给出同一序列，写入合同 | 阶段二 |

### 3.2 依赖操作系统的

| 包 | 内容 | 需要的平台能力 | 主要的跨平台差异 | 先后 |
|---|---|---|---|---|
| `koven.io`（标准流） | `stdin` / `stdout` / `stderr` | 读写三个标准句柄 | Windows 控制台的编码不是 UTF-8，须在平台层转换；是否连接终端的判断 | v1 |
| `koven.io`（文件与目录） | 读写、打开、元数据、遍历、删除、重命名 | 文件句柄操作、目录枚举 | 路径分隔符与盘符；Windows 路径本质是 UTF-16，且存在无法表示为 UTF-8 的文件名；重命名是否原子；大小写是否敏感；符号链接权限 | v1（便利函数）；IO0–IO1（显式流） |
| `koven.time` | 单调时钟 `Instant`、时长 `Duration`、日历时间 `SystemTime`、`sleep` | 两种时钟、休眠 | 时钟分辨率；休眠是否计入系统挂起的时间。**时区与历法不在标准库内**，只提供 UTC 与秒数 | v1（基础部分） |
| `koven.random`（熵源部分） | 从系统取不可预测的随机字节；用它为生成器播种 | 系统随机源 | 各平台接口不同但语义一致；早期启动阶段可能阻塞 | 阶段二 |
| `koven.process` | 命令行参数、环境变量、退出、当前目录；启动子进程、管道、等待 | 进程创建与等待 | 环境变量在 Windows 上不区分大小写；参数在 Windows 上是一整个字符串，需按约定切分；POSIX 的 `fork` 没有可移植的对应物，只提供“启动新程序” | 参数与退出：v1；子进程：IO3 |
| `koven.thread`、`koven.sync` | 线程、`Mutex`、条件变量、原子类型、线程停驻与唤醒 | 线程创建、等待队列 | 底层原语各不相同，但都能实现同一套语义 | v1（受限线程）；C4 |
| `koven.net` | TCP、UDP、地址类型、名称解析 | 套接字 | 名称解析在各平台都是阻塞调用；套接字选项的可用集合不同；Windows 需要初始化网络库 | IO3 |
| `koven.reactor`（暂名；`async` 是保留字，不能作包名的一段） | 异步 IO 的事件来源 | 就绪通知或完成通知 | **最大的结构性差异**：Linux 与 macOS 传统上是“就绪后再读写”，Windows 与 Linux 的新接口是“提交操作、完成后通知”。可移植接口须按“完成”模型设计，就绪模型可以包装成完成模型，反之不行。完成模型下，每个请求须有可验证的身份与代际，接管与终结逐请求取证，见 [IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md) | IO4 |
| `koven.signal` | 把终止请求等信号转为 channel 消息 | 信号或控制台事件 | Windows 没有 POSIX 信号，只有少数几种控制台事件。可移植接口只承诺“中断”与“终止”两种 | IO3 之后 |
| `koven.mem` | 全局分配接口、按页申请内存 | 堆分配、页映射 | 页大小不同 | U1 |
| `koven.dylib` | 运行时加载动态库并查找符号 | 动态加载器 | 文件扩展名与搜索规则不同 | FF3 之后 |
| `koven.os.unix`、`koven.os.windows` 等 | 权限位、文件描述符、用户与组；句柄、注册表 | 各自平台 | 按定义不可移植（J52） | 按需 |

### 3.3 明确不进标准库的

时区数据库与历法、区域相关的格式化与排序、正则表达式、压缩、加密与 TLS、HTTP、JSON 等数据格式、图形界面。
理由相同：体量大、更新节奏与语言不同步、或有多种合理实现。它们是独立的库；标准库只保证它们所需的基础（字节流、套接字、时间、熵源）齐备。

## 4. 平台层

平台层是[之九](evolution-09-architecture.md)分层图中 L4 的最底部：一组以 `unsafe` 调用外部函数的 Koven 源码，对上提供安全签名。
按功能分组的接口范围（具体函数名与签名属于实施 Spec）：

| 组 | 接口范围 | 最小实现的规模 |
|---|---|---|
| 内存 | 申请、释放、调整大小；按页申请与归还 | 很小 |
| 标准流 | 读、写三个标准句柄；判断是否为终端 | 很小 |
| 文件 | 打开、关闭、读、写、定位、截断、同步到磁盘、元数据 | 中 |
| 目录与路径 | 枚举、创建、删除、重命名、当前目录；路径的平台表示与 UTF-8 的相互转换 | 中 |
| 时间 | 单调时钟、日历时钟、休眠 | 很小 |
| 熵 | 取随机字节 | 很小 |
| 进程 | 参数、环境、退出、启动、等待、管道 | 中 |
| 线程 | 创建、等待结束、停驻与唤醒、线程标识 | 小 |
| 网络 | 套接字的创建、绑定、监听、接受、连接、读写、关闭、选项；名称解析 | 中 |
| 事件 | 提交异步操作、等待完成 | 大，且各平台差别最大 |
| 错误 | 把平台错误码映射为可移植的错误种类，同时保留原始码 | 小 |

规则：

1. 平台层是标准库中**唯一**出现外部函数声明的地方；其余标准库代码只调用平台层。可用脚本检查。
2. 平台层的每个函数都有一份与平台无关的合同文档，各平台实现对照它验收；合同里写明 J55 所说的“不保证”项。
3. 路径用一个能无损保存平台表示的 `Path` 类型（2026-11-14 修订，评审 R8；原稿为“UTF-8 `String`，不可表示的文件名跳过并计数”）。Unix 文件名同样不保证是合法 UTF-8，跳过它们会让备份、清理、同步类工具看不见真实文件。`String` 用于显式的文本转换与显示：显示可以转义或有损，资源身份、枚举与再次打开不能有损。接受 `String` 的便利函数可以保留，因为 `String` 到 `Path` 总能转换。验证至少包含：枚举到非 UTF-8 的 Unix 文件名，并用得到的 `Path` 再次打开。
4. 错误类型沿用 `IoError` 的做法：一个可移植的种类枚举，加一个原始平台错误码字段；用户按种类分支，诊断时可看原始码。
5. 目标分级。一级：有 CI、发布安装包、全部包可用。二级：能构建、标准库的子集可用、无发布承诺。现行两个目标是一级；新增目标先进二级。

## 5. 步骤

| 步骤 | 内容 | 新增内核 | 依赖 | 验收 |
|---|---|---|---|---|
| PL0 | 在 v1 的 runtime 内部，把系统相关的调用收拢到一个模块后面，并为每个调用写下与平台无关的合同。不改变任何用户可见行为 | 无 | 无 | 两个现行目标的测试结果不变；runtime 其余部分不再直接出现系统头文件 |
| PL1 | v1 的 `time` / `sleep` / `math` 表面定稿时按 §3 的命名与划分（单调时钟与日历时间分开、时区不进标准库） | 无 | v1 路线图中的对应条目 | 表面评审通过；与 §3 一致 |
| PL2 | 平台层由 runtime 内部模块改为 Koven 源码（即之七 IO2 的全部范围，不只是 IO） | 无 | U1、FF1 | runtime 只剩启动代码与少量垫片；两个目标行为不变 |
| PL3 | 第三个一级目标，优先选与现有两者差别最大的：Windows。它检验 J52–J55 是否成立 | 无 | PL2 | 一致性测试集在三个目标上结果相同；§3.2 列出的差异逐条有用例 |
| PL4 | 二级目标：一个无线程的环境（WebAssembly）与一个无操作系统的环境（freestanding），检验 J53 与标准库三分 | 无 | PL2、U4、之十 §7.5 | 只依赖核心单元的程序在两者上都能构建；使用不存在的包得到编译错误 |

PL0 与 PL1 不需要任何未启用的语言能力，是现在就可以结合 v1 工作做的两件事。其意义在于：
v1 一旦发布，`koven.time` 等包的公开名字就定了下来；若届时的划分与 §3 不一致，以后只能增加不能修改。

## 6. 开放问题

- 一级目标是否包含 Linux 的 musl 与 AArch64 Linux；它们与现有目标差别小，成本主要在 CI。
- `koven.math` 的超越函数是否要求跨平台逐位一致。要求则须自带实现而不用平台的数学库；倾向不要求，但在合同里明说。
- 异步反应器按“完成”模型设计后，在只有就绪通知的平台上多一次缓冲区所有权的往返，其成本要由 IO4 的试金石测量。
- 平台层合同文档放在 Compiler Contracts 还是标准库自己的文档目录。
