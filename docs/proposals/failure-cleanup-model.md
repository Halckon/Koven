# 失败出口与清理义务的状态模型（内核 MVP 第 4 步）

## 1. 目的与方法

第 1–3 步的[借用内核演算](loan-kernel-calculus.md)检验的是编译期规则。失败出口与在途 IO 的问题是运行时的次序问题：若干执行者交错运行，某一步失败之后，谁在什么时候可以析构什么。
这一步因此不扩展借用检查器，而是写两个很小的状态模型，穷举全部事件交错，比较候选政策各自违反哪条不变量。

模型在 `scripts/loan_kernel/failure_model.py`，预期在 `scripts/tests/test_failure_model.py`。运行：`python3 scripts/loan_kernel/failure_model.py`。
每个模型不超过一百个状态。它能给出反例，不能给出证明：没有违反只说明在这组状态、事件与不变量之内没有违反。

## 2. 模型 A：借用型子任务与失败的传播

对应 J48 行为草案第 7 条：借用型子任务不是监督边界，失败必然传给父；作用域须先等到全部子结束，再让父失败。

- **状态**：父（作用域体内、等待子、作用域之后、正常结束、失败）；被借出的数据（存活、已析构）；每个子（运行、阻塞、结束、失败）；父是否带着待传播的失败。“阻塞”指子在等一个不会自己到来的事件。
- **事件**：子结束、失败或进入阻塞；父到达作用域出口，或在作用域体内失败；父展开并析构数据；父离开作用域并使用数据。
- **不变量**：数据已析构时没有存活的子；子失败之后父不再使用被借出的数据。另记录一种卡住：失败待传播，但没有任何事件可以发生。

| 政策 | 结果 |
|---|---|
| 一有失败父立即展开 | 违反：子仍存活而父帧已析构 |
| 等齐全部子，但子的失败不传给父 | 违反：子失败后父继续使用被借出的数据；并且会卡住 |
| 等齐全部子，再让父失败 | 没有违反；会卡住：父在等一个阻塞的子 |
| 同上，且失败待传播时阻塞的子能被唤醒 | 没有违反，不卡住 |

子任务数取 2 与 3 时结果相同。

## 3. 模型 B：在途 IO、取消、执行器失败与终止窗口

对应 IO 原则页的 §2.1、§2.2、§2.5 与 §3 的失败政策，以及评审 R4 的场景：任务把帧内缓冲区提交给完成式 IO 后挂起。

- **状态**：任务（运行、挂起、恢复后运行、结束、帧已销毁、帧被整体保留）；缓冲区（在帧内、帧已销毁但被保留、已释放）；帧内另一项清理义务，记作守卫（未履行、已履行），例如释放一把锁；请求（未提交、在途、已有终结证据）；执行器（正常、失败）；进程（运行、已请求终止、已终止）。
- **事件**：任务提交请求并挂起；外部写入缓冲区；外部使请求终结；执行器凭终结证据恢复任务；取消；执行器失败；回收被保留的缓冲区；进程终止生效；帧所在的存储被父释放。
- **不变量**：请求在途且进程未终止时，缓冲区没有被释放；执行单元结束后，帧内的清理义务已履行。另记录一种不算违反的终态：缓冲区被永久保留。

| 政策 | 结果 |
|---|---|
| 取消请求一发出，任务就拿回缓冲区 | 违反：外部仍可访问时缓冲区已释放 |
| 执行器失败时随帧销毁全部内容 | 违反：同上 |
| 执行器失败时整帧保留，不运行任何析构 | 违反：清理义务未履行 |
| 执行器失败时析构帧内其余内容，只保留请求在途的缓冲区 | 没有违反；缓冲区永久保留 |
| 同上，但帧位于父的存储里 | 违反：父展开时释放了帧所在的存储 |
| 终止进程，但终止生效之前继续展开 | 违反：外部仍可访问时缓冲区已释放 |
| 保留优先，保留不了则终止进程，终止生效之前不再释放 | 没有违反；帧独立分配时缓冲区永久保留，帧在父存储里时进程终止 |
| 缓冲区在提交时移交给操作、终结后交还；执行器失败时整帧销毁（帧在父存储里） | 没有违反；缓冲区永久保留 |
| 同上，且有后继凭终结证据回收 | 没有违反，不泄漏，不需要终止进程 |

第七行就是 2026-11-14 选定的失败政策方向。后两行是针对 §4 发现 3、4、6 补上的形态。

## 4. 发现

1. **J48 第 7 条的两半缺一不可，并且还缺第三半。** “等齐”防的是释放后使用，“传播”防的是父在不变量可能已被破坏的数据上继续运行。两者都有之后仍会卡住：父带着失败等一个阻塞的子。
   所以 J48 “尚未解决的问题”里的“展开途中等待健康的长期线程”不是边角情形，它是这条规则可用的前提：失败待传播时，作用域内的阻塞点必须能被唤醒。这对借用型子任务可用的阻塞原语是一条要求。
   模型假定运行中的子最终会结束或阻塞；一个不让出的计算循环不在模型之内，它会让父一直等下去。
2. **取消不能让任务提前拿回缓冲区**，与 IO 原则页 §2.2 一致。模型里唯一安全的做法是等到终结证据。
3. **执行器失败时既不能整帧销毁，也不能整帧保留。** 整帧销毁释放了外部仍在访问的缓冲区；整帧保留让帧内其他清理义务落空（[U0 提纲](unsafe-aliasing-contract-outline.md) FS3 收窄后的条款正是禁止这一点）。
   可行的是逐项处理：帧内没有在途请求的值照常析构，有在途请求的缓冲区留下。这要求帧的析构入口能逐项知道“这个值名下是否有在途请求”——也就是 IO 原则页 §4 表格最后一行的待办：内核一侧需要“由操作持有的资源”这样一类 owner，使缓冲区在提交时离开帧的所有权。
   这是这一步对内核提出的唯一一条新要求。
   模型已补上这种形态：缓冲区由操作持有时，整帧销毁不违反不变量，析构入口不必逐项判断。
4. **保留的前提是存储不随帧消失。** 帧独立分配时可以保留；帧位于父的存储里时（借用型子任务的帧若分配在父帧里，就是这种情形）保留不了，只能等到终结或终止进程。
   所以“借用型子任务的帧放在哪里”不只是性能决定，它决定失败时走哪条路。之七 S2 须写明。
   缓冲区由操作持有时这层耦合消失：帧在父存储里也不需要终止进程。
5. **终止窗口必须冻结释放。** 请求终止之后、终止生效之前继续展开，与随帧销毁是同一个错误。J48 第 6 条“致命错误不执行尚未运行的 drop”与此一致；还须保证其他线程在窗口内同样不释放外部仍在访问的资源，模型只有一个执行单元，没有检验这一点。
6. **保留之后没有人回收。** 执行器已经失败，被保留的缓冲区在请求终结后也没有回收者，模型里它一直留着。要回收，需要 IO 原则页 §2.3 的责任交接：在声明的失败域内有一个可激活的后继。模型没有后继这个角色。
   按选定的政策这是允许的结果（保留而不释放），但监督边界接住失败后进程继续运行，每次失败泄漏一块缓冲区，长期运行的服务需要后继。
   模型已补上后继这一项：有后继时不泄漏。模型假定终结证据能到达后继；证据随执行器丢失的情形没有建模，按原则页 §2.2 那时须按未知处理，即继续保留。

这些发现已于 2026-11-14 并回[之十一](evolution-11-failure-interfaces-units.md) J48 第 7 条、[之七](evolution-07-concurrency-async-io-ffi.md) §2.7 与 IO 原则页 §3、§4。

## 5. 模型没有覆盖的

- 多个请求、批次、证据丢失或迟到、请求身份与代际（IO 原则页 §2.2、§2.3）。模型只有一个请求，终结证据要么有要么没有。
- 清理进度的记录与恢复（§2.4）。
- 监督边界本身：失败到达边界后监督者得到什么、边界内外是否共享状态（J48 改写后的第 4 点）。
- 多个线程在终止窗口内的行为；锁的“持有者异常终止”状态；channel 对端的关闭。
- 析构中再次失败。
- 模型的状态与事件是我选的；遗漏的事件不会被发现。
