# 演进总纲之三：路线 X——抽象打包（dyn 与 callable）

> **性质**：非规范候选实施计划 · **状态**：未启用 · **读取时机**：仅在规划存在类型、动态分发、闭包表示统一时 · **唯一真源**：本页维护路线 X 的步骤、规则草案、验收设计与 interface 的终态范围（决断 J37–J38）；表面语义候选仍见 [v2 interface 值候选](v2-interface-values-and-dynamic-dispatch.md)，判据与决断见[之一](evolution-01-kernel-and-decisions.md)

本文不启用任何规则、不批准 Spec 或 ADR。规则均为草案，代码均为候选伪代码。
现行 v1 没有 interface runtime value，这一事实在新 Guide 启用前保持不变。

## 1. 目标

把基底能力 KB5 的缺口——**存在类型的 pack 与 open**——补成一个与表面拼写无关的内核，并让闭包、函数类型、
匿名对象、interface 值共用它。路线终点是：编译器里只有一种“被擦除的值”的表示、一套析构与调用机制。

与既有候选的分工：那份文档定义用户看到的语义（裸 `Shape`、按位置区分、expected-type 转换、容器不靠型变）；
本文定义内核操作、它们与所有权内核的接口、以及推进步骤。两者冲突时以用户后续启用的 Guide 为准。

## 2. 内核

### 2.1 五个操作

```text
pack_borrow(place: C, W)   -> borrow ∃I     不分配；结果持有 place 上的 Shared loan
pack_inout (place: C, W)   -> inout  ∃I     不分配；结果持有 place 上的 Exclusive loan
pack_owned (owner: Ind<C>, W) -> ∃I         不分配；接管一个已是间接表示的 owner
open(e)                    -> (载荷指针, W)  仅编译器内部使用，不向用户暴露被擦除的类型
drop(e: ∃I)                经由 W 中的析构入口精确析构并释放

其中 C 是满足 interface I 的具体类型，W 是 (C, I) 的见证表，
Ind<C> 指已经以单一指针间接持有 C 的 owner：普通 class 实例，或 Box<C>
```

要点：

- **内核的 pack 永不分配**（决断 D6）。`value class` 进入 owned existential 需要先成为 `Box`；
  是否由编译器隐式插入这一步是 X4 的转换糖，与内核无关。
- 借用形态的 existential 就是路线 L 意义上的不可逃逸值（Holder），loan 规则完全复用，不新增任何借用规则。
- 对一个 owned existential 的 place 再借用，得到的仍是 `borrow ∃I`：复制其两个字即可，不产生“指向胖指针的指针”。

### 2.2 见证表

```text
Witness(C, I) = {
    size, align,                 // 载荷布局，供析构与释放
    drop_in_place,               // 精确析构
    capability_bits,             // I 经继承携带的能力（见 2.3）
    methods[...]                 // I 的动态可分发方法，顺序由 I 的声明确定
}
```

- 每个 (具体类型, interface) 一张表，置于只读数据；对象本身不带表指针。
- 父 interface 向上转换、槽位顺序、重复 requirement 合并属于 ABI ADR 的内容。
- 表中默认不含类型标识、名称或向下转换入口；需要时另行设计显式能力（见既有候选 §6.2）。

### 2.3 能力

- 存在类型默认 `MoveOnly`、`Escapable`，`DropPolicy` 取最保守值（载荷未知，必须假定析构可观察）。
- interface 可在声明处继承能力（例如 `interface Job : Transferable`），此时所有实现者必须满足该能力，
  相应存在类型也满足。这是能力进入存在类型的唯一途径，不引入交集类型。
- 由此带来一条须在 Guide 中写明的后果：把 `DropPolicy` 默认取保守值意味着 owned existential 不参与 ASAP。
  若 interface 声明继承一个表示“析构不可观察”的能力，可恢复 ASAP；该能力的命名与是否开放给用户留待路线 C 的 C1 决定。
- 载荷必须 `Escapable`，直至路线 L 的 L5。

### 2.4 自满足

动态兼容的 interface `I` 对应的存在类型自动满足 `<T : I>`：泛型实例以存在类型为实参单态化，
方法调用经见证表转发。这一条属于内核而非糖，因为缺了它，“值位置的 `Shape`”与“约束位置的 `Shape`”会分裂成
两个需要用户手工桥接的世界。

推论：参数位置的 `shape: Shape` 在语义上只承诺“接受任何满足 `Shape` 的值”。实现可以选择传见证表，
也可以在实参静态类型已知时特化为直接调用。这是优化自由度，不是语言规则。

**对可变访问的限制（2026-11-14，采纳[evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md) R2）。** 可变访问有两种权限，类型检查、泛型匹配与调用约定都须区分：

- **载荷可变访问**：只能经它调用被擦除类型的方法，不能更换具体类型。`inout s: Shape` 一律是这一种；实参可以是具体类型的 place，也可以是存在类型的槽位。
- **槽位可变访问**：可以替换 owner 与见证表。只在两处出现：对拥有存在类型值的变量直接赋值；泛型 `inout T` 且 `T` 实例化为存在类型，此时实参必须是真正的存在类型槽位。

载荷可变访问**不能**匹配 `inout T`（`T` = 存在类型）。否则 `fun <T : Shape> overwrite(inout dst: T, own value: T)` 以 `T = Shape` 实例化后，
可以经一个只是“载荷指针加见证表”的参数，把任意 `Shape` 写进静态类型为 `Circle` 的位置。两种权限可以共用 pack/open 机制，但不共用类型。

**原型的检验结果（2026-11-14，[借用内核演算](loan-kernel-calculus.md) §10，用例 I1–I5）。** 上面的区分在原型里成立，并补充四点。这是用例检验，不是健全性证明。

- 排除评审的反例需要两条规则并存：`inout T` 对所指类型不变（`T` 在一次调用里的各处实例须是同一类型，`Circle` 与 `Shape` 不是）；载荷访问不能充当槽位。只有前一条时，“先按 `inout s: Shape` 接收再转交”这条路仍然通。
- 载荷与槽位是借用值上的一个标记，由借用的来由决定，不需要用户书写，也不需要两种拼写。得到载荷访问的来由有三处：`borrow` / `inout` 的存在类型参数；返回 `borrow` / `inout` 存在类型的调用结果；**存放在视图字段里的存在类型借用，以及经它重借出来的借用**。
  第三处是原型发现的漏洞：只在参数上区分时，把具体类型的独占借用存进视图再取出，就绕过了限制。所以这个标记必须跟随借用值到每一处存放位置，包括 X3 之后的容器与闭包捕获。
- 代价之一：类型自己的方法返回内部真实存在类型槽位的独占借用时，调用方也不能经它整体替换。放开需要在返回类型上区分两种访问（一种新拼写）；先不加。
- 代价之二：载荷访问不能交给**任何**泛型 `inout T`，包括不做替换的函数；按 `inout T` 写的泛型算法因此不能直接用于 `inout s: Shape`。
  精确的做法是在调用处执行 §2.1 的 `open`，把 `T` 绑定为那个未知的具体类型：不做替换的函数可用，`overwrite` 仍被拒绝（拿不出类型恰为该未知类型的值）。这是否向用户开放、是否隐式发生，见 §5。
  原型已按“隐式打开”实现（演算 §11 的 X4，用例 I5）：不做替换的函数可用，结果仍是载荷访问；`overwrite` 与“交换两个载荷访问”被拒绝。可行性成立，是否采用仍待裁决。

## 3. 步骤

### X0 callable 重建（无语言变化）

**目的**：在引入任何用户可见的 dyn 之前，先让编译器里最早出现的存在类型——函数值——使用 §2 的内核。

内容：

- 闭包定义为**匿名积类型 + 单方法见证**：捕获是字段，调用是见证表中唯一的方法；
- 函数类型 `(A) -> R` 视为内建的单方法 interface 族；其值是该 interface 的存在类型；
- move closure 的环境是 owned 载荷；无捕获函数是零大小载荷；
  borrowed / mutating closure 的环境是含借用字段的匿名视图（依赖路线 L 的 L3，可后置为 X0 的第二片）；
- `Transferable` 等能力检查改为对匿名积类型做 KB4 的结构推导，取代专门的 capture 事实查询。

工作分解：

| Phase | 工作 |
|---|---|
| 2 | 函数类型在类型模型中表示为内建 interface 族的存在类型；重载与 lambda 推导行为保持 |
| 3 | 捕获分析的输出改为匿名积类型的字段表；逃逸检查改为“不可逃逸值的位置检查”（与 L3 共用） |
| 4 | 闭包值表示统一为 (载荷指针, 见证指针)；间接调用经见证表；drop 经见证表 |
| ADR | 新 ADR 说明与 [ADR 0009](../adr/accepted/0009-concrete-closure-internal-abi.md)、[ADR 0034](../adr/accepted/0034-refine-closures-and-callable-views.md) 的取代或细化关系 |

验收：

- 行为等价：现有闭包测试的诊断、所有权事实与原生输出不变；
- 性能不回退：已知具体闭包类型的调用点仍为直接调用（见证表只在类型被擦除处使用）；
- 度量：闭包专用的 SSA 操作与 verifier 规则数量下降。

**决定（2026-11-10 用户确认）**：闭包在前提满足后重建，不采用“只在规范层面统一”的备选。

现状核对（见之一 §7）使这一步比最初估计的小：ADR 0034 的 callable view 已经是借用形态的存在类型
（Borrow 函数参数不单态化，经视图调用），ADR 0009 的具体闭包是函数指针 + 内联环境。因此 X0 的实质是
把 callable view 的表示与规则**推广**为 §2 的通用内核，再让具体闭包成为其载荷，而不是另起一套。

重建的前提（全部满足后才启动对应分片）：

| 分片 | 前提 | 理由 |
|---|---|---|
| X0-a 无捕获函数值与 move closure | L0 完成；C0 完成 | 需要归一后的 loan 模型承载调用期借用；环境的能力改由通用引擎推导 |
| X0-b callable view 推广为借用 existential | X0-a；X1 的类型身份 | 多方法见证表是单方法情形的推广，须先有存在类型身份 |
| X0-c borrowed / mutating closure 改写为匿名视图 | L3（只读视图）；mutating closure 另需 L4（独占视图） | 环境含借用字段，即 `view class` 的匿名形态 |

每个分片的门槛都是行为等价加性能不回退；任何一片未达标时保留旧路径，不做部分切换。
ADR 0036（独占闭包捕获存储，proposed）与 ADR 0025（递归闭包环境句柄，proposed）应在 X0-c 之前与本路线对账，
避免在即将被取代的表示上继续投入。

### X1 存在类型身份与动态兼容性

**目的**：类型系统能区分“约束位置的 `I`”与“值位置的 `I`”，并判定哪些 interface 可以成为值。尚不生成代码。

规则草案：

- R1.1 interface 名出现在值类型位置时，解析为存在类型 `∃I`，其内部身份与名义类型 `I` 不同。
- R1.2 动态兼容性在使用点检查，判定条件沿用既有候选 §5；不兼容的 interface 仍可用于泛型约束。
- R1.3 转换只在存在 interface 期望类型时发生；不从多个具体实参推导公共 interface。
- R1.4 重载决议：精确类型匹配优先于存在类型转换；两个候选都需转换时按现行歧义规则报错。
- R1.5 存在类型的能力按 §2.3 判定；自满足按 §2.4。
- R1.6 表面拼写（裸名字或带关键字）不影响以上任何一条（决断 D2）。

工作分解：Phase 2 新增类型身份、兼容性检查与诊断；Phase 1 不变（裸名字无需新语法）。
此步可以先于任何后端工作完成并独立验收，产物是一组“应接受/应拒绝”的类型检查测试。

### X2 借用 existential

**目的**：交付成本最低、收益最大的一片——参数位置的动态分发。不涉及分配，也不涉及 owned 载荷的析构。

规则草案：

- R2.1 `fun f(s: Shape)`、`fun f(inout s: Shape)`：实参为具体类型的 place 或临时值时，执行 `pack_borrow` / `pack_inout`。
- R2.2 `value class` 实参以指向其现有存储的指针打包，不装箱。
- R2.3 loan 的建立、存活、冲突完全按路线 L 的调用期规则；`from` 可以出现在返回 `borrow Shape` 的签名上。
- R2.4 `inout s: Shape` 是载荷可变访问（§2.4）：只允许经 `s` 调用方法，**不允许整体替换**，也不能转交给 `inout T`（`T = Shape`）的泛型参数。
  这条对任何实参都成立，包括实参本身是存在类型槽位的情形；限制直接赋值的语法不够，必须连同经泛型与辅助函数转发的路径一并拒绝。

R2.4 是对既有候选 §4.1 的一处细化，应在 Guide 文字中显式区分这两种 `inout`。

工作分解：Phase 3 把 pack 记为建立 loan 的一种来源；Phase 4 增加 pack/间接调用操作、见证表生成与 verifier 规则
（胖借用的 loan 必须有来源；见证表与载荷类型一致）。

验收：

- 试金石：`fun totalArea(shapes: List<Circle>, extra: Shape)` 一类把具体值传给 interface 参数的程序；
  以 interface 参数实现的访问者、比较器；
- 原生验证：不发生堆分配（以分配计数断言）；
- 反例：动态不兼容的 interface、把借用 existential 存入字段或返回而无 `from`、R2.4 的替换。

### X3 owned existential 与容器

**目的**：interface 值可以被拥有、存储、返回与放入容器。

规则草案：

前置裁决（来自[之六](evolution-06-text-globals-extensions-metadata.md) J10）：同一对“类型 × interface”在全程序至多有一个实现。
若将来允许在类型与 interface 所在的编译单元之外补写实现，必须先有这条一致性规则，否则见证表的选择取决于 import，
owned existential 离开构造它的编译单元之后行为不确定。扩展函数不参与见证表。

- R3.1 local、字段、返回值、容器元素位置的 `Shape` 是 owned existential；转换执行 `pack_owned`。
- R3.2 源为普通 `class` 实例时接管其 owner，原绑定不可用；源为 `Copyable` 的间接 owner 时按 Value delivery 复制。
- R3.3 源为 `value class` 时需要间接 owner：内核要求显式 `Box`；X4 的转换糖可省去书写。
- R3.4 析构经见证表；`DropPolicy` 依 §2.3。
- R3.5 owned existential 的 place 可以整体替换（先求值新值，再析构旧值，再提交）：对拥有它的变量直接赋值，或作为槽位传给泛型 `inout T`（§2.4）。经 `inout s: Shape` 参数不能替换。
- R3.6 `List<Shape>` 的元素是定长的 owned existential；`List<Circle>` 与 `List<Shape>` 之间没有隐式转换。
- R3.7 nullable 的 `Shape?` 利用指针 niche，不增加标志位（与 ADR 0033 核对）。

工作分解：

| Phase | 工作 |
|---|---|
| 2 | 各存储位置的期望类型传播；容器字面量在期望类型下逐元素转换 |
| 3 | pack_owned 作为所有权转移点；existential owner 的 move/drop 事实；容器元素 place 复用现有规则 |
| 4 | owned 表示、经见证表的 drop 与释放、verifier 规则（每个 owned existential 恰好析构一次） |
| 5 标准库 | 容器对存在类型元素的构造、索引、替换、移除 |
| ADR | 布局、槽位顺序、父 interface 向上转换、nullable niche、与 `Rc` 控制块的关系 |

验收：

- 试金石：插件注册表、表达式树求值器、事件总线（`List<Handler>`）；
- 原生验证：析构计数精确；sanitizer 无泄漏与重复释放；`class` 载荷的转换不发生分配；
- 反例：隐式 `List<Circle>` → `List<Shape>`、无期望类型的公共 interface 推导、转换后使用原绑定。

### X4 糖与派生能力

以下各项互相独立，均可由局部翻译得到，按用例单独提案：

| 项 | 翻译为 | 备注 |
|---|---|---|
| `value class` 的隐式装箱 | `pack_owned(Box(v), W)` | 建议与 X3 同版启用；须可被编译报告列出 |
| 匿名对象 `object : I { … }` | 匿名积类型 + 多方法见证 | 捕获规则即闭包规则，X0 完成后几乎没有新增内核 |
| `sealed interface` | 枚举 + 静态分发 | 与本路线无依赖（决断 D5）；穷尽 `when` 属于其表面语义 |
| `Rc<Shape>` | 共享控制块 + 见证指针 | 依赖路线 C 的共享库与 ABI ADR |
| 类型判定与向下转换 | 显式 `TypeId` 能力 | 不进默认见证表 |
| 型变 | 类型关系规则 | 按既有候选 §6.1 后置，不与本路线混合 |

## 4. 验证设施

1. 见证表一致性检查：verifier 对每次 pack 检查 (具体类型, interface, 见证表) 三者一致；对每次间接调用检查槽位与签名一致。
2. 与路线 L 的参考检查器共用：借用形态的 existential 作为普通 Holder 进入同一模型，不需要第二个检查器。
3. 分配审计：测试支持中提供分配计数，X2 断言零分配，X3 断言 `class` 载荷零额外分配。
4. 等价测试：X0 以行为等价为门槛；X2/X3 中“实参静态类型已知时的特化”与“经见证表调用”两种 lowering 的结果必须一致。

## 5. 开放问题

- 载荷可变访问交给泛型 `inout T` 时是否隐式打开存在类型（§2.4 的代价之二）。不打开则 `inout s: Shape` 不能用于任何 `inout T` 的泛型算法；打开则每个这样的调用点多一次经见证表的实例选择，且与“泛型实例以存在类型为实参单态化”（自满足）并存两条路径，须规定何时走哪一条。原型已建模隐式打开，规则可行；两条路径何时各走哪一条没有建模。
- 返回类型上是否需要区分载荷访问与槽位访问（§2.4 的代价之一）。
- consuming receiver（`own this`）在 owned existential 上的调用：载荷被移出后间接 owner 的释放由谁负责。
- X0 重建后的函数类型须为“挂起”预留一维（与 `move`、借用捕获并列），见证表槽位相应区分普通方法与挂起方法；
  具体规则属[之七](evolution-07-concurrency-async-io-ffi.md) S4，X0 只需保证加入这一维时不必再次重建。
- 默认方法与父 interface 方法是否各占槽位，还是经 thunk 共享。
- 存在类型是否参与 `==` 与哈希；倾向只在 interface 继承相应能力时参与。
- 见证表是否承诺跨编译单元稳定；倾向只保证单元内部，公共 C ABI 不暴露。
- 单态化与见证传递之间的选择是否需要给用户控制手段（代码体积 vs 速度）；倾向先不提供。

## 6. interface 的终态范围与一致性规则（2026-11-11 增补）

路线 X 给 interface 增加了第二种用法（存在类型）。在此之前须回答：interface 最终做到什么程度。

现状（[Guide 03](../guide/03-types-generics.md)）：interface 可带类型参数，可有默认方法，可继承父 interface，可经 `by` 委托；
类型参数至多一个显式上界，泛型不变，不接受递归的 F-bound；实现关系只能写在类型自己的声明处；没有存在类型。
因此“泛型 interface”已经有了，问题是其余部分。

| # | 决断 | 理由 |
|---|---|---|
| J37 | **一致性规则分三级放开，每一级都保证“同一对（类型，interface）全程序至多一个实现”**。R0（现状）：实现只写在类型的声明处。R1：增加“在 interface 所在的编译单元内为外部类型声明实现”。R2：两者都不属于自己时，经 `value class` 包装为新类型再实现。判定只看 interface 声明与类型声明各在哪个编译单元，不看类型实参。不允许两个实现在泛型实例上重叠 | 这是[之六](evolution-06-text-globals-extensions-metadata.md) J10 的具体化。R1 覆盖最常见的需求（“我定义的接口 × 别人的类型”），且编译单元之间的依赖无环（[之十一](evolution-11-failure-interfaces-units.md) J45），类型一侧与 interface 一侧不可能各写一份。R2 用的是已有的零开销包装，不需要新规则。取严是因为 T3：放宽兼容，收紧不兼容。不采用 Rust“按类型实参是否本地”的细化，它是该规则里最难解释的部分 |
| J38 | **interface 的终态是“一份声明、两种消费”加四项补充，到此为止**。两种消费：作泛型约束（单态化，静态分发）与作存在类型（见证表，动态分发）。四项补充：多约束与 `where` 子句；条件实现；签名中的 `Self`；`suspend` 方法。明确不做：关联类型、声明处型变、高阶类型、特化、否定约束 | 见下表逐项说明 |

J38 各项：

| 能力 | 结论 | 说明 |
|---|---|---|
| interface 带类型参数 | 已有，保持 | `Iterator<T>`、`Comparable<T>` 这一形态与 Kotlin 一致，也让 `dyn Iterator<Int>` 无须额外语法 |
| 默认方法、父 interface、`by` 委托 | 已有，保持 | R2 需要 `by` 对 `value class` 生效，现行只对普通 `class` 生效，届时一并放宽 |
| 多约束与 `where` | 做 | 现行“至多一个上界”是 v1 的简化。`where` 已是保留字。不引入交集类型：多约束只出现在约束位置，不成为一个可以写在别处的类型 |
| 条件实现 | 做，且是 **U2 的前提** | 现行 `Equatable`、`Hashable`、`Comparable` 是编译器按结构推导的能力，用户不能手动实现。容器迁为用 `unsafe` 实现的库类型后，结构推导看到的是裸指针，推不出“`List<T>` 当 `T` 可判等时可判等”，必须能在源码里声明。它在形式上与能力的结构推导（KB4）是同一种规则。清单见[之十一](evolution-11-failure-interfaces-units.md) §2 |
| 签名中的 `Self` | 做 | 二元操作（判等、比较）需要它。含 `Self` 参数的方法不能动态分发，属于 X1 的动态兼容性规则 |
| 泛型方法 | 允许 | 同样不能动态分发 |
| `suspend` 方法 | 做 | 见 §5 的“挂起”一维；经存在类型调用时需要间接帧（之七 §2.2） |
| 能力继承（`interface Job : Transferable`） | 做 | 见 §2.3 |
| 静态成员要求（不经实例调用的函数、常量） | 后置，单独提案 | 泛型代码里“构造一个 `T`”“取 `T` 的零值”需要它；但它不能动态分发，且与 companion 的关系要先理清 |
| 关联类型 | 不做 | 用类型参数代替。代价是泛型签名里要多带一个类型参数；收益是存在类型的写法简单，且少一个概念。以后加入是兼容的（T3） |
| 声明处型变 | 不做 | 仅保留“子 interface 的存在类型可向上转换为父 interface 的存在类型”。泛型保持不变 |
| 高阶类型、特化、否定约束 | 不做 | 特化与 J37 的“不重叠”直接冲突 |
| 向下转换、运行时类型查询 | 不在见证表内 | 见 §2.2；需要时另设显式能力 |

R1、R2 之外的可选放宽（不在本次决断内）：允许**最终的应用编译单元**为任意外部类型与外部 interface 声明实现，因为没有别的编译单元依赖它，全程序唯一性可在链接时检查。它是兼容的放宽，等 R2 的样板代码确实成为负担时再议。

J37 的前提是编译单元之间的依赖无环。现行 Guide 尚未定义编译单元之间的依赖；该前提由之十一 J45 提出，须与 J37 一并启用。Koven 的 `package` 只是命名空间，不是这里的判定单位。
