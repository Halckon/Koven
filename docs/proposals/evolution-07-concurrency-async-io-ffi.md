## 1. 调研：并发模型

### 1.1 各家的选择与代价

| 模型 | 代表 | 得到了什么 | 付出了什么 |
|---|---|---|---|
| 有栈协程 + 运行时调度 | Go goroutine、Java 虚拟线程 | 没有函数着色，阻塞式写法，任务极廉价 | 必须有运行时；栈要么可移动（需要精确知道所有指向栈的指针，通常依赖 GC），要么预留地址空间；调用 C 需要切栈；难以用于无运行时环境 |
| 无栈状态机 | Rust `async`、Kotlin `suspend`、Swift `async`、C# | 无强制运行时；帧大小编译期已知；可用于嵌入式 | 函数着色（同步与异步两套 API）；递归与动态调用需要间接帧 |
| Rust 特有的代价 | `Pin`、在任意 `await` 处丢弃即取消、缺少异步析构、带借用的 scoped 任务不健全 | — | future 在首次轮询前是可移动的普通值，于是需要 `Pin`；可被 `forget` 的值无法保证析构，于是借用型任务不能安全表达 |
| Kotlin 的修正 | 调用处无 `await`、结构化并发、协作式取消 | 顺序代码与同步代码外观一致；任务有父子关系 | 取消以异常传播，依赖异常机制；帧依赖 GC |
| Actor | Erlang、Pony、Swift actor | 状态被隔离，消息传递 | Swift 的 actor 方法可重入，引入了新的一类错误；Swift 因此同时维护 `Sendable` 与隔离域两套规则 |
| 通信顺序进程 | Go channel + `select` | 组合性好 | channel 自身不提供数据竞争安全，Go 靠竞争检测器补 |
| 效应处理器 | OCaml 5 | 生成器、异步、异常统一为一种机制，直接风格 | 一次性续体仍需要可切换的栈片段；类型化效应尚在研究阶段 |
| 执行方式作为参数 | Zig 0.16 的 `std.Io` | 同一份代码可在线程或事件循环上运行，签名相同 | 需要把接口值一路传递；已发布的可用实现只有线程版 |

两篇定义了讨论框架的文章：Nystrom 的“函数着色”说明着色的成本在于它把生态一分为二；
Nathaniel Smith 的“结构化并发”说明不受约束的任务启动与 `goto` 是同一类问题——控制流离开了词法结构，错误与取消无处可去。

近期动向印证了两点。其一，Swift 6.2 把默认行为改为“默认隔离到主 actor、异步函数留在调用者所在的执行器上”，
即从“默认可能并行”退回“默认单线程、并行显式”。其二，Rust 2026 年的项目目标里仍有“不可移动类型与保证执行的析构”，
用来补上 scoped 任务与异步析构的缺口。两者都是后补，说明这两条性质应当一开始就写进基础。

### 1.2 Koven 已有的条件

三条现行事实决定了选型空间：

1. v1 已经有**结构化的线程**：`Thread<T>` 未 join 就析构时阻塞等待，“函数返回时它创建并仍持有的线程都已结束”。
2. 没有异常与栈展开。错误是值（`Result`）、缺失是 `T?`、不变量破坏是进程级 abort。
3. 路线 L 将提供**不可逃逸类型**（`Escapable` 能力为假）：这种值不能存入堆、字段或逃逸闭包，只能住在局部。

第 3 条带来一个 Rust 没有的推论，是本页多数决断的基础：

> **保证析构**：不可逃逸、且析构策略为 `LexicalRequired` 的值，其析构必然在所在作用域结束前执行。
> 因为它无法被放进 `Rc` 环或任何长寿命容器，安全代码里也没有“遗忘”原语。

这条推论目前只是论证，**须在路线 L 的形式化小演算中证明**（J17 的前提）。最初的论证还依赖第三条理由“abort 终止整个进程”。
[之十一](evolution-11-failure-interfaces-units.md) J48 若引入线程失败边界，abort 就成为函数的又一种出口，推论须在含失败出口的模型里重新证明，并至少满足以下条件（独立复审给出）：

1. 每条失败出口都按后进先出执行这类值的析构，包括表达式求值到一半时已构造的临时值。
2. 析构体内部若要发起 abort，不得跳过它尚未完成的等待义务：作用域须先等到全部借用型子线程结束，再让父线程 abort。
3. 析构过程中的第二次 abort 直接终止进程（对健全性是安全的：进程没了，没有代码能观察到悬垂借用）。
4. 执行器线程失败时，挂起的帧按“子先于父”的次序销毁。

J48 不引入时，这四条自动满足。

## 2. 决断：并发与异步

| # | 决断 | 理由 |
|---|---|---|
| J14 | **并发安全只有一套规则：`Transferable` 与 `Shareable`**。不引入 actor 隔离域、不引入第二套“可跨任务”能力 | 一套能力加借用规则已经能表达“独占转移”与“只读共享”。Swift 的经验是两套规则的交互成为主要学习负担 |
| J15 | **KB8 就是无栈的帧变换**：把一个函数编译为可在挂起点保存并恢复的状态机。有栈纤程不进内核 | 判据是“库写不出来的才进编译器”。帧变换必须由编译器做；有栈切换用 KB7（外部函数与少量汇编）即可在库里实现。无栈也是唯一能进入 freestanding（U4）的模型 |
| J16 | **表面采用 Kotlin 式**：定义处写 `suspend fun`；在挂起函数里调用另一个挂起函数与普通调用同形，顺序执行，不产生可存放的 future / promise 值；并发必须经作用域 API 显式发起。`async`、`await` 继续保留不启用。（结论经过两次修订后回到最初形态，理由已更换，见 §2.4） | 其一，`suspend` 准确描述语义——“这个函数可能挂起”；`async` 在多数语言里意为“返回一个 future”，与这里的语义相反。其二，调用点标记的主要用处是提示“此处别的任务可能改动你正在用的状态”，而 Koven 的借用规则已经排除了这种情况的大部分（§2.4）。其三，与“类似 Kotlin 的开发体验”一致。代价：这是 T3 上不可逆的一侧，以后不能再要求标记 |
| J17 | **结构化并发由“不可逃逸 + 词法析构”保证**：任务作用域与子任务句柄都是不可逃逸的资源类型，作用域析构时等待全部子任务。借用型并发因此健全，不需要生命周期参数 | 直接使用 §1.2 的保证析构推论。脱离作用域的启动等价于现行 `thread(move { … })`，要求所有权转移 |
| J18 | **默认不迁移线程**：任务在所属作用域的执行器上恢复；跨线程并行是显式的另一个入口，只有它要求捕获与跨挂起点存活的值满足 `Transferable`（共享借用的对象满足 `Shareable`） | 默认情形下 `Rc`、普通借用都可以跨挂起点使用，不出现“为什么这个任务不能发送”的诊断。与 Swift 6.2 的修正方向相同 |
| J19 | **取消是值，不是控制流**：取消是对作用域的一个请求；挂起原语（等待 IO、接收消息、睡眠）在被取消时提前返回一个表示取消的错误值，由现行 `Result` 与 postfix `?` 传播。**正常路径上**任务总是运行到自己返回；`deinit` 永不挂起。作用域对子任务的等待发生在作用域函数返回之前（它本身是挂起函数），不发生在析构里；析构只是失败路径上的兜底，那时它销毁而不是等待 | Koven 没有异常，无法照搬 Kotlin；把“在挂起点销毁帧”用作取消手段（Rust 的做法）会让每个挂起点都成为隐式的提前退出。值传播避开了这一点，且更严格的一侧可逆（T3）。例外只有一种：所在执行器线程异常终止（之十一 J48）时，挂起的帧不会再被恢复，只能按当前状态销毁；这要求帧有“按状态析构”的入口，但不改变正常路径的规则 |
| J20 | **KB8 的第一个交付物是生成器**，不是异步 IO | 生成器只需要帧变换与路线 S 的三条约束，不需要调度器、取消、线程或 IO。它单独就有价值（自定义迭代器目前要手写状态机），并能在最小范围内验证 KB8 |
| J21 | **channel、`select`、actor、线程池、执行器、定时器都是库**。`actor`、`spawn` 关键字继续保留不启用 | actor 即“一个拥有状态的任务 + 一个邮箱”，用 v1 的 `thread` 与 `channel` 已能表达。把它做成关键字只换来方法调用语法，并带来重入问题 |

### 2.1 为什么不是有栈协程

有栈方案对“较少心智负担”最友好，值得正面回答为什么不选：

- 它要求一个始终在场的运行时，与“后期能做系统级编程”冲突；无运行时环境里无处安放调度器与栈池。
- Koven 的 loan 是指向帧内的地址。可移动栈需要在移动时重写这些地址，等于为所有借用维护重定位表；不可移动栈则每个任务预留一段地址空间，任务数量受限。
- 每次调用 C 函数都要处理栈大小与切栈，FFI（§4）不再是零成本。

J16 之后无栈方案的主要可见成本只剩函数着色，其后果在 §2.3 列为开放问题，而不是假装不存在。
本决断的**证伪条件**：若 S3（生成器）阶段发现“帧在创建后不移动”无法与值语义的调用约定共存，或 S4 的试金石程序表明两套 IO API 的维护成本不可接受，应重新评审有栈方案作为库能否成为默认。

### 2.2 帧在哪里

帧的存放是表示承诺（T4），走 ADR；语言层只固定三条：

- 顺序调用的被调帧**嵌入**调用者的帧，不分配。
- 帧大小无法静态确定的情形——递归的 `suspend` 函数、经 existential 的 `suspend` 调用——需要间接帧。先要求写出显式间接（与 D6“pack 永不隐式分配”同一原则），隐式装箱作为糖后置。
- 帧一旦开始执行就不移动（S0.1）；因此“已创建未启动”与“已启动”是两个状态，后者不是可 move 的值。

### 2.3 开放问题

- **着色与高阶函数**：`list.map { suspendCall(it) }` 是否合法。Kotlin 靠内联解决。Koven 的泛型按实例单态化，理论上可以让“以 `suspend` 闭包实例化的泛型函数自身成为 `suspend` 实例”，
  即经单态化获得颜色多态。这是语义承诺而非优化，需单独提案；在此之前只允许内联形态。X0（callable 重建）须为函数类型预留“挂起”这一维。
- **同步与异步 IO 的重复**：无栈模型下不可避免。减轻手段是让两套操作共享资源类型与底层非阻塞系统调用层，并提供“在线程池上执行阻塞操作”的桥。是否足够要由 S4 的试金石判断。
- **跨挂起点持有锁**：J18 默认单线程执行器下不成问题；并行入口下 guard 不是 `Transferable`，按规则自然被拒绝。需要确认诊断能指出“是哪个挂起点让它跨越了”。
- **origin 流入已有持有者**：动态数量的借用型子任务要求 `scope.launch(f)` 把 `f` 的来源并入 `scope`。同一能力也是“把视图加入一个局部容器”所需要的。
  须确认[之二](evolution-02-route-loan-kernel.md) L5 的合同形式覆盖它；若不覆盖，S2b 之前要补。

### 2.4 拼写、可调试性、安全优先级与开销（2026-11-11 增补并修订）

**`suspend` 还是 `async` / `await`。** 这一条改过两次，记录如下以免再次反复：

| 日期 | 结论 | 当时的理由 | 后来的判断 |
|---|---|---|---|
| 11-10 | `suspend`，调用处无标记 | “不启用 `await` 保留了以后要求标注的余地” | 结论可取，理由错误：事后要求标注会破坏既有代码 |
| 11-11 第一次修订 | `async fun` + 强制 `await` | T3 取严；挂起点需要可见 | 高估了标记在 Koven 里的价值 |
| 11-11 第二次修订 | `suspend`，调用处无标记 | 见下 | 现行结论 |

调用点标记在 Swift 里的核心用途是：`await` 两侧，actor 的状态可能已被别的任务改动。在 Koven 里逐一检查“别的任务能否在挂起期间改动我正在用的数据”：

- 我持有它的独占借用（`inout`）或所有权：不能。借用规则禁止第二个访问者，挂起不改变这一点。
- 我持有它的共享借用：别的任务也只能共享借用，谁都不能改。
- 它经内部可变类型共享（`Rc` 里的 `Cell`、`Mutex`、全局的原子类型或 `Mutex` 实例）：能。

独立复审指出最初的枚举不完备，另有三种“挂起之后世界变了”的途径，借用规则都不管：

- **内部可变被藏在别的类型里**。私有字段、闭包捕获、存在类型的载荷里都可以有 `Cell`；持有 `borrow Config` 或一个 `Shape` 的读者从类型上看不出来。所以“类型上已有标记”只对直接使用者成立，不具有传递的可见性。
- **进程外的状态**：文件、套接字、环境。
- **经句柄间接指向的数据**：区域加句柄、数组加下标。手里拿的不是借用，挂起回来后句柄指向的内容或代际可能已变。

因此准确的结论是：需要提醒的情形 = 可达的内部可变状态 + 外部状态 + 句柄，标记的价值不为零。仍然不采用调用点标记，理由改为权衡而非“没有需要”：
后两类在同步代码里同样存在（调用任何函数之后文件都可能变了），标记并不能区分它们；第一类里标记确实有信息量，但代价是每个挂起调用多一个词并偏离 Kotlin 的体验。
这是一个可以被经验推翻的判断：若 S4 的试金石程序里反复出现“没意识到这里会挂起”导致的缺陷，应重新评审。它是 T3 上不可逆的一侧，这一点不变。

补偿措施有三项，都不需要语法：诊断在涉及跨挂起点的借用时指明是哪一个调用；编辑器标示挂起调用；对“跨挂起点持有内部可变类型的访问凭据”给出警告。第三项只能覆盖直接可见的内部可变类型，覆盖不到藏在私有字段里的。

**与 TypeScript 的 `async` / `await` 的差别。** 不采用它的语义，原因与拼写无关：

| | TypeScript | Koven |
|---|---|---|
| 调用挂起函数得到什么 | 一个已经在运行的 Promise，可以存放、传递、稍后再等 | 函数的返回值；调用者等它返回 |
| “先启动、稍后再等” | `const p = f(); …; await p` | `val job = scope.launch { f() }; …; job.join()` |
| 同时等多个 | `Promise.all([a(), b()])` | `parallel({ a() }, { b() })`（库） |
| 实参能否借用调用者的局部数据 | 不涉及（有垃圾回收） | 能，因为被调者一定在调用者之前结束 |
| 每次调用是否分配 | 是 | 否（帧嵌入调用者，§2.2） |

一个“已在运行、可以到处传”的 Promise 必然逃逸，它借用的东西就得延长寿命；没有垃圾回收时只能靠生命周期参数或强制拷贝解决。
Rust 的 future 是值，其代价是 `Pin` 与每个挂起点都可能被取消。

| # | 决断 | 理由 |
|---|---|---|
| J34 | **可调试性是 KB8 的验收条件，不是后续改进**。S3 与 S4 的交付必须同时具备下列四项，缺一项不算完成 | 无栈方案把一个函数拆成状态机，物理调用栈上只剩执行器。Kotlin 的做法可作对照：调试模式下靠“栈迹恢复”给异常补帧，另有调试探针模块；恢复有覆盖不到的情形，且在 Native 目标上不可用 |
| J35 | **优先级次序：内存与数据竞争安全 > 行为可预测 > 吞吐**。安全规则不因执行方式而异：线程、任务、并行执行器用同一套 `Transferable` / `Shareable` 判定，全部在编译期完成 | 即 J14。协程默认不迁移线程（J18）让“默认形态零竞争、并行形态由类型检查把关”成为同一条规则的两个取值 |
| J36 | **不用不付**：不调用任何挂起函数的代码，其编译结果与没有这一特性时逐指令相同；不开启并行入口的程序里没有原子操作与锁 | 这是无栈方案相对有栈方案（每个函数入口检查栈、每次调 C 切栈）的主要收益，应作为可测量的验收项 |

J34 的四项：

1. **逻辑调用链**。按 §2.2，顺序调用的帧嵌入调用者的帧，所以一个任务的调用链就是“根帧 + 每一级当前所在的状态”。
   编译器为每个挂起函数生成一张只读的帧描述表（状态 → 源码位置、子帧在帧内的偏移）。
   abort 报告沿它打印出与同步代码形状相同的调用链。正常运行时这张表不被访问，没有运行时开销。经间接帧的调用本来就有指针，同样可遍历。
2. **任务树**。任务作用域持有子任务（J17、J39），因此任意时刻都能列出“哪个作用域在哪一行启动了哪些任务，各自停在哪里”。abort 报告与调试器都使用它。
3. **调试信息**。帧里的每个局部变量在调试信息中有名字、类型与位置；恢复点有行号。目标是在挂起调用之后的断点上，看到的局部变量与同步函数里一样。
   帧变换在所有权图上进行（[之八](evolution-08-compiler-ir-escape-simd-selfhost.md) J27），源码位置与去糖来源本来就保留着。
4. **错误传播迹**。错误是值，经 postfix `?` 逐层返回，到达处理点时原始位置已经丢失——这个问题在同步代码里今天就存在。
   做法与 Zig 的错误返回迹相同：在每个 `?` 的传播分支向当前任务的一个定长缓冲区记一笔源码位置；只在出错路径上执行。调试构建默认开启，发布构建可关闭。
   它对程序不可观察，属于工具而不是语言语义，可以独立于 KB8 提前交付。

**不保证的事。** J35 的“安全”指内存安全与无数据竞争。以下三类问题规则不排除，须在文档中明说：
死锁；经内部可变类型共享的状态在挂起两侧被别的任务改动（单线程上也会发生）；饥饿与公平性。

**开销清单。** 对“当前选型是否有额外开销”的逐项回答：

| 项 | 何时发生 | 量级与说明 |
|---|---|---|
| 调用挂起函数 | 每次 | 一次普通调用加写入状态编号；不分配、不切栈 |
| 帧大小 | 每个任务 | 等于跨挂起点存活的局部变量之和，按最深调用链累加。可能大于必要值；不存活的变量不进帧 |
| 间接帧 | 递归的挂起函数、经存在类型的挂起调用 | 每次调用一次分配；须显式写出（§2.2） |
| 取消检查 | 仅在挂起原语处 | 一次分支；普通代码路径没有 |
| 作用域结束时等待子任务 | 每个任务作用域 | 语义所需，不是额外开销；线程形态下是一次阻塞等待 |
| 代码体积 | 每个挂起函数 | 状态机分派表与帧描述表；后者不参与执行 |
| 错误传播迹 | 仅出错路径 | 一次写内存；发布构建可关 |
| 能力检查 | 编译期 | 运行时为零。`Rc` 保持非原子计数；只有用户选择的共享类型才用原子操作 |
| 两套 IO 接口 | 标准库与生态 | 这是无栈方案真正的成本，不是运行时开销而是维护成本，见 §2.3 |

相对有栈方案，少掉的是：每个任务一段预留栈、函数入口的栈检查、调用 C 时切栈。多出来的是最后一行，以及函数着色带给使用者的负担。

### 2.5 父子关系：从 Kotlin 的 Job 层次取什么（2026-11-11 增补）

Kotlin 的协程有父子层次：每个协程有一个 `Job`，在某个作用域里启动的协程成为该作用域 `Job` 的子节点。它规定了四件事，逐条对照：

| Kotlin 的规则 | 是否采用 | Koven 的形态 |
|---|---|---|
| 父等待全部子任务结束后才结束 | 采用，且更强 | 作用域是不可逃逸的值，析构时等待全部子任务（J17）。Kotlin 靠约定避免泄漏（仍可写 `GlobalScope`），这里由类型保证 |
| 取消自上而下传播：取消父即取消全部子 | 采用 | 取消是对作用域的请求（J19），作用域把它转给每个子任务 |
| 子的失败向上传播：普通 `Job` 下，一个子失败会取消父与其余兄弟；`SupervisorJob` 下不传播 | 采用为**两种作用域策略**，都是库 | 子任务的失败是它返回的 `Err`。`coroutineScope`：第一个 `Err` 出现时取消其余子任务，作用域返回该 `Err`。`supervisorScope`：各子任务的结果互不影响，由调用者逐个取回 |
| 上下文由父传给子（调度器、名字、自定义元素） | 采用 | 执行器随作用域继承（J18）；其余上下文用作用域值库（之六 J7） |

| # | 决断 | 理由 |
|---|---|---|
| J39 | **任务的父子关系就是作用域树**：父 = 启动它的作用域；树的边承载等待、取消、失败策略与上下文继承四件事。不设可脱离作用域存在的任务，不设全局作用域 | 这四件事 Kotlin 已验证是结构化并发的完整内容。差别只在载体：Kotlin 的 `Job` 是可以到处传的堆对象，层次靠运行时维护；Koven 的作用域是词法上的不可逃逸值，层次由类型系统保证，没有运行时登记开销之外的成本 |

不采用的三处：取消以异常形式传播（Koven 用值，J19）；未捕获异常处理器（没有异常）；`Job` 可被存入任意位置（会破坏 J17 的前提）。

库命名向 Kotlin 靠拢（均为库函数，非关键字；`spawn` 是保留字，不用作函数名）：

| Koven（草案） | Kotlin | 说明 |
|---|---|---|
| `coroutineScope { }`、`supervisorScope { }` | 同名 | 任务作用域的两种失败策略 |
| `threadScope { }` | 无对应 | 线程形态的作用域（S2b） |
| `scope.launch { }` | `launch` / `async` | 启动子任务，返回 `Job<T>`；Kotlin 区分无结果的 `launch` 与有结果的 `async`，这里合一 |
| `job.join()` | `join` / `await` | 等待并取回结果 |
| `scope.cancel()`、`job.cancel()` | `cancel` | 请求取消 |
| `withTimeout(d) { }` | `withTimeout` | 超时即取消内层作用域 |
| `Channel<T>`、`send` / `receive` | 同名 | 现行 `channel` 已有 |
| `Mutex`、`withLock { }` | 同名 | C4 |
| `yield(value)`（生成器） | `sequence { yield(v) }` | S3 |

### 2.6 数据怎样在任务之间传递，以及概念集的收敛（2026-11-11 增补）

各家的默认做法：Go 提倡经 channel 通信，但同样提供共享变量加锁，由约定而非编译器区分；Kotlin 两者都有（`Channel`、`Mutex`、共享可变状态），
另有 `select` 表达式用于同时等待多个操作，它在官方指南中至今仍标为实验性；Rust 两者都有，由类型系统把关。

Koven 的所有权规则使这个选择不必靠约定。四种方式按下列次序选用，前一种够用就不用后一种：

| 次序 | 方式 | 何时用 | 成本与保证 | 可用起点 |
|---|---|---|---|---|
| 1 | **返回值**：子任务算出结果，`join()` 取回 | 分叉–合并，占并发代码的多数 | 无共享，无同步 | v1（`Thread<T>.join()`） |
| 2 | **只读借用**：子任务借用父作用域的数据 | 多个子任务读同一份输入 | 零拷贝；借用规则保证无人能写 | S2a |
| 3 | **channel**：把值的所有权交给另一方 | 生产者–消费者、流水线、长期运行的任务之间 | 发送即移交，发送方之后不能再碰它；不复制、不加锁。“通过通信共享内存”在这里由类型系统强制 | v1 |
| 4 | **共享可变**：`Mutex`、原子类型 | 多方更新同一状态（计数器、缓存、连接池） | 需要 `Shareable`；加锁有运行时成本；死锁不被排除 | C4 |

| # | 决断 | 理由 |
|---|---|---|
| J49 | **默认是返回值与 channel；共享可变是显式选择，且排在最后**。标准库的文档、示例与 API 次序都按上表 | 前三种在编译期就排除了数据竞争，且没有锁。第四种必要但应当少用。v1 已经是“只转移所有权、没有共享内存”，这一次序是它的自然延伸而不是新方向 |
| J50 | **面向用户的并发概念收敛为五个**：挂起函数、作用域、`Job`、`Channel`、执行器。其余 Kotlin 概念不引入或并入这五个（见下表）。`select` 是库，且排在最后 | Kotlin 协程的学习成本主要来自概念数量。能并掉的并掉，剩下的每个都对应一件用户必须决定的事 |

| Kotlin 的概念 | Koven 的处理 |
|---|---|
| `suspend` 函数 | 保留 |
| `CoroutineScope`、`coroutineScope`、`supervisorScope` | 保留为“作用域”一个概念，两种失败策略（J39） |
| `Job` 与 `Deferred` | 合并为 `Job<T>` |
| `launch` 与 `async` / `await` | 合并为 `launch` 与 `join` |
| `Channel` | 保留；线程与任务共用同一个类型 |
| `Dispatcher`、`withContext` | 并入“执行器”。默认不切换线程（J18），所以多数代码见不到它；并行入口是一个单独的作用域函数 |
| `CoroutineContext` 及其元素 | 不引入。需要随任务传递的值用作用域值库（[之六](evolution-06-text-globals-extensions-metadata.md) J7） |
| `Flow` | 不引入。同步的惰性序列就是生成器（S3）；异步序列等有需求时再议，届时它是“`next` 为挂起函数的迭代器” |
| `GlobalScope`、可脱离作用域的 `Job` | 不引入（J39） |
| `CoroutineExceptionHandler`、`CancellationException` | 不引入：没有异常；取消是值（J19） |
| `Mutex`、`Semaphore` | 保留为库（C4），不计入五个核心概念 |
| `select` | 库，S5。多数用途已被其他手段覆盖：多个来源汇入一处，用多生产者 channel 加和类型消息；超时用 `withTimeout`；放弃等待用取消。剩下的“在几个不同类型的 channel 之间择一”才需要它 |

一个尚未解决的问题由此显现：线程里的 `send` / `receive` 是阻塞的，任务里的是挂起的，而 J50 希望两者共用一个 `Channel` 类型。
这是函数着色在库层面的表现（§2.3），倾向是同一类型提供两组方法，名字待定；不为它引入新的语言机制。

## 3. 路线 S 的展开

| 步骤 | 内容 | 新增内核 | 依赖 | 验收（试金石） |
|---|---|---|---|---|
| S1 | 闭合 v1 线程与 channel 合同（[线程候选](thread-transfer.md) H1–H6） | 无 | 稳定的 closure 交付边界 | 生产者–消费者；worker abort 终止进程；未 join 句柄析构时阻塞 |
| S2a | 分叉–合并：`parallel(a, b)`、对区间的并行遍历。实参是非逃逸闭包，可借用外层数据 | 无（库用 unsafe 实现） | C3、非逃逸闭包（L3 或现行 borrowed closure）、U1 | 并行求和借用同一只读数组；尝试并行写同一变量被借用规则拒绝 |
| S2b | 动态作用域：`threadScope { scope -> scope.launch { … } }`；`Mutex`、条件变量、线程池（C4） | 无 | S2a、§2.3 的 origin 流入、保证析构推论的证明 | 数量运行时决定的 worker 借用同一配置；作用域值库（之六 J7） |
| S3 | 生成器：`yield`（已保留）；帧变换、S0.1–S0.3 进入参考检查器 | **KB8** | L1（流敏感）、之八 IR3 起的中间表示 | 树的中序遍历写成生成器；跨 `yield` 持有借用；在 `yield` 两侧状态不守恒的反例矩阵 |
| S4 | `suspend` 函数、单线程执行器上的任务作用域、取消（J19）、异步 IO 反应器（§4 IO4） | 复用 KB8 | S3、S2b 的作用域模型、IO2 | 单线程回显服务器承载大量空闲连接；取消一个作用域后全部子任务以取消错误返回且资源全部释放 |
| S5 | 并行执行器（J18 的显式入口）、`select`、有界 channel、actor 库 | 无 | S4、C3 | 多核回显服务器；带背压的流水线 |

路线上的次序含义：S2 与 S3 互不依赖，可并行推进；S4 是两者的合流点。S1–S2 不触及 KB8，因此“先有健全的共享内存并发，再有挂起”是路线本身的结构，不是日程安排。

## 4. IO、网络、系统 API 与 FFI

### 4.1 分层

```text
应用代码
  └─ 流抽象     Reader / Writer interface、缓冲、文本编解码          库（静态分发；异构集合待路线 X）
      └─ 资源    File、Socket、Dir、Process：拥有描述符的资源类型    库（deinit + 显式 close）
          └─ 平台 koven.sys.*：每个目标一份系统调用封装              库（unsafe，按目标选择源集）
              └─ FFI  extern "C"、RawPtr、布局、调用约定             内核 KB7（路线 U）
```

现状：便利文件、目录与标准流合同已启用（v0.47），由 native runtime 提供；显式流 owner、关闭语义、网络仍待合同。
上图自下而上只有最底一层是内核，且已由路线 U 覆盖；本节的决断都是关于**边界合同**，不是新机制。

### 4.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J22 | **FFI 只承诺 C ABI**，并固定五条边界合同：外部调用一律是 unsafe 操作；借用实参以指针传入，仅在调用期间有效，被调方若要留存必须在 Koven 一侧显式使用 `RawPtr`；回调只接受无捕获的、以 C ABI 导出的函数，上下文经显式的用户数据指针传递；`String` 与 C 字符串之间只有显式转换；abort 不展开，跨越 C 帧时直接终止进程 | “借用仅调用期有效”与 Koven 的调用作用域 loan 完全同构，不需要新规则。失败不穿过 C 帧（到达边界即终止进程），因此不需要穿越 C 帧的展开表；这一点在引入线程失败边界后仍然成立。C++、Objective-C 等一律经 C 垫片 |
| J23 | **关闭资源有两条通道**：`deinit` 尽力关闭并丢弃错误；显式 `own fun close(): Result<Unit, IoError>` 消费资源并报告错误。带缓冲的写入方等“丢弃错误即丢数据”的类型，是 `ExplicitConsume`（D11 预留）的首个候选使用者 | 不能从 RAII 推导“关闭必成功”（现行文本与 IO 后继已写明）。两条通道使普通用法无负担，需要严格时有手段 |
| J24 | **平台差异在源集粒度选择**：project 模型按目标选择文件集合；不设语言内的条件编译 | 条件编译会让同一文件存在多个互不可见的版本，类型检查、格式化与 LSP 都要处理“未选中的代码”。源集选择的内核成本为零；确需声明级选择时再以 AT1 的封闭注解补充（T3） |
| J25 | **环境权限保持隐式**：`readFile` 之类是全局函数，不要求把 IO 或分配器作为参数传递 | Zig 的显式参数换来可替换性，代价是每个签名多一个参数。Koven 的定位取“较少心智负担”。需要可替换性的库可以自行以 interface 参数化，这不需要语言支持 |
| J26 | **同步 IO 先行，异步 IO 是 S4 之上的库**；两者共享资源类型，操作集合分开 | 同步 IO 不依赖 KB8，足以支撑编译器自举与多数工具。资源所有权（谁关闭描述符）只定义一次 |

### 4.3 步骤

FFI（即路线 U 面向外部符号的一侧，步骤与 U0–U3 对齐）：

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| FF0 | J22 的五条合同写入 unsafe 别名合同文档 | U0 | 每条合同一个“违反它会怎样”的说明性反例 |
| FF1 | 特权包内的 `extern "C"` 声明、`RawPtr`、外部符号名注解；链接输入写在 project 清单而非源码 | U1、之六 AT1 | 标准库以 Koven 源码调用 `malloc`、`write`；符号缺失是链接阶段的结构化诊断 |
| FF2 | C 兼容布局与对齐注解、C 字符串类型、以 C ABI 导出的函数定义及其作为回调传递 | FF1 | 调用需要回调的 C 函数（如排序）；与 C 结构体互传并核对布局 |
| FF3 | 向用户代码开放；由 C 头文件生成绑定的工具（使用之六 AT2 的生成器协议） | U3 | 用户包绑定一个第三方 C 库；unsafe 使用点可被工具枚举 |
| FF4 | 把 Koven 代码产出为带 C 头文件的静态库或动态库 | FF2 | C 程序链接并调用 Koven 库；这是之八“按部件自举”的前提 |

IO：

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| IO0 | 流 owner 与关闭合同（J23）；闭合文本与 IO 后继中列出的显式流项 | 无 | 关闭两次、关闭失败、未关闭即析构三种情形的可观察行为矩阵 |
| IO1 | `Source` / `Sink` interface（命名见[之十一](evolution-11-failure-interfaces-units.md) J43，原稿作 `Reader` / `Writer`）、缓冲包装、按行与按块读取。缓冲区参数先用 `inout` 容器，L3/L4 之后换成字节视图 | IO0；视图形态依赖 L3、L4 | 逐行处理大文件的峰值内存与文件大小无关；零复制读入调用方缓冲区 |
| IO2 | `koven.sys` 层：把 native runtime 中的 IO 实现迁为经 FFI 的 Koven 源码；runtime 收缩为启动代码与少量垫片 | FF1、J24 | 两个宿主平台的同一组 IO 测试；runtime 导出符号数下降 |
| IO3 | 阻塞式网络：TCP、UDP、地址类型、名称解析；进程与环境 | IO2；并发服务依赖 S2 | 每连接一线程的回显服务器；连接被对端关闭、超时的错误值 |
| IO4 | 异步反应器与异步操作集 | S4 | 见 S4 的试金石 |

明确不进标准库的：TLS、HTTP、压缩、数据库协议。它们经 FF3 绑定现有 C 库或作为独立包发展。

## 5. 对其他文档的影响

- 之四 §4：路线 S 由“仅前置约束”扩展为 S1–S5；S0.1 的开放问题由 §2.2 给出倾向。跨路线依赖增加：`L3 ──> S2a`、`C3 ──> S2a`、`L1 ──> S3`、`S2b + S3 ──> S4`、`FF1 ──> IO2`、`IO2 ──> S4`。
- 之二：形式化小演算增加一条待证性质（保证析构）；L5 的合同形式须覆盖“origin 流入已有持有者”。
- 之三 X0：函数类型预留“挂起”维度。
- 线程候选 H3（句柄生命周期）：现行隐式 join 即结构化语义，应保持；本页不建议增加 detach。
