# 析构义务的原型（内核基底 KB1）

> **性质**：非规范候选设计（原型规格） · **状态**：未启用；原型已实现并通过自身的用例（2026-11-16），不构成正确性证明 · **读取时机**：设计或评审[演进总纲之四](evolution-04-route-capability-unsafe-suspend.md) C1 的统一析构规则、“消费并解除析构”原语，或[之十一](evolution-11-failure-interfaces-units.md) J48 的失败出口清理时 · **唯一真源**：本页维护原型的规则、用例与发现；析构时机的裁决见[析构时机：两个方案的对比](drop-timing-comparison.md) §8，现行规则以 [Guide 10](../guide/10-ownership-borrowing-drop.md) 为准

## 1. 目的与做法

KB1 的不变量是：每个需要析构的 owner 在每条路径上恰好清理一次，移走之后不可用。要检验的是已裁决的统一规则——值在词法作用域结束时按声明逆序析构，析构不可观察时可以提前——加上部分移出、“消费并解除析构”、必须消费与失败出口之后，是否仍能由一个规划器给出，并且结果可以被独立地检验。

原型分成互不信任的两半（`scripts/loan_kernel/drop_plan.py`）：

- **规划器**：输入一段只含所有权操作的程序，输出插入了显式析构的程序，并为每个可能失败的操作列出失败时要析构的变量。
- **检验器**：只执行规划后的程序，自己不推断任何析构。它穷举全部路径（分支两边、循环零到两次、每个可失败操作成功或失败），检查五条不变量。

演算的语句：`let`、`use`、`move`（把所有权交出去）、`call`（一个可能失败的操作）、`set`（赋值）、`take y = x.f`（移出一个字段）、`open x as a, b`（消费并解除析构）、`forget`、`return`、`break`、`if`、`loop`、代码块。类型只有三种标记：`deinit`、`consume`（必须显式消费）、`unforgettable`。都是原型记法。

## 2. 规则

规划器拒绝程序的规则：

| # | 规则 |
|---|---|
| D1 | 使用、移动、拆开一个已移走、可能已移走或已部分移出的值 |
| D2 | 从声明了 `deinit` 的类型部分移出字段；这类类型只能整体 `open` |
| D3 | 可观察的值只在一条分支上被移走（仅当政策选“拒绝”时） |
| D4 | 循环体内移走或析构循环之外声明的值 |
| D5 | 必须显式消费的值被隐式析构：留到作用域结束、被覆盖、只在一条分支上被消费 |
| D6 | 遗忘一个不可遗忘的值（或含有它的值） |
| D7 | 在 `deinit` 里经借用的 `this` 移出字段；经只读借用的 `this` 改写字段（§6） |
| D8 | 取出字段并在原处留下空值，而该字段的类型没有空值（§6） |
| D9 | 在 `deinit` 里整体移走、遗忘或拆开 `this`（§6） |

检验器的不变量：

| # | 不变量 |
|---|---|
| V1 | 离开作用域时（正常、`return`、`break`、失败）名下没有仍被拥有的义务 |
| V2 | 不析构已不拥有的值 |
| V3 | 可观察的值被析构之后，它所在的作用域不再执行别的语句（赋值替换旧值除外） |
| V4 | 可观察的值按声明逆序析构 |
| V5 | 不使用已析构或已移走的值 |

## 3. 用例与变异

| 文件 | 内容 |
|---|---|
| D1 | 词法析构与逆序、移动、嵌套块、提前返回、循环与 `break`、赋值、含可观察字段的复合类型 |
| D2 | 只在一条分支上被移走：不可观察的值、可观察的值、两个值各在一条分支上、之后再使用、两条分支都移走、“返回或移走” |
| D3 | 部分移出、`open`、必须消费、遗忘 |
| D4 | `deinit` 函数体：见 §6 |

测试里的变异与对照：

- 一律留到作用域结束的规划，与提前析构不可观察值的规划，得到相同的结果。
- 把可观察的值也提前析构：检验器报 V3。
- 失败出口上不清理、合流处忽略“可能已移走”：检验器报 V1。
- 手写的错误规划（顺序颠倒、重复析构、移走后使用）：检验器分别报 V4、V2、V5。

## 4. 发现

1. **统一规则可以由一个规划器实现，“提前”确实只是许可。** 两种规划——全部留到作用域结束、不可观察的在最后一次使用后析构——都满足全部不变量。所以一致性用例应当断言 V1–V5 这类性质，而不是析构出现的位置；这与析构时机对比页 §8 的裁决一致。
2. **可观察的值只在一条分支上被移走，现行规则没有说清楚，需要裁决。** Guide 10 写的是“某条路径已移动时该路径不析构”，对不可观察的值足够：在没有移走的那条分支末尾析构即可。
   对可观察的值，这种做法使析构早于作用域结束（V3），是可观察的差别。剩下两种选择：
   - **析构标志**：运行时记一个布尔，作用域结束时“若仍拥有则析构”。规则保持一条线；代价是每个这样的变量一个布尔，其余变量没有成本。
   - **拒绝**：要求两条分支对它的处置一致，用户在另一条分支显式消费。没有隐藏的运行时状态；代价是常见写法 `if (c) { consume(f) }` 要补一个分支。
   **裁决（2026-11-15）：用析构标志。** 原型默认即此。实现现状：用 2026-11-08 构建的 `kovenc`（不是最新 main）试了这种程序，native 构建报“ownership analysis contains deferred codegen facts”，即现在不支持；没有读规划器代码确认原因。
3. **失败出口不需要另一套分析。** 每个可能失败的操作要一份清理清单，内容就是规划器此刻的状态：仍被拥有的变量，自内向外、声明逆序；“可能已移走”的带上标志。部分移出与部分初始化由同一份状态覆盖。
   成本的形状因此很清楚：清单的数量等于可失败操作的数量。这印证之十一 J48 的成本表，没有新增成本项。
4. **“必须显式消费”在有失败出口之后不能是绝对的。** 持有这样一个值时调用了会失败的操作，失败路径上它只能被隐式清理——原型的规划器正是这样做的（用例 `ticketAcrossFailure`），而 D5 只约束正常路径。
   所以这类类型仍然需要一个失败路径上的清理动作：要么它也声明 `deinit` 作为失败时的兜底，要么规定持有期间不得调用可失败的操作（几乎不可用）。之四 C1 把 `ExplicitConsume` 列为预留。**裁决（2026-11-15）：继续预留；暂定方向是这类类型同时声明 `deinit` 作为失败时的兜底，“必须显式消费”只约束正常路径。**
5. **隐式析构的来源有五处，必须消费的检查要覆盖全部。** 作用域结束、提前析构、赋值覆盖、分支合流时的补偿析构、失败清理。第一版原型漏了第四处：只在一条分支上被消费的票据在另一条分支被悄悄析构，是“全部留到作用域结束”与“提前析构”两种规划的对照测试发现的。已把检查集中到“生成析构”这一个出口。
6. **`open` 之后，各字段成为在 `open` 处声明的局部变量。** 它们的析构次序按 `open` 的位置排，而不是按原值的声明位置。显式 `close()`（之七 J23）与守卫的 `dismiss` 都由它组成：拆开、对需要的字段做收尾、其余字段照常析构。这一点要写进原语的规则。
7. **部分移出只对没有 `deinit` 的类型开放**，剩余字段在作用域结束时析构。现行 Guide 10 整体禁止普通字段的部分移出；内核可以放开到这个范围，而声明了 `deinit` 的类型只走 `open`。
8. 赋值的次序“先求值新值、再析构旧值、再提交”在失败出口下是对的：求值失败时旧值仍被拥有，并在清理清单里。

## 5. 没有覆盖的

- **与借用的配合**：存活的 loan 使 owner 保持存活、析构与 loan 冲突。已在借用原型一侧补上（[借用内核演算](loan-kernel-calculus.md) §14）；借用原型定下的析构现在交给本页的检验器检验（演算 §20），活性分析只剩借用原型的一份。
- 临时值；闭包环境；`Rc`。`deinit` 函数体见 §6。
- 循环体内移走循环外的值一律拒绝（D4），没有区分“移走后立即 `break`”。
- 析构标志与循环的配合；嵌套复合类型的逐层部分移出。
- 本原型自己的用例里，“不可观察”仍由类型标记直接给出；经借用原型进来的程序取自[能力推导原型](capability-derivation-model.md)。
- 规则是否正确，没有证明；检验器只穷举到循环两次。

## 6. `deinit` 函数体（2026-11-15）

此前 `deinit` 只是类型上的一个标记。这一步把函数体写出来，检验两件事：`this` 以什么方式交给函数体，以及函数体里失败之后怎么办。用例 D4。

### 6.1 增加的记法

- `deinit T { … }`：类型 `T` 的析构函数体，里面的 `this` 是被析构的值。检验器在析构一个 `T` 时真的执行它，并穷举其中的失败。
- `replace y = x.f`：取出字段，在原处留下空值，`x` 仍然完整。只对标了 `empty` 的类型可用（代表可空类型留下 `null`）。
- 两个政策开关：`this` 的访问方式（只读借用、独占借用、拥有）；`deinit` 在正常路径上失败时终止进程，还是当作普通失败。

次序沿用 [Guide 08](../guide/08-class-family-members.md)：先执行函数体，再按声明逆序析构字段。`this` 为拥有时，余下的字段由函数体自己的规划析构。

### 6.2 `this` 的三种访问方式

| 函数体做的事 | 只读借用（现行） | 独占借用 | 拥有 |
|---|---|---|---|
| 调用 `this` 上的方法、调用可能失败的操作 | 接受 | 接受 | 接受 |
| 取出一个有空值的字段，原处留空（逐个摘下链表后继） | 拒绝（D7） | 接受 | 接受 |
| 按值取走一个没有空值的字段（守卫按值调用它存的动作；把句柄交给按值接收的关闭函数） | 拒绝（D7） | 拒绝（D7） | 接受 |
| 只在一条分支上取走字段 | 拒绝（D7） | 拒绝（D7） | 接受，余下的带析构标志 |
| 取走字段之后再把 `this` 当整体使用 | — | — | 拒绝（D1） |
| 整体移走、遗忘或拆开 `this` | 拒绝（D9） | 拒绝（D9） | 拒绝（D9） |

### 6.3 发现

1. **“拥有”不需要新的规划规则。** 把 `this` 当作一个类型为“`T` 的各字段”的普通局部变量即可：`deinit` 这份义务正在履行，不再另算。部分移出、只在一条分支上移走时的析构标志、失败时的清理清单、提前析构，全部由已有规则给出。新增的只有 D9。
2. **独占借用只够用于有空值的字段。** 没有空值的字段要想在析构时按值取走，只能把字段类型改成可空的，这正是 Rust 里 `Option<T>` 加 `take()` 的绕行写法。[之四](evolution-04-route-capability-unsafe-suspend.md)的通用守卫（按值调用存放的动作）在独占借用下写不出来。“拥有”是独占借用的超集：独占借用能写的，它都能写。
3. **之四里有两处说法不一致，已裁决。** R1.4 记的是“已决（2026-11-10）：放宽为独占借用”；守卫一节后来建议“拥有，且允许部分移出”。**裁决（2026-11-15）：采用“拥有各字段”**，取代 2026-11-10 的“独占借用”。理由是上面两条：它不增加规划规则，并且覆盖独占借用覆盖不了的情形。之五 G3 的逐个摘下后继在两种方式下都能写。
4. **“拥有”不是完整的所有权。** `this` 不能整体移走（D9）：那会得到一个完整的 `T`，它离开作用域时再次运行 `deinit`。所以准确的说法是“拥有各字段”，`deinit` 不能复活被析构的值。
5. **函数体里的失败出口不需要另一套分析。** 函数体内可失败操作的清理清单里自然包含 `this` 余下的字段（用例 `Taker`：取走一个字段后调用失败，清单是被取走的字段与 `this` 的余下部分）。
6. **`deinit` 在正常路径上失败，现有文字没有说清楚，需要裁决。** [之十一](evolution-11-failure-interfaces-units.md) J48 第 6 条说的是“析构过程中**再次**失败”终止进程，即清理途中的第二次失败。作用域正常结束时 `deinit` 第一次失败怎么办，没有写。原型检验了两种做法：
   - **终止进程。** 不需要任何新东西。
   - **当作普通失败继续清理。** 可行，但每个析构点都成了可失败的操作，各要一份清理清单；去掉这些清单，其余的值就泄漏（变异测试报 V1）。清理清单的数量从“可失败调用的数量”变成“再加上可观察值的析构点的数量”，作用域结束、赋值覆盖、提前返回都算。失败也因此可以出现在源码里没有任何调用的位置。
   两种做法之下，清理途中的第二次失败都只能终止进程。**裁决（2026-11-15）：先定为终止进程，并保留以后放宽为“当作普通失败”的余地。** 从终止放宽到传播不破坏已有程序，反过来会。没有监督边界时两者没有区别；在监督边界之内，终止意味着一个 `deinit` 里的失败会绕过监督，所以设计监督边界时须重新评估。需要报告关闭失败的类型用显式的 `close(): Result`（之七 J23）。C++ 与 Swift 是终止，Rust 是传播、二次失败才终止（凭记忆，未逐条查证）。
7. 取走字段之后不能再对 `this` 调用方法（D1）。要先用整体、后拆字段；这是部分移出的既有规则，不是新限制。

### 6.4 没有覆盖的

- 一个值内部各字段之间的析构次序：检验器把一个变量的析构当作一步。
- 长链的递归深度（之五 G3 关心的事）：原型没有栈深度的概念，只检验了“逐个摘下”写得出来。
- `this` 作为借用时与借用规则的配合（函数体里从 `this` 借出的引用）；泛型类型的 `deinit`；析构标志与循环。
- `this` 余下的字段不可观察时，原型会在最后一次使用后提前析构它们；这与统一析构规则一致，没有单独检验。

## 7. 类型的性质取自能力推导（2026-11-16）

析构是否可观察、可否遗忘、可否隐式析构，此前由本原型按自己的标记判断；现在把类型标记翻译成[能力推导原型](capability-derivation-model.md)的声明，由它按字段推导。换过之后暴露出一个漏洞：“必须显式消费”此前只看类型自己的标记，装着这种值的类型可以被隐式析构；按字段推导后它同样被拒绝（D5，用例 D3 `boxedTicketDropped`）。检验器另外接受“只用到一个字段”的使用，供[借用内核演算](loan-kernel-calculus.md) §26 的部分移出使用。
