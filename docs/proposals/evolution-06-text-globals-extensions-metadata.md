# 演进总纲之六：文本、全局状态、扩展函数与元数据

> **性质**：非规范候选设计 · **状态**：未启用 · **读取时机**：仅在裁决 String/Str、顶层与静态状态、扩展函数、注解与代码生成的中后期方向时 · **唯一真源**：本页维护这四项的判据应用、决断 J1–J13 与路线步骤；各项既有细则仍在 [String Copyable](string-copyability.md)、[全局与静态状态](global-and-static-state.md)、[受限扩展函数](restricted-extension-functions.md)，现行语义以 [Guide v0.47](../guide/README.md) 为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。判据（T1–T4）与基底能力（KB1–KB8）见[之一](evolution-01-kernel-and-decisions.md)。
代号：决断 J1–J13；文本步骤 TX、元数据步骤 AT 仅在本系列使用。全局状态沿用其提案自己的分层 G0–G5 与步骤 S1–S5
（与[之五](evolution-05-data-structure-fitness.md)的缺口 G1–G6、路线 S 无关，引用时一律写“全局 G2”“全局步骤 S2”）。

## 1. 共同结论

1. 四项里**没有一项需要新的所有权机制**。文本切片是视图（路线 L3），静态存储是一种永不失效的来源（KB3 的一个取值），
   扩展函数是纯糖，注解是不带语义的元数据。它们的工作量在库、名称解析和工具，不在内核。
2. 检验发现内核清单漏了一项**已经存在**的基底：编译期求值。`const val` 的封闭求值、静态初始化、注解实参、
   向量宽度、布局常量都依赖它。补记为 **KB9**（J8），不新增能力，只是承认它是内核并要求它只有一个实现。
3. 每一项都有一个“看似自然、实则把库的问题推给内核”的方案被否决：给字面量单独造 `Str` 类型、允许 main 之前执行用户代码、
   让扩展函数参与 interface 一致性、提供运行时反射。否决理由都落在 T2（不变量归属）或 T3（可逆性）。

## 2. 文本：String / Str

### 2.1 现状与需求分解

现行：`String` 不可变、UTF-8、`MoveOnly` + `Transferable`，显式 `clone()`；字面量是 `String`，可引用不 `free` 的静态字节
（[ADR-0018](../adr/accepted/0018-string-owner-runtime-abi.md)）；独立 `Str` 与 `toString()` 切换延后
（[Guide 13](../guide/13-program-runtime-standard-library.md#静态字符串类型的延后边界)）。Char 迭代、任意索引、trim、builder 仍待合同
（[文本与 IO 后继](text-input-and-io.md)）。

文本实际有三个角色，各语言的差别只在用几个类型承载它们：

| 角色 | 需要什么 | Rust | Swift | Kotlin/Java | Go |
|---|---|---|---|---|---|
| 拥有缓冲区 | 唯一 owner、可构造、可转移 | `String` | `String`（COW） | `String`（GC） | `string`（GC，不可变） |
| 借用的一段 | 不复制地指向别人的字节 | `&str` | `Substring`、`UTF8Span` | 无（复制或共享底层数组） | `string` 切片共享底层 |
| 字面量 | 随进程存活、无需释放 | `&'static str` | `StaticString`/常量 | 常量池 | 只读段 |

有 GC 的语言三个角色合成一个类型；Rust 用两个类型加一个生命周期参数，代价是新手最常见的困惑
（“该写 `String` 还是 `&str`”）。Koven 不引入生命周期参数（之一的总论点），于是“字面量”这一角色不能靠 `'static` 表达。

### 2.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J1 | **两个类型承载三个角色，不设 `Str`**：`String`（owner）+ `StringView`（路线 L3 的只读视图）。字面量继续是带静态字节表示的 `String` | `Str` 想要的三件事都已有着落：不复制地传递——借用；不复制地切片——视图；静态表——全局 G2 的静态 `String`。新增类型换来的只有“可放进 `Copyable` 聚合”，见下方触发条件 |
| J2 | **文本算法定义在 `StringView` 上**，`String` 通过转发获得同名成员；`borrow String` 到 `StringView` 的转换先显式（`s.view()`），隐式转换作为糖后置 | 否则子串无法传给只接受 `String` 的函数，被迫 `clone()`。这是 Rust 把 API 写在 `&str` 上的原因；Koven 用成员转发避免让用户在签名里做选择 |
| J3 | **下标以字节偏移为单位，`Char` 只经迭代取得**；非字符边界的切片 abort，并按 [错误模型](../guide/09-nullability-errors.md)配一个返回 `T?` 的版本 | UTF-8 下 O(1) 的字符下标不存在；提供它等于隐藏 O(n)。须与 Guide 13 已启用的字节文本合同逐条核对后再定稿 |
| J4 | **表示优化不是语言规则**：小字符串内联、静态字节、静态 `String` 的 O(1) `clone()` 都属于表示承诺，走 ADR（T4） | 用户可观察的只有“值语义 + 显式 clone”，表示可以换 |

`Str` 的**重启条件**（满足才重新评审，不预先设计）：出现必须把字面量文本放进 `Copyable` 聚合的真实程序，且符号表（把文本驻留为整数句柄的库）
不能满足。届时的形态应是库类型——一个只能由字面量构造、内部持有静态地址与长度的 `Copyable` `value class`，
依赖 KB7 与 KB9，不占用内核；它与 `StringView` 的关系是“来源为静态 root 的视图的可存储版本”。

### 2.3 核、糖、库

| 层 | 内容 |
|---|---|
| 内核 | 无新增。依赖 KB3（视图）、KB7（缓冲区）、KB9（字面量与 `const`） |
| 糖 | 字符串插值（已有）；`borrow String → StringView` 隐式转换；`+` 拼接 |
| 库 | `String`、`StringView`、`StringBuilder`（`own fun build(): String` 零复制交出缓冲区）、字节与字符迭代器、解析、格式化、符号表 |

### 2.4 步骤

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| TX0 | 闭合现行文本后继：字符迭代、`trim`、builder 的公共签名；全部以“将来接收者换成视图也不变”为约束审查 | 无 | 三个示范程序（[M1](../development/ecosystem/M1.md)）不需要为取子串而 `clone()` 的地方被逐一列出，作为 TX1 的需求证据 |
| TX1 | `StringView` 及其成员；`String` 成员改为转发 | L3、扩展函数步骤 1 或成员转发机制 | 分词器试金石：全程不分配地产出 token 视图；视图不可存入字段的诊断矩阵 |
| TX2 | `String` 迁为库类型 | U2（容器迁移第 4 步） | ADR-0018 的 ABI 由库代码复现；内建 String 相关 SSA 操作数量下降 |
| TX3 | 共享文本：`String` 满足 `Shareable` | C3 | 跨作用域线程只读共享同一 `String` |
| TX4 | `Str` 重启评审 | 触发条件成立 | 触发程序与符号表方案的对照测量 |

## 3. 顶层状态与静态存储

### 3.1 对既有提案的检验

[全局与静态状态提案](global-and-static-state.md)的分层（G0 常量、G1 收窄、G2 静态不可变、G3 显式惰性、G4 共享可变、G5 线程局部）
按四个测试复核后**方向全部保留**。它的三条否定——不开放自由全局 `var`、不允许 main 之前执行用户代码、不做退出时析构——
正是 T2 的直接应用：全局可变状态的不变量没有任何单一模块能负责，初始化与析构顺序没有局部推理可言。

需要补的是它与内核的接口，共四点。

### 3.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J5 | **静态存储是 Origin 的一个取值**：统一模型（[之二](evolution-02-route-loan-kernel.md) §2）中增加来源种类 `Static(decl)`，它永不失效。返回静态借用的函数写 `from` 加静态声明名，例如 `fun defaults(): borrow Config from DEFAULTS` | 全局 G2 提案中“Phase 3 需新增 root 类别”因此不是特判，而是 Origins 集合多一种元素。显式 `from` 与 D3（先显式后省略）一致 |
| J6 | **“静态可构造”是结构谓词，不引入 `const fun`**：字面量、`const`、实参全部静态可构造且无 `init` 块的主构造器调用。空容器是否静态可构造取决于“空即无缓冲区”的表示承诺，走 ADR | 全局 G4 的 `val HITS = AtomicInt(0)` 需要它。`const fun` 把“函数体可编译期执行”变成公开合同，一旦给出不可收回（T3）；结构谓词可以以后放宽为 `const fun` |
| J7 | **`Lazy`、原子类型、`Mutex` 的全局实例都是库**，内核只提供静态存储与 J6；**线程局部不做成语言特性**，同一需求由“作用域值”库满足（值绑定到结构化作用域而非线程） | once 原语 = 原子状态 + `RawCell`（C2、U1），没有内核成分。任务可能在线程间迁移后（[之七](evolution-07-concurrency-async-io-ffi.md) J18），线程局部的含义变得不可预测；Java 在虚拟线程之后同样以 Scoped Values 取代线程局部 |
| J8 | **补记 KB9 编译期求值**：封闭、无副作用、确定；`const val`、J6、注解实参、布局与向量宽度常量共用一个求值器 | 现状是已有能力，补记的意义是禁止各处各写一个求值器。长期落点见[之八](evolution-08-compiler-ir-escape-simd-selfhost.md) IR5 |

全局 G2 的类型约束“纯内存 + `Transferable` + 不含内部可变”在 C3 之后统一为 `Shareable` 且析构不可观察；在此之前是 C0 引擎里的一个内部谓词，不向用户暴露名字。

### 3.3 步骤

沿用全局提案的步骤 S1–S5，仅补依赖：

| 全局步骤 | 补充的前置 | 补充的验收 |
|---|---|---|
| S2（静态不可变） | J5 进入参考检查器（L0 之后任意时点）；KB9 求值器支持 `value class` | 返回静态借用的函数在调用方可无限期持有；同一静态值被两个线程闭包引用不构成捕获 |
| S3（`Lazy`、共享可变） | C2、C3、U1；J6 | once 的并发初始化压力测试；重入 abort |
| S5（线程局部） | 改为“作用域值”库，依赖之七 S2 | 子作用域可见父作用域绑定，离开作用域后不可见 |

## 4. 扩展函数

### 4.1 定位

扩展函数通过 T1 的“糖”判定：`x.f(a)` 可局部改写为 `f(x, a)`，静态分发，不改变任何不变量。
[受限扩展候选](restricted-extension-functions.md)已给出与完整形态兼容的四步演进，本页只裁决四个它留下或没有触及的问题。

注意动机会变：受限候选的动机是“内建类型无法声明成员”。容器迁为库类型（U2）之后这一动机消失，届时保留扩展函数的理由是
**模块化**——算法可以放在类型所在包之外，用户可以给不属于自己的类型补辅助函数。两个动机得出同一设计，不需要返工。

### 4.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J9 | **扩展函数是纯糖，按候选的步骤 1→2→3 放开，不做步骤 4（扩展属性）**。固定四条：成员优先；不能访问私有成员；候选集由 import 决定，同名同形冲突是歧义错误而非按优先级裁决；接收者模式与成员共用 [Guide 08](../guide/08-class-family-members.md) 的定义 | 私有访问限制保证类型的不变量仍只归声明它的模块（T2）。扩展属性需要自定义访问器，后者仍在“去掉的语法糖”清单内 |
| J10 | **“为不属于自己的类型声明 interface 实现”与扩展函数是两件事，分开裁决**。扩展函数永不使类型满足某 interface | 前者影响 witness table 与能力位，属于内核（KB5）；且需要一致性规则（同一对“类型 × interface”全程序至多一个实现），否则 existential 的行为取决于 import。**该规则须在 X3 之前裁决**，倾向：实现只能写在 interface 或类型的声明包内。**已具体化为[之三](evolution-03-route-existential.md) §6 的 J37**（2026-11-11） |

另两点是工程约束而非决断：泛型与带约束的接收者（`fun <T: Comparable<T>> List<T>.sorted()`）是标准库算法的主要形态，步骤 1 就必须支持；
`Type::name` 形式的引用把接收者视为第一个参数，与“接收者是隐藏的第一个操作数”一致。语法进入 Parser 前先过路线 F 的 F5 门
（[Parser 评审](parser-grammar-verification-review.md)）：`fun a.b.C<T>.name(` 中最后一个 `.Identifier` 才是函数名，需要在机器文法里消除与限定名的歧义。

## 5. 元数据与注解

### 5.1 需求分解与调研

“注解”在各语言里承担四种不同的工作：

| 需求 | 例子 | 何时起作用 |
|---|---|---|
| N1 编译器指示 | 内联提示、弃用、布局、测试入口、外部符号名 | 编译期，封闭集合 |
| N2 样板派生 | 相等、哈希、调试输出、序列化 | 编译期，需要类型结构 |
| N3 工具元数据 | 文档、lint 抑制 | 工具读取，编译器忽略 |
| N4 运行时发现 | 依赖注入、路由表、ORM 映射 | 运行期，需要反射 |

| 语言 | N2 的做法 | N4 的做法 | 教训 |
|---|---|---|---|
| Java | 注解处理器 | 运行时反射 | 反射使启动变慢、妨碍裁剪；原生镜像不得不回头要求反射配置 |
| Kotlin | KSP（编译期符号处理，生成源码） | JVM 反射 | 生态正从运行时反射迁向编译期生成 |
| Rust | 属性 + 过程宏 | 无反射；宏生成静态表 | 能力强；编译时间、宏内诊断与工具支持是长期成本 |
| Swift | 类型化的宏（5.9 起，编译器插件） | 有限的运行时元数据 | 宏的输入输出都是语法树，展开结果可查看 |
| Zig | 编译期执行 + 类型反射 | 无 | 机制统一，但泛型体只在实例化时检查 |
| C# | 源生成器 | 反射 | 新框架优先用源生成器以支持 AOT |
| Go | `go generate` + struct tag | `reflect` | tag 是无类型字符串，错误只在运行时暴露 |

共同趋势：AOT 编译的语言都在把 N4 改写成 N2——编译期生成一张静态表，运行时只是查表。

### 5.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J11 | **语义用关键字，指示用注解**。注解不改变合法程序的类型检查与所有权结论；改变语义的修饰（`move`、`inout`、`suspend`）必须是关键字。注解语法统一为 `@Name(实参)`，实参限 KB9 可求值的常量；编译器只认识一个封闭集合，未知注解是诊断而非忽略 | 读代码时不必查注解定义就能判断所有权，这是“较少心智负担”的直接要求。未知即报错保证以后新增内建注解不会与用户代码冲突（T3） |
| J12 | **不提供运行时反射**。“动态注解”类需求由编译期生成的静态表承担：生成物是普通声明，存放于全局 G2 的静态存储 | 反射读写字段会绕过借用检查与可见性（T2）；它还要求为所有类型保留元数据，与“按单态类型精确布局、无对象头”的定位冲突。`Any` 在现行规范中已明确不是反射基类 |
| J13 | **代码生成分三级，逐级放开**：内建派生（编译器实现的封闭集合）→ 外部生成器（编译器导出稳定的声明清单，工具读取后生成普通源码加入编译）→ 语言内宏（自举之后） | 第一级零机制；第二级内核成本为零，生成物是可读、可调试、可格式化的普通源码，同一份声明清单还服务 LSP、文档与 FFI 绑定生成；第三级要求编译器能在编译期运行 Koven 代码，这正是自举的副产品，提前做等于提前自举 |

内建派生与 KB4 的关系：KB4 推导的是**谓词**（某类型是否 `Copyable`），派生生成的是**成员实现**（逐字段比较）。两者共用同一次结构遍历，
但后者产出代码，应在 C0 引擎之外单独实现，不把“生成成员”塞进能力引擎。

### 5.3 步骤

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| AT0 | 通用注解文法进入 Parser，语义层只接受 `@Test`；其余一律诊断 | F5 语法门；Guide 01 对 `@` 的预留条款改写 | 注解位置的语法矩阵；未知注解的稳定诊断 |
| AT1 | 封闭指示集按需增补：弃用、布局与对齐（U1）、外部符号名（之七 FF1）、目标特性（之八 VE3）。每项随其依赖步骤进入，不预先批量添加 | 各自依赖 | 每个注解一份“删除它之后类型与所有权结论不变”的对照测试 |
| AT2 | 首个进程外生成器驱动声明清单协议，声明 schema/语言版本、输入与工具版本、生成来源和失败合同；生成物作为源集参与正常编译 | CLI project 模型；当前 `doc` 仅导出 syntax-only 顶层普通函数，所需语义字段须另行设计 | 同输入生成字节一致；协议不兼容与生成失败可定位；失败输出不进入本轮源集；生成的非法源码由正常检查器拒绝 |
| AT3 | 内建派生：相等、哈希、调试文本 | 对应 interface 的定义；AT0 | 派生实现与手写实现的行为对照；对含不可比较字段的类型给出定位到字段的诊断 |
| AT4 | 语言内宏 | 之八 BS3；KB9 求值器可执行一般函数 | 另行提案，`macro`、`reify` 保持保留 |

## 6. 对其他文档的影响

- 之一 §3：基底能力增补 KB9；§3.1 派生表增加“静态存储 = KB3 的 `Static` 来源 + KB9”。
- 之二 §2：Origins 的元素增加 `Static(decl)`；`from` 可指名静态声明（J5）。
- 之三 X3：前置增加 J10 的一致性规则裁决。
- F5 新语法表增加：扩展函数声明、通用注解。

## 7. 开放问题

- J2：成员转发用什么机制——扩展函数、现有的 `by field` 委托，还是由视图类型上的成员加隐式转换。三者对用户等价，对名称解析的要求不同。
- J3：切片参数用字节区间还是“位置”抽象类型（防止把任意整数当作合法边界）。
- J5：`from` 指名静态声明时，跨包引用是否暴露实现细节；可能需要允许写 `from static` 的匿名形态。
- J10：已由之三 J37 回答——“interface 所在编译单元内可声明实现”加“经 `value class` 包装”两级并用；是否再向应用一侧放宽留待以后。J10 表中的“声明包”应读作“声明所在的编译单元”。
- J13：声明清单的稳定性等级——它一旦被外部工具依赖，就成为事实上的公开接口，需要版本号。
