# 演进总纲之八：编译器内部——中间表示、逃逸分析、向量化与自举条件

> **性质**：非规范候选设计 · **状态**：未启用 · **读取时机**：仅在评审是否引入 HIR/MIR 类中间表示、逃逸分析与向量化的定位，或判断编译器自举的条件与路径时 · **唯一真源**：本页维护这四项的调研、决断 J27–J33 与路线步骤（IR0–IR5、VE0–VE3、BS0–BS4）；当前实现事实以 [Architecture](../architecture/README.md) 为准，既有架构决定见 [ADR-0032](../adr/accepted/0032-ownership-refinement-layer.md)

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现；其中 §2 的建议与 ADR-0032 的“方案 C 不采用”相反，
**只能经新的 ADR 改变**，在此之前现行架构决定继续有效。判据与基底能力见[之一](evolution-01-kernel-and-decisions.md)。

## 1. 共同结论

四项都不是语言特性，用户看不到它们；但前两项决定了路线 L、C、S 的实现成本，后两项是对整个设计的检验。

1. **中间表示**：值得增加，而且只增加一层。理由不是“别的编译器都有”，而是路线 L1（流敏感）、C1（单一析构规划）、S3（帧变换）
   与 KB9（编译期求值）四件事都要求同一个载体——控制流图上的 place 与显式的 move、loan、drop。
2. **逃逸分析**：在 Koven 里分成两件互不相干的事。决定程序是否合法的“逃逸”是类型系统的一部分（路线 L），必须可预测；
   决定是否把堆分配换成栈分配的“逃逸分析”是不可观察的优化，不设路线，按测量结果零散进行。
3. **向量化**：第一步不改语言——让普通循环能被后端自动向量化，它依赖的恰好是 U0 的别名合同。显式向量类型是一项表示原语，放进 U1 的特权集合。
4. **自举**：是检验而不是带日期的目标。给出客观门槛与按部件渐进的路径；在路线 L、X、U 的主要步骤完成前开始，等于让编译器本身成为阻碍语言演进的最大存量代码。

## 2. 中间表示：是否需要 HIR / MIR

### 2.1 调研

| 编译器 | 层次 | 所有权或借用检查在哪一层 | 备注 |
|---|---|---|---|
| Rust | AST → HIR（去糖、已解析名称）→ THIR（带类型）→ MIR（控制流图、place）→ LLVM | **MIR**。2018 年为获得流敏感（NLL）把借用检查从 HIR 迁到 MIR | 析构展开、常量求值（解释 MIR）、协程的状态机变换都是 MIR 上的遍 |
| Swift | AST（带类型）→ SIL（raw → canonical）→ LLVM | **SIL**。所有权 SSA 给每个值标注 owned / guaranteed，仅移动类型的检查、确定初始化都是 SIL 上的强制诊断遍 | 只有一层中间表示，类型检查留在 AST |
| Go | AST → 类型检查 → IR → SSA | 无所有权；逃逸分析在进入 SSA 之前的 IR 上 | SSA 先通用后按目标降低 |
| Kotlin（K2） | FIR（解析后的前端树）→ 后端 IR | 无 | 前端树承担解析与类型，后端 IR 承担降低 |
| Zig | AST → ZIR（无类型）→ 语义分析 → AIR（带类型，按函数）→ 机器码 | 无 | 语义分析与编译期执行合一 |

可以确定的共性：**凡是做所有权或借用检查的编译器，都把检查放在以控制流图和 place 为基础的中间表示上，而不是语法树上。**
Rust 是在树上做过一遍之后迁移的，迁移的直接动因就是流敏感。层数没有共性：Rust 四层，Swift 一层。

### 2.2 Koven 的现状

```text
AST ──> 名称 ──> 类型事实 ──> 所有权事实 ──┬─> [细化层 RefinedBody：槽位 CFG] ──> typed SSA ──> 校验 ──> LLVM
        （lang-frontend，树 + 侧表）        │        （lang-codegen）
                                            └─> [unit_lower：按家族直接从 AST 发射]（迁移中，逐步删除）
```

[ADR-0032](../adr/accepted/0032-ownership-refinement-layer.md) 已经引入了一个事实上的中间表示：`RefinedBody` 是基于槽位的控制流图，
语句只有 `Init`、`Assign`、`Move`/`Copy`、`Drop`、`LoanBegin`/`LoanEnd`。它与 Rust 的 MIR 在形态上很接近，差别在**位置**：
它位于所有权检查**之后**，消费 frontend 发布的事实（析构点、loan 起止、交付点），自己不做判断。于是现在存在三样东西：

- frontend 的所有权数据流，直接在语法树上进行，每种控制流构造各自处理；
- 把结论传给后端的**事实协议**（析构点的种类、loan 的起止位置等），两侧不一致时表现为 `MissingFact` / `InvalidModel`；
- 后端的槽位图与 SSA 校验器，后者对 loan 与消费唯一性再检查一遍。

本轮粗略量了规模（按文件名排除测试后的物理行，含注释与空行，仅作量级参考）：frontend 所有权检查约 5.9 万行，类型检查约 6.1 万行；
codegen 的 `ssa` 约 10.9 万行，其中细化层约 2.1 万行、`unit_lower` 约 1.8 万行；codegen 非测试源码中 `UnsupportedNode` 出现约 650 处。
这些数字**不能直接证明**问题出在分层上——它们同样可能来自迁移尚未完成。因此 IR0 是归因，而不是直接动手。

### 2.3 判断

把路线上各步对载体的要求列出来：

| 需求 | 来自 | 在语法树上做 | 在控制流图上做 |
|---|---|---|---|
| 逐程序点的 loan 存活、合流取并 | L1 | 每种语法构造各写一遍传播与合流 | 一个通用数据流框架 |
| 析构策略由单一算法消费 | C1 | 现有两个规划器 | 一遍“析构展开”，把义务变成显式 `Drop` |
| 挂起点两侧状态守恒、生成状态机 | S3、KB8 | 不现实 | 标准做法（Rust 的协程变换即 MIR 遍） |
| 封闭的编译期求值 | KB9 | 树解释器，只能覆盖表达式 | 解释控制流图，可覆盖一般函数 |
| 新语法的成本 | 全部 | 检查与降低各加一份 | 只加“语法 → 图”的一份翻译 |

四项需求指向同一个载体，这是引入它的充分理由。反过来，没有任何一项需求要求在类型检查**之前**去糖，
所以不需要单独的 HIR：smart cast、穷尽性、重载选择都需要类型信息才能去糖，树加侧表的现有形态足够。

### 2.4 决断

| # | 决断 | 理由 |
|---|---|---|
| J27 | **不引入独立的 HIR；增加唯一一层位于 frontend 的中间表示（下称“所有权图”）**：按函数的控制流图，操作数是 place，语句是显式的初始化、move、copy、借用起止、调用与（展开后的）析构，保留源码 `Span` 与去糖来源。它不含 SSA 类型、ABI 与布局 | 所有权检查、析构展开、帧变换、编译期求值都在它上面进行。不含 ABI 回应了 ADR-0032 否决“由 frontend 产出细化 IR”时的理由——那里反对的是把 Phase 4 的输入放进 frontend |
| J28 | **细化层保留，输入由“语法树 + 事实”改为“已检查的所有权图”**，成为从所有权图到槽位与 SSA 类型的薄映射；事实协议随之消失；SSA 校验器保留为翻译校验 | 语义只定义一次（在图上的检查器），后端只做表示选择。这是 D10 与 E3 两次收敛的同一方向的第三步 |
| J29 | **所有权图以影子模式进入，载体就是路线 L 的参考检查器**：先只为参考检查器构图，与生产检查器逐用例对照诊断；一致率达到门槛并持续一个周期后再切换权威 | 避免一次性重写。参考检查器（[之二](evolution-02-route-loan-kernel.md) L0）本来就需要一个载体，不是额外工作 |
| J30 | **启动时机在细化层迁移完成之后**（`unit_lower` 的函数体路径删除、SPEC-0392 的结构复审收口），且须先有新的 ADR | 不在一次进行中的迁移上叠加另一次迁移。ADR-0032 的决定在新 ADR 接受前有效。用户已于 2026-11-11 同意届时以新 ADR 调整；这是方向上的同意，不等于 ADR 已提出或已接受 |

### 2.5 步骤

| 步骤 | 内容 | 类别 | 验收 |
|---|---|---|---|
| IR0 | 归因：统计近期所有权与降低相关的修复中，有多少属于“同一规则两处实现不一致”“事实协议缺失或多余”“新语法构造未覆盖”；据此写出所有权图的规格（语句集、place 文法、不变量）作为 compiler-specs 候选 | 文档 | 归因表；若三类合计占比低，本路线降级为“仅参考检查器使用” |
| IR1 | 构图器与校验器，覆盖直线代码、分支、循环、调用；接入参考检查器 | 新增（影子） | 对现有所有权测试集，参考检查器与生产检查器的接受/拒绝结论一致；差异逐条归类为“生产实现的缺陷”或“规格的缺陷” |
| IR2 | 析构展开作为图上的一遍；与现有析构计划对照 | 新增（影子） | 析构点集合逐函数相等；C1 的 `DropPolicy` 在此实现一次 |
| IR3 | 切换权威：Phase 3 的诊断由图上的检查器产生；按构造逐步删除树上的数据流 | 纯重构 | 诊断码、主 `Span` 与文本不变（或逐条审阅的差异）；frontend 所有权检查行数单向下降 |
| IR4 | 细化层改为消费所有权图；删除事实协议 | 纯重构 | SSA 产物逐函数等价；`MissingFact` 类错误路径消失 |
| IR5 | 在图上承载帧变换（S3）与编译期求值器（KB9） | 新增内核的载体 | 见之七 S3 与之六 J8 |

风险与对策：诊断质量可能下降（图上的位置离源码更远）——语句携带 `Span` 与“由哪种语法去糖而来”，诊断模板按来源选择；
泛型在图上是否保持多态（一份图服务所有实例）会影响编译时间与将来的分离编译，IR0 的规格必须写明，倾向保持多态、能力判定在实例化时代入。

## 3. 逃逸分析

### 3.1 两种“逃逸”

| | 语义逃逸 | 优化逃逸 |
|---|---|---|
| 回答的问题 | 这个程序合法吗 | 这次分配能否更便宜 |
| 归属 | 类型系统：`Escapable` 能力、非逃逸闭包、`from` 合同（路线 L） | 优化器 |
| 要求 | 可预测、有规格、诊断稳定 | 不可观察：不改变析构时机、不产生诊断 |
| 用户如何影响 | 写类型与参数模式 | 不需要也不应该去“迎合” |

Go 把两者合一（编译器决定变量在栈上还是堆上），代价是性能随无关改动突变，用户要靠编译器输出去猜。
Koven 的所有权已经把大部分答案写在类型里：值默认内联存放，间接只发生在 `Box`、`Rc`、容器、闭包环境等显式位置；
`borrow` 参数按合同就不留存实参。因此留给优化逃逸分析的空间本来就小。

### 3.2 决断与可做的事

| # | 决断 | 理由 |
|---|---|---|
| J31 | **语义逃逸只由类型系统定义；优化逃逸不可观察、不出诊断、不设路线**，每一项都以测量为前提单独立项 | 把合法性绑在优化器上会使规格依赖实现；把性能绑在不可见的分析上会制造性能断崖 |

按成本从低到高，可做的三件事：

1. **由参数模式生成后端属性**：`borrow` → 不捕获、只读；`inout` → 不别名。现状是 codegen 不发射这些属性（之一 §7 的核对结果）。
   前置是 U0 的别名合同——在合同写明之前发射属于未经论证的承诺。这一项同时是向量化的前提（§4）。
2. **给分配与释放函数标注后端可识别的属性**，让后端已有的“成对分配消除”“堆转栈”对 `Box` 与闭包环境生效。不需要自己写分析。
3. **所有权图上的提升遍**：一个从未被移出所在帧的 `Box` 可直接栈分配。有了 §2 的图，这是一个局部判断；只在测量显示第 1、2 项不够时才做。

三项都需要证明不改变可观察的析构时机：被提升的对象若是资源类型，其 `deinit` 仍在原定程序点执行，变的只是存储位置。

## 4. 向量化

### 4.1 调研

| 做法 | 代表 | 要点 |
|---|---|---|
| 仅自动向量化 | Go（基本没有）、多数语言的默认 | 零语言成本；效果取决于别名信息与循环形态，不可靠 |
| 内建向量类型 | Zig `@Vector(N, T)`、Mojo 的 SIMD 类型 | 内核只有一个类型构造器与逐分量运算，映射到后端向量类型 |
| 库类型 + 编译器内在表示 | Swift `SIMD4<Float>`、C# `Vector128<T>`、Rust `std::simd` | 用户看到的是库；Rust 的可移植 SIMD 长期停留在 nightly，说明 API 面比机制难定 |
| 目标专用 intrinsic | Rust `std::arch`、C# 硬件 intrinsic | 需要目标特性标注与运行时特性检测 |
| 语言级数据并行 | ISPC | 另一种编程模型，不适合通用语言 |

### 4.2 Koven 的特殊约束

- **checked 算术**：现行规则是整数溢出即 abort，且 v1 不提供 wrapping 变体（[Guide 04](../guide/04-expressions-operators.md#整数溢出与除零)）。
  循环体内的溢出检查是一个可能提前退出的分支，通常阻止整数循环的自动向量化。浮点不受此影响，但浮点归约需要允许重结合，而语言没有、也不应默认提供这种许可。
- **下标检查**：对容器的区间遍历已用长度快照（当前实现事实），检查可被提出循环；任意下标的循环不行。
- **没有 const 泛型**：`Vector<T, N>` 这种写法目前表达不了。

### 4.3 决断

| # | 决断 | 理由 |
|---|---|---|
| J32 | **三层推进，前一层不依赖语言变化**：先让标量循环可被自动向量化；显式向量类型以**特权的内在表示**进入 U1 的原语集合，由标准库包装成具名的 `value class`；目标专用 intrinsic 与特性检测放到 U3 之后。**不为向量化引入 const 泛型** | 第一层的收益最广且全部来自已规划的工作（U0 属性、迭代器形态）。向量表示是 T4 意义上的表示承诺（对齐、ABI），必须经 ADR。const 泛型若因定长内联数组等系统编程需求另行进入，向量类型届时再泛化 |

### 4.4 步骤

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| VE0 | 基准与现状：选定一组核心循环（求和、点积、逐元素运算、字节查找），记录后端是否向量化及原因 | [测量候选](measurement-distribution.md) | 一张“循环 × 是否向量化 × 阻碍原因”的表 |
| VE1 | 消除阻碍：§3.2 第 1 项的参数属性；提供显式的环绕与饱和算术**函数**（库加 intrinsic，不改变运算符的默认语义） | U0；Guide 增量 | VE0 表中由别名与溢出检查导致的失败项转为成功；默认运算符语义不变的回归 |
| VE2 | 向量内在表示与标准库向量类型（固定的几种宽度与元素类型）、逐分量运算、与数组的装载和存回 | U1；ADR | 手写向量版点积与标量版结果一致；在不支持的目标上退化为标量实现 |
| VE3 | 目标特性注解、运行时特性检测、目标专用 intrinsic | U3、之六 AT1 | 同一函数的多个目标版本按运行时检测分派 |

## 5. 编译器自举的条件

### 5.1 调研

| 语言 | 路径 | 教训 |
|---|---|---|
| Go | 1.5 起自举，C 源码经工具机械翻译为 Go | 翻译得到的是“C 风格的 Go”，但避免了重写期间的语言冻结 |
| Rust | 早期即由 OCaml 实现换为自举 | 语言尚在剧变时自举，编译器长期背负旧惯用法；引导链很长 |
| Zig | 历时数年，最终以一个可重现的引导产物替换 C++ 实现 | 双实现并存期间语言演进明显变慢 |
| Swift | 至今主体仍是 C++，逐步把语法库、宏、部分优化遍换成 Swift | **按部件渐进**是可行的，不自举也不妨碍语言成功 |
| Kotlin | 很早就以 Kotlin 编写，运行在已有的 JVM 上 | 有成熟宿主平台时自举成本低，Koven 不具备这一条件 |

### 5.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J33 | **自举是检验，不设日期**。满足 §5.3 的门槛前不开始；开始后按部件渐进（先工具，后前端部件，最后整体），每一步以现有 Rust 实现为差分基准；Rust 实现至少保留到自举编译器达到不动点并稳定若干版本 | 过早自举使编译器成为最大的存量代码，每次所有权模型的调整都要改写它，直接妨碍路线 L、X、U。保留 Rust 实现还提供了针对“编译器自身被污染”的对照编译手段 |

### 5.3 门槛

**语言与库**（编译器这类程序实际需要的东西）：

| 需要 | 对应步骤 | 说明 |
|---|---|---|
| 带载荷的 enum、`when`、泛型、interface | 已有 | 语法树与诊断的主体 |
| 以索引表达的树与图 | 已有（[之五](evolution-05-data-structure-fitness.md) §1） | 现行编译器的索引式 AST 可原样照搬 |
| 有序与哈希映射、集合、可变列表 | 已有；库化见 U2 | 确定性要求有序迭代 |
| 文本视图、builder、符号表 | 之六 TX1 | 词法分析不应为每个 token 分配 |
| 深结构的迭代式析构 | 之五 G3（已决：`deinit` 独占 `this`） | 深层语法树 |
| 文件、目录、进程参数、子进程（调用链接器） | 之七 IO1–IO3 | |
| 调用后端的 C 接口 | 之七 FF3 | 最大的单项依赖；没有它只能自举到中间表示为止 |
| 测试框架 | 之六 AT0（`@Test`） | |
| 错误值传播与诊断格式化 | 已有 `Result` 与 postfix `?` | |
| 抽象打包 | 路线 X（非必需） | 遍管理器等处有用，可用 enum 替代 |
| 并发 | 之七 S2（非必需） | 语言服务与并行编译需要，首个自举版本可单线程 |

**工程**：

1. Guide 达到 1.0 并冻结语义，一致性测试集可作为与实现无关的判定基准；
2. 路线 L 至少到 L3、路线 U 至少到 U2（否则自举编译器要随内核变化反复改写）；
3. 编译产物确定（现行护栏已要求），以便验证不动点；
4. 用 Koven 写成的非平凡工具已在日常使用中（见 BS1），证明语言对这类程序是顺手的。

### 5.4 步骤

| 步骤 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| BS0 | 标准库以 Koven 源码实现并逐步取代 runtime 中的对应部分 | U2、之七 IO2 | 即路线 U 的验收；这是最早的自用 |
| BS1 | 用 Koven 编写独立工具：格式化器、文档生成器、绑定生成器、之六 AT2 的源码生成器 | 之六 TX1、之七 IO1 | 工具进入日常开发流程；记录写起来别扭之处并反馈到四个测试 |
| BS2 | 前端部件：词法与语法分析以 Koven 重写，产出 C ABI 库嵌入现有驱动；与 Rust 实现做差分测试 | 之七 FF4；路线 F 的机器文法作为共同规格 | 全部语法测试上两个实现的语法树与诊断一致 |
| BS3 | 整体自编译：Rust 实现编译出第一代，第一代编译出第二代，第二代编译出第三代 | §5.3 全部门槛 | 第二代与第三代逐字节相同；一致性测试集全部通过 |
| BS4 | 调整 Rust 实现的地位 | BS3 稳定若干版本 | 需用户决定：保留为参照实现、仅保留为引导来源，或退役；退役前必须有可重现的引导路径 |

BS2 是可选的中间台阶：它的价值在于让“用 Koven 写编译器”的经验提前出现，而不必等到门槛全部满足。若 FF4 迟迟不具备，可直接从 BS1 到 BS3。

## 6. 对其他文档的影响

- 之二 L0：参考检查器的载体明确为所有权图（J29）；L1 的实现前提是 IR1。
- 之四 C1：单一析构规划器的落点是 IR2。U0 增加一项产出：参数模式到后端属性的映射表。U1 的原语集合增加向量内在表示（VE2）。
- 总纲 K8：改为引用本页 §5 的门槛与步骤。
- 跨路线依赖增加：`细化层迁移完成 ──> IR1`、`L0 ⇄ IR1`（同一工作）、`IR2 ──> C1`、`IR3 ──> S3`、`U0 ──> VE1`、`U1 ──> VE2`、`FF4 ──> BS2`、`FF3 ──> BS3`。

## 7. 开放问题

- J27：所有权图放在 `lang-frontend` 的一个模块还是独立 crate。现行规则是新增 workspace member 需要独立架构决策；倾向先作为模块。
- J28：SSA 校验器作为翻译校验保留多久；它与图上检查器的职责重叠应在 IR4 后重新划分。
- J32：环绕算术函数的命名与是否同时提供“本作用域内不检查溢出”的块形式（倾向不提供，T3）。
- J33：BS4 中 Rust 实现的最终地位。
- 编译期求值器（KB9）在 IR5 之前的过渡形态：现有的 `const` 求值是否继续在树上扩展，还是冻结到 IR5。

## 8. 来源与核对状态

- 仓库事实：编译数据流、细化层的两段式与 `RefinedBody` 的语句集取自 [流水线](../architecture/pipeline-and-workspace.md)、
  [所有权细化层](../architecture/ownership-refinement.md)与 ADR-0032 原文；规模数字为本轮在 HEAD `a775568f` 上的粗略统计（方法见 §2.2）。
- Rust 可移植 SIMD 的状态：检索结果互相矛盾（个别文章称已在 1.89 稳定，跟踪问题与多数讨论仍称仅 nightly），**未能确认**，本页按“长期未稳定”表述。
