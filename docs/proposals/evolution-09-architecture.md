# 演进总纲之九：总体架构——内核与扩展的分层、接口与原则

> **性质**：非规范候选设计 · **状态**：未启用 · **读取时机**：仅在确认或评审 Koven 中后期的总体架构（语言分层、内核之间的接口、扩展点范围）时 · **唯一真源**：本页维护分层视图、内核接口矩阵、架构规则 A1–A9 与经典案例的借鉴表；当前实现事实以 [Architecture](../architecture/README.md) 为准，各内核的内容以[之一](evolution-01-kernel-and-decisions.md)至[之八](evolution-08-compiler-ir-escape-simd-selfhost.md)为准

本文不修改或启用任何 Guide 规则，不批准 Spec/ADR，不授权实现。它不提出新的语言能力，
只把前八页已经得出的结论整理成一张可以检查的架构图：有哪些层，层与层之间、内核与内核之间经由什么接口交互，
哪些地方允许扩展、哪些地方不允许。

## 1. 共识的准确表述

“内核 + 扩展”在本系列里的含义是：

- **内核**：必须由编译器强制的不变量，共九项（KB1–KB9，见[之一](evolution-01-kernel-and-decisions.md) §3）。判据是之一 §2 的四个测试。
- **扩展**：内核之外的一切，分三类，各有不同的接口：
  - **糖**：由编译器做的局部翻译，结果是内核语言。接口是“去糖规则”。
  - **库**：用 Koven 写成。少数库用 `unsafe` 实现并对外给出安全签名，其余只用安全代码。接口是“特权原语清单”与公开 API。
  - **工具**：格式化、诊断渲染、代码生成器、调试与测量。接口是编译器的稳定产物（诊断、声明清单、调试信息）。

内核不可插拔，扩展可以替换。这是本页全部规则的出发点：一条不变量如果可以被插件改写，它就不再是不变量（T2）。

需要三张图才能说清，因为“架构”在这里有三个互不相同的问题：
程序建立在什么之上（§2 语言分层）、内核彼此怎样交互（§3）、编译器怎样实现这些层（§4）。

## 2. 语言分层视图

```text
层    内容                                         向上提供的接口
──────────────────────────────────────────────────────────────────────────────
L6   应用与生态                                    —
     用户程序、第三方库、外部代码生成器
        ▲ 公开 API + 能力约束（Copyable / Transferable / Shareable …）
L5   标准库 · 策略层（只用安全代码）
     集合算法、文本、channel、执行器、任务作用域、
     Lazy、IO 的缓冲与编解码
        ▲ 安全签名：签名本身就是合同，调用方无须知道实现用了 unsafe
L4   标准库 · 特权层（用 unsafe 实现、对外安全）
     Box / Rc / List 的存储、Cell、原子类型、Mutex、
     平台层（经 FFI 调系统接口）
        ▲ 特权原语清单：封闭、有版本（RawPtr、布局查询、内部可变标记、
          extern、向量表示 …）。相当于操作系统的系统调用表
L3   表面语言（糖）
     for、?.、字符串模板、解构、lambda、扩展函数、?（错误传播）…
        ▲ 去糖规则：每条糖登记一条到 L2 的局部翻译
L2   核心语言（内核 KB1–KB9）
     值与析构、Place 与 Loan、Origin、能力推导、类型抽象、
     内部可变单元、裸内存、帧挂起、编译期求值
        ▲ 已检查的程序（长期：所有权图）+ 每个类型的能力与析构策略
L1   表示与 ABI（由 ADR 管辖）
     布局、调用约定、见证表、帧布局、C ABI
        ▲ typed SSA → LLVM IR；对外只承诺 C ABI
L0   平台
     LLVM 与目标机器、操作系统 / libc、裸机
```

读图的四条规则：

1. **依赖只向下**。L5 不得依赖 L6；L2 的语义不得引用 L1 的布局（除非用户显式要求某种表示，属于路线 U）。
2. **每个接口都是可以列举的**。去糖规则、特权原语、能力集合都是封闭清单，不是“编译器内部都能用”。
3. **L4 是唯一允许 `unsafe` 的库层**。L5 及以上出现 `unsafe` 需要单独理由（FFI 绑定是主要例外）。
4. **相邻层之间可以跳层调用，但不能绕过接口**。应用可以直接用 L4 的 `Box`；不可以直接用 L4 所依赖的特权原语，除非自己声明 `unsafe`。

当前实现与此图的差距（不是缺陷，是路线 U 的内容）：`List`、`Map`、`Rc`、`Box`、`String` 目前由编译器与 native runtime 直接实现，
即 L4 的一部分还在 L2/L1 里。路线 U 的 U2“容器迁移”做的就是把它们移回 L4。

## 3. 内核之间的接口

内核之间**不互相读取内部数据结构，只交换五类判定**。这五类判定就是内核的接口（最初列为四类，2026-11-11 对照文献后拆分并补充，见本节末）：

| 判定 | 提供者 | 含义 |
|---|---|---|
| 能力谓词 `Cap(T)` | KB4 | 类型 `T` 是否 `Copyable` / `Transferable` / `Shareable` / `Escapable`，以及它的 `DropPolicy` |
| 冲突判定 `conflict(p, q, 访问)` | KB2 | 两个 place 上的访问是否重叠且冲突 |
| 来源包含 `origins(v)` | KB3 | 值 `v` 持有哪些 loan，它们的来源在某一点是否仍然有效 |
| 初始化状态与活性 `init(p, 点)`、`live(v, 点)`、`drop_at(v)` | KB1 | 某一点上 place `p` 是否已初始化、未移出（向前的数据流）；`v` 此后是否还会被用到（向后的数据流）；它在哪里析构 |
| 上下文许可 `ctx(点)` | 函数签名与块标记 | 某一点是否处于 `unsafe` 块、挂起函数、编译期求值之内；分别是 KB7、KB8、KB9 的操作是否允许出现的依据 |

```text
                     ┌──────────────────────────┐
                     │ KB4 能力推导（Cap）       │
                     └───┬──────┬──────┬────────┘
            DropPolicy   │      │Escapable     │ 能力位、Transferable
                         ▼      ▼              ▼
┌────────────┐ live ┌────────┐ ┌──────────┐ ┌─────────────────┐
│ KB1 值与析构 │────▶│ KB2    │▶│ KB3      │▶│ KB5 类型抽象      │
│            │      │ Place  │ │ Origin   │ │ 泛型、存在类型     │
└─────┬──────┘      │ Loan   │ │ 携带     │ └─────────────────┘
      │             └───▲────┘ └────┬─────┘
      │ 活性、析构点      │ 唯一例外    │ 跨挂起点的 loan
      │             ┌───┴────┐     ▼
      │             │ KB6    │ ┌──────────┐      ┌──────────────┐
      └────────────▶│ 内部   │ │ KB8      │      │ KB9 编译期求值 │
                    │ 可变   │ │ 帧挂起    │      │ 常量、静态初值 │
                    └───▲────┘ └──────────┘      └──────┬───────┘
                        │ 裸指针                         │ Static 来源的初值
                    ┌───┴────┐                          ▼
                    │ KB7    │                        （KB3）
                    │ 裸内存  │
                    └────────┘
```

图只画主要流向；完整关系以下面的矩阵为准（行是消费者，列是提供者，格内是消费的判定）：

| 消费者 ＼ 提供者 | KB1 | KB2 | KB3 | KB4 | KB6 | KB7 | KB9 |
|---|---|---|---|---|---|---|---|
| KB1 值与析构 | — | | | `DropPolicy` | | | |
| KB2 Place 与 Loan | 活性 | — | | | 例外类型标记 | 别名合同（U0） | |
| KB3 Origin 携带 | 活性 | 冲突 | — | `Escapable` | | | 静态初值 |
| KB5 类型抽象 | 析构入口 | | 借用 existential 是持有者 | 能力位 | | | |
| KB6 内部可变 | | | | 叶子公理（不 `Shareable`） | — | 裸指针 | |
| KB8 帧挂起 | 活性、析构点 | 冲突 | 跨挂起点的 loan | `Transferable`（仅并行入口） | | | |

三条由此得出的结构性结论：

- **KB4 是枢纽，KB8 是纯消费者**。KB8 不向任何内核提供判定，所以它最后做、且做错了不会污染其他内核。KB4 被所有内核消费，所以它的引擎通用化（C0）排在各路线最前。这与之一 §5 的依赖图一致，可以互相校验。
- **KB7 只向库和 KB6 提供东西**，不被其余内核消费。因此“安全代码的不变量不依赖 unsafe 以外的东西”可以按层检查。
- **五类判定的共同载体是所有权图**（之八 J27）。每个判定都是图上的一个查询，这是“一种中间表示就够”的架构理由：判定只有五类，不需要为每个内核各建一层。

判定集合是否完整的核对（2026-11-11）。对照对象是 Rust 借用检查器的 Polonius 表述，它把检查所需的输入事实明确列了出来：

| Polonius 的输入事实 | 对应的判定 |
|---|---|
| loan 的发出、被覆盖而失效、被某次访问作废 | 冲突判定（KB2） |
| origin 之间的包含关系 | 来源包含（KB3） |
| 变量的使用、定义与析构时的使用（推出活性） | 活性（KB1） |
| 路径的移出与赋值（推出初始化状态） | 初始化状态（KB1） |
| 控制流边 | 载体本身，不是判定 |

由此得到两点修正：KB1 提供的其实是两个方向相反的分析，原先合写为一项，现拆开表述；类型能力查询在 Rust 中由独立的 trait 求解提供，对应这里的能力谓词。
Polonius 不覆盖、而 Rust 编译器另有独立检查的三件事——`unsafe` 检查、常量求值检查、协程跨挂起点的类型集合——前两件与第三件的“是否在挂起函数内”归入新增的**上下文许可**；
第三件的实质内容“哪些值跨挂起点存活、它们是否可转移”可由活性与能力谓词组合得出，不需要新的判定。
“挂起点两侧状态守恒”（KB8）因此是派生性质，不是第六类。这一结论是对照得出的论证，仍须在之二的小演算中形式化确认。

## 4. 编译器管线视图

各阶段只经产物通信，这一点是现行硬边界（[AGENTS](../../AGENTS.md) §3），不是新提议。下图标出现状与之八建议的目标：

```text
              现状                                   目标（之八，须新 ADR）
源码 ─▶ Lexer ─▶ Parser/AST                        同左
      ─▶ 名称 ─▶ 类型                               同左
      ─▶ 所有权检查（在语法树上，产出事实）           ─▶ 构造所有权图 ─▶ 图上检查
      ─▶ OwnedCompilationUnitView                   （析构展开、帧变换、编译期求值都在图上）
 ════════════════ frontend / codegen 边界 ════════════════
      ─▶ 细化层（语法树 + 事实 → 槽位 CFG）          ─▶ 细化层（所有权图 → 槽位与 SSA 类型）
      ─▶ typed SSA ─▶ 校验器                        同左（校验器成为翻译校验）
      ─▶ LLVM IR ─▶ 目标文件 ─▶ 可执行文件           同左
```

对应到 crate：`lang-frontend`（语义）、`lang-codegen`（表示）、`lang-cli`（编排）、`lang-lsp`（协议适配）、`lang-std`（L4、L5）。
管线有两处“细腰”：所有权图（语义的唯一定义点）与 typed SSA（表示的唯一定义点）。表面语法可以增加，后端可以增加，腰不增加。

## 5. 架构规则

把“高内聚、低耦合、单一职责、简单、模块化、插件化”落到可以检查的条目上：

| # | 规则 | 对应原则 | 如何检查 |
|---|---|---|---|
| A1 | 一条不变量只有一个强制点。析构只由一个规划器决定；loan 只有一种；能力只由一个引擎推导 | 高内聚、单一职责 | 路线 L0、C0、C1 的归一验收；同一规则不得出现两份实现 |
| A2 | 内核之间只交换 §3 的五类判定 | 低耦合 | 所有权图上的查询接口是这五类；新增一类须先修订本页 |
| A3 | 依赖单向：层只向下依赖，crate 无环，阶段只经产物通信 | 低耦合 | 已有（Cargo 依赖、阶段产物类型）；L5 不出现 `unsafe` 可脚本检查 |
| A4 | 越靠下越稳定。内核变更最少、要求最高（Guide + ADR）；库变更最频繁 | 稳定依赖 | 变更入口不同：内核走 Guide 版本，库走普通评审 |
| A5 | 机制在内核，策略在库。调度、缓冲、重试、分配策略、编码都不进编译器 | 单一职责 | 每个新关键字提案须回答“库为什么写不出来”（T1、T2） |
| A6 | 先严后宽。只能放宽的方向现在取严 | 简单 | T3；提案须写明哪一侧是兼容的 |
| A7 | 扩展点是封闭清单（见下） | 插件化 | 清单之外的扩展需求先归类到已有扩展点，归不进去才新增 |
| A8 | 每个接口都有机器校验 | 可验证 | 见 §5.2 |
| A9 | 零成本边界：层的划分不得引入运行时间接。库实现的容器与编译器内建的性能相同 | 层次不等于开销 | U2 迁移以测量为验收（[测量候选](measurement-distribution.md)） |

### 5.1 扩展点清单（A7）

| 扩展点 | 谁来扩展 | 接口 | 状态 |
|---|---|---|---|
| 库 | 任何人 | 公开 API、能力约束 | 已有 |
| 派生与代码生成 | 编译器内建 → 外部生成器 → 语言内宏 | 声明清单（之六 J13） | 候选 |
| 平台实现 | 标准库维护者、移植者 | 源集（之七 J24）与平台层接口 | 候选 |
| 执行器与调度 | 库作者 | 任务唤醒接口（之七 S4） | 候选 |
| 分配器 | 程序最终链接者 | 全局分配接口（见[之十](evolution-10-coverage-gaps.md) W4） | 方向稿 |
| abort 处理与报告 | 程序最终链接者 | 一个受限钩子，不能恢复执行（[之十一](evolution-11-failure-interfaces-units.md) §1） | 方向稿 |
| 编译目标 | 编译器维护者 | typed SSA → 后端 | 现为 LLVM 一种 |
| 外部语言 | 任何人 | C ABI（之七 J22） | 候选 |

明确**不是**扩展点的：能力（用户不可声明新的结构能力，也不可为类型手工断言能力，`unsafe` 层的叶子公理除外）、
借用规则、析构时机、编译器插件、运行时反射。把这些做成可插拔，等于放弃 A1。

### 5.2 接口与其校验手段（A8）

| 接口 | 校验 |
|---|---|
| 文法 | 机器文法与一致性测试（[Parser 评审](parser-grammar-verification-review.md)路线 F） |
| 去糖规则 | 每条糖一组“糖形与展开形诊断、行为一致”的对照用例 |
| 五类判定 | 参考检查器与生产检查器逐用例对照（之二 L0、之八 J29） |
| 所有权图 → typed SSA | SSA 校验器作为翻译校验 |
| 特权原语与别名合同 | 检测扩展（[检测候选](native-safety-validation.md)） |
| 库的安全签名 | 试金石程序 + 反例矩阵（之五） |
| 语言整体 | 一致性测试集（见之十） |

## 6. 经典架构的借鉴

每个案例取一条原则，写出 Koven 的对应物；最后一列标明它是已有结论的印证，还是带来了新的待办。

| 案例 | 原则 | Koven 的对应 | 结论 |
|---|---|---|---|
| Unix：一切皆文件 | 少数几个抽象覆盖多数对象，工具因此可组合 | **一切皆有主的值**：文件、套接字、线程、锁的 guard、任务作用域都是带析构义务的值，统一服从 KB1；关闭只有一种协议（之七 J23） | 印证。新增待办：资源类型的接口须统一审一遍，不允许某类资源另有生命周期规则 |
| Unix：一切皆文件（反面） | 强行统一会漏：`ioctl` 是抽象盖不住的部分 | 例外必须在类型上可见：内部可变（KB6）与 `unsafe`（KB7）是仅有的两个例外，且都有标记 | 印证 |
| Unix：管道 | 小工具经统一的流接口组合 | 标准库只定少数“通用接口”：迭代、读、写、显示、相等/哈希/排序。它们是库层的细腰 | 新增待办：通用接口的清单与数量上限应先于各库 API 定下（之十） |
| Unix：机制与策略分离 | 内核提供机制，策略留给用户态 | A5；之七 J15（帧变换是机制）与 J21（调度是库） | 印证 |
| POSIX | 窄而稳定的接口让上下两侧独立演进 | 三处窄接口：特权原语清单（L4/L2）、C ABI（对外）、一致性测试集（语言对实现） | 新增待办：特权原语清单需要版本号；一致性测试集尚无规划 |
| 网络分层：沙漏模型 | 腰越细，上下越自由 | 所有权图与 typed SSA 两处细腰（§4） | 印证之八 J27 |
| 网络分层：端到端原则 | 功能尽量放在端点，除非下层不做就无法正确或无法高效 | 即 T1、T2：库能做对的不进内核 | 印证 |
| 网络分层：OSI 七层与 TCP/IP 四层 | 层由真实接口产生，不由分类学产生；多余的层只增加转换成本 | 不引入 HIR（之八 J27）；本页的层也只在存在可列举接口处划分 | 印证 |
| 网络：版本协商 | 两端可以在不同版本下继续互通 | 语言版本与包的版本声明；旧包不必随新语法一起迁移 | 新增待办：尚无“一个程序内混用语言版本”的规则（之十） |
| 关系数据库：关系代数 | 少数算子，且**封闭**——算子的输出仍是算子的输入 | 内核的组合封闭性：泛型 × 传递模式 × 能力 × 存在类型的任意合法组合都应当成立，不出现“单独可用、组合不行” | 新增待办：把之五的适配性检验扩成组合矩阵，作为每条路线的验收 |
| 关系数据库：逻辑与物理独立 | 查询不依赖存储布局 | 语义不承诺表示：字符串表示（之六 J4）、逃逸优化（之八 J31）、见证表布局都不可观察，除非显式要求 | 印证 |
| 关系数据库：事务 | 原子、一致；中间状态不可见 | `replace` / `swap` 是原子的所有权操作；每条路径恰好析构一次；失败是值或 abort，没有“执行到一半被展开”的状态 | 印证。“没有执行到一半又被接住继续运行的状态”由之十一 J40（不可捕获）保证；J48 的线程失败边界不改变这一点 |
| 微内核（L4） | 一个概念只有在移出内核就无法实现所需功能时才留在内核 | 与 T1、T2 是同一条判据 | 印证 |
| 微内核（反面） | 早期微内核因跨边界开销而失败 | A9：层的边界必须在编译后消失（单态化与内联） | 印证；U2 的验收必须含测量 |
| LLVM | 一种中间表示服务多个前端与后端；每个变换独立且可校验 | 所有权图上的检查、析构展开、帧变换各为独立的一遍 | 印证 |

五项新增待办已并入[之十](evolution-10-coverage-gaps.md)的清单，不在本页展开。

## 8. 开放问题

## 9. 来源与核对状态

2026-11-11 联网核对过的：

- Liedtke《On µ-Kernel Construction》（SOSP 1995）的最小性原则：一个概念只有在移出内核会妨碍实现系统所需功能时才被容许留在内核内；判据是功能而非性能（[论文副本](https://cgi.cse.unsw.edu.au/~cs9242/22/papers/Liedtke_95.pdf)）。
- Polonius 的输入事实（loan 的发出与失效、origin 包含、变量活性、路径移出与赋值）：[Polonius 文档：输入关系](https://rust-lang.github.io/polonius/rules/relations.html)、[loan 分析](https://rust-lang.github.io/polonius/rules/loans.html)。路径移出一类事实只在事实文件列表中见到名称，未取到规则说明。

**仍未核对、依据通行的教科书表述**：Saltzer、Reed、Clark 的端到端论证；沙漏模型；Codd 的关系模型；Unix 的设计哲学；早期微内核的性能问题；
Rust 编译器中 `unsafe` 检查、常量检查与协程见证类型各为独立检查这一说法。引用它们只为说明原则，不作为任何决断的证据。
