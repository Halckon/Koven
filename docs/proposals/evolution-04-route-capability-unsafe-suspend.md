# 演进总纲之四：路线 C/U/S——能力与共享、裸内存、挂起

> **性质**：非规范候选实施计划 · **状态**：未启用 · **读取时机**：仅在规划能力推导通用化、`DropPolicy`、内部可变性、`Shareable`、`unsafe`/FFI、标准库去特殊化或协程前置约束时 · **唯一真源**：本页维护路线 C、U、S 的步骤、规则草案与验收设计；判据与决断见[之一](evolution-01-kernel-and-decisions.md)，相关既有候选见 [unsafe/FFI](unsafe-and-ffi-boundary.md)、[线程转移](thread-transfer.md)、[全局状态](global-and-static-state.md)

本文不启用任何规则、不批准 Spec 或 ADR。规则均为草案，代码均为候选伪代码。

## 1. 三条路线的共同点

路线 L 与 X 各自补一个“缺的内核操作”。这三条路线性质不同：它们主要是**把已有的内核做成库可以搭建东西的形状**。

- 路线 C：能力推导已经存在，要做的是通用化，并补上三个叶子（`DropPolicy`、内部可变标记、`Shareable`）；
- 路线 U：裸内存能力已经以编译器内建和 runtime 的形式存在，要做的是给它一个语言层的名字和一份合同；
- 路线 S：协程属于 v3，这里只写必须提前固定、否则会让前面的选择返工的约束。

## 2. 路线 C——能力与共享

### C0 能力引擎通用化（无语言变化）

**目的**：让“结构推导的能力”成为一个机制，新增能力只是往表里加一行。

模型：

```text
Capability = { 名称, 值域（布尔，或有序的有限格）, 组合方式（对字段取合取 / 取最保守）,
               叶子公理表（内建类型与标记类型的取值）, 泛型实例的推导方式 }

已有 : Copyable（布尔，合取）、Transferable（布尔，合取）
新增 : Escapable（布尔，合取）            —— 路线 L 的 L3 使用
       DropPolicy（三值格，取最保守）      —— C1
       Shareable（布尔，合取）            —— C3
```

现状（已核，见之一 §7）：`Copyable`、`Transferable` 与资源分类是三套各自实现的推导，且 Single 与 Unit 各有一份。
工作：抽出一个以能力描述为参数的推导器，把三者迁入并保持判定结果逐类型一致；Single 一侧随 D10 的管线收敛退役，不另行迁移。泛型上界、诊断中“因哪个字段不满足”的解释路径由引擎统一提供。

验收：现有全部能力判定与诊断不变；新增一个仅用于测试的虚构能力，验证“加一行即可获得推导、上界与诊断”。

### C1 `DropPolicy`

**目的**：把双轨析构表述为一项能力，并为 `Weak` 与裸指针准备好屏障（决断 D8、D10、D11）。

规则草案：

- R1.1 值域为有序三值：`EarlyEligible` < `LexicalRequired` < `ExplicitConsume`；复合类型取字段中的最大值。
- R1.2 叶子公理：声明 `deinit` 的类型为 `LexicalRequired`；其余现行类型为 `EarlyEligible`。这一条使现行行为不变。
- R1.3 后续路线追加的叶子：可被 `Weak` 观察的共享 owner（C4）、标准库以标记声明“派生过裸指针”的 owner（U1）、
  载荷未知的存在类型（路线 X）取 `LexicalRequired`。
- R1.4 `ExplicitConsume` 预留不启用：其含义是作用域结束时仍未被消费即为编译错误。
- R1.5 确定性不变：`EarlyEligible` 的析构点仍是现行定义的最早边界，drop facts 的顺序与位置不变。

工作：与路线 L 的 L0 合并实施——Drop 规划器改为“一个算法，按策略选择死亡点”。
验收即 L0 的事实等价门槛；另加一组以测试专用标记类型模拟 R1.3 的用例，确认屏障生效。

用户可见的文字变化只有一处：Guide 中“纯内存 / 资源”二分改述为一条规则加一张封闭的来源列表（见之一 D10）。

#### 双轨是否应收敛为单轨

应当，而且与 D10 收敛 Single/Unit 是同一类问题：**一个语义被实现了多次**。但要分清三个层次，它们的答案不同。

| 层次 | 现状 | 目标 | 何时 |
|---|---|---|---|
| 实现 | 两轨各有专用模块，且 Single、Unit 各一份，共四处（之一 §7） | 一个规划器，析构点 = f(活性, `DropPolicy`)；资源不再是特殊路径，只是策略取值不同 | C1，与 L0 同批；Single 侧随 D10 退役 |
| 规范表述 | 两节规则（ASAP、词法逆序）并列 | 一条规则 + 一张“析构可观察”的封闭来源表 | 与 C1 同版 Guide |
| 语义本身 | 两种可观察的析构时机 | **保留两种时机**，不合并 | 不变 |

第三行需要说明理由。把语义也并成一种有两个方向，都不建议：

- **全部词法析构**（Rust 的做法）：规则最简单，但放弃了现行已承诺的“纯内存尽早归还”。在 L1 之后借用的结束已不依赖析构点，
  所以这样做不会影响借用检查，只影响内存峰值与分配复用。它是一个合理的备选，但属于收回已有承诺，应由用户明确决定，不由实现便利驱动。
- **全部 ASAP**（Mojo 的做法）：guard 一类类型会在声明后立即析构，现行 Guide 已明确否定；Mojo 自己也要为通配 origin 的指针关闭 ASAP。

因此建议的终态是“**一个算法、一条规则、两种取值**”。Swift 的词法生命周期加 deinit barrier 是同一终态的另一种写法。

还有一个可以进一步简化的表述，供启用 Guide 时选择：把规范写成“值在词法作用域结束时析构；析构不可观察的类型，编译器会在其最后一次使用后提前析构”。
两种写法对合法程序的可观察行为相同，后者把提前析构定位成“不可观察前提下的确定性提前”，读者只需记住一个默认时机。
确定性的最早析构点仍须保留在规范里（drop facts 与黄金输出依赖它），所以这只是叙述顺序的选择，不是语义变化。

### C2 内部可变标记

**目的**：提供“共享借用下仍可修改”的唯一内核入口（决断 D4）。

本节在数据结构适配性检验（[之五](evolution-05-data-structure-fitness.md) §4）后修订：最初设想把安全的 `Cell<T>` 做成内核原语，
但原子类型需要“内部可变且 `Shareable`”，而 `Cell` 必须不 `Shareable`，两者无法由同一个带安全操作的原语派生。
因此内核只提供更底层的标记，安全类型全部下放到库。

规则草案：

- R2.1 内建标记类型（暂称 `RawCell<T>`）：对它的 Shared loan 可以取得指向内部的裸指针；它自身不提供任何安全的读写操作。
  取指针是安全操作，经指针读写须在 `unsafe` 中进行。
- R2.2 `RawCell<T>` 恒不满足 `Shareable`；`Transferable` 随 `T`。包装类型若要 `Shareable`（原子类型、`Mutex`），用受信任声明（C3）。
- R2.3 含 `RawCell` 的类型（递归）在代码生成层不得被标注为“经共享借用不可变”。现状核对（之一 §7）：后端目前未对借用参数使用
  只读或无别名属性，所以这一条当前不需要改动代码，是对未来优化的前置限制。它也是这个标记必须在内核而不能是纯库的原因。
- R2.4 `Cell<T>`（整值 `get`/`set`/`replace`，不借出内部引用）、带运行时借用标志的单元、原子类型、`Mutex` 都是 `RawCell` 之上的库。

工作：Phase 2 内建类型与叶子公理；Phase 3 无新增规则（取裸指针不产生 loan）；Phase 4 在将来引入别名属性时以此为条件。
验收含一条原生负例：对库实现的 `Cell` 经两个共享借用交替读写，结果必须反映每次写入。依赖：U1（需要 `unsafe` 与 `RawPtr`）。

### C3 `Shareable`

**目的**：定义“可被多个线程同时引用”，使借用能够跨越结构化并发的边界。

规则草案：

- R3.1 结构推导，合取。叶子：数值、`Boolean`、`Char`、`Unit` 满足；`String` 满足（ADR 0018：不可变、唯一 owner、无隐式共享）；
  `RawCell<T>`、`Rc<T>` 恒不满足；标准库以 `unsafe` 实现的同步类型（`Mutex`、原子类型、`Arc`）经受信任声明满足。
- R3.2 `borrow T` 满足 `Transferable` 当且仅当 `T : Shareable`；`inout T` 满足 `Transferable` 当且仅当 `T : Transferable`。
- R3.3 只读视图的 `Transferable` 按字段推导，于是自动遵循 R3.2。
- R3.4 非逃逸闭包的 `Transferable` 同样按其匿名视图的字段推导。它仍然不可逃逸——能否交给另一线程执行，
  取决于接收它的 API 是否保证在返回前完成（C4 的作用域线程）。
- R3.5 现行 `thread(move { … })` 的规则不变。

R3.1 中“受信任声明”是这一步唯一的新增语言面：标准库需要一种方式为 `unsafe` 实现的类型断言能力。
它只在特权 package 中可用，开放条件与路线 U 的 U3 相同。

### C4 共享库

此步不新增内核，全部是标准库工作，用来验证 C1–C3 与路线 U 的原语足够。

| 类型 | 依赖的基底 | 要点 |
|---|---|---|
| `Weak<T>` | KB7、C1 | `upgrade()` 返回 nullable 的强引用；被观察的 `Rc` 进入 `LexicalRequired` |
| 带运行时借用标志的可变单元 | KB6、KB7 | 首选作用域 API：`cell.read { v -> … }`、`cell.write { inout v -> … }`；返回 guard 视图的形态依赖 L4 |
| `Arc<T>` | KB7、C3 | 要求 `T : Shareable` 才满足 `Shareable` 与 `Transferable` |
| `Mutex<T>`、原子类型 | KB6、KB7、C3 | `mutex.withLock { inout state -> … }` 为首选形态 |
| 条件变量 | KB7、C3，通用形态另需 L4 | 作用域形态只能提供 `waitUntil(谓词)` 一类组合子；通用的 `wait` 必须交出并取回锁的独占访问，需要 guard 视图（见之五 §3） |
| 作用域线程 | KB7、C3、非逃逸闭包 | `threadScope { scope -> scope.launch { … } }`：子任务闭包可借用父作用域数据，作用域返回前全部 join |
| `Arena<T>` 与 `Handle<T>` | KB7 | 代际检查；句柄 `Copyable`、`Escapable`；访问首选 `arena.with(handle) { … }` |

验收（库优先）：双向链表与带父回指的树（`Weak` 或句柄两种写法各一）、观察者注册表、并行 map-reduce（作用域线程只读借用输入）、
LRU 缓存。每个程序的应用层代码不出现 `unsafe`。

## 3. 路线 U——裸内存与去特殊化

### U0 unsafe 别名合同（文档先行）

**目的**：在任何人写 `unsafe` 之前，规定 unsafe 代码必须遵守、安全代码可以依赖的规则。

Koven 的安全子集里 loan 都有静态确定的范围、没有可存储引用，因此合同可以写成少量条目，而不需要 Rust 那样的
操作语义模型。草案条目：

1. 经裸指针读写某 place，不得与该 place 上存活的 loan 冲突（按 Guide 10 的矩阵）。
2. 裸指针的使用不得晚于其所指存储的 owner 被析构或移动。
3. 交还给安全代码的每个值，必须满足其类型的全部不变量（已初始化、能力判定成立、析构义务恰好一份）。
4. 声明了 `from` 的 unsafe 函数，其结果实际依赖的存储必须被所声明来源的 loan 覆盖。
5. 受信任的能力声明（C3）必须在所有调用序列下成立。

合同定稿的标志：路线 L 的参考检查器能把 1、2 两条表述为对其模型的附加前提，且每条都有一个“违反即被 sanitizer 捕获”的示例。

### U1 特权原语

**目的**：把现有以内建和 runtime 形式存在的能力，命名为标准库可以直接书写的最小集合。仅特权 package 可用。

最小 intrinsic 集（目标是不可再减）：

```text
RawPtr<T>                          不拥有、不借用、不析构的地址
alloc(size, align) / dealloc       原始分配
ptr.read(): T                      把值移出（此后该存储视为未初始化）
ptr.write(own value: T)            把值移入（不析构原内容）
ptr.offset(n) / ptr.cast<U>()      地址运算与重解释
addressOf(place)                   由 place 取地址（建立 C1 的析构屏障）
sizeOf<T>() / alignOf<T>()         布局查询
dropInPlace(ptr)                   按 T 的析构规则原地析构
atomicLoad / atomicStore / atomicCompareExchange / atomicFetchAdd 等，带内存序参数
                                   原子读写不能由普通 read/write 表达，必须是 intrinsic
extern "C" fun …                   外部符号（线程挂起/唤醒、futex 等经此取得，不设专门 intrinsic）
unsafe { … }                       上述操作的唯一合法位置
```

配套规则草案：

- R1.1 **受信任合同**：unsafe 函数体不做借用检查的部分，由其签名（参数 mode、`from`、返回类型的能力）对外负责；调用方只按签名检查。
  这使 `splitAt`、`Arena.get` 一类操作可以由库提供，而内核不需要理解下标或代际。
- R1.2 `addressOf` 作用过的 owner 在其作用域内按 `LexicalRequired` 处理（C1 的 R1.3）；另提供显式的存活延长原语供跨作用域场景使用。
- R1.3 `ptr.read` 与 `ptr.write` 是所有权转移点，进入 Phase 3 的 move 事实；`replace`、`swap` 可据此在库中重写。
- R1.4 **析构中的字段移出**：现行 `deinit` 的 `this` 是只读借用，用户无法在析构时取走字段。这使长链结构只能依赖编译器生成的递归析构，
  深度与链长成正比。需要一种在析构路径上拆解自身的手段。**已决（2026-11-10）**：`deinit` 的 `this` 放宽为独占借用，
  用户以 `replace(&this.next, null)` 之类的现有原语逐个摘下后继；约束与依据见之五 §4 的 G3。须在 U2 之前进入 Guide。

### U2 容器迁移

**目的**：用 U1 的原语在 `koven/**/*.ko` 中重写核心类型并替换内建。这是整套设计“内核是否够用”的最终检验。

建议顺序（由简到繁，每个类型独立成片）：

| 序 | 类型 | 新暴露的需求 |
|---|---|---|
| 1 | `Box<T>` | 泛型类型上的 `deinit`、`dropInPlace`、单一分配 |
| 2 | `Array<T>` | 定长缓冲、元素访问器（需 L4） |
| 3 | `List<T>` / `MutableList<T>` | 增长与重分配、未初始化尾部、迭代器视图（需 L3） |
| 4 | `String` | 字节缓冲之上的不变量（编码有效性） |
| 5 | `Rc<T>` | 控制块、`Cell` 计数、与 `Weak` 的屏障（需 C1、C2） |
| 6 | `Map` / `MutableMap` | 哈希与探测、可空借用结果（需 L2） |

每片的门槛：

- **差分等价**：同一测试语料在内建版与库版上的可观察行为、析构计数一致；
- **性能门禁**：选定的微基准不劣于内建版的约定比例（比例在 Spec 中固定）；
- **内核收缩**：对应的编译器 intrinsic、专门的 lowering 与 verifier 规则被删除，并记入之一 §3.2 的清单；
- 迁移期间内建版保留为对照，直到上述三项通过后在同一变更中移除。

迁移中若发现必须新增 intrinsic 才能完成，视为内核缺口，回到之一的四个测试重新论证，而不是就地添加。

### U3 向用户开放

进入条件：U0 合同定稿；U2 至少完成前三个类型（证明原语集足够且稳定）；决断 D7 的门控方式已由用户决定。

新增面：用户 package 的 `unsafe` 与 `RawPtr`；`extern "C"` 的声明与导出；C 兼容布局、对齐与填充的标注；
受信任能力声明。每一项都是把特权 package 已在使用的能力去掉限制，不引入新语义。

验收：一个 C 库绑定样例、一个用户自写的定长环形缓冲；应用层调用方不出现 `unsafe`。

### U4 freestanding

无 runtime 的构建档位、可定制的 abort 路径、可替换的全局分配器、分配器参数化容器。属于系统编程的收尾，
依赖 U2 全部完成（标准库不再依赖 native runtime 中的容器实现）。此处不展开。

## 4. 路线 S——挂起（前置约束）

并发与异步的模型选型、路线 S 的完整步骤 S1–S5 见[之七](evolution-07-concurrency-async-io-ffi.md)；本节只保留三条前置约束，它们须在 v3 之前进入 ADR 或 Guide 的保留条款：

- S0.1 **帧地址稳定**：协程一旦开始执行，其帧不再移动。于是跨挂起点的局部借用和帧内自引用合法，不需要用户可见的固定概念。
  后果：已启动的协程值不可 move；这要求它的类型在启动前后是两个状态，或以间接 owner 持有。
- S0.2 **结构化是借用的前提**：`suspend` 函数的借用参数在调用方等待期间保持 loan——调用方本身被挂起，因此来源不会失效。
  只有脱离作用域的启动（等价于现行 `thread(move { … })`）要求所有权转移。
- S0.3 **挂起点的状态守恒**：挂起点两侧的 owner 可用性、loan 集合与待执行的析构义务必须相同；
  这是路线 L 参考检查器在引入 KB8 时要增加的唯一一条不变量。

有了 KB8，以下各项才值得讨论，且都是糖或库：生成器、需要收尾代码的访问器、异步 IO、取消。

## 5. 跨路线的工程纪律

1. **每一步声明自己属于哪一类**：纯重构（门槛是等价）、放宽（门槛是只增不减）、新增内核（门槛是参考模型 + 反例矩阵）、
   库或糖（门槛是试金石程序）。一个 Spec 只属于一类。
2. **内核变更先改参考模型**：路线 L 的参考检查器与本文的能力表是规格。先改规格并评审，再改生产实现。
3. **内核收缩清单是首要度量**：每完成一步，更新之一 §3.2 的清单与总纲 §11.3 的三个数字。清单不缩短的步骤要解释原因。
4. **糖永远后置**：任何省略、隐式转换、默认值都在其显式形态交付并积累用例之后再提案（之一 §2 的 T3）。
5. **遇到“库写不出来”先怀疑内核**：试金石程序写不顺时，回到四个测试判断是缺基底、缺糖还是需求本身应导向另一种机制，
   不为单个程序添加特判。

## 6. 开放问题

- C1：表示“析构不可观察”的能力是否向用户开放、如何命名（它影响 owned existential 能否参与 ASAP）。
- C2：`RawCell` 的命名与是否对用户可见（倾向仅在 `unsafe` 开放后可见，此前只见到库封装）。
- U1：未初始化存储是否需要类型层面的表达（类似“可能未初始化的 T”），还是由 `read`/`write` 的移动语义加合同约束即可。
- U2：迁移后内建容器的专门优化（若有）如何保留；倾向以通用优化替代，不保留特判。
- S0.1：帧稳定性与“协程值作为普通 MoveOnly 值传递”之间的取舍需要在 v3 设计初期首先决定；倾向见之七 §2.2（“已创建未启动”与“已启动”是两个状态，后者不可 move）。
- U0、U1 的增补产出：参数模式到后端属性的映射表、向量内在表示，见[之八](evolution-08-compiler-ir-escape-simd-selfhost.md) §3、§4；外部函数边界的五条合同见之七 J22。
