## 2. Origin 已明确的安全方向

以下为收尾总结及其复核明确支持的安全不变量，不等于某个抽象域或 lowering 已通过：

1. Register 是语义/IR 事件：已有义务须保有可跟踪身份和有效责任持有者；Register 与 `from` 都不自动等于发布。
2. `from` 是依赖摘要。同责任域内、不保留的中间返回不自动构成发布；实际跨域保留前须有安全交接或已证明安全的同步方案，不能先发布再补责任。
3. Transfer 不以当下 Eligible 为必要条件；Execute 必须满足执行时条件。重新分拆可以延后 Eligible，但义务的责任、权限、存储和执行路径不能丢失；更新当前后代，不复制义务，子 End 不等于整个 Discharge。
4. CFG join 必须保留义务存在性与 holder 关系；证据不足不能授权有关 Transfer、Execute、Discharge、逃逸或退出。不同 holder 并非天然不安全，但摘要必须可检查。
5. 部分构造或执行失败仍保留剩余责任，不能伪装为完成；有效转移后的 pending 义务不等于无 holder。

共识范围按原总结的发言归属记录：Gemini 接受 r2；Grok、Cooper 附条件接受；Claude 接受主线并撤回“所有重新分拆均禁止”和“三值注册状态已经足够”的断言。
这些接受不能扩写为各方同意之后的每个实现提议，未逐项回复者不计为逐项签署。

### Origin 尚未决定的合同

- 首片 holder 抽象身份及可检查析取的边界；同名不等于同身份，place 也不自动等于 SSA 身份。
- 同域且不保留的正向可判定条件、调用摘要、Transfer 完成点和退出检查；“每次返回都 Transfer”与“只在最外层 Transfer”均不能当成统一结论。
- 已持有相同有效 holder 的路径是否需要再次交接，以及 `from` 链式规则的完整化。
- 后继执行域故障时由谁观察、何时激活、默认处理是什么。静态拒绝无责任路径，不证明运行时后继永不失败。
- 现有 `error()` abort / 不展开规则不能自动覆盖所有执行域故障；新的 abort 政策未决定。

固定反例/验收面：分支有/无义务及不同 holder、重新分拆、容器进出、合法/非法 guard 结束、部分副作用之前/期间/之后失败。

### 后续讨论输入：身份、帧与非普通退出

以下是待证明的合同细节，不追加全员共识、既定 IR 或现行 Phase 能力：

- [跨函数与帧边界反馈](https://app.slack.com/archives/C0CBH9KMS1M/p1794647506353229?thread_ts=1794610098.521549)要求分别说明跨函数义务身份与逐帧责任持有者的关系。义务身份不能因穿越调用边界丢失，也不能把逐帧 holder 表示等同于义务身份；具体摘要、表示和验证算法待证明。
- [义务区分判据反馈](https://app.slack.com/archives/C0CBH9KMS1M/p1794650600874749?thread_ts=1794610098.521549)补充：仅以源码 site 或 Origin 集合作为判据，不足以区分循环、递归及同源多个义务。候选约束是避免义务错误合并；不在此规定动态 ID、SSA 或特定 IR 编码。
- 后续反馈对交接边界的澄清是：H 继续有效时无需仅因调用/返回逐跳 Transfer；H 消失前必须完成有效交接，发布另行检查。仍须证明“继续有效”的条件、交接完成点与发布安全条件，不能用这一原则跳过调用摘要和退出验证。
- [FFI / 非本地退出反馈](https://app.slack.com/archives/C0CBH9KMS1M/p1794650483476849?thread_ts=1794610098.521549)要求声明故障模型是否包含协程帧销毁、FFI 非本地跳转等不沿普通返回路径退出的情况。若纳入，须证明 holder 消失前的交接或独立安全措施；若不支持，须明确排除与拒绝边界。现有 `error()` abort / 不展开规则不替代这些证明，也不因此启用协程或 FFI 能力。

新增验收问题是跨函数往返、循环/递归同 site 多义务、H 保持有效和 H 即将消失的对照，以及非普通退出时责任是否仍可达；这些仍是待验证问题，不是测试通过记录。

## 3. IO 六项候选验收矩阵

每项都区分设计要求与后端待证明；统一责任词汇不等于统一设备、并发和故障证明。

| 场景 | 候选安全要求 | 后端仍须提供的证据 |
|---|---|---|
| 1. 部分接管 / 从未接管 | 逐请求区分 takeover、terminal、never-taken；不能把整批状态套到单请求。证据丢失不是 never-taken；本地证明失败也可独立禁止释放/复用 | 请求关联唯一性、外部证据与本地资源证明、在声明故障模型内可恢复的责任/历史 |
| 2. 责任转移后 holder 在终态证据前失败 | 后继不仅有名字，还须有幸存的激活路径；不能依赖已经失败的 holder 激活自己 | 激活者和责任域故障边界；没有幸存激活者的类别须明确标为未解决 |
| 3. 晚到 / 错投通知 | 先绑定 request + generation，再判断冲突、陈旧或乱序；绑定失败可能是错投/未知，不能一概叫冲突 | 通知关联证明及冲突分类；generation 匹配本身不延长 buffer 生命周期 |
| 4. 执行标记确认丢失 / 副作用完成却未记录 | 状态未知不等于未执行或完成；自动重试需资源专属幂等性、稳定 ID 查询/去重或解决一致性的协议 | 记录与真实效果的一致性；重写记录仍对应同一逻辑操作/身份/generation，不重新获取执行权；单步幂等不证明整个后缀可重放或已 Discharge |
| 5. 已请求 abort 但外部访问未结束 | abort 请求不等于终态；继续保留资源直到访问安全证据成立 | 完成观察者覆盖真实外部访问，不能假定进程死亡后还能自我观察；无安全责任路径时的保留/隔离/终止政策待所有者决定 |
| 6. 部分证据 / 记录损坏 | 分别保留仍可靠的事实与未知部分，不能因缺失重写可靠事实；若访问安全证据已不可靠则仍禁止释放 | 可靠性边界、恢复路径、损坏检测及可观测事实；具体表示保持开放 |

### 最新反馈的采纳边界

逐请求判定、幸存激活、通知先关联、重试身份不变以及实际访问结束的观察条件，可作为上述矩阵的澄清。
下列主张不能未经证明提升为共识：

- **IO 记录 CAS 或单次原子写只使记录本身原子，不能单独解决外部副作用与记录的原子性。**
  需要覆盖两者的同一事务，或具有资源专属一致性证明的稳定 ID 查询/去重等协议；intent/start 位不足。
- 非幂等多步清理不必一律采用 vector。受保护阶段枚举或有序日志也可能满足要求；vector 自身不解决崩溃一致性。
- never-taken 证据与责任采用同一故障域不是唯一必选编码。必须证明声明故障模型下的证据、责任及历史可恢复性，而非只选择字段布局。
- **abort 政策未决定。** 不能把“无证明则不释放”偷换成“必定 process abort”，也不能宣称未选择的保留/隔离方案已经可实现。

### 后续讨论输入：abort 请求到终止的并发窗口

[IO 后续反馈](https://app.slack.com/archives/C0CBH9KMS1M/p1794647507071769?thread_ts=1794585763.924749)补充矩阵第 5 项：从发出 abort 请求到终止实际生效之间，其他线程仍可能运行并尝试释放或复用资源。
须证明这段窗口内所有相关释放/复用路径受有效责任与访问安全条件约束，不能以“已经请求 abort”代替同步、资源保留或外部访问结束证据。
[后续联合证明反馈](https://app.slack.com/archives/C0CBH9KMS1M/p1794650627335309?thread_ts=1794585763.924749)进一步要求联合核对后端外部访问依赖、责任与运行时/资源合同，证明终止生效前不会释放或撤销所依赖资源；参与的分配器、监督者也须分别声明并验证其保证，不假定必须采用某种机制。
终止作用域、观察者、并发线程可见性和外部访问停止条件分别待证明；本页不选定进程终止、线程终止或其他失败政策，也不宣称某种锁、标志位或通知足以实现它。

IO 此处仍是第二轮后的候选验收基线；后续最终总结须明确未决项，不能以本页替代第三轮结论。
最终总结见 [IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md)。

## 4. 实施门槛与可并行范围

1. 可先推进：把已确认不变量转换成反例/正例清单、限定故障模型、梳理现有实现证据和未决合同。后继规范正文须明确哪些是保留、补充或取代，不能由候选文档静默启用。
2. Origin 正式语义扩展前：冻结 holder/join、同域不保留、Transfer 完成/退出与调用摘要合同，明确执行域失败责任；形成可验证 Spec，并按仓库治理获得相应 Guide 启用。
3. IO 正式实现前：每个后端分别交付关联唯一性、可靠证据、幸存激活、重试/查询一致性和外部访问结束证明。仅有设计草案、记录 CAS 或通知到达不能通过门槛。
4. 未决失败政策需所有者裁决；未决证明需实现/后端证据，两者不能互相替代。未指定责任人处保持待指派，不由本文向外部 agent 派任务。
5. D10/E2 已授权、现行规范内的开发可继续并行；本页不扩大普通 binding、完整 Unit 或生产 native 接纳面，不把实验能力提升为生产承诺。
6. 完成标签分开：讨论整理完成、规范启用、后端证明通过、实现测试通过、PR 合入各是独立事实。本文仅交付候选审计，尚无后四者的新增证明。
