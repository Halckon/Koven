## 1. 失败模型

### 1.1 现行事实（已对照 Guide 09）

- 没有异常：没有 `throw`、`try`、`catch`、`finally`，没有异常栈展开。
- 三种失败各用一种表达，不得混用：没有值用 `T?`；可预期、可恢复的失败用 `Result<T, E>`；不变量被破坏用 `error()`，即进程级 abort。
- **任何线程中的 abort 都终止整个进程**，不转成 `Err`，不展开其他线程的栈；abort 报告写完后进程终止，**不执行尚未运行的 drop**。
- `?` 的 `Err` 传播是普通的提前返回，lowering 在该路径生成正常的 drop，不得引入展开清理。
- 标准库中凡可能因调用者输入而 abort 的 API，必须同时提供返回 `T?` 或 `Result` 的版本。
- postfix `?` 只传播 `Result`，要求错误类型 `E` 精确相同，不做隐式错误转换；错误类型变化须显式 `when` 或后续标准库的 `mapError`。

所以“不做栈展开、线程 abort 即进程 abort”在 v1 已经是规范。之十 W1 原先写“从未被裁决”不准确，已更正：待定的是**v1 之后的长期方向**，以及配套的隔离手段与人机工程。

### 1.2 其他语言的做法

| 语言 | 可预期失败 | 程序错误（越界、断言失败等） | 一个线程出错的后果 |
|---|---|---|---|
| Rust | `Result` + `?` | panic：默认展开栈并执行析构，也可整体配置为 abort | 展开模式下只终止该线程，`join` 得到错误；持有中的 `Mutex` 被标记为“中毒”，后来者加锁时得到错误 |
| Go | 多返回值中的 `error`，逐处 `if err != nil` | panic，可在同一 goroutine 的延迟调用里 `recover` | 未被 recover 的 panic 终止整个程序 |
| Swift | `throws`（本质是值，带传播语法） | 运行时陷阱（`fatalError`、前置条件失败），不能被 `catch` | 进程终止。社区对“服务器上无法拦截”有持续的批评 |
| Kotlin / Java | 异常 | 同样是异常，展开栈 | 未捕获异常只结束该线程 |
| Zig | 错误值 + `try`，带错误返回迹 | panic，默认终止 | 进程终止 |
| Erlang | 值或让进程崩溃 | 进程崩溃 | 只有该进程结束，由监督者重启；进程之间不共享内存 |

可以读出的规律：**“一个出错不拖垮全部”要么靠栈展开加共享状态的善后（Rust、JVM），要么靠不共享内存（Erlang）**。
共享内存而又不展开的语言（Swift、Zig、现行 Koven）都以进程为失败单位。

是否存在“线程终止、进程继续、又不做展开”的做法，值得正面检查，因为它看上去最省事：让出错的线程原地停住，不执行任何析构。
问题出在它持有的跨线程资源上。现行 channel 合同规定“全部发送端都已析构时 `receive()` 返回 `null`”；
停住的线程手里的发送端永远不会析构，等它的接收者就永远阻塞。锁同理。要让别的线程得知“对方已经没了”，
就得找到并释放那个线程持有的这些值，而“找到并释放栈上的值”正是执行析构，也就是栈展开。
所以结论是：**线程级的失败隔离需要栈展开，但可以把展开限制在很窄的范围内**（§1.4）。

### 1.3 决断

2026-11-11 的初稿把“永不栈展开”定为长期承诺、以进程为唯一的失败单位。用户指出线程出错不应导致进程终止（并非要求线程可恢复），
复核后认为这一要求成立，且初稿对可逆性的判断过早：只要现在做四项预留，是否引入展开可以推迟到有服务器类试金石时再定。J40、J41 据此修订，新增 J48。

| # | 决断 | 理由 |
|---|---|---|
| J40 | **长期承诺的是“没有可捕获的异常”，不是“永不展开”**。任何版本都不提供 `try` / `catch`，不提供在出错线程内部继续执行的手段；abort 之后，该线程一定终止 | 异常的主要负担来自“任何调用都可能跳到某个 catch 并继续运行”，读代码的人必须为每个调用考虑这种路径。去掉恢复，这一负担对普通用户消失：出错之后本线程再没有代码会运行，只剩析构 |
| J41 | **失败分三级，各有自己的隔离单位**（§1.4） | 回答“线程是否允许失败”：允许以值的形式失败；程序错误使线程终止，是否波及进程由 J48 决定 |
| J48 | **目标方向：失败在显式的监督边界处被接住**（2026-11-14 改写）。越界、`!!`、`error()`、溢出这类“失败”的终止范围是最近的监督边界；没有监督边界时就是进程。监督边界是一种新的显式构造，不是普通的 `thread(move { … })`，也不绑定操作系统线程。v1 的 Guide 不改 | 见 §1.4。v1 程序里没有监督边界，行为完全不变，日后增加这一构造是纯增量。它需要“只到监督边界、不可捕获”的栈展开，成本集中在编译器与 `unsafe` 库作者 |
| J42 | **`Result` 的人机工程按五步补齐**，目标是业务代码里错误处理只占一个 `?` | 见 §1.5。Go 的样板来自缺少传播运算符与和类型，Koven 两者都有，剩下的缺口是错误类型转换与上下文 |

### 1.4 三级失败与线程失败边界

| 级别 | 表达 | 隔离单位 | 说明 |
|---|---|---|---|
| 可预期失败 | `Result<T, E>` | 一次调用 | 线程或任务的函数体可以返回 `Result`，`join()` 把它交给等待者。一个线程返回 `Err` 不影响其他线程。兄弟任务是否因此被取消，是作用域的策略（[之七](evolution-07-concurrency-async-io-ffi.md) J39） |
| 输入导致的失败 | `T?` 或 `Result` 版本的 API | 一次调用 | 现行规则已要求成对提供。处理不可信输入的代码只用这一组，就不会因输入而 abort |
| 失败（程序错误：越界、`!!`、`error()`、溢出） | abort | 最近的监督边界；没有则为进程（v1 只有进程） | 不可恢复：边界之内的执行一定终止 |
| 致命错误（析构中再次失败、失败穿过外部函数边界、runtime 内部错误） | abort | 进程，任何版本都如此 | 不执行尚未运行的 drop |

**2026-11-14 改写：边界从“线程”改为“显式监督边界”。** 起因是[evolution 系列评审](../reviews/2026-11-13-evolution-language-architecture-review.md)的 R7 与 R4：

- R7：把“是否执行 drop”放宽为未指定，并不能使 v1 与原 J48 兼容。原 J48 让普通线程成为失败边界，监督者接住失败后进程继续运行，而 v1 承诺的是进程一定终止，这同样可观察。
- R4：边界固定为操作系统线程，会使应用从“一请求一线程”迁移到单线程异步执行器后，隔离能力反而退化。

改写后的规则：

1. 两个概念。**失败**可以被监督边界接住；**致命错误**永远终止进程。上表已分列。
2. 监督边界是显式的新构造（名字待定），以“只转移所有权”的方式启动一个执行单元：一个线程，或执行器上的一棵任务子树。边界之内发生失败时，展开到边界为止，监督者得到一个表示失败的值。
3. 普通的 `thread(move { … })` 与普通的任务作用域**不是**边界：其中的失败继续向外，直到遇到监督边界或终止进程。因此 v1 的全部程序行为不变，Guide 09 与 Guide 13 都不需要修改，v1 冻结前的“选项 a”作废。
4. 任务子树作为边界时，须回答它与同线程其他任务经 `Rc` 共享的状态怎么办。倾向与线程相同：边界只接受 `Transferable` 的捕获，所以边界内外没有共享的 `Rc`。这一点未证明。
5. 借用型子任务不是边界，理由不变（下面第 6 条）。

已知代价：同一个 `error()`，在监督边界之内与之外的终止范围不同。接受它的理由是 U0 的失败安全条款本来就要求 `unsafe` 作者按“可能不返回”编写，普通用户则只需知道“边界之内出错只丢这个单元”。

**J48 的行为草案**（2026-11-14 按显式监督边界重写；未定稿，API 名字都是占位）。“单元”指监督边界启动的执行单元：一个线程，或执行器上的一棵任务子树。

1. 单元内发生失败：按现行合同向 stderr 写出报告；然后自内向外执行单元内各作用域的析构，直到监督边界。这期间只运行析构（其中的 `deinit` 是用户代码），不再运行该单元的其他代码。
2. 析构使跨单元的资源得到正常处理：发送端析构，接收者按现行合同得到 `null`；单元持有的锁被释放并标记为“持有者异常终止”，后来者加锁时得到一个可辨别的结果。名下有在途 IO 的值按[IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md)处理：没有终结证据的资源保留，不随析构释放。
3. 监督者从监督句柄得到 `Result<T, Failure>`：单元正常结束给出 `T`，失败给出一个描述失败的值。监督句柄没有“失败时让等待者也失败”的接口；想要那种行为，监督者自己对 `Err` 调用 `error()`。
4. 未取结果的监督句柄析构时只等待单元结束，不传播失败。失败的报告已经写到 stderr。
5. 普通的 `thread(move { … })` 句柄不变：`join(): T`，其中的失败不在该线程处停住，继续按“没有监督边界即进程”处理。v1 行为因此完全不变。
6. 致命错误（析构过程中再次失败、失败穿过外部函数边界、runtime 内部错误）直接终止进程，不执行尚未运行的 drop，无论是否在监督边界之内。
7. 借用型子任务与借用型子线程（S2）不是边界：它们与父共享借用的数据，子异常终止后父不得继续使用这些数据，所以失败必然传给父。此时作用域**必须先等到全部子结束，再让父失败**，否则仍在运行的子会借用到正在被析构的父帧。

**尚未解决的问题**，任何一项解决不了，J48 都不应进入 Guide：

- **与现行 Guide 的冲突**（2026-11-14 已消解）。原草案让普通工作线程在 abort 后执行析构，与 Guide 09“不执行尚未运行的 drop”冲突。边界改为显式监督构造后，析构只在监督边界之内执行，那是 v1 不存在的新构造，Guide 不需要改。
- **展开途中等待健康的长期线程**。没有 detach，句柄析构要等线程结束；若那个线程在等一个永远不来的消息，展开就卡住，表现从 v1 的“立即崩溃”变成“挂起”。需要一种让被等待线程得知“持有者正在终止”的手段（例如其 channel 对端随展开而关闭，这在所有权转移模型下多数情况自然成立，但不是全部）。
- **监督形态写不出来**。“每连接一个线程、一个连接出错其余不受影响”的服务器需要：持有数量不定的句柄、非阻塞地回收已结束的线程、对其中失败的调用 `joinCatching`。现有 API 只有阻塞的 `join`。FD3 的“监督设施”必须包含这样一个作用域类型，且应当先用这个试金石手写一遍再定第 3、4 条。
- **与“任务总是运行到自己返回”的关系**。执行器线程异常终止时，其上挂起的任务不会再被恢复，它们的帧只能按当前状态销毁。这只发生在失败路径上，但意味着“按状态析构帧”的入口必须存在（之七 J19 已相应补充）。
- **在途 IO 与终止窗口**（2026-11-14，来自 [IO 资源借用、责任交接与清理](io-resource-handoff-cleanup.md)）。两点：
  其一，出错线程执行析构时，若某个值名下有已提交、尚无终结证据的 IO 操作，其缓冲区不能随析构释放（之七 §2.7）；
  其二，“请求 abort”不等于“已经终止”。从发出请求到终止生效之间，其他线程仍在运行，可能释放或复用外部仍在访问的资源。
  这个窗口对第 5 条的“直接终止进程”同样存在：须由后端、运行时与资源合同联合证明终止生效前不会释放所依赖的资源。进程终止之后则不再要求任何观察或清理。
  失败政策的方向已于 2026-11-14 选定：证明不足时保留资源，不释放、不复用；仍可能存在外部访问、且已没有安全责任路径时，终止进程。
- **对“保证析构”推论的影响**。推论原先的理由之一是“abort 终止整个进程”。有了失败出口，推论须在含失败出口的模型里重新证明（之七 §1.2 已改写为待证，并列出所需条件）。

**成本，逐项列出。**

| 成本 | 落在谁身上 | 说明 |
|---|---|---|
| 每个调用多一条“失败出口”，其上要生成析构 | 编译器；代码体积 | 现行 ADR 与 Guide 明确“不得引入展开清理”，须新 ADR。正常路径不变慢（表驱动的展开）或略变慢（以隐藏返回值实现），二选一属于表示决定 |
| 部分初始化、部分移出状态在失败出口上的精确析构 | 所有权检查与析构规划 | 与 `?` 提前返回所需的分析相同，只是出口多。应在所有权图上实现（[之八](evolution-08-compiler-ir-escape-simd-selfhost.md)），不在现行语法树路径上叠加 |
| `unsafe` 代码须在任何可能 abort 的调用处保持不变量 | 特权层的库作者 | 这是展开带来的最重的长期负担。普通用户不写 `unsafe`，不受影响 |
| 锁的“持有者异常终止”状态 | 共享库（C4） | 设计时就带上，比事后补便宜 |
| 挂起任务 | 执行器 | 一个执行器线程异常终止时，其上全部任务随之终止；它们停在挂起点上的帧需要“按当前状态析构”的入口 |

**收益的边界，同样要明说。** 下面这段写于改写之前，当时边界是线程；改写后任务子树也可以是边界，前提是上面第 4 点成立。原文：失败边界是线程。一个线程处理一个请求的服务器可以做到“一个请求出错只丢这个请求”；
单线程执行器上跑一万个任务的服务器做不到，执行器线程终止会带走其上全部任务。把边界缩小到任务，需要回答“同线程的其他任务与它经 `Rc` 共享的状态怎么办”，本页不裁决。
不依赖 J48 也能用的手段仍然有效，且是 v1 的全部手段：输入相关的失败做成值；标准库提供启动与监督子进程的设施；abort 前的报告入口。

**现在要做的预留**（除第 2 项外都不改变 v1 的行为，目的是让 J48 日后仍然可行）：

1. `unsafe` 合同（U0）从第一版起就写入“失败安全”条款：`unsafe` 代码不得假设其调用的函数一定返回。在出现第一行用户 `unsafe` 之前定下它没有成本，之后再加等于让全部既有 `unsafe` 代码失效。草案见 [U0 提纲](unsafe-aliasing-contract-outline.md) §4。
2. （2026-11-14 取消）原先要在 v1 冻结前放宽 Guide 09 的措辞。边界改为显式构造后不需要：v1 的 Guide 不改。
3. `join(): T` 的签名保持，J48 不需要改它。
4. 所有权图的语句集（之八 IR0）为调用预留失败出口，即使 v1.x 不使用。
5. 锁与 channel 的库设计（C4、S1）为“对方异常终止”预留返回值的位置。

**步骤**（FD 为本页代号）：

| 步骤 | 内容 | 依赖 |
|---|---|---|
| FD0 | 上述预留；用“每连接一线程的服务器”试金石手写监督形态，据此定行为草案第 3、4 条 | U0 文档；T1（v1 线程）定稿时 |
| FD1 | 所有权图上的失败出口与其上的析构展开；参考解释器先行验证 | IR2 |
| FD2 | 后端的展开实现与线程入口的拦截；`join` 的传播；ADR（取代现行“不得引入展开清理”的决定） | FD1、IR4 |
| FD3 | `joinCatching`、锁的异常终止状态、监督用的库设施 | FD2、C4 |

**证伪条件**：FD1 的评估若表明失败出口使代码体积或编译时间的增长不可接受，或 `unsafe` 库的“失败安全”审查成本过高，则放弃 J48、回到以进程为失败单位，届时各项预留中只有第 1 项成为多余的约束。

### 1.5 `Result` 的人机工程（J42）

| 步 | 内容 | 归类 | 依赖 |
|---|---|---|---|
| E1 | `mapError`、`orElse` 等组合函数 | 库 | 无（Guide 09 已预告） |
| E2 | `?` 处的错误转换：操作数的错误类型可经**已声明的转换**变为所在函数的错误类型时，`?` 合法 | 糖：等价于先 `mapError` 再 `?`。转换必须显式声明，编译器不猜 | 转换以 interface 表达，需要[之三](evolution-03-route-existential.md) J37、J38 |
| E3 | 通用错误接口 `Error` 与它的存在类型：应用代码写 `Result<T, Error>`，库继续用精确的枚举 | 库 + 存在类型 | 路线 X 的 X3 |
| E4 | 错误传播迹 | 工具 | 无，可提前（之七 J34 第 4 项） |
| E5 | 附加上下文：`.context("读取配置")` | 库 | E3 |

不做的：`throws` 一类第二种声明方式（返回类型已是完整契约，Guide 09）；`try` / `catch` 块；让 `?` 同时传播 `T?`。
最后一项现行明确禁止，放开它会让 `?` 的含义依赖操作数类型，等有用例再议。

到 E3 之后，应用层代码的形态是：

```kotlin
fun loadUser(id: Int): Result<User, Error> {
    val text = File.readText(pathFor(id), 4096)?     // IoError 自动转为 Error（E2、E3）
    val user = parseUser(text)?                      // ParseError 同上
    return Ok(user)
}
```

与 Go 相比每个可失败调用少三行；与异常相比，哪些调用会失败在调用处可见。

## 2. 通用接口清单

### 2.1 现行事实（已对照 Guide 03、12、13）

- `Equatable`、`Hashable`、`Comparable` 是**编译器推导的能力，用户不能手动实现**；`Hashable` 蕴含 `Equatable`；可作泛型上界。
- `Display` 是预声明的 interface，成员为 `toString(): String`，用户类型可实现。
- `for` 的迭代来源只有编译器绑定的 `Array`、`List`、`MutableList`、整数 `Range` 与 `Map`；用户声明的 `Iterable` / `Iterator`、`iterator()` / `hasNext()` / `next()` 不取得任何特殊身份。
- 文件与标准流是便利函数；显式的流 owner 与 `close` 是后继合同。
- `Float` / `Double` 满足 `Equatable` 与 `Comparable`（按 IEEE 754，`NaN` 的比较均为假），不满足 `Hashable`。

### 2.2 决断

| # | 决断 | 理由 |
|---|---|---|
| J43 | **通用接口是一份封闭清单，第一、二优先级合计十个，命名向 Kotlin 靠拢**；清单之外的抽象属于各个库，不取得语言级地位（不与运算符、`for`、字符串模板、`use` 绑定） | 之九 §6 的“管道”原则：库与库能组合，靠的是少数人人都实现的接口。数量一多，每个类型的作者都得逐个决定实现哪些 |
| J44 | **命名对齐 Kotlin，协议形状在三处偏离**：迭代用单方法 `next()`，返回不折叠的和类型（2026-11-14 修订，原为 `T?`）；哈希用“写入哈希器”而非返回整数；关闭返回 `Result` | 这三处 Kotlin 的形状建立在垃圾回收与异常之上，照搬会与所有权或错误模型冲突。逐条理由见下表 |

### 2.3 清单

下表“已有”指 Guide 已定义；其实现在 v1 路线图中仍是未开始（条目 L1）。

优先级含义：P0 须在容器迁为库类型（U2）之前定形；P1 须在显式流（IO0）与文本视图（TX1）之前定形；P2 是库，可后置。

| 级 | 名称 | Kotlin 对应 | 成员（草案） | 绑定的语言设施 | 现状与要点 |
|---|---|---|---|---|---|
| P0 | `Equatable` | `Any.equals` | 由编译器推导；库类型可声明 | `==`、`!=` | 已有。缺口：用 `unsafe` 实现的库容器无法被结构推导，需要“条件实现”（之三 J38） |
| P0 | `Hashable` | `Any.hashCode` | `hash(hasher: inout Hasher)` | `Map` / `Set` 的键 | 已有。**偏离**：不返回 `Int`。组合多个字段时，写入哈希器比各自算整数再混合更不易出错，哈希算法也可以整体替换 |
| P0 | `Comparable` | `Comparable<T>.compareTo` | 推导；库类型可声明 `compareTo(other): Int` | `<`、`<=`、`>`、`>=`、排序 | 已有，目前不带类型参数。排序需要全序，而浮点的 `Comparable` 是 IEEE 语义；须另给浮点一个全序比较函数，不改 `<` |
| P0 | `Display` | `Any.toString` | `toString(): String` | 字符串模板 | 已有。后续增加“写入 `Appendable`”的形态以避免中间分配，`toString` 由它派生 |
| P0 | `Iterable<T>` | `Iterable<T>` | `iterator(): Iterator<T>` | `for` | 新增。按值迭代的签名成立；借用与独占借用两种来源的签名尚无可行设计，见 §2.4 |
| P0 | `Iterator<T>` | `Iterator<T>` | `next(): Step<T>`（暂名），`Step<T>` 是 `Yield(T)` 与 `Done` 的和类型 | `for` | 新增。**偏离**：不用 `hasNext()` + `next()`。两个方法之间有必须按序调用的隐含协议，且“先问后取”在消费型迭代里要缓存一个元素。也不用 `T?`：可空类型是扁平的，`Iterator<Int?>` 遍历 `[1, null, 2]` 时无法区分“下一个元素是 null”与“迭代结束”（评审 R6）。用户主要经 `for` 使用，很少直接见到 `Step` |
| P1 | `Closeable` | `AutoCloseable` + `use {}` | `own fun close(): Result<Unit, E>` | `use { }`（库函数） | 新增。**偏离**：关闭返回 `Result`（之七 J23）。不关闭时由 `deinit` 尽力关闭 |
| P1 | `Source` / `Sink` | kotlinx-io 的 `Source` / `Sink` | `read(into: inout …): Result<Int, IoError>`；`write(…)`、`flush()` | 无 | 新增。字节流的读与写；缓冲、文本解码都是包在它外面的库类型 |
| P1 | `Appendable` | `Appendable` | `append(text)` | 字符串模板的输出目标 | 新增。文本的写入端；`String` 的构建器与文本 `Sink` 都实现它 |
| P1 | `Error` | `Throwable`（去掉抛出） | `message`、`cause: Error?` | `?` 的错误转换（E2） | 新增。继承 `Display` |

P2（库，按需）：

| 名称 | Kotlin 对应 | 倾向 |
|---|---|---|
| `Sequence<T>` | `Sequence<T>` | 惰性序列，由生成器（之七 S3）产生；它就是 `Iterable<T>`，不另立接口 |
| `Cloneable` | `Cloneable` | 通用复制能力，[显式 clone 候选](explicit-clone.md)明确不在其范围内；等容器深拷贝有需求时单独提案 |
| `Collection` / `List` / `Set` / `Map` 的接口层次 | 同名接口 | **不照搬**。Koven 的 `List`、`Map` 是具体类型；把它们变成接口要等存在类型（路线 X）落地并有第二种实现时再议 |
| `Comparator<T>` | `Comparator<T>` | 用函数类型 `(T, T) -> Int` 即可，不设接口 |
| `ClosedRange<T>` | `ClosedRange<T>` | 现行整数 `Range` 是内建；泛化为接口不急 |
| `CharSequence` | `CharSequence` | 不设。文本的只读抽象由 `StringView` 这个具体类型承担（[之六](evolution-06-text-globals-extensions-metadata.md) J1） |
| `Lazy<T>` | `Lazy<T>` | 是类型不是接口（之六 J7） |

与并发相关的库命名同样向 Kotlin 靠拢，见之七 J39 的命名表（`launch`、`Job`、`supervisorScope` 等）。

### 2.4 由清单带出的前置工作

- `Equatable`、`Hashable`、`Comparable` 从“只能推导”变为“可推导，也可由库类型声明”，是一次能力规则的变更，须与条件实现一并设计（之三 J38）。声明的实现须满足的规律（自反、对称、与哈希一致）无法由编译器检查，属于库作者的责任。
- **借用迭代目前没有可行的签名，这是本清单最大的未决设计**（独立复审指出）。`Iterator<T>` 要覆盖“借用元素”，`T` 就得能取借用类型，接口方法还得能声明结果来自 `this`；
  而[之二](evolution-02-route-loan-kernel.md)的 R2.2 禁止借用类型作泛型实参，R3.7 要求视图的类型实参可逃逸，能放开它们的 L5 被标为“没有用例就不启动”。
  这正是 Rust 里需要泛型关联类型才能表达的“出借迭代器”问题，而本系列既不做关联类型也不做生命周期参数。两条出路：
  （a）把“不可逃逸类型作泛型实参，以及 interface 方法的来源合同”从 L5 提前为 L3 的必经子步骤，`Iterator` 在此之后才定形；
  （b）`for` 不绑定单一接口，而是绑定“有一个返回可空值的 `next` 方法”这一结构性约定，按值、借用、独占借用三种迭代器是三个各自独立的类型。
  （b）更早可用，但泛型算法无法对“任意迭代器”编写一次。**在此裁决之前，J43 中的 `Iterable` / `Iterator` 只对按值迭代成立**；借用迭代先由标准库的具体视图类型提供。
- **裁决（2026-11-14）取（a）**：迭代器所需的泛型能力提前为 L3 的必经子步骤（之二 L5 的进入条件已相应修订）。定形之前先用原型验证四种迭代，并覆盖“空序列”“仅含 null”“null 之后仍有元素”三个用例。
- **原型结论（2026-11-14）**：四种迭代不能归到一个接口。泛型算法能依据的合同只有出借式与转发式两种，J43 的单一 `Iterator<T>` 须拆成两个接口或加标记；另需“转发全部来源”的写法与“流向”子句。见[借用内核演算](loan-kernel-calculus.md) §9.3。J43 尚未据此改写。
- 独占借用的迭代另有一个问题：泛型代码同时持有多个元素的独占借用时如何保持健全，须与 L4 的访问器规则一并回答。
- `for` 从“编译器绑定的几种来源”改为“任何 `Iterable`”，现有的专用路径应保留为优化，而不是第二套语义。

## 3. 编译单元之间的依赖

### 3.1 现行事实（已对照 Guide 02）

- `package` 是命名空间，对应目录；一个**编译单元**是 driver 一次显式交付的一组源文件，可含多个 package。
- 可见性三级：`public`（可向将来依赖它的编译单元导出）、`internal`（同一编译单元内）、`private`（同一源文件内）。
- 依赖清单、依赖解析、跨编译单元的 ABI 与链接策略**尚未定义**。

所以“包依赖图是否无环”这个问题在 Koven 里要拆成两层来问。

### 3.2 通行做法

| 语言 | 命名空间层 | 分发与编译层 |
|---|---|---|
| Go | package 即编译单位，**禁止循环导入**（官方理由之一是初始化次序必须确定） | module 是版本单位 |
| Rust | crate 内的模块可以互相引用 | crate 之间无环 |
| Kotlin / Java | 同一模块内的包可以互相引用 | 模块之间无环（构建工具强制） |
| Swift | 同一模块内的文件互相可见 | 目标与包之间无环 |

除 Go 把两层合一以外，其余都是“内层可以有环，外层必须无环”。Go 一栏本轮已联网核对；Rust、Kotlin、Swift 三栏来自已有知识。

### 3.3 决断

| # | 决断 | 理由 |
|---|---|---|
| J45 | **两层规则：同一编译单元内的 package 可以互相引用；编译单元之间的依赖必须无环** | 外层无环是分别编译、增量构建、确定的链接次序与一致性规则（J37）的共同前提，也是之九 A3 的直接要求。内层不禁止环，因为 package 只是命名空间，要求它无环会迫使用户为了目录结构去拆类型，换不来上述任何一项好处。需要更严的团队可以用检查工具自行约束 |
| J46 | **依赖经“接口产物”而不是源码**：编译单元 A 依赖 B 时，A 的编译只读取 B 导出的声明清单（之六 J13 的同一份产物）与泛型函数体 | 这样环在构造上不可能出现（B 的产物必须先存在），不必靠事后检测。泛型按实例单态化，所以泛型函数体必须随清单导出，这是表示承诺，走 ADR |
| J47 | **语言版本按编译单元声明**；新启用的关键字只在声明了相应版本的编译单元内是关键字 | 保留字的启用因此不再是全局破坏性变更，旧的依赖不必同步迁移。跨版本调用以被调用方声明时的规则检查其声明，以调用方的规则检查调用处 |

J37 的一致性规则相应表述为：interface 的实现只能写在**类型的声明处**，或写在**interface 所在的编译单元内**；
依据 J45，这两处不会同时出现针对同一对（类型，interface）的实现。之三已同步改为“编译单元”。

打破环的常规办法应写进文档而不是做成语言特性：把两个单元共同需要的 interface 抽到第三个单元（依赖倒置）；或把互相依赖的两个单元合并。

### 3.4 开放问题

- J46：泛型函数体以什么形式导出——源码、语法树还是所有权图。倾向所有权图（之八 J27），但它尚不存在；过渡期只能是源码。
- J47：一个编译单元能否对其依赖的最低语言版本提出要求。
- 标准库是一个编译单元还是三个（之十 W6 的三分）；若是三个，它们之间同样受 J45 约束。
- 测试代码是否构成独立的编译单元（影响 `internal` 是否对测试可见）。

## 4. 来源与核对状态

本轮联网核对过的：

- Kotlin 的 `select` 表达式在官方指南中仍标为实验性（[Kotlin 文档：select 表达式](https://kotlinlang.org/docs/select-expression.html)）。
- Rust：线程 panic 只终止该线程、`join` 得到错误；`Mutex` 中毒及其可绕过性（[标准库 Mutex 文档](https://doc.rust-lang.org/std/sync/struct.Mutex.html)）；展开与 abort 两种 panic 处理（[Rust Reference：Panic](https://doc.rust-lang.org/reference/panic.html)）。
- Swift：致命错误不能被 `do`–`catch` 捕获；社区讨论[“fatalError 无法拦截对服务器有害”](https://forums.swift.org/t/fatalerror-without-a-way-to-intercept-it-is-harmful-on-the-server/74386)。“不做栈展开”这一点检索结果没有直接陈述。
- Zig：错误返回迹记录错误被返回的各个位置，Debug 与 ReleaseSafe 默认开启（[Zig 提交说明](https://git.medv.io/zig/commit/f0697c28f80d64c544302aea576e41ebc443b41c.html)；未取到现行官方文档的对应章节）。
- Go：禁止循环导入及其理由（[说明文章](https://appliedgo.net/spotlight/no-import-cycles/)，非官方文档）。

**未核对、来自已有知识**：Go 未恢复的 panic 终止整个程序；Kotlin/JVM 未捕获异常只结束线程；Erlang 的监督模型；Zig 的 panic 行为；
Cargo、Gradle、SwiftPM 拒绝循环依赖；kotlinx-io 的 `Source` / `Sink` 命名。
