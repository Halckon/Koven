# ordinary Function expected 上下文中的 move lambda 候选澄清

> **性质**：非规范候选澄清 · **状态**：proposed，未启用 · **读取时机**：决定 SPEC-0279 的 move literal 前置时 · **唯一真源**：本候选；现行语义仍由 Guide v0.40 决定

## 1. 冲突与现状

[Guide03](v0.40/03-types-generics.md#expected-typelocal-与-lambda)正文要求 expected lambda
的参数数量和 `move` / mode 结构精确匹配；[Guide07](v0.40/07-calls-lambdas-closures.md)
又说明 Function 的 move 前缀表示不含借用捕获的约束，并给出
`fun makeMatcher(own label: String): () -> Boolean = move { ... }` 合法示例。
两处不能直接推导同一个 literal contextual gate。按照 docs/AGENTS.md 的正文优先与
冲突规则，先登记，不能把例子直接升级为生产修改授权。

两个当前前端都按 move marker 精确相等拒绝 ordinary Function expected 中的 move literal。
SPEC-0279 的四个候选成功测试已经实际失败于 L0084；这证明实现现状，不证明哪个规范应获优先。
类型/所有权成功断言尚未运行到，生产 checker 未修改。

## 2. 可审阅的推荐替换文本

若用户明确接受并启用下一版 Guide，仅替换 Guide03 对 expected lambda 的该项合同：

> lambda 是独立 callable。存在 expected function type 时，先精确匹配参数数量与有序参数
> mode。expected Function 带 move 约束时，literal 必须使用 move；普通 Function expected
> 上下文允许普通或 move literal。literal 的静态类型沿用 expected Function 的 canonical
> identity，shared / owned capture 仍由 literal 语法与 ownership facts 决定。结构不匹配使用
> L0084，再以对应参数类型检查 body；参数类型不从 body 反推。

保留以下既有边界，不增加新的 named Function 转换：

- 无 expected type 的 move literal 继续推导含 move 的 Function 身份。
- 已定型的 named `move Fn` 与普通 Fn 不自动互转，assignability 和参数 mode 精确规则保持。
- move capture 仍必须满足已有 owning/available 和 L0138 规则；ordinary borrowed closure
  escape 仍为 L0137；捕获 loan、Transferable 和 ASAP drop 不从 Function 标签猜测。
- 不增加 erased callable、类型型变或 lambda-body 泛型推导。

另一可选决定是保留 Guide03 的现行精确 marker 规则，并纠正 Guide07 的示例/约束表述。
这样 ordinary Fn initializer 无法接收 owned move literal，SPEC-0279 的三环境完整目标必须
暂停或另行排期，不能只实现两个环境后宣称完成。
