## 0. 结论

**范围选得对，可以作为冻结评审的输入；但它还是一份"范围与待决清单"，不是可以启用的 Guide 草案。**

做得好的地方：

- 六项都直接对应审计里证据最充分的缺口（C1 合并到 `Any`、p42 赋值、range、整数转换、Map 遍历），没有把大块设计（相等协议、文本 IO、闭包可变捕获）硬塞进来。
- 每项都写了非目标和成对验收，并且明确"冻结时必须选定，不能留给实现自选"。这是对的。
- 对审计的纠偏大多成立（见 §5），尤其是 p25 的两层问题和泛型推导"不是全部调用都推不出"。

冻结前还需要做四件事：

1. **把四个待决问题定下来。** 本文 §2 给出推荐答案：Map 遍历用插入顺序；Range 可存储、Copyable；转换首片只做 checked Abort；只读 Map 走 consume 而不是带参工厂。
2. **调整分期。** 把 C（while 收窄）从第一阶段挪后；把 F 拆成"遍历"和"构造"两件，构造降为可选。见 §3。
3. **评估三项新合同是否纳入**：Abort 输出消息、`is E.Case` 类型实参推导、顶层 runtime `val`/`var` 正式禁用。三项都是独立的新合同，各有需要冻结的细则，不是附带的措辞修改，见 §4。
4. **写明实现前置。** 草案的 native 验收会撞上已知的后端缺口：一般 nullable 值的构造、返回与参数路径（`Map.get` 等特定路径已可用）、`when (Int)`、CLI 不加载 `Pair`/`Result`、两条管线各做一遍。这些应在每项的"实施依赖"里写出来，否则会在实现阶段变成一串追加切片。

## 1. 逐项意见

| 项 | 判断 | 意见 |
|---|---|---|
| A if/when join | ✅ 纳入 | 建议直接写成封闭规则：同型取原型；与 `Nothing` 取另一侧；与 `Nothing?`（单独的 `null`）取 `T?`；`T` 与 `T?` 取 `T?`；同一 enum 的 case 流类型取 root；其余报错。`if` 与 `when` 用同一错误码（现在分别是 L0089 和 L0112）。语句位置不求 join，结果固定 `Unit`。顺带把 `is E.Case` 的类型实参改为从 subject 推断（§4） |
| B 简单变量 `=` | ✅ 纳入，已批准 | 结果为 `Unit` 后，`a = b = c` 与 `if (x = 1)` 都会自然变成类型错误。建议在 Guide 里用示例写明这两种写法被拒绝。注意"结果为 Unit"并不等于"只能作语句"：后者还会禁止 Unit 值上下文（如 Unit 期望下的初始化、lambda 尾表达式），超出已批准合同，本版不应引入。B 同时解决了 10-15 增量审计 §3.2 提到的单文件 L0165 遮蔽 L0135 |
| C while 保守流事实 | ◐ 纳入但后移 | 语义正确，但收益低于 D/E：真正的使用场景（链表游标）仍被 ownership 拒绝，草案自己也承认。native 验收还依赖 nullable class 原生路径，而 `3104baa4` 上 nullable 参数判空、局部 nullable smart cast 都还是后端拒绝（q05、p14b）。建议放到第三阶段，与 Map 遍历同批；后移只改变顺序，native 验收仍是 C 的交付门 |
| D 整数 Range / in / for | ✅ 纳入，优先 | 用户价值最高。建议首片类型为 Int 与 Long；反向区间（`5..1`）为空；闭区间用"先比较、相等即退出、再自增"实现，不对 MAX 加一。Range 的可存储性见 §2.2 |
| E 显式整数转换 | ✅ 纳入 | 命名要特别注意：Kotlin 的 `Long.toInt()` 是**静默截断**，Koven 若沿用同名却做 checked Abort，Kotlin 背景的读者会误判。建议沿用 `toInt()` 名称并在 Guide 里写明"与 Kotlin 不同，越界 Abort"，截断另用 `truncateToInt()` 一类显式名字（可延后）。失败 API 见 §2.3 |
| F 非空只读 Map 构造 + 借用遍历 | ◐ 拆分 | 遍历是高价值项，应保留；非空只读构造价值低、开放问题最多，建议降为可选或改走 consume，见 §2.4 |

## 2. 四个待决问题的建议答案

### 2.1 Map 遍历顺序：保证插入顺序

- 现有 runtime 是开放寻址表，`{buffer, size, capacity, tombstones}`，哈希确定、无随机种子。按槽位遍历虽然在同一编译器版本内可复现，但顺序取决于哈希函数和容量；改一次哈希或扩容策略，所有依赖输出的程序和测试都会变。
- 仓库的工程规则本身就要求"稳定产物不得依赖无序集合迭代"。语言层面给出同等保证，用户写的程序才能有稳定的 golden 输出。
- 实现上是一次 runtime 布局调整：改成"索引表 + 稠密条目数组"（Python 3.6+、IndexMap 的做法），删除留洞、遍历跳过、超过阈值时压缩。Map ABI 只是内部合同，现在改代价最小，之后有了遍历用户就很难再改。
- 需要同时写明：覆盖已存在 key 不改变其位置；`remove` 后再 `put` 进入末尾。
- 这是一项需要单独实现与验收的存储改造，不是小补丁；建议先冻结存储方案再做遍历。遍历顺序也不自动等同析构顺序，Map 整体析构时各条目的清理次序需另行规定或明确不保证。
- 如果这一版不愿意动布局，退一步也应在 Guide 里写"同一程序、同一输入顺序下遍历顺序确定"，并明确"不同编译器版本之间不保证"。不建议完全不指定。

### 2.2 Range 是否可存储：可以

- 整数 Range 不携带任何 loan，它只是两个端点加一个开闭标记。把它做成编译器绑定的 Copyable、Transferable 值类型，可以存进局部、字段、容器、返回值，不需要任何新的非逃逸规则。
- 如果限制为"不可存储"，就要再造一种只在表达式里出现的特殊值，正好与审计 §5 批评的"非逃逸机制过多"同类。
- 与 `View<T>` 的区分很简单：`View` 借用一个容器，Range 只是数值。草案"须与已有 View 区分"的担心，用"Range 是普通值"一句即可消除。
- 首片对外只需要 `in` 与 `for`。`first`/`last`/`isEmpty` 等成员可以后加，不影响可存储性。

### 2.3 转换失败 API：首片只做 checked Abort

- `toXxxOrNull()` 需要从普通函数返回 nullable 标量。标量 nullable 并非完全不可用（`Map.get` 的结果路径已原生可用，词频程序依赖它），但一般 nullable 构造、函数返回与参数路径尚未完整支持（probe p14c、q05）。把 OrNull 族纳入，就会把这部分后端补齐拉进 v0.44 的关键路径。
- 建议首片：只做 checked 转换，源值落在目标类型值域内则成功，否则 Abort。是否"总是成功"取决于值域包含关系而不是位宽：`Int → Long`、`UInt → Long` 总能成功，`Int → ULong` 对负数仍须失败。OrNull 族与截断族后续再加，名字现在先保留。Abort 是否带消息取决于 §4 的独立合同，不作为本项前置。

### 2.4 consume 还是带参工厂：建议 consume（或本版不做只读构造）

带参工厂 `mapOf(Pair(k, v), ...)` 需要先解决的问题，在草案和 `collection-api-followups.md` 新增节里已经列了很多：

- 标准 `Pair` 的名义身份。实际情况比草案写的更靠前：普通单文件和 project CLI 目前**根本不加载** prelude 里的 `Pair`/`Result`（README 已如实写明，probe s01/s02 为 L0080）。
- 不允许逐字段偷搬 MoveOnly，需要复用完整解构。
- 只读 Map 的"构造装填权限"与公开只读不变的隔离。
- 重复 key 的胜出与旧 key、旧 value 的释放时点。
- 条目求值中途正常退出时，半成品与未提交条目的清理。

改走 `MutableMap` 装填后整体 consume 成只读 `Map`（即 0291）：

- 重复 key、drop 次序、求值顺序全部沿用已经实现并验证过的 `put`，不需要新规则。
- 没有"构造权限"问题：consume 之前是可变的，之后是只读的，转移本身就是封存。
- 不依赖 `Pair` 身份，也不依赖完整解构。
- 代价只是写法稍长。等 `Pair`/`to` 成为用户可见的标准类型后，带参工厂可以作为语法糖再加，届时按 consume 展开即可。

再往前一步：v1 里只读 `Map` 的实际用途有限，用户完全可以只用 `MutableMap`。如果 consume 也不想在本版启用，**建议 F 只做遍历**，只读构造整体移出 v0.44。

## 3. 分期建议

用户提出的三阶段：① A+B+C；② D+E；③ F（构造 + 遍历）。建议调整为：

| 阶段 | 内容 | 理由 |
|---|---|---|
| 1 | A、B | 都是修正现有规则的冲突或空白，改动小；B 同时消除单文件 L0165 遮蔽 |
| 2 | D、E | 用户可见收益最大，可并行；不依赖 nullable 原生路径 |
| 3 | Map 遍历；C | 若采用插入顺序，先单独冻结并验收存储方案，再做遍历，避免两片返工；C 后移但保留 native 验收 |
| 独立穿插 | 只读 Map 的 consume 移交 | 不依赖遍历与新布局，可任意阶段插入；它不替代将来简洁的 `mapOf` 初始化语法 |

草案"冻结时六项一起评审、逐项定合同"的原则可以保留。分期调整只影响实现顺序，不影响一次性启用 v0.44。

## 4. 三项需要单独评估的新合同

| 项 | 现状 | 建议 |
|---|---|---|
| Abort 输出消息 | Guide 13 明确"不保证 stderr 文本或 message 一定被打印"；实测 `error("boom")`、溢出、`!!` 失败均无输出（经 `kovenc run` 观察到的退出状态为 1，原生产物本身的 abort 状态由平台决定，不等于固定 `exit(1)`） | 作为新合同设计，至少要冻结：消息内容与格式；stderr 写入失败或短写时如何处理（例如尽力写入后仍 Abort，不得递归 Abort 或改走正常退出）；与尚未刷出的 stdout 的先后关系；可观察的进程终止状态是否保持平台 abort 语义。E 与 D 的价值会因它提升，但不以它为前置 |
| `is E.Case` 省略类型实参 | `when (r) { is Result.Ok -> … }` 报 L0091，必须写 `is Result.Ok<Int, Int>` | 新合同：需定义推断来源（subject 静态类型）、部分实参、显式实参与 subject 冲突时的诊断，以及 subject 本身含未定类型时的行为。可与 A 同批评审，但不是 A 的一部分 |
| 顶层 runtime `val`/`var` | 语法接受、语义未定义；project 下报 L0165"未实现"，单文件为后端拒绝 | 正式禁用是接纳面收窄的新合同：需要新诊断码、确定与 `const val` 的边界、核对现有测试与示例的影响，并说明将来开放全局状态时如何迁移。建议在 v0.44 冻结时给出"纳入或不纳入"的明确结论 |

## 5. 对草案纠偏意见的回应

| 草案的纠偏 | 回应 |
|---|---|
| 泛型析构不默认改为资源轨，承接"依赖实例"的现有事实 | 同意不默认改为资源轨。另需写清现有规则本身：类型未知时的保守处理必须继续成立，实例化不得据此重新安排可观察的析构时点。审计原意只是要求把现行行为写进 Guide 10，不是承诺按实例提前或改变析构顺序 |
| "R 永远推不出来"不适用于全部调用 | 同意，审计措辞过宽。显式类型实参和已定型函数值确实能推。审计原意是"直接传 lambda 字面量时推不出"，这一点仍成立，主要影响 `map` 这类结果类型只出现在 lambda 返回值里的调用；`filter` 的类型参数可从接收者确定，不受影响 |
| p42 结果是"捕获赋值仍拒绝"，可变捕获是另一项设计 | 同意 |
| p25 有两层问题，C 只解决 while 事实传播 | 同意。由此也说明 C 对链表场景单独没有收益，支持 §3 的后移 |
| C3/C4/C14 不能称为无语义变化的整理 | 同意，单独走合同。C3（13 节 unsafe/FFI 草图）建议尽快决定，它和 v1 std 规划里的"用户 FFI"直接相关 |

## 6. 对 `docs/v1-std-plan` 规划的意见

`v1-collections-io-delivery.md` 的方向与 v1 范围文档基本一致，"输入 → 解析 → 集合 → 格式化输出 → 错误与清理"的闭环目标很好，P0/P1/P2 的分层也合理。具体意见：

1. **前置依赖要写进表格。** 文件 IO 的返回值是 `Result`，但 CLI 不加载 prelude（s01/s02），自声明的 `Result` 加 `?` 也还不能原生编译（p16）。"Result 可见性 + Result/`?` 原生链路"应当作为第 4 步（文件 IO）的显式前置，而不只是一句"不证明所有泛型 payload 可执行"。
2. **forEach（第 3 步）可以考虑调整优先级，但它仍是 v1 承诺。** `forEach` 本身不依赖可变捕获，同步、非逃逸的 Borrow 回调可以独立交付；只是 `forEach { sum += it }` 这类累加写法要等可变捕获另行设计。是否先于 Map 遍历和文件 IO 交付，可按代表应用的实际需要排序。
3. **map（第 5 步）的常见写法依赖泛型推导读取 lambda 结果**，否则需写显式类型实参；`filter` 的谓词返回 `Boolean`，元素类型来自接收者，不依赖这项推导。建议在第 5 步的"冻结前必须决定"里分别写明。
4. **第 1 步与 v0.44 F 的取舍要统一。** std 规划把"非空 mapOf"列为第一个实现候选，`collection-api-followups.md` 新增节也按带参工厂展开。若采纳 §2.4 的 consume 建议，这两处要同步改，避免规划和 Guide 草案各选一条路。
5. **stdout/stderr 一行里提到"error 不保证 stderr 内容"。** 建议与 §4 的 Abort 消息规则合并处理，不必等 IO 合同。
6. **整数 math（min/max/abs/clamp）可以并入 v0.44 的 E 或 D 一起做。** 它们是普通函数，不需要新语法，`abs(Int.MIN)` 按 checked 规则 Abort 即可，和 E 共用同一套边界测试。
