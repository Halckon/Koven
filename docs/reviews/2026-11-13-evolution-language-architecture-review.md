## 2. 总体结论

**主方向值得保留，但目前不能作为已经闭合、可以直接拆 Spec 实施的语言设计。**
问题不在于偏离现行 Guide，而在于几个基础抽象尚未覆盖它们自己承诺支持的组合。

- 不需要推翻所有权语言、无默认 GC、长期关系走句柄这些核心方向。
- 需要重新设计或补全：来源与访问授权模型、可变 existential 的合同，以及失败与挂起任务的清理协议。
- “应用代码不用写生命周期参数”是值得坚持的体验目标；“所以内部不需要依赖关系、约束或授权模型”不是成立的推论。

本轮结论是**阻止把当前候选冻结为可实施的健全性合同**，不是反对保存或提交探索稿。
下列建议均待裁决，不因与 proposal 同批提交而自动被采纳。

## 3. 主要发现

### R1 · P1：Origins 混合不同依赖，统一内核尚未定型

**位置**：[路线 L](../proposals/evolution-02-route-loan-kernel.md) §2、R3.4、R4.4（本次输入第 31、143、192 行起）。

目前至少需要区分三种关系：

1. **存储依赖**：返回值指向谁的存储。
2. **来源转发**：返回值沿用参数已经携带的借用。
3. **访问授权依赖**：某个 guard 或父借用必须保持有效，访问才合法。

R3.4 对不可逃逸参数无条件采用第二种，覆盖不了第一、三种：

```kotlin
// 设计反例伪代码
view class Window(borrow val source: Array<Int>, val start: Int) {
    fun element(): borrow Int from this = source[start]
    fun metadata(): borrow Int from this = start
}
```

`element()` 可以在 Window 消失后继续借用底层数组；`metadata()` 指向 Window 自己的字段，不能如此。
当前两者却得到相同的来源合同。若检查器正确拒绝 `metadata()`，说明合同缺少表达这种合法访问器的能力；
若按 R3.4 无条件转发，则遗漏了存储依赖。

只读 guard 更敏感：返回引用不能越过 guard 释放动态借用的时刻，即使底层存储仍活着。
`LexicalRequired` 只把析构推迟到 guard 自己的作用域结束，不能使返回的访问权限越过该作用域。

R4.4 又规定子 loan“调用返回即结束”，但访问器可以把重借结果返回：

```text
p = 独占借用某个 Record
q = project(p)       // 返回其中 Field 的独占借用
修改 p.field
使用 q
```

`q` 存活时必须继续限制 `p`，不能在 `project` 返回时恢复父权限。
扁平地让两者共享同一个 loan 也不够：R4.3 允许父 Holder 凭该 loan 访问来源，需要表达父授权被子借用暂停。

**建议**：重新定义 OriginContract，至少区分借用参数存储、转发参数来源、保持授权持有者存活；
Loan 模型显式表达派生关系与父权限暂停。调用返回只结束没有流入结果或其他存活 Holder 的子 loan。
表面仍可使用简短的 `from`，不必因此引入 Rust 式用户生命周期参数。

**验证要求**：上面的冲突访问必须拒绝；最后使用 `q` 后重新使用 `p` 应接受；
视图自身字段的借用不能超过视图存储，guard 交付的引用不能超过授权有效期。
这不是 L4 的局部补丁，而是 L、X、S 共用内核的基础。

### R2 · P1：inout existential 混淆载荷访问与存储槽替换

**位置**：[路线 X](../proposals/evolution-03-route-existential.md) §2.4、X2 R2.4、X3 R3.5（第 64、140、172 行起）。

X2 允许把具体 Circle 的 place 转成 `inout Shape`，但禁止整体替换；X3 又允许替换 owned existential。
仅限制直接赋值语法不够：

```kotlin
// 设计反例伪代码
fun <T : Shape> overwrite(inout dst: T, own value: T) {
    dst = value
}

fun forward(inout dst: Shape, own value: Shape) {
    overwrite<Shape>(dst, value)
}
```

existential 自满足使 `T = Shape` 合法，但 `overwrite` 要求的是能存放任意 Shape 的槽位。
`forward` 从具体 Circle 得到的却可能只是载荷指针与见证表。
不在合同中区分，就可能把替换任意 Shape 的权限授予静态类型为 Circle 的位置，或按 existential slot 的布局操作具体载荷。

**建议**：在类型检查、泛型匹配与 ABI 中区分：

- **载荷可变访问**：只能调用被擦除类型的方法，不能更换具体类型。
- **existential 槽位可变访问**：可以替换 owner 与 witness，只接受真正的 existential 存储槽。

前者不能匹配 `inout T`、`T = existential I` 所要求的后者。
可以统一 pack/open 机制，但不能为了“一种表示”抹掉不同权限。
验证须同时覆盖直接调用和经泛型、辅助函数转发后的替换路径。

### R3 · P1：允许泄漏与结构化并发的保证析构直接冲突

**位置**：[U0](../proposals/unsafe-aliasing-contract-outline.md) FS3（第 69 行起）；
[并发路线](../proposals/evolution-07-concurrency-async-io-ffi.md) §1.2（第 39 行起）。

FS3 无条件允许失败路径上的值泄漏；结构化并发却依赖不可逃逸资源必定履行等待义务。
反例路径：

1. 子线程借用父线程局部缓冲区。
2. 父线程失败，但进程继续。
3. unsafe 实现按 FS3 泄漏持有等待义务的作用域状态。
4. 父线程释放缓冲区，子线程仍在访问。

这不是普通内存泄漏，而是跳过了内存安全所必需的动作。
问题不在于安全用户已经能写出 `forget(scope)`，而在于 unsafe 合同授予的泄漏许可与安全 API 依赖的保证矛盾。

**建议**：FS3 只允许不破坏安全义务的泄漏；保证析构、等待借用型子任务、结束访问授权等义务不得因此消失。
增加失败注入用例，确认释放来源之前已完成必要等待。

更深一层，建议将“何时析构”“是否必须显式消费”“是否允许遗忘”“清理是否承担借用安全义务”分开设计，
而不是全部塞进一个三值 DropPolicy。它们不是天然构成一条大小顺序的同一维度。

### R4 · P1：执行器失败后直接销毁帧，与完成式异步 IO 尚不兼容

**位置**：[并发路线](../proposals/evolution-07-concurrency-async-io-ffi.md) J19（第 63 行）；
[失败模型](../proposals/evolution-11-failure-interfaces-units.md) §1.4（第 86 行附近）；
[平台层](../proposals/evolution-12-stdlib-platform.md) 异步 IO 完成模型（第 51 行）。

一个任务把帧内缓冲区提交给完成式 IO，随后挂起。执行器线程发生失败时：

- 销毁帧会释放缓冲区。
- 操作系统可能仍持有该地址。
- 请求取消通常不等于操作已经完成，也不等于系统不再访问缓冲区。

“子帧先于父帧销毁”解决不了操作系统这个外部访问者。
必须先选定清理协议，例如：

- 停止运行用户代码，但保留清理机制，取消并收割全部在途操作，再销毁帧。
- IO 操作持有独立 owner，直到完成通知到达。
- 无法保证停止外部访问时，升级为进程终止。

这不是 IO4 可自行补上的库细节；它会反向影响 J19、失败边界和保证析构。
验证须包含“操作已提交、取消未完成、执行器失败”的时序，而不能只测试普通任务取消。

**进一步建议**：失败边界固定为 OS 线程，使应用从“一请求一线程”迁移到单线程异步执行器后，故障隔离能力反而退化。
应把任务树的失败域与执行器线程分开评审，不要先冻结线程边界再让协程适应它。
无需开放任意 `try/catch`，也可以只允许监督边界处理失败；具体共享状态与借用传播规则仍须证明。

### R5 · P1：Arc 的跨线程条件遗漏载荷析构的转移要求

**位置**：[路线 C4](../proposals/evolution-04-route-capability-unsafe-suspend.md) 的 Arc 条件（第 123 行）。

当前只要求 `T : Shareable`，便让 `Arc<T>` 同时满足 Shareable 和 Transferable。
但其他线程可以共享读取，不意味着其他线程可以拥有并析构它。
例如一个 FFI 资源允许跨线程只读查询，却必须在创建线程释放。

普通 Arc 的最后一个强引用可能在任意持有线程析构，因此通常需要：

```text
Arc<T> 的跨线程能力要求 T : Shareable + Transferable
```

共享 Arc 也需要考虑其他线程通过共享访问取得强引用、最终成为最后持有者的情况。
独立复审未找到 `Shareable(T) ⇒ Transferable(T)` 的独立公理；也不建议添加该公理补洞，
因为它会排除合理的线程亲和资源共享读取。

**建议**：修正普通 Arc 的能力条件，并以可共享读取但不可跨线程析构的类型作为反例。
需要支持这类资源时，使用不同的借用句柄或显式回送析构机制，不由普通 Arc 隐含承担。

### R6 · P1：Iterator.next 返回可空值不能覆盖通用按值迭代

**位置**：[通用接口清单](../proposals/evolution-11-failure-interfaces-units.md) J44、Iterator 签名与 §2.4（第 151、166、189 行起）。

文档已承认借用迭代尚未解决，但还有一个独立问题：`Iterator<Int?>` 遍历 `[1, null, 2]` 时，
`next()` 返回 null 究竟表示“下一个元素就是 null”，还是“迭代结束”？
若继续采用现有扁平可空语义，两者无法区分。协议需要表达的信息比返回类型能承载的更多。

**建议**：使用不折叠的和类型，例如 `Step<T> = Yield(T) | Done`，或者真正可嵌套的 Option。
验证“空序列”“仅含 null”“null 后仍有元素”均能区分。

同时，不应继续把 L5 泛型可组合性视为“没有三个用例就不启动”。迭代器、局部视图容器、高阶借用函数已经是主路线承诺的消费者。
应先设计并验证四种迭代：

1. 按值迭代。
2. 借用外部存储的迭代。
3. 可同时保留多个独占元素的迭代。
4. 下次调用会使上次结果失效的 lending 迭代。

不必强行让它们属于一个接口，但必须明确哪些算法可以统一、哪些不能，以及原因。

### R7 · P1：Z1 的预留不能使未来线程失败模型兼容

**位置**：[v1 冻结约束](../proposals/v1-freeze-decisions.md) Z1（第 36 行起）。

文档认为“任何线程 abort 都终止整个进程”足够宽，只需把“是否执行析构”放宽为未指定，即可为 J48 留空间。
实际上这仍保留了明确承诺：进程一定终止。

J48 允许监督者接住线程失败、进程继续运行，改变的是失败隔离单位，不只是析构副作用。
即使放宽 drop 行为，这个变化仍然可观察。

**建议**：不要用“未指定”制造兼容假象。直接选择：

- 将可展开的线程或任务失败与不可恢复的进程 abort 分成两个概念；或
- 明确未来这是一次带迁移规则的语言版本变更。

倾向第一种。同一个 abort 随所在执行上下文改变终止范围，会增加用户与 unsafe 作者的推理负担。
验收应覆盖监督者继续执行这一可观察结果，而不只检查析构是否出现。

### R8 · P2：UTF-8 路径加跳过不可表示文件名，不适合作为长期系统库设计

**位置**：[平台层](../proposals/evolution-12-stdlib-platform.md) §4 规则 3（第 85 行）。

这不只是 Windows 的问题；Unix 文件名也不保证为合法 UTF-8。
“跳过并计数”意味着遍历不能完整表示文件系统，备份、清理、构建、同步工具会看不见真实文件。
这不符合可组合平台抽象的目标。

**建议**：原生路径使用能无损保存平台表示的 Path 类型；String 用于显式文本转换和显示。
显示可以转义或有损，但资源身份、枚举和再次打开不能有损。
本次不受既有 Guide 限制，不建议继续维护“路径必须是 String”的限制。
验证至少包含非 UTF-8 Unix 文件名的枚举与原路径再次打开。

## 4. 建议改变的架构判断

### A1 保留小内核，但不以内核条目数或特判删除数作为首要成功标准

[之一 §3.2](../proposals/evolution-01-kernel-and-decisions.md) 把退役清单缩短速度作为首要度量，容易产生错误激励：
把编译器复杂度搬进 unsafe 库，不代表复杂度或可信计算基变小。

更重要的指标是：独立库作者能否仅凭公开合同正确实现；抽象组合是否成立；受信任声明是否不断增加；
安全代码能否保持局部推理；优化前后是否保持语义。容器库化是好的验收手段，但不是凌驾于这些目标之上的目的。

### A2 保留所有权图，撤回以查询类别数量决定 IR 层数的论证

[之九 §3](../proposals/evolution-09-architecture.md) 认为“KB8 是纯消费者，所以做错不会污染其他内核”。
帧变换会改变存储位置、存活区间和清理路径，R4 即跨内核影响的反例。
“五类查询，因此一层 IR 足够”同样不能成立。

建议保留统一的语义 IR 家族，但区分未完成所有权检查、已检查、析构已展开、协程已降低等阶段及其不变量。
不要为了层数少，让一个图结构同时承担互不兼容的阶段状态；边界应来自真实合同，不是预先规定查询类别数量。

### A3 重新评估确定性最早析构是否值得成为长期语言承诺

[路线 C1](../proposals/evolution-04-route-capability-unsafe-suspend.md) 保留 ASAP 的理由部分来自既有承诺和黄金输出。
按本次评审标准，它们不应成为设计理由。

倾向：语言默认规定词法资源生命周期，在确实不可观察的前提下允许优化提前释放。
借用结束与 owner 析构继续分离；需要降低峰值内存时，提供显式缩短作用域或消费手段。

至少应把此方案与 ASAP 加 Weak 屏障、裸指针屏障的方案正面对比，不能因为已有测试依赖精确 drop 点而排除它。
本条是待裁决的设计建议，不声称已证明性能或可观察行为等价。

## 5. 建议的下一步：先验证组合，再冻结路线

不是马上推倒全部实现，也不是继续细化十三份路线图。先用小型语义原型验证：

| 验证组 | 要证明或明确拒绝的组合 |
|---|---|
| Slice、自有字段视图、只读 guard | 存储依赖与授权依赖可以区分 |
| 返回重借、splitAt、可变迭代器 | 父子权限、分割后的授权与恢复规则成立 |
| nullable 元素迭代、高阶借用函数 | 泛型与来源合同可组合 |
| 可变 existential 经泛型转发 | payload 与 slot 的权限不混淆 |
| 借用子线程失败、完成式 IO 在途失败 | 来源释放前完成必要清理义务 |

这些验证过关，再冻结内核和安排版本。若某个组合必须靠“这个内建类型例外”才能成立，应回到设计而非增加特判。

**最终判断**：方案不是救不回来，但目前对“内核已足够简单、路线可独立扩展”的信心过高。
应保留产品方向，重做关键合同，而不是只修文档间的编号与依赖。
