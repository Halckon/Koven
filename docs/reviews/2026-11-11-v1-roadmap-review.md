## 0. 结论

路线图的结构是清楚的，状态记录也足够诚实（明确区分了单宿主本机实测与双宿主 CI）。主要问题不在记录，而在三处：

1. **结构工作与可见进展脱节**。P1 的三项全部在进行中，其中细化层一项已挂了 33 份 Spec；同期能力指标几乎没动（154 个 probe 中 137 → 138 通过，74 个基础程序停在 58，六个验收程序 0 个可运行）。P1 没有写下可度量的出口。
2. **必做项太多且缺少排序依据**。v1 范围内 84 项，必做 75 项，已交付 37 项；P3、P4 共 23 项未开始，全部或大部分标为必做，没有按“哪个验收程序需要它”分层。
3. **阶段次序与验收门槛互相牵制**。六个验收程序里至少词频与配置解析需要文本与文件 IO，而这两项排在 P4；P4 的门槛却是“六个验收程序至少 3 个可运行”。

## 1. 发现与建议

按影响排序。每条写明依据来自路线图的哪一处。

### R1 给 P1 一个可度量的出口，并设上限

- **依据**：P1 的目标写的是“两模式差异 0、InvalidSsa 0、原成功能力无损失、删除旧 checker 与 lower_frontend”。前两项按实测已满足；“删除旧路径”没有剩余量的记录。细化层条目（E3）列了 0350–0397 共 33 份 Spec，仓库里 0398–0409 仍在继续同一方向的退役工作。
- **问题**：无法从路线图看出 P1 还剩多少。P2 的门槛（74 个基础程序 ≥ 70）自 10 月以来没有靠近。
- **建议**：在 E3 的备注里登记一个数字化的剩余量（例如仍走旧降低路径的构造数，或 `unit_lower` 函数体路径的剩余入口数）与出口条件；出口条件满足即关闭 P1，不追求把所有旧壳删净——余下的清理可以作为 v1.1 的归一工作（之十三阶段一），那里本来就要在其上引入所有权图。

### R2 用六个验收程序倒推 P2–P4 的顺序

- **依据**：V1 的备注写明六个程序“全部为两模式一致的 known_unimplemented”；路线图没有记录每个程序被哪些条目挡住。
- **建议**：做一张“验收程序 × 阻塞条目”的表（每个程序首个未实现诊断对应的条目，逐层剥到可运行为止），据此给 P2–P4 排序。预期会看到：N08（`Result` 与 `?`）、L5/L6（文本与 IO）、L1/L2（值语义协议与插值）处在多数程序的路径上，应当前移；而若干 P3 必做项不在任何程序的路径上。
- 这张表本身是半天量级的工作，产出的排序比按阶段编号推进更可靠。

### R3 P4 的文本与 IO 不应排在最后

- **依据**：P4 门槛“≥ 3 个验收程序可运行”与其内容（文本 API、同步 IO）的关系；L6 备注“依赖 L5、N08、E4”，其中 E4 已完成。
- **建议**：把 N08 → L5 → L6 → L21 作为一条独立的纵向切片，与 P2 的其余家族并行推进。它对细化层的依赖只在 `Result` 与 `String` 两个家族，不必等 P2、P3 全部完成。

### R4 给 P3 的必做项分层

- **依据**：P3 有 18 项未开始，其中 12 项标为必做。
- **建议**：分三层——（a）验收程序需要的；（b）不做就会冻结错误表面的（L17 必须使用 `Result`、L18 按名解构、L20 不 abort 的变体、L14 把不做的内容移出 Guide，这几项晚做等于破坏性变更）；（c）其余。只有（a）（b）保持必做，（c）降为建议或移到 v1.1。按路线图现有标题判断，L11（泛型体内未约束 `T` 的析构轨道）与 L7（消费式匹配）需要看 R2 的表才能定层。

### R5 需要新增 Guide 规则的条目应成批启用

- **依据**：P3、P4 中标为“需新增”Guide 规则的有 L3b、L7、L8、L9c、L11、L16、L17、L18、L20、L14、S1–S7、T1、L6b，共 19 项。
- **问题**：逐项提升 Guide 版本会让规范入口频繁变动；逐项不提升又违反文档治理。
- **建议**：合并为一到两个 Guide 小版本启用，第一批只含 R4 的（a）（b）两层。[约束清单](../proposals/v1-freeze-decisions.md)里涉及 Guide 的 Z2、Z5、Z7 随对应条目进入同一批。

### R6 线程（T1）的发布门槛表述不一致

- **依据**：D5 写“用户确认 v1 必须实现最基础的线程能力，不再允许推迟到 v1.1”，T1 标为必做；V1 的备注却写“另设第七个线程程序验收 T1，不计入 v1.0 硬门槛”；v1 的定义写的是“单进程、同步 IO”，未提线程。
- **建议**：三处统一为一种说法。若线程是 v1.0 的必做项，第七个程序应当是硬门槛；若不是硬门槛，T1 的优先级应相应调整。

### R7 发布标准中的“100% 运行”与“明确的未实现诊断”需要统一

- **依据**：v1 定义允许“合法程序要么正确运行，要么得到明确的‘未实现’诊断”；V2 的标题写“合法 100% 运行”。当前有 16 个 probe 属于已登记的未实现。
- **建议**：写明 v1.0 发布时允许的未实现清单是否必须为空；若允许非空，说明进入“已知限制”文档的标准。

### R8 最近一次实测的来源等级偏低

- **依据**：`meta.metrics` 注明口径是“未提交工作树、macOS 单宿主、非 main/PR CI”，原始证据在仓外；可比的双宿主基线停在 2026-10-27。
- **建议**：SPEC-0392 当前切片合入后，在 main 上取一次双宿主基线并更新指标，再据此做 R2 的排序。这不是对记录方式的批评——路线图已经如实标注了等级——而是说在这个等级的数据上不宜做范围决定。

### R9 路线图缺少的条目

对照[演进总纲之十至之十三](../proposals/evolution-10-coverage-gaps.md)，以下事项在 v1 范围内有影响但路线图没有条目，或只隐含在别的条目里：

| 事项 | 现状 | 建议 |
|---|---|---|
| project 清单的语言版本字段 | 无条目 | 作为 V6（发行）的子项或独立小条目（Z8） |
| 测试设施（`@Test` 的语法与运行方式，含“应当 abort”的断言） | Guide 01 只预留了 `@`；路线图未见条目 | 明确它属于 v1 还是 v1.1；验收程序目前靠外部脚本比对输出，可以支撑 v1.0 不带语言内测试 |
| runtime 中系统调用的集中（Z3） | 隐含在 L6、T1、L6b | 在这三项的备注里写明，免得各自为政 |
| 一致性矩阵对内部产物的依赖（Z9） | V2 进行中 | 作为 V2 后续切片的一项核对 |
| `exitProcess` | L6 备注称“另行定义”，D9 称“随 L6” | 给它一个明确归属 |

### R10 条目编号与后续路线的代号相撞

- **依据**：路线图用 `L1`–`L21`、`S1`–`S7`、`X02`–`X12`、`V1`–`V6` 作条目编号；演进总纲用 `L0`–`L5`、`S1`–`S5`、`X0`–`X4` 表示路线步骤。
- **建议**：v1 路线图不动。v1 之后的各阶段路线图文件里，路线步骤带前缀登记（之十三 §6 已写明）。

### R11 “X v1 之外”一节可以指向新的分阶段计划

- **依据**：X02–X12 共 11 条，按 v1.x / v2 / v3 粗分；其中 X11 把“associated type”列为 v2 候选，X12 把协程与自举并为一条。
- **建议**：X 节保留为边界声明，但在备注中链接之十三的阶段表。两处已有出入的地方由用户裁决后同步：之三 J38 建议不做关联类型；之十三把自举单列在最后一个阶段。
