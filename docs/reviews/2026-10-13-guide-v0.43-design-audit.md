## 0. 结论

**内核方向是对的，值得保留。** owned value + 调用期 loan、声明端 `own`/`borrow`/`inout` 加调用点只标 `&`、
abort-only（drop 没有 unwind 边）、checked 整数算术、单态化静态分发、纯内存 ASAP 与资源按词法作用域析构的双轨策略、
`replace`/`swap`、receiver 两阶段借用、带唯一来源的 `borrow T from x`，这些组合在一起是自洽的。
它让 Koven 能在不引入用户生命周期参数的前提下拿到确定性的内存和资源管理。v0.37/v0.38 审计提出的大部分结构问题
（块内语句分隔、软关键字、具名位运算、`deinit`、所有权原语、两阶段借用、借用返回）都已经进入规范。

**问题不在借用模型本身，而在借用模型之外。** 用"能否写出一个真实的小型命令行程序"作标尺，v0.43 缺的是另一批承重件：

1. **值语义的基本协议没有定义**：用户类型的 `==`、哈希、排序、文本表示都没有语义。`when (subject)`、Map 键、排序、字符串插值都依赖它们。
2. **文本和 IO 几乎为空**：String 只有 `+`、`==`、`clone()`、`println`。没有长度、字节或字符访问、子串、数字格式化与解析、插值降级，也没有 stdin、文件、退出码。
3. **数值转换族缺失**：已定型整数之间没有任何显式转换，`Char` 与码点之间也没有。
4. **范围（range）只有语法没有语义**：Guide 12 把 `i in 0..<xs.size` 定为唯一安全访问写法，但没有任何一页定义 range 的类型和 `in` 的语义；`for` 也明确不接受 range。
5. **几个已经写进规范的规则互相冲突**（见 §3），其中 `when` 合并到 `Any` 与 `Any` 没有运行时表示的冲突属于类型系统层面的漏洞。

**规范形态本身是推进最大的阻力**（见 §4）。Guide 有相当篇幅在规定 Parser 恢复、Span 合成、AST 字段、错误码分配和 Phase/native 首轮范围，
语言语义和"当前实现到了哪一步"交织在一起。结果是：语义缺口不显眼，实现进度却被写进了规范。

## 1. 审计标尺

本审计不以"文档是否自洽"为终点，而是问：**按 Guide 字面实现后，下面这些 v1 级别的程序能不能写出来**。

| # | 程序 | 依赖的语言能力 |
|---|---|---|
| A | `wc`/词频：从 stdin 或文件读文本，分词计数，按次数排序输出 | IO、String 访问、Map 迭代、排序、整数格式化、退出码 |
| B | 配置/INI 解析器，错误带行号 | `Result` + `?`、子串、数字解析、MoveOnly enum 匹配、插值 |
| C | 递归表达式求值器（AST 用 enum + Box） | `Box.value`/`unbox`、MoveOnly enum 匹配、递归 |
| D | 带 RAII 资源的状态机（文件句柄 + 状态 enum） | `deinit`、`replace`、enum 状态转移 |
| E | 小型二进制协议编解码 + CRC | 位运算、`UByte`/`Int` 转换、`Array<UByte>` |
| F | 单链表/栈/队列，含迭代遍历 | 借用结果、`replace`、nullable 遍历 |

这六个程序都不需要 `dyn`、协程、unsafe、自举或跨线程共享。A、B、C、E 在 v0.43 下按字面**写不出来**（E 卡在 `UByte` 与更宽整数之间没有任何转换），D、F 能写但有明显绕路（F 的链表只能递归遍历，见 §2 各项）。

## 2. 承重语义缺口

每项给出：现状 → 后果 → 建议。"v1"列是本审计对是否进入 v1.0 的判断，详细排期见 v1 范围文档。

### 2.1 值语义协议：相等、哈希、排序、文本表示 〔v1 必须〕

- **现状**：03 的运算符规则只说 `==`/`!=` "接受相同类型"，没有定义 value class、enum、class 的相等含义；
  只有 String 在 13 定义为字节相等。`<`/`>` 只接受数值和 `Char`，String 不能比较大小。
  12 的 Map 需要 `Hashable`，但它是一个只在 Map 一节出现的"内建 capability"，规则只列了 `Int`、`Boolean`、`Char`、`String`，
  连 `Long`、`UInt`、value class、enum 是否满足都没说。插值在 13 被明确禁止降级，因为"可打印/转换协议尚未封闭"。
- **后果**：`when (x) { Point(0,0) -> … }`、enum 带 payload 的比较、`MutableList.contains`、排序、复合键 Map、
  `println(count)` 都缺语义。实现层面也只做了"无 payload Copyable enum 比较 tag"一条（见 guide-conformance）。
- **建议**：用现有的 interface + 单态化机制补一组协议，而不是另造 capability 体系。
  - `Equatable`、`Hashable : Equatable`、`Comparable : Equatable`、`Display` 定义为预声明 interface。
  - 内建标量、`Char`、`String` 由编译器绑定实现；value class 和 enum 在所有分量都满足时**自动推导**（与 `Copyable` 同一套结构递归），
    普通 class 必须显式实现（unique ownership 下 identity 比较没有意义，不提供默认 identity `==`）。
  - `==` 定义为 `Equatable` 的语法；没有实现的类型上写 `==` 是类型错误，不是"未定义"。
  - Map 的键约束改写成普通泛型 bound `K : Hashable`，删除 12 里的私有 capability；这也顺带消除"单一 bound 只允许 interface/Copyable/Transferable"（03:173）与 `Hashable` 的矛盾。
  - 插值 `"${x}"` 要求 `x : Display`。这样插值在 v1 可以落地，同时满足 13 的"不能只支持若干 builtin 假装完整协议"的原则。

### 2.2 文本、IO 与进程边界 〔v1 必须〕

- **现状**：String 的封闭操作集只有拼接、clone、相等、`println`、`error`（13:132–161）。09 的示例用了不存在的
  `name!!.length` 和 `File.readText(path)?`，13 又写 `val content = File.readText(...)` 不带 `?`，`File`、`IoError` 均未定义。
  `main` 只能返回 `Unit`（13:62），除 abort 外无法设置退出码。教程里的词频程序用十分支 `when` 手写十进制转换。
- **后果**：程序 A、B 写不出来。M1B-b 一直卡在这里。
- **建议**（全部按 owned 结果设计，不依赖视图或借用返回，能立刻实现）：
  - String：`size`（UTF-8 字节数）、按 `Char` 的借用式迭代 provider、`byteAt(i): UByte`、
    `substring(begin, end): String`（字节偏移，不在字符边界则 abort）、`indexOf`、`startsWith`/`endsWith`、
    `split(sep): List<String>`、`trim()`、`lines()`，以及 `StringBuilder`（MutableList<UByte> 风格的可变缓冲 + `toString()` 消费）。
  - 数字：每个内建数值类型 `display()`（经 `Display`），`String.toInt(): Int?` 等解析函数。
  - IO：`readLine(): String?`（stdin，EOF 为 null）、`File.readText(path): Result<String, IoError>`、`File.writeText`、
    `eprintln`；`IoError` 先定义成封闭 enum（NotFound、PermissionDenied、InvalidUtf8、Other）。
  - 进程：`exitProcess(code: Int): Nothing`，或允许 `main` 返回 `Int`；二选一即可，推荐前者，不动 entry 签名。
  - `Str`/视图继续延后。owned API 的分配成本是已知取舍，等借用视图成熟后再加零拷贝重载。

### 2.3 数值转换族与浮点 〔v1 必须〕

- **现状**：03:75 明确"不允许已定型变量发生隐式数值转换"，但整份 Guide 没有任何**显式**转换。`Char` 与码点也不能互转。
  浮点只有字面量和四则规则，`Double` 不能转整数、不能格式化。
- **后果**：程序 E（`UByte` ↔ `Int`）、任何 `size` 与 `Long` 混算、字符分类都写不出来。
- **建议**：`toInt()`/`toLong()`/`toUByte()` 等成员族。扩宽无损转换总是成功；收窄转换按 checked 语义越界 abort，
  另配 `toXxxOrNull()`。显式截断用 `truncateToXxx()` 一类名字。`Char.code: Int`、`Char.fromCode(Int): Char?`。
  浮点到整数采用 checked（NaN/越界 abort）。这与 04 的 checked 算术一脉相承。

### 2.4 Range 的类型与语义 〔v1 必须〕

- **现状**：04 有 `..`/`..<` 语法，03:89 把 range 标为 deferred，此后没有任何一页定义它的类型、`in` 的含义或求值方式。
  但 12:177、12:185–187 把 `i in 0..<container.size` 写成越界访问的唯一安全写法。12 §37.1 又明确 range 不是 `for` source。
- **后果**：规范要求用户写一个规范没定义的表达式。`for (i in 0 until n)` 这一系统语言最常见的循环只能改写成 `while`。
- **建议**：定义 `IntRange`（以及 `LongRange`）为 Copyable 的 value 类型，`a..b`/`a..<b` 只对同型整数成立；
  `x in r` 是比较的语法糖；range 作为 `for` source 时按升序产生 Copyable 值（不是 element place，因此不涉及 provider 借用）。
  `step`/`downTo` 可以延后。

### 2.5 MoveOnly enum 的匹配与 `Box` 访问 〔v1 必须〕

- **现状**：`Result<String, E>`、带 String payload 的 enum 都是 MoveOnly。Guide 06 的 smart cast 允许在稳定 place 上读 payload 字段，
  但"读字段"对 MoveOnly payload 只能是借用；把 payload 移出来只有 `?` 和 `!!` 两条特权通道。
  `Box.value`/`unbox()` 在 11:75–78 写成"规范语义"，但同一段又写"其 lower/codegen 属于后续计划"，而且把类型写成了不存在的
  `borrow T` 与 `own T`（13:262 自己说 `own` 不是返回类型修饰符）。
- **后果**：程序 B（`when (r) { is Ok -> 用 r.success 的 String }`）、程序 C（`eval(e.left.value)`）卡住。
  `Result.mapError` 这类组合子对 MoveOnly payload 写不出来。
- **建议**：
  - 规定 `when` 对 subject 的两种模式：subject 是 place 时，分支内 payload 字段是借用 place（现状）；
    subject 是 temporary 或显式消费的 owned 值时，分支获得 payload 的 owned 绑定。
    语法上可以复用现有解构：`is Ok(val v) ->` 或 `is Ok -> { val (v) = consume subject }` 二选一，推荐前者。
  - `Box.value` 改写成"只读 projection place"，与 `Rc.value` 同一措辞；`unbox()` 的返回类型写成 `T`。

### 2.6 闭包不能修改捕获状态 〔v1 建议做；不做则需约束 API 设计〕

- **现状**：borrowed closure 只建立 shared capture，捕获名在体内不可赋值；move closure 捕获的 `var` 是快照，也不可赋值（07:16–36）。
- **后果**：`each(xs) { sum += it }` 不成立。更要紧的是，Guide 已经在用回调做访问接口：Map 的 `withValue(key, action)`（12:210）。
  回调里改不了外部状态，这个接口几乎只能用来打印。
- **建议**：允许**非逃逸**闭包以 exclusive loan 捕获 `var` 局部。闭包本身已经非逃逸、loan 活到闭包 drop，
  只需把 capture 模式从"只读"扩成"体内有赋值则独占"。闭包存活期间源变量按 exclusive loan 冲突规则处理。
  这一项不需要 FnMut/FnOnce 类型层级，move closure 维持现状。若 v1 不做，就不应再新增回调式访问 API，统一走借用返回。

### 2.7 泛型推导不读 lambda 返回值 〔与集合算法同进同退〕

- **现状**：07:130–134 规定推导只读非 lambda 实参，lambda body 不参与。
- **后果**：`fun <T, R> map(xs: List<T>, f: (T) -> R): List<R>` 调用时 `R` 永远推不出来，每次都得写 `map<Int, String>(…)`。
- **建议**：采用两段式：先从非 lambda 实参解出可解的类型参数，再用已知参数类型检查 lambda，最后用 lambda 的结果类型补齐剩余参数。
  仍是单向、确定性的，不是全局约束求解。只要 v1 提供任何 `map`/`fold` 类 API，这条就必须同时做。

### 2.8 顶层 `val`/`var` 没有语义 〔v1 必须决定〕

- **现状**：02 的 `source_file` 产生式允许顶层 `val`/`var`，05 §36 明确"不引入 runtime global"，但没有任何一页规定顶层
  `val`/`var` 的初始化时机、顺序、所有权、析构和线程可见性。
- **建议**：v1 直接收窄。顶层只允许 `const val`；顶层 `val`/`var` 报"顶层可变状态未支持"。
  可变全局要等线程共享模型（`Shareable`）一起设计，否则会是 Transferable 体系之外的数据竞争入口。

### 2.9 泛型体内类型参数的析构轨道 〔v1 必须补一句规则〕

- **现状**：10 的双轨析构按"是否递归包含 `deinit` 类型"分类，但泛型体内的 `T` 在单态化前不知道属于哪一轨。实现里按"参数依赖"保留（`type_checking/resource.rs`），Guide 没有规定。
- **建议**：明文规定"泛型体内未约束的 `T` 按资源轨道（词法作用域）析构"。这是保守且可预测的选择；单态化后的优化可以 as-if 提前释放纯内存实例，但不改变可观察顺序。

### 2.10 Map 的完整性 〔迭代 v1 必须，其余可延后〕

- `mapOf()` 无参，只读 `Map` 无法带初值构造（0291 草案在处理）；Map 不能 `for` 迭代，教程只能把 argv 扫两遍来规避。
- 建议：定义 Map 的借用式迭代 provider，**顺序规定为插入顺序**。确定性对 Koven 的工具链和测试文化都是刚需，实现成本也已知（有序数组 + 索引）。
- `withValue` 回调接口建议降级为可选；主访问路径用 `requireValue(key): borrow V from this` 和 `get` 即可。

### 2.11 递归结构不能迭代遍历 〔v1 建议做〕

- **现状**：`borrow val` 不能重新绑定，10:118 禁止 `borrow var`；普通 `var cur = head` 再 `cur = cur.next` 是从借用中移出（L0133，实测 probe p25）。
- **后果**：链表、树的遍历只能写成递归，长链表有栈溢出风险。
- **建议**：允许只读 `borrow var`，限制为"重新绑定到同一根来源的 shared 投影"。所有 loan 都是 shared 且同根，不引入新的别名风险；
  根保护规则沿用现有借用结果合同。exclusive 游标（边遍历边修改）留到 v2。

## 4. 规范形态：语言参考和实施合同仍然混写

v0.37 审计已经提过这一点，Compiler Contracts 分离（SPEC-0233）是起点，但 Guide 主体没有变化。

- **实现细节占用了规范篇幅。** 01、02、05、06、07、12 有大段在规定恢复时消费哪个 token、零宽 Span 是否扩张父节点、
  AST 必须有哪些字段且"不得建立第五张 AST table"、L 码编号如何连续分配、某恢复路径是 `O(n)`。
  这些对编译器是好约束，但它们不是语言语义；按 Guide 的 4,000 行非空文本粗略统计，约五分之一的行直接谈 Span/恢复/AST/诊断码/Phase/SSA。
  与之对比，§2 的十项语义缺口在 Guide 中合计不到一页。
- **实现进度被写进了规范。** Guide 正文有四十余行提到 native、SPEC 编号、验收或实施进度，例如"首轮 native 只覆盖……""规范启用不代表 SPEC-0289 已完成"，集中在 12、13、15 三页。
  规范应当只说"这个程序合法吗、它做什么"，"编译器现在能编到哪一步"属于 Architecture。混写的直接代价是：每推进一个实现切片都要改 Guide，
  每次改 Guide 都触发版本升级、启用账本和迁移记录。
- **Litmus 不检验真正的风险点。** 12 个 Litmus 主要是语法覆盖；它们都能过前端，却不包含 §1 的任何一个程序。

**建议**：

1. Guide 只保留：词法与文法（EBNF）、静态语义、动态语义、可观察的诊断类别。恢复算法、Span 合成、AST 形状、L 码编号表、Phase 交接全部迁到 Compiler Contracts。
2. 删掉 Guide 里所有"当前实现/首轮 native"的句子，由一张 Architecture 覆盖矩阵（特性 × 前端 × native）承载。
3. 把 §1 的六个程序（加上已有 Litmus）做成 conformance 程序集，按"前端接受 / native 运行输出"两列验收。
4. 版本策略：语义变化才升版；措辞与结构修正不升版。

## 5. 对 N1a 范围 carrier 的意见

`View<T>` 解决了一个真实需求（不复制的子序列），但它在 v1 引入了第三种"非逃逸值"机制：
borrowed closure 的 loan、普通借用结果 `borrow T from x`，再加上 carrier 结果 `T from x`、`borrow val` 接新描述符时"拥有 metadata 不拥有元素"、
父子兄弟描述符的根保护、仅限可信标准库的扩展声明。每一条都需要前端、所有权、SSA verifier 和 native 四层分别证明。

建议 v1 **冻结在已交付的 take/drop/dropLast**，不再扩展 N1b、filter、更多算法。
v2 再把三种机制合并成一个统一概念（非逃逸类型，Swift `~Escapable` 一类），届时 `View`、迭代器、借用闭包共用一套规则。
v1 的集合算法改用 owned 结果（返回新 List），简单、可预测，性能代价在 v1 是可以接受的。

## 7. 值得保留、不建议改动的决定

- 调用点只为 `Inout` 标 `&`，Borrow/Value 不标。读起来干净，且 `&` 不再承担位与。
- abort-only，`Result` + 后缀 `?` 处理可恢复错误，`?` 要求错误类型精确相同。
- 资源类型按词法作用域析构。这一条解决了 ASAP 与 RAII 的根本冲突。
- 接口只做静态分发，异构集合用 enum。v1 不需要 `dyn`。
- 不提供默认参数值、`vararg`、属性访问器、匿名对象、属性委托。v1 不应该加回来。
- 字符串字面量是普通 MoveOnly `String`，`clone()` 显式。在没有借用视图之前，这比提前引入 `Str` 简单。
- `class` 的 `val` 绑定可调用 `inout` 方法而 value class 不可以。这是有意的引用直觉，但应在 08 用一段话写明，避免被当成缺陷反复讨论。
