# 《Growing a Language》深度解读：对 Halckon/Koven 语言架构的启发

我找到了 Guy L. Steele Jr. 在 1998 年 OOPSLA 大会上发表的经典演讲 Growing a Language（让一门语言成长） 的完整英文演讲稿、学术论文版本和演讲录像。

这篇演讲对 Koven 很有参考价值，尤其涉及三个正在面临的问题：

1. Koven 应该把多少功能直接设计为语言特性，多少交给标准库？
2. 如何设计一套稳定、可组合、可扩展的语义核心，而不是不断增加语法和编译器特殊处理？
3. 如何让 Koven 的 Parser、类型系统、所有权系统和编译器架构能够长期演进，而不至于随着特性增加越来越复杂？

我的核心判断是：

> Koven 不应该追求成为一门预先拥有所有高级特性的语言，而应该成为一门拥有少量强大抽象机制、严谨语义边界，并且能够由程序员持续扩展的语言。

这与 Steele 的主张非常接近，但 Koven 还要面对 1998 年这篇演讲没有深入解决的问题：所有权、生命周期、编译器正确性，以及用户扩展能力与语义确定性之间的冲突。

## 二、演讲究竟讲了什么？

### 1. 他的结论不是设计一门小语言，而是设计一门能够成长的语言

Steele 在演讲开头使用了一个非常特殊的技巧：

他规定自己只能使用英语中的单音节词。需要使用多音节词时，就必须先用已有词汇定义新词，之后才能继续使用。

这样一来，本来非常容易表达的想法，变得异常繁琐。

这种做法是在模拟程序员使用一门抽象能力不足的编程语言的体验。

程序员真正想说的是：

```
对集合中的所有元素执行某种操作
```

但如果语言缺乏集合、泛型、高阶函数等抽象机制，就需要不断重复构造底层代码。

因此他提出：

> “I need to design a language that can grow.”

也就是说，语言设计的关键不是选择一个固定的语言规模，而是设计出让语言能够自然成长的机制。

langev.com+1



### 2. 最有价值的区分：增加词汇，还是增加语义规则？

Steele 把语言增长区分为两种类型：

| 增长方式                      | 具体含义                               | 示例                             |
| ----------------------------- | -------------------------------------- | -------------------------------- |
| Vocabulary growth（词汇增长） | 利用已有规则定义新的类型、操作与抽象   | `Complex`、`Vector`、`Result`    |
| Semantic growth（语义增长）   | 改变或扩充语言本身允许的结构与意义规则 | 新控制流、新类型规则、新求值机制 |

前者通常可以由库完成，后者往往需要编译器参与。

真正值得追求的是：尽可能让新功能通过第一种方式实现，同时让少数必要的第二种扩展具有明确边界。

例如，语言能够由用户定义数值类型并支持运算符，那么复数、矩阵、有理数等就不需要分别成为编译器内置类型。

这可以让语言保持相对小的核心，但具有很大的实际表达能力。

langev.com+1



### 3. 用户定义的抽象应该尽可能与内置抽象平等

Steele 对比了 APL 和 Lisp。

他认为，APL 的部分内置操作与用户代码在表达形式上存在明显差异，妨碍了用户自然地扩展语言。

而 Lisp 的一个突出优势是，用户定义的抽象可以非常自然地与内置形式组合。

这引出了一个重要设计目标：

Built-in 和 User-defined 不应该成为两套平行、互不兼容的世界。

这不代表所有内置机制都必须能用普通库完全实现，而是希望用户代码能够获得尽可能相同的组合能力。

langev.com



### 4. 设计语言扩展能力，比不断增加具体功能更重要

Steele 以 Java 为例，提出应优先支持：

- 泛型类型；
- 用户自定义运算符重载；
- 轻量级值类型。

有了这些机制，就可以通过库定义复数、有理数、区间、向量、矩阵等类型，而不用让语言设计者把它们逐一加入编译器。

这里和 Koven 的 `Value class` 设计有一个非常直接的对应关系。

值得注意的是，Steele 在 1998 年就已经明确讨论了可自由复制、适合栈上使用的轻量对象。这种思想今天依然适用于值语义设计。

langev.com



### 5. 真正的最高层结论：设计模式，而不仅是设计成品

演讲最后，Steele 把观点推进了一层。

传统语言设计可以理解为：

```
语言设计者
    ↓
设计语言
    ↓
程序员使用语言编写程序
```

而他的目标更接近：

```
语言设计者
    ↓
设计可扩展的语言机制
    ↓
程序员构造新的抽象
    ↓
形成面向不同领域的语言词汇
    ↓
其他程序员继续复用和组合
```

语言设计不再只是规定程序可以怎么写，而是规定程序员可以如何安全、自然地创造新的表达能力。

Steele 将这种思路称为走向 meta 层次：不只是设计工具，而是设计能够创造更多工具的工具。

## 三、对 Koven 语言设计最重要的六个启发

结合此前讨论过的 Koven `Value class`、`data class`、所有权与借用、Parser 形式化验证，以及 D10/E2/E3 编译器分层问题，我认为有六个方向值得重点考虑。

### 1. 区分语言核心机制和标准库能力

这是我认为优先级最高的一条。

建议 Koven 在设计时始终划分三类：

| 层次             | 应该包含什么                                 | 设计原则           |
| ---------------- | -------------------------------------------- | ------------------ |
| Core Language    | 类型系统、所有权、借用、函数、控制流、泛型等 | 小而稳定，语义严谨 |
| Standard Library | 集合、Result、Option、迭代器、并发抽象等     | 用核心机制构建     |
| Ecosystem        | HTTP、数据库、数学计算、领域框架等           | 用户和社区自由扩展 |

例如，Koven 如果已经有泛型和适当的类型约束能力，`Result<T,E>`、`Option<T>`、`Vector<T>` 就应尽量成为普通库定义的类型。

关键不在于它们是否属于标准库，而在于：

标准库能不能像普通程序员一样使用 Koven 的公开语言能力完成实现？

如果标准库大量依赖编译器内部特殊语义，就意味着核心抽象能力可能仍然不足。

不过，`Result` 的错误传播语法、`await` 的暂停语义、所有权转移规则等，不能仅因为想减少内建特性就强行塞进普通库。它们可能确实需要核心语言支持。

我的建议是建立一项新规则：

> 每次新增语言特性前，先论证为什么它不能由现有语言机制和库实现。

### 2. `Value class` 可能是 Koven 最重要的基础抽象之一

Steele 当年提出的轻量值类型，与 Koven 的设计方向非常吻合。

可以考虑：

```
// 概念性 Koven 伪代码，不代表当前已支持的语法
value class Point(
    val x: Float,
    val y: Float
)

value class Complex(
    val real: Float,
    val imag: Float
)
```

如果 Koven 能实现下面几个性质：

- 值类型不依赖对象身份。
- 复制行为由明确的 `Copyable` 等语义约束决定。
- 编译器可根据逃逸分析、布局约束和调用约定选择内联或其他存储方式。
- 可以通过统一机制定义运算行为。
- 泛型能以一致的方式处理普通类型和值类型。

那么从 Point、Complex 到 Matrix，绝大部分都可以交给库处理。

这里需要澄清一个重要概念：

值语义不等于必须放在栈上。

Koven 应该把值语义视为语言合同，把栈、堆、寄存器和内联布局视为实现策略。

同样，`data class` 也未必需要成为一种新的对象存储模型。

它可能只是普通 `class` 的一组派生能力，比如相等性、解构、字符串表示等。

这使得 `data class` 更适合先考虑作为受约束的派生机制，而不是直接扩展新的运行时对象类别。

### 3. 所有权和生命周期规则应当封闭，抽象组合能力应当开放

这一点是 Koven 和 Lisp 式可扩展语言的重要差异。

Koven 不能简单模仿 Lisp 的宏扩展能力，因为它有更严格的资源安全目标。

例如，如果用户可以任意生成改变变量生命周期的代码，那么编译器必须确保宏展开后仍然符合：

- 借用不会超过对象生命周期。
- Move 后不可再使用原值。
- 临时对象在正确的位置释放。
- 不会发生重复释放。
- 控制流退出路径具有一致的所有权处理。

因此，我更倾向于以下设计：

固定的语义内核

类型约束 · 所有权 · 借用 · 生命周期 · 控制流 · Effect（如未来引入）

开放的类型抽象

Generics、Traits、Value types

受约束的代码生成

Derive、Compile-time generation

可扩展标准库与生态系统

集合、数值、异步抽象、领域库、框架

换句话说：

用户可以创造新的抽象，但不能绕过底层语义规则。

这会比“允许任意重写语法和编译规则”更加适合 Koven。

### 4. Parser 应该稳定，语言不应该依赖不断增加特殊解析规则成长

这条与此前讨论的 Koven Parser 二义性问题直接相关。

Steele 所说的可成长，并不等于允许用户任意创造新语法。

恰恰相反，我认为对 Koven 更好的路线是：

固定语法结构，开放组合语义。

举个例子，假如用户可以任意声明新的中缀运算符及其优先级，那么每引入一个库，都可能改变表达式解析行为。

这会带来几个问题：

- 不同依赖组合可能产生新的解析歧义。
- Parser 的确定性更难证明。
- IDE、格式化器、语法高亮工具都必须追踪动态语法。
- 错误信息和增量编译将更加复杂。

因此建议：

| 扩展能力                     | Koven 建议               |
| ---------------------------- | ------------------------ |
| 用户定义函数和类型           | 完全开放                 |
| 泛型与类型约束               | 完全开放，但遵守一致规则 |
| 固定运算符集合上的重载       | 建议支持                 |
| 用户声明任意新运算符         | v1 不建议                |
| 用户修改运算符优先级         | 不建议                   |
| 任意文本宏                   | 不建议                   |
| 结构化、受类型检查的派生机制 | 中期考虑                 |
| 任意修改语言控制流语义       | 不建议                   |

特别是此前提到的 `<`、`>`、`>=`、泛型、比较表达式等问题，我不建议主要依靠空格决定语法含义。

例如让 `a<b` 与 `a < b` 表达不同含义，会让格式化器和代码生成工具承担额外的语义风险。

更理想的方式是：

- Lexer 确定 Token 边界。
- Parser 用明确的语法上下文消歧。
- 必要时要求括号或显式标记。
- 对不同的合法格式化结果保持一致语义。
- 通过形式化语法和差分测试验证解析器。

Steele 的观点应当被理解为开放语义表达能力，而不是无边界开放语法结构。

### 5. D10/E2/E3 的统一语义管线，应成为长期扩展的架构基础

这里是从语言设计延伸到编译器工程。

Koven 正在推进的 D10 统一管线、E2 及 E3 SSA refine，与这场演讲有一个间接但重要的关联：

如果语言可以通过组合少数核心机制不断增长，那么编译器就应尽量让所有高级特性通过统一的语义结构进行处理。

我建议目标架构如下：

Source / Lexer / Parser

固定且可验证的词法与文法

AST / Name Resolution

名称绑定、语法结构

Typed HIR

统一类型、泛型、所有权语义

Core IR

规范化求值顺序和控制流

SSA / Refine

SSA 构建、不变量检查与优化准备

LLVM IR

目标无关优化与后端代码生成

Machine Code

最终可执行程序

这是一种建议的目标分层，并不代表 Koven 当前已经完全按此结构实现。

其中最关键的架构判断是：

在 Typed HIR / Core IR 阶段就让高级抽象转化成少量、明确的核心语义形式。

例如：

- `withValue` 等借用结构的生命周期行为应由统一规则解释。
- `when` 应转换为规范化的分支与匹配结构。
- 用户自定义运算符重载应解析为具有明确目标的调用。
- 用户定义的值类型应与内置值类型尽可能共用布局和操作规则。

这里要避免一个误区：不是越早降低成 LLVM 风格的低层指令越好。

过早丢失所有权、泛型和类型信息，会让后续正确性证明及诊断变得困难。

因此建议先保留适合语义分析的信息，在完成相关验证后再逐步降低抽象层级。

对 D10/E2/E3 而言，这意味着最终验收不能只看测试通过数量，还需要验证：

1. 是否减少了不同语言结构之间的重复实现。
2. 是否消除了同一个语义概念的多套解释。
3. 是否具有可执行或可检查的 IR 不变量。
4. 新增语言抽象是否无需穿透修改多个编译阶段。

这比单纯减少代码行数更能证明统一管线的架构价值。

### 6. 从功能开发转向“抽象能力”的验收

Steele 的演讲还启发了另一种衡量语言成熟度的方法：

不是统计支持了多少关键字、多少功能，而是观察使用者可以用已有语言能力构造多少新的东西。

例如，Koven 想支持 `Complex`，就不应该只验收能不能编译一个内建 `Complex`。

应该尝试让一个普通用户使用公开语言机制定义它。

进一步定义：

```
// 概念验证伪代码
value class Complex(
    val real: Double,
    val imag: Double
)

fun Complex.plus(other: Complex): Complex {
    return Complex(
        real + other.real,
        imag + other.imag
    )
}
```

然后检查是否能够自然支持泛型集合、复制约束、函数传参、运算符表达式及所有权行为。

这可以称为 Library-first Language Capability Test（库优先语言能力测试）。

如果一个需求必须修改编译器才能实现，应先分析真正缺失的基础抽象是什么，而不是直接为该需求添加特殊语法。

## 四、Koven 应当如何取舍？

我把建议整理成一个优先级矩阵。

| 工作方向                         | 建议                        | 优先级 |
| -------------------------------- | --------------------------- | ------ |
| Parser 文法明确化与验证          | 固定语法边界，减少歧义      | P0     |
| 所有权与生命周期语义闭合         | 明确核心规则和 IR 合同      | P0     |
| D10/E2/E3 统一语义管线           | 减少特殊分支，统一 lowering | P0     |
| 泛型、Value class、Copyable 能力 | 构造可扩展类型抽象          | P1     |
| 标准库去特殊化                   | 尽可能由普通 Koven 实现     | P1     |
| Trait / Protocol / Operator 抽象 | 提供组合扩展能力            | P1     |
| `data class` 派生能力            | 优先考虑库或 derive         | P2     |
| 结构化编译期代码生成             | 等语义内核稳定后考虑        | P2     |
| 任意用户自定义语法与宏           | 暂不引入                    | P3     |

这里的 P0/P1 是建议的架构优先级，不代表现有开发计划中的具体进度或已经完成的能力。

## 五、我认为可以建立的三个长期设计原则

### 原则 A：Minimal Semantic Kernel, Rich Expressive Language

最小化语义内核，同时保持丰富的表达能力。

所谓“最小”，不是强迫程序员写大量样板代码，而是让复杂功能由可组合的基本机制完成。

### 原则 B：Library First, Compiler Only When Necessary

优先使用库构建功能，只有确实无法通过安全且自然的公共机制实现时，才引入新的编译器语义。

注意这里不是绝对禁止内建特性，而是提高引入新特性的论证门槛。

### 原则 C：Extensibility Must Preserve Semantic Invariants

扩展性必须维护语义不变量。

这一条对 Koven 尤其重要，因为所有权、借用、生命周期和内存安全并不是可选的库约定，而是语言层面的保证。

如果某种可扩展性会破坏这些保证，就需要限制其能力或重新设计扩展接口。

## 六、把思想落实到 Koven v1：我建议做一个小型架构实验

与其立即引入更复杂的宏系统或元编程，我建议先选择三个典型需求，验证 Koven 现有抽象是否足够。

实验一：用户自定义 Complex / Vector

验证 Value class、Copyable、泛型、运算符及布局语义能否自然组合。

目标：证明用户能够扩展数值领域，而不是要求编译器内建新数值类型。

实验二：Result / Option / 资源作用域

验证泛型枚举、模式匹配、错误处理和所有权生命周期能否形成一致的组合规则。

目标：找出真正需要内建的控制流语义，以及可以在库中实现的部分。

实验三：不增加语法的领域抽象

选择一个小型 DSL 场景，例如 SQL 查询构造器、状态机或测点计算表达式，用普通 Koven 类型、泛型和函数组合实现。

目标：验证 Koven 能否在不动态改变 Parser 的情况下形成自然、可读的领域语言。

实验成功的标准不应只是代码可以运行，还应该包括语言表达自然、编译错误清晰、跨平台行为一致，以及不需要引入违反统一语义管线的特殊处理。

## 七、最终结论

这场演讲对 Koven 最大的价值，不是泛型、运算符重载或者 Value class 本身——这些都只是具体例子。

真正有价值的是改变语言架构设计的衡量标准。

过去我们可能会问：

“这门语言应该有哪些功能？”

Steele 则要求我们进一步追问：

“这门语言应该提供什么样的基础机制，使未来的程序员可以创造我们今天还没有想到的功能？”

对 Koven，我认为应该再加上一句：

这种创造能力必须建立在可验证、可组合、不会破坏所有权与生命周期安全的语义基础之上。

所以，我不建议 Koven 目前大规模引入宏、语法扩展和元编程机制。更合适的顺序是：

先证明语法正确性 → 统一语义与所有权模型 → 验证核心抽象的表达能力 → 将更多能力转移到标准库 → 最后开放受约束的元编程。

这既符合《Growing a Language》的精神，也能避免 Koven 因为追求可扩展性而重新制造 Parser、类型检查器和后端架构上的复杂性。

还有一个值得长期坚持的目标：新特性的增加速度可以越来越快，但编译器语义复杂度的增长速度应该越来越慢。 这将是 Koven 是否真正成为一门可成长语言的重要检验标准。
