# 依赖与开源复用治理

> **性质**：工程规则 · **状态**：current · **读取时机**：新增、替换、升级依赖或复用外部代码/算法时 · **唯一真源**：本页

先明确所需行为、性能、错误模型、平台和验收，再依次检查标准库、workspace 既有依赖和仓库公共
能力。通用协议、序列化、Unicode、文件遍历、测试支持和目标信息优先评估成熟组件；Koven 语义、
类型/所有权规则、诊断含义和 typed SSA 契约必须由项目掌控。

新增直接依赖前记录：

- **适配度**：是否精确解决当前需求，是否带入未授权能力或大量 glue；
- **兼容性**：edition、MSRV、目标平台、LLVM major 和 feature 组合；
- **维护性**：发布活跃度、API 稳定性、升级/替换边界；
- **供应链与安全**：传递依赖、通告、unsafe、build.rs、过程宏、原生库和下载行为；
- **许可**：组件及传递依赖是否可追溯并与分发方式兼容；
- **成本**：默认 feature、编译时间、体积、运行时开销和平台工具要求；
- **质量属性**：panic、确定性、线程安全、性能和错误模型。

版本由根 manifest 集中管理并由 `Cargo.lock` 固定；禁止通配版本和未固定 branch。只启用实际使用且
已验证的 feature。复制/改编代码必须记录来源、版本/commit、许可证并保留所需 NOTICE。

第三方 API 只有在跨 crate 泄漏、不稳定、含 unsafe/native 或需要统一错误模型时才增加薄 adapter；
单一局部调用不为“以后可替换”创建额外抽象。
