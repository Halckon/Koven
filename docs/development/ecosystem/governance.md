# 生态里程碑与 Spec 治理

> **性质**：交付治理 · **状态**：current · **读取时机**：跨仓库立项、排期和验收时 · **唯一真源**：本页的生态协作规则；仓库 Spec 生命周期仍遵循各自治理

## 权威与身份

语言以现行 Guide 为准。生态里程碑决定成果和联合验收，仓库里程碑组织本仓库工作，Spec 定义一个 Goal，
PR 交付实现与证据。生态编号 ECO-V1-M0…M4 不占用编辑器 M0…M5，也不替代语言 Phase 0…6。
一个 Spec 只有一个主仓库里程碑，可被其他生态目标引用；跨仓库引用使用仓库名、真实 Spec ID 与链接。
每仓独立编号，不预分配远期 ID。已有 Spec 不为满足新分组而机械改写或重复立项。

里程碑状态为 approved / in-progress / completed，未批准候选用 draft；取消需理由。
本目录正文是生态状态真源。Spec 状态只在所属仓库记录；冻结盘点必须附日期和提交，不充当实时进度。

## 立项与依赖

2026-10-22 用户追加“按路线图中的里程碑持续实施”，授权依次落实路线图及分支／PR 交付；
该持续授权不自动启用新语言／API 合同。范围内且依赖完备的实施合同可继续推进；
范围外或 Guide 冲突必须先澄清。消费者 fixture 只验证适配，不能替代真实生产方验收。
前置 Spec done、必要 ADR accepted、语义 Guide 已启用后才能实施依赖它的功能。
取消、superseded 或编号存在均不等于依赖满足；必须明确替代关系并重新核验。

跨仓库合同由生产方维护。每次联合验收记录：仓库与 commit/tag、Guide 输入、工具链产物身份、平台、
实际命令／用例和结果。固定提交内容版本不等于已发布工具链版本，也不代表该提交已合入远端 main。
不得把不同版本混成一个成功组合。无法核实远端时注明只读本地 snapshot。

## 里程碑模板

每份里程碑包含以下信息；本目录 M0–M4 是首批实例。

- 身份、状态、优先级、是否阻塞正式 v1。
- 目标、范围、非目标、输入基线链接。
- 候选 Spec 工作项：主题、主归属仓库里程碑、依赖、必需性与验收。
- 联合场景、完成条件、证据及阻塞。

工作项键（如 M1-S1）只用于规划依赖，不是 Spec 编号。进入实施时绑定真实仓库 Spec；
工作项覆盖多个独立 Goal 时进一步拆分，保留原目标与全部后继关系。

## Spec 最小合同

沿用各仓库模板，明确主里程碑、单一目标、范围／非目标、行为与公共接口、失败场景、
前置依赖、成功标准、定向测试、输入身份和证据。语义候选和可实施合同必须分开。
优先复用现有实现和已认领缺口；标准库逻辑以 Koven 源码为真源，受控 runtime 只承担必要边界。

## 交付与清理

1. 盘点 active／draft／archive；只按原证据判定，不把摘要、提交标题或其他 Spec 归档当作完成证明。
2. 实施 Spec 从 main 建 feature/spec-<id> 或 fix/spec-<id>，独立审查、PR、CI 和验收。
3. done 后归档，生命周期、目录、库存、链接和里程碑引用一起更新。
4. 必需子项完成且联合验收通过，生态里程碑才能 completed；可选项不进入其发布门槛。
5. 延期或取消保留原因、后继归属和剩余目标；不能删除失败项来降低验收标准。

纯文档落地沿用仓库豁免，不为本次路线图创建空功能 Spec，不更改已有功能状态。
文档门禁只证明结构和引用；不证明运行行为、远端 CI、商店发布或服务上线。

## 仓库里程碑命名

主仓库近期工作归属 CORE-V1-M0…M4；网站归属 SITE-V1-M0…M3。
它们是对应生态页面表格中的本仓库工作集合，不建立第二份状态文件；需要独立状态时再迁出并以链接替换。
编辑器沿用自己的 M0–M5 及库存，不改号。Playground 服务启动时建立 PG-M0（合同与隔离）、
PG-M1（执行与分享）；此前只是候选归属，不要求仓库存在。
